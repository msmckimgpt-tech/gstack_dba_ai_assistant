# ANCHOR: feature-0021-redteam-review assistant 자가 적대 리뷰

## §1. 외부 관점 요약
<!--
이 기능을 모르는 사람이 처음 코드를 열어봤을 때
"왜 이렇게 만들었지?" 또는 "이게 왜 필요하지?"라고 의문을 가질 법한 지점.
3~5줄.

예시:
"왜 이 계산을 클라이언트에서 하지? 서버에서 하면 안 되나?"
→ 이유: 실시간 UI 업데이트가 요구되고 서버 round-trip 레이턴시가 사용자 체감에
부정적. 계산 결과는 짧은 생명주기라 일관성 위험도 낮다.
-->

"답변마다 LLM 을 한 번 더 호출한다고? 비용·지연이 늘 텐데 왜?" — 이 제품의 답변은
사내 DB 에 대한 사실 주장 (수치·스키마·SQL) 이라 환각 1건의 비용이 리뷰 1회 비용보다
훨씬 크다. 리뷰어는 저비용 모델 + 추론 강도 게이팅 + fail-open 으로 비용·가용성 영향을
제한하며, 이는 Claude Code 가 검증 서브에이전트로 작업 품질을 담보하는 것과 같은 구조다.
"왜 리뷰어에게 대화 전체를 안 주지?" — fresh-context 원칙: 초안을 만든 사고에 오염되지
않은 리뷰가 결함을 더 잘 찾고, 토큰도 절약된다.

## §2. 대안 분기
<!--
선택하지 않은 옵션 2개 이상 + 각 옵션을 선택할 법한 페르소나.
"이 옵션 안 고른 이유"까지.

형식:
- **Alt-A: X 방식.** 페르소나: Y 성숙한 팀. 안 고른 이유: ...
- **Alt-B: Z 방식.** 페르소나: W 빠른 iteration 팀. 안 고른 이유: ...
-->

- **Alt-A: 프롬프트 단일화 (self-critique 를 초안 생성 프롬프트에 내장).** 페르소나:
  호출 비용 최소화를 최우선하는 팀. 안 고른 이유: 같은 컨텍스트 안의 자기 비평은 자기
  편향에 오염되어 (Claude Code 문서의 "작업을 만든 에이전트가 채점하지 않는다" 원칙 위반)
  실측 결함 검출률이 낮고, 판정 기록·오케스트레이션 제어도 불가.
- **Alt-B: 사후 배치 감사 (답변 전달 후 백그라운드 리뷰 → 사람 알림).** 페르소나:
  지연에 극도로 민감한 실시간 챗 서비스. 안 고른 이유: 오답이 이미 사용자에게 도달한 뒤라
  피해를 막지 못함. 본 제품은 poll 기반 비동기 답변이라 리뷰 지연 수 초를 흡수 가능.
- **Alt-C: DB 테이블 기반 메모리 (파일 아님).** 페르소나: 다중 호스트 스케일아웃 팀.
  안 고른 이유: 사용자가 임시 파일 + 만료 정리를 명시 요청. /shared 볼륨은 이미 워커 간
  공유·reaper 패턴이 있어 저비용. 스케일아웃 시 DB 승급은 후속 분기로 명시.

## §3. 가정된 사용 시나리오
<!--

운영팀 김대리는 매출 마감 수치를 assistant 에게 물었고, 초안 답변은 미리보기 50행 절단본
을 근거로 "전체 데이터가 이렇다" 고 단정했다. red-team 리뷰어가 grounding 축 BLOCK
(부분 증거 전수 단정) 을 잡아 수정본이 "표본 기준" 단서를 달고 전달됐다. 6개월 후 이
코드를 인수한 동료는 관리 콘솔 "AI 추론" 탭에서 assistant 가 어떤 지침·스킬로 작동하고
리뷰가 무엇을 잡아냈는지 코드를 열지 않고 파악한다.
