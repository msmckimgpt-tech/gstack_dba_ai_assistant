# Report

## 진행 요약 (2026-07-31)

ITEM-10(검증층) 구현 완료. codex 적대 리뷰 P1 4건·P2 1건 반영, 출하 중.

## 무엇을 만들었나

노드 분석문을 L0 통계 증거와 대조해 `supported`/`contradicted`/`unverifiable` 로 판정하고
근거 한 문장과 함께 저장한다. **AI 의 말을 AI 가 평가하는 게 아니라 AI 의 말을 실제 측정값과
대조**한다 — "이 컬럼이 레코드를 고유 식별한다"는 서술 옆에 `distinct_est=12, sampled_rows=100`
이 있으면 그 서술은 틀렸다.

## 이 기능의 전부는 정직성이다

```
판정 실패는 "검증됨"이 아니다.
```

LLM 오류·계약 위반 응답·근거 없는 응답·증거 부재·저장 실패·예산 소진 — 전부 **행을 만들지
않는다(미검증)**. 확인 도장이 잘못 찍히면 그 도장을 근거로 위층(요약·답변)이 더 확신하게 되고,
그러면 이 층은 없느니만 못하다. 그래서 fail-soft 가 "통과"가 아니라 "침묵"이다.

예외는 하나다: **예산 모듈을 못 읽으면 중단**한다. 계량 장애로 기능이 멈추는 것보다 상한을
모른 채 자동 지출을 계속하는 쪽이 위험하다.

## 리뷰에서 드러난 것

codex 가 P1 4건을 잡았고, 그중 하나가 특히 아팠다:

- **`c` 미정의 — 배선이 통째로 죽어 있었다.** 테스트 38건이 모듈 내부를 촘촘히 덮었지만
  `insight.py` 의 호출 한 줄이 정의되지 않은 변수를 쓴다는 사실은 잡지 못했다.
  **모듈 테스트가 배선을 보증하지 않는다.**
- **재판정이 안 됐다.** 저장 키에는 `analysis_hash` 가 있는데 대상 조회는 그것을 비교하지 않아,
  분석이 갱신돼도 옛 판정이 남았다 — 내가 문서에 적은 계약과 정반대로 동작했다.
- **근거 없이 `supported` 를 저장**할 수 있었다. 프롬프트는 reason 을 필수로 요구했지만 코드가
  강제하지 않았다. 재확인할 수 없는 확인 도장이 이 층의 최악의 실패인데 그 문이 열려 있었다.
- 실패한 증거로 판정할 수 있는 race.

그리고 `cursor()` 를 try 밖에 두는 실수를 **네 번째** 반복했다. 이제는 패턴이다 —
**자원 획득은 언제나 try 안**.

## 지금의 한계

판정 대상이 **7건** 수준이다. 분석문과 증거가 둘 다 있어야 대조가 되는데 증거 커버리지가
아직 낮다. 플래너(feature-0035)가 커버리지를 채운 뒤에야 이 층이 실질 값을 한다 — 인프라를
먼저 놓는 판단이었고, 그 사실을 숨기지 않는다.
