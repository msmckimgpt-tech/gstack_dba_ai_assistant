# ANCHOR: feature-0032-llm-token-budget 백그라운드 LLM 토큰 예산

## §1. 외부 관점 요약

"이미 `TODOS.md` 에 *일일 cap 은 가치 0* 이라고 종결해 놓지 않았나? 왜 다시 만드나?"
→ 그 종결의 근거가 **사실이 아니게 됐다**. 당시 판단은 "라이브 100% edge(로컬 Ollama) →
per-token 과금 없음"이었는데, 2026-07-30 실측은 정반대다: 최근 7일 Anthropic 8,654콜 /
5,557만 토큰 대 edge 25콜 / 3만 토큰 — **과금 lane 99.7%**. 그중 사람이 요청하지 않은
백그라운드 소비가 약 2,600만 토큰/7일이다. 즉 지금은 자동 지출에 상한이 없다.
전제가 바뀌었으니 결론도 바뀐다.

"그럼 왜 circuit-breaker 는 안 만드나?"
→ 이미 있다. `llm_provider_health` 가 429/401 을 분류해 provider 를 restricted 로 내리고
복구 probe 로 되살린다. 없는 것은 **누적 소비 상한** 하나뿐이라, 그것만 만든다.

"상한에 걸리면 사용자 답변도 멈추나?"
→ 아니다. 그렇게 만들면 비용 통제가 아니라 서비스 장애다. 대화 답변·자가검증·제목 생성처럼
사람이 기다리는 호출은 **세지도 막지도 않는다**. 예산은 사람이 기다리지 않는 지출만 다룬다.

## §2. 대안 분기

- **Alt-A: 호출 수(콜) 기준 상한.** 페르소나 — 구현이 단순한 쪽을 택하는 팀. 안 고른 이유:
  비용은 콜이 아니라 토큰에 비례한다. 긴 payload 한 번이 짧은 호출 백 번보다 비싸므로 콜 상한은
  실제 지출과 어긋난다. 이미 `AUTO_CHANGE_CAP`(콜 기준)이 있고, 그것과 다른 축이 필요했다.
- **Alt-B: 자정 리셋 일일 예산.** 페르소나 — "일일 한도"의 직관을 중시하는 운영자. 안 고른 이유:
  타임존을 정해야 하고(서버 TZ vs 사용자 TZ), 자정 직후 폭주가 그대로 재개된다. **rolling 24h**
  는 두 문제가 모두 없다.
- **Alt-C: LLM 호출 함수 단일 choke-point 에 게이트.** 페르소나 — 커버리지 100%를 원하는 팀.
  안 고른 이유: 단일 choke-point 가 없다 — `chat.completions.create` 가 15곳에서 직접 호출된다.
  전부에 게이트를 걸면 사용자 경로까지 침습하고 회귀 표면이 커진다. 백그라운드 **진입점** 3곳이
  소비의 96%를 차지하므로 거기서 막고, 나머지는 계량만 하되 그 사실을 숨기지 않는다.

## §3. 가정된 사용 시나리오

어느 날 밤 그래프 스키마에 대규모 DDL 이 적용돼 change-reanalysis 가 대량 트리거된다. 지금까지는
이런 상황에서 아침에 사용량 대시보드를 보고서야 밤새 나간 지출을 알았고, 그때는 이미 늦었다.

예산이 있으면 다르다. 백그라운드 소비가 24시간 2,000만 토큰에 닿는 순간 새 분석 tick 이
"토큰 예산 소진"으로 다음 주기에 밀리고, 관리 콘솔 'AI 운영 현황'에 **상한 도달**이 뜬다.
운영자는 아침에 그 배너를 보고 "밤새 무슨 일이 있었나"를 먼저 묻게 된다 — 청구서가 아니라.
그 사이에도 사용자의 대화 답변은 평소대로 나간다.
