# TASK-20260902T100000 — 이미 연결해 본 사용자에게는 [내 AI 실행] 을 자동으로

## 1. 요청 (사용자, 2026-09-02)

> 「"내 AI 연결하기" 에 대한 일반 사용자들의 접근성을 늘리기 위해 이미 한 번 연결이 진행된
>  사용자들의 대상으로는 자동으로 '내 AI 실행' 이 진행될 수 있도록 구성해주세요.
>  - 미연결 상태에서 '연결 필요' 버튼을 누를 경우
>  - 로그인을 통해 서비스에 진입했을 경우
>  '업데이트 필요' 가 버튼에 나타날 경우, 사용자가 해당 버튼을 클릭하는 것 만으로도 러너가
>  재구성될 수 있도록 동작시켜주세요.」

## 2. 「이미 한 번 연결했다」를 무엇으로 아는가

서버가 이미 안다 — `connect_status.last_os` 는 **러너가 실제로 연결됐을 때만** 기록되므로
(`WebAccounts.BridgeLastOs`, TASK-20260901T160000 축) 그 값의 존재가 곧 연결 이력이다.

브라우저 로컬 저장을 쓰지 않는 이유: 다른 브라우저·기기에서 로그인한 **같은 사람**에게 이력이
사라진다. 그러면 「한 번 연결한 사용자」가 브라우저마다 다른 뜻이 된다.

## 3. 이 기능이 조용히 죽는 유일한 방식 — 사용자 활성화

실행은 `location.href = mysql-ai-bridge://start?token=…` 이고, 그 URL 에는 **토큰이 실린다**.
토큰 발급은 네트워크 왕복이라 「클릭 → `await` 발급 → 이동」 순서로 짜면 이동 시점에 사용자
활성화가 이미 끊겨 **크롬이 조용히 거른다**(기존 `_launchRunner` 첫 줄 주석이 같은 이유로
`location.href` 를 첫 await 앞에 못박아 두었다).

그래서 자격이 확인되는 순간(상태 조회 응답) **미리 발급받아 두고**, 클릭은 동기적으로 이동만
한다. 이것이 이 설계의 중심이고, 테스트가 그 순서를 잠근다.

## 4. 진입점 4개

| # | 계기 | 동작 | 실패 시 |
|---|---|---|---|
| A | 칩(`연결 안 됨`·`대기 안 함`) 클릭 | 자동 실행 | 연결 창 |
| B | 컴포저 게이트(`연결하기`·`내 AI 실행하기`) | 자동 실행 | 연결 창 |
| C | **로그인 후 진입** | 세션당 1회 자동 시도 | **창 열지 않음** |
| D | 칩 `업데이트 필요` 클릭 | 자동 실행 + **런처가 러너를 최신본으로 교체** | 연결 창 |

C 에서 창을 열지 않는 이유: 로그인하자마자 창이 튀어나오는 것은 접근성 개선이 아니라 방해다.
A·B·D 는 사용자가 이미 「연결하겠다」고 누른 것이므로 막다른 길로 끝내지 않는다.

이력이 **없는** 사용자(설치부터 필요)는 네 경로 모두 **종전대로 창**이다 — 실행할 것이 그
컴퓨터에 아직 없는데 스킴을 쏘면 「알 수 없는 프로그램을 열까요?」만 뜬다.

## 5. D — 「업데이트 필요」가 클릭만으로 풀리려면 런처가 바뀌어야 한다

**핵심 발견**: 스킴 핸들러가 부르는 `launch.sh`/`launch.ps1` 은 **디스크에 있는 러너를 그대로
다시 띄운다**. 그래서 종전에는 「업데이트 필요」에서 [내 AI 실행] 을 눌러도 **같은 낡은 러너가
다시 떴다** — 갱신 경로가 거기서 끊겨 있었다.

런처가 기동 직전에 최신본을 받아 교체하도록 했다:

- 무결성: 이 시점에는 CA 를 **이미 신뢰**하므로 `https` + `--cacert`(POSIX) /
  `Invoke-WebRequest`(Windows). 설치 때의 평문 HTTP + 체크섬 대조와 목적은 같고 수단이 더 강하다.
- **토큰 검증 뒤**에 한다. 이 스킴은 아무 웹페이지나 열 수 있으므로, 검증 전 부수효과는 임의
  사이트가 남의 러너 파일을 갈아치우는 통로가 된다(같은 이유로 `pkill` 도 검증 뒤에 있다).
- 실패는 **종전 동작**으로 떨어진다 — 못 받았거나·빈 파일이거나·문법이 깨졌으면 있던 파일을
  그대로 쓴다. 갱신하려다 멀쩡한 러너를 못 띄우게 만드는 것이 가장 나쁜 결말이다.

### ⚠ 발효 범위 (정직 표기)

런처는 **사용자 머신에 설치된 파일**이라 이 변경은 «다음에 설치·재설치한 사람» 부터 발효한다.
지금 이미 낡은 런처를 가진 사용자는 D 를 눌러도 러너가 갱신되지 않고, 그때는 대기 판정이
`runner_stale` 을 계속 보므로 **연결 창으로 떨어져 최신 명령을 받는다**(= 종전 경로, 나빠지지
않음). 한 번 그 경로로 재설치하면 그다음부터는 클릭만으로 갱신된다.

## 6. AC

- **AC-1** 이력 판정은 서버 `last_os` (브라우저 저장 금지).
- **AC-2** 이력 없음·이미 사용 가능이면 자동 실행하지 않는다.
- **AC-3** `runner_stale` 은 자동 실행 **대상**이다.
- **AC-4** 클릭 경로는 이동 앞에 `await` 가 없다(활성화 보존). 프리페치는 자격 확인 뒤·중복 없음.
- **AC-5** 쓴 실행 URL 은 버린다.
- **AC-6** 칩·게이트가 **한 진입점**을 공유하고, 그 진입점은 창으로 떨어질 수 있다.
- **AC-7** 로그인 진입은 세션당 1회이고 창을 열지 않는다.
- **AC-8** 대기·판정은 자동/수동이 **같은 함수**(`_awaitUsable`)를 쓰고, «무응답» 과 «서비스
  응답 없음» 을 구분한다.
- **AC-9** 런처가 기동 직전 러너를 최신본으로 교체하되, **토큰 검증 뒤**에 하고 **실패는 기동을
  막지 않는다**. POSIX·Windows 양판 동일 계약.

## 7. 범위 밖 (의도적)

- **러너 자가 갱신**(러너가 스스로 내려받아 재실행)은 넣지 않았다. 런처 교체로 D 가 성립하고,
  자가 갱신은 「사용자가 누르지 않아도 바뀐다」는 다른 계약이라 별 결정이 필요하다.
- 자동 실행을 끄는 사용자 설정(opt-out)은 두지 않았다 — 요청에 없었고, 실패가 조용하므로
  현재 피해면이 없다. 필요해지면 별 항목.
