### 3. Challenge to current spec

신뢰 모델에 대해 분명히 말한다: **적대적이거나 침해된 러너는 `caps_self_report` 를 선언해 정확히 같은 구멍을 다시 열 수 있고, 이것은 수용 가능하다 — 다만 코드의 어휘가 그것이 무엇인지 오도한다.** 기능 문자열은 하트비트 본문(`bridge_agent.py:449`, `body["features"] = list(self.features)`)으로 도착해 `parse_runner_features` 로 정규화되고 그대로 저장된다. 서버측 검증은 없고 구성 가능하지도 않다 — 서버는 AI 의 답과 클라이언트에 컴파일된 표를 구별할 수 없다. 위조된 선언의 blast radius 는 그 사용자 **자기** 모델 드롭다운 하나이며, 하트비트를 위조할 수 있는 자는 이미 그 계정의 살아 있는 OAuth 토큰을 쥐고 있다 — 그 토큰은 인증된 API 표면 전체를 준다. 그 사용자에게 틀린 모델 목록을 보이는 것은 토큰이 이미 허용하는 것에 대한 escalation 이 아니다. 그러므로 게이트는 **호환성 검사로서** 건전하며 그 조건으로 출하해야 한다. 바꿔야 할 것은 명명이다: `_caps_trusted`·`caps_trusted`·전반의 `자격` 프레이밍이 인가 경계처럼 읽히고, 러너쪽 주석(`서버는 그 거짓을 검증할 수단이 없다(그것이 이 자격의 유일한 전제다)`)만이 반대로 말한다. 실제 의미 쪽으로 rename 하라 — `caps_source_declared` / `declares_caps_contract` — 그래야 미래 변경이 자기신고 위에 진짜 보안 결정을 얹지 않는다. 인젝션은 점검했고 깨끗하다: 안내는 `textContent`, 모델 `label`/`group`/`description` 은 `escapeHtml`, `value` 는 `setAttribute`, 그룹 헤더는 `textContent`.

**이 변경은 이제 「이 러너가 낡았는가」에 서로 다른 두 답을 갖고 있고, UI 가 둘을 동시에 보일 수 있다.** 이 커밋 이후, `caps_self_report` 를 선언하되 배포본과 다른 지문을 신고하는 러너는 *보이는* 모델 선택기(caps 게이트 통과)와 동시에 `runner_stale` 연결 칩 + `runner_update.current: False` 를 받는다. caps 게이트로 지문을 기각한 논거는 `bridge_tasks.py` 에 잘 적혀 있으나(`러너 파일을 고치는 모든 배포가 전 사용자의 선택기를 지운다`), 그 귀결 — 한 화면의 두 낡음 판정 — 은 이 변경 어디에도 다뤄지지 않는다. 둘 다 알 때 caps 안내가 `runner_stale` 에 양보하게 하거나, 칩은 정체성에 답하고 안내는 계약에 답한다고 `FUNCTION.md` 에 명시해 다음 사람이 둘을 「통일」하지 않게 하라.

**부수 피해: 점검했고 깨끗하다. 형태 wart 하나 있음.** `features`·`agent_version`·`listening` 은 게이트가 건드리지 않으므로 `_console_llm._classify`(콘솔 위임), `_runner_job_grants`(per-token), `account_has_live_token`/`connected`/`ready`/`compose_blocked`, `count_live_runners` 는 전부 무영향 — 각각 읽어 확인. `_bridge_model_offered` 는 `account_runner_capabilities` 를 통해 올바르게 게이트를 상속한다. wart: `console_llm_state` 가 전체 프로필을 `runner` 에 담아 `"runner": runner` 로 돌려주므로 성공 분기는 이제 5키(`capabilities`·`caps_trusted` 포함)인데 초기화자와 `except` 분기는 여전히 3키를 만들고 docstring 도 3키를 기록한다. 게이트가 걸려 있어 새지는 않으나, 비대칭 때문에 `runner.caps_trusted` 를 읽는 소비자가 성공 시 `false`, 실패 시 `undefined` 를 받는다.
