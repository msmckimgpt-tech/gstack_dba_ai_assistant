# 제안: 빈번한 DB 구성 변경에 대한 모범 대응책

> 본 문서는 **제안서(draft)** 다. TASK-20260618T025755(검색 필터 + 정규식 일괄 선택)는
> "선택을 빠르게" 만들었을 뿐, 아래 Tier 2·3 은 별도 cycle + 소유자 결정(특히 자동 부여 계열은
> RBAC/보안 영향 → `feedback_outside_voice_for_rbac` 에 따라 outside-voice 리뷰 필수)이 필요하다.

## 1. 문제 정의

사내 데이터소스는 DB 의 추가/삭제가 잦다. 그런데 제품의 접근 가능 DB(allowlist, `WebProducts`↔
`product.databases`)는 **DB 이름을 정적으로 박제(materialize)** 한 목록이다. 그래서:

- **신규 DB**: 데이터소스에 DB 가 생겨도 제품 allowlist 에 자동 반영되지 않음 → 관리자가 제품마다
  수동 추가. 누락 시 에이전트가 그 DB 를 못 본다(조용한 누락).
- **삭제 DB**: 데이터소스에서 DB 가 사라져도 allowlist 항목은 그대로 남음(stale) → 연결 실패
  행(`is-offline`)으로만 표시, 능동 정리 없음.
- **N×M 폭증**: 데이터소스가 늘고 제품이 늘수록 "DB 변경 1건 → 손봐야 할 제품 K곳" 이 곱으로 증가.

핵심은 **allowlist 가 "이름의 스냅샷" 이라 살아있는 DB 구성과 자동으로 어긋난다(drift)** 는 것이다.

## 2. 이미 적용한 즉시 완화 (TASK-20260618T025755)

'+ 데이터베이스 추가' 드롭다운에 **검색 필터 + 정규식 일괄 선택**을 추가했다. 다수 DB 를 패턴으로
한 번에 골라 allowlist 에 넣을 수 있어 "수동으로 하나씩" 의 통증을 줄인다. 단 이것은 여전히
**관리자가 변경 시점에 직접 행동(pull)** 해야 하는 수동 모델이다 — drift 자체를 없애지는 못한다.

## 3. 제안 (3단계)

### Tier 1 — 변경 가시화 (drift 를 "안 보임" → "보임", 낮은 위험·먼저 권장)

1. **DB 구성 drift 위젯/배너**: 데이터소스의 *실제* DB 목록(이미 `/api/admin/datasources/{key}/databases`
   로 분류해 받아옴)과 제품 allowlist 를 주기적으로 대조해 두 가지를 표면화:
   - **미배정 신규 DB**: 어떤 제품 allowlist 에도 없는 신규 사용자 DB("새로 생겼는데 아무도 안 씀").
   - **끊긴 항목(stale)**: 실제로는 사라진 DB 를 가리키는 allowlist 항목.
   관리 콘솔 대시보드 위젯(`_DASHBOARD_WIDGETS` 패턴) 또는 제품 상세 상단 배너로 노출.
   → 관리자가 폴링하지 않아도 "손볼 게 생겼다"를 시스템이 먼저 알림. **읽기 전용이라 보안 영향 0.**
2. **stale 항목 원클릭 정리**: 끊긴 allowlist 항목에 "제거" 단축(현재 `is-offline` 행 시각 표시의
   능동 버전). 파괴적이므로 확인 + 기존 `product.manage` 게이트 재사용.
3. **DB 변경 이력**: 데이터소스 DB add/remove 를 감지해 audit 에 남겨 churn 의 출처를 추적
   (`agent_kb`/insight 스캔 부산물로 이미 일부 신호 보유).

### Tier 2 — 패턴 기반 동적 allowlist (drift 를 구조적으로 제거, **중간 위험**)

정적 이름 목록 대신, 제품-데이터소스마다 **규칙(rule)** 을 저장한다:

```
include: ["^prod_", "_live$"]   # 정규식/glob
exclude: ["_bak$", "^tmp_"]
```

질의 시점에 규칙을 **살아있는 DB 목록에 평가**해 allowlist 를 동적 산출한다. 규칙에 맞는 신규
DB 는 자동 포함, 사라진 DB 는 자동 탈락 → **drift 가 원천 소멸**. (이번 cycle 의 정규식 선택이
이 모델의 디딤돌이다 — 다음 단계는 "패턴으로 선택" → "패턴 자체를 저장".)

- **보안 트레이드오프(중요)**: 패턴이 신규 DB 를 *자동 부여* 하면 과도 부여(over-grant) 위험.
  완화: (a) `exclude` 우선 + 시스템/내부 스키마 강제 제외(기존 검증 재사용), (b) 규칙이 만드는
  집합을 곧장 적용하지 않고 **"제안 → 관리자 승인"**(drift 위젯과 결합)하는 **반자동(semi-auto)**
  기본값, (c) 규칙 변경/자동 편입을 audit 에 기록. → RBAC 경계 변경이므로 **outside-voice 리뷰 필수.**
- 정적 목록과 **공존**: 규칙 미설정 제품은 기존 정적 allowlist 그대로(무회귀 마이그레이션).

### Tier 3 — 논리 그룹/거버넌스 (장기·운영 규율)

1. **DB 태그/그룹**: 데이터소스에서 DB 에 태그(env=prod, game=kr 등) 부여, 제품은 개별 DB 가 아닌
   **태그를 참조**. 신규 DB 에 태그만 달면 그 태그를 쓰는 제품에 자동 흐름. Tier 2 규칙의
   "이름 패턴" 보다 명시적·안전(이름 규칙에 의존 안 함).
2. **DB 네이밍 컨벤션**: 게임/환경별 접두어(`kr_`, `qa_`, `_log`) 표준화 → Tier 2 패턴 규칙의
   신뢰도를 높이는 전제. (현재 제품 키 KR/MV/GZ 등 접두어 체계가 이미 있어 적용 쉬움.)
3. **구성 복제/템플릿**: "이 제품의 DB 구성을 다른 제품에 복사" — 동일 allowlist 를 공유해야 하는
   제품군(예: 본판/QA)의 반복 입력 제거.

## 4. 권장 로드맵

| 순서 | 항목 | 위험 | 효과 | 비고 |
|---|---|---|---|---|
| 0 (완료) | 검색 + 정규식 일괄 선택 | 낮음 | 수동 선택 가속 | TASK-20260618T025755 |
| 1 | drift 위젯 + stale 원클릭 정리 | 낮음(읽기/기존 게이트) | drift 가시화 | **다음 권장** |
| 2 | 패턴 기반 반자동 allowlist(승인형) | 중간(RBAC) | drift 구조 제거 | outside-voice 필수 |
| 3 | DB 태그/그룹 + 네이밍 컨벤션 | 중간(설계) | 장기 운영 규율 | 소유자 결정 |

**한 줄 요약**: 지금은 "관리자가 변경 때마다 손으로 당기는(pull)" 모델이다. Tier 1 로 *언제 손볼지를
시스템이 알려주고(push 알림)*, Tier 2~3 으로 *손볼 일 자체를 규칙·태그로 없애는* 방향을 권장한다.
자동 부여 계열(Tier 2~3)은 보안 경계를 건드리므로 "제안 → 승인" 반자동을 기본값으로 두고
outside-voice 리뷰를 거쳐야 한다.
