# Report

## 진행 요약 (2026-07-31)

ITEM-08(L3 도메인 합성) 구현 완료 — **로드맵 마지막 항목**. codex P1 1건·P2 2건 반영, 출하 중.

## 무엇을 만들었나

스키마(DB) 하나의 도메인 개요를 3~5문장으로 합성한다. 입력은 그 스키마의 **클러스터 요약들**
이지 개별 테이블이 아니다 — 이미 한 번 접힌 것을 다시 접는다.

라이브 실측: 클러스터 요약 1,006건이 120개 스키마에 걸쳐 있다(평균 8개/스키마). "이 DB 가
어떤 도메인인가"를 알려면 여전히 8개를 읽어야 했다.

## 설계의 전부: 요청과 생성의 분리

두 제약이 얼핏 모순이었다 — **사전 전량 생성 금지**(120개 중 대부분은 아무도 안 읽는다)와
**답변 경로 런타임 합성 금지**(체감 지연 잠식).

해법은 "누가 실제로 찾았는가"를 생성 신호로 쓰는 것이다. grounding 이 요약을 찾다가 없으면
요청만 남기고(LLM 0, 지연 0), insight tick 이 그것을 보고 합성한다. 첫 질문은 요약 없이
답하지만 120번의 헛된 합성을 치르지 않고, **자주 찾히는 도메인이 먼저 채워진다**.

## 리뷰에서 배운 것

codex P1 은 **최적화가 정확성을 조용히 깨뜨린 사례**였다. payload 를 25개로 자른 것은 토큰
보호였는데, 그 잘린 목록으로 재생성 해시를 계산하면서 "입력이 바뀌었는가"라는 다른 질문의
답까지 잘라 버렸다 — 26번째 이후 클러스터가 전부 바뀌어도 재생성되지 않는 상태였다.
그리고 카운트(커버리지)를 해시에서 빼놓아, 근거가 두터워져도 요약이 옛 기준으로 남았다.

**같은 데이터를 두 목적으로 쓸 때는 각 목적이 요구하는 범위를 따로 봐야 한다.**

## 이것으로 로드맵이 닫힌다

`docs/improvements/analysis-orchestration/ROADMAP.md` 의 12항목이 모두 done 이다.
L0(증거) → L1(접지 분석) → L2(클러스터 요약) → L3(도메인) 4층과, 그 위의 소비(grounding)·
검증(판정)·계획(플래너)·비용(예산) 4축이 모두 배선됐다.
