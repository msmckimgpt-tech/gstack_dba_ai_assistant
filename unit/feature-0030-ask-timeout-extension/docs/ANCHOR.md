# ANCHOR: feature-0030-ask-timeout-extension

## §1. 외부 관점 요약

- "타임아웃을 사용자가 풀 수 있게 하면 타임아웃이 왜 있나?" — 타임아웃의 목적은
  *무한 대기 방지* 이지 *추론 중단* 이 아니다. 사람이 화면 앞에서 기다리고 있다는
  사실이 확인된 순간, 그 요청에 한해 상한을 푸는 것이 원래 의도에 더 맞다. 사람이
  없으면(무응답) 상한은 그대로 작동한다.
- "그럼 비용이 폭주하지 않나?" — 시간만 푼다. 도구 호출 상한(`max_steps`), 취소·즉시
  답변 버튼, 워커 lease fencing 은 그대로다. 그리고 연장은 사람이 매번 명시로 눌러야
  하는 opt-in 이라 자동 반복되지 않는다.
- "왜 80% 인가, 왜 100% 에서 묻지 않나?" — 100% 에 물으면 사용자가 버튼을 누르는
  사이에 이미 run 이 죽는다. 남은 20% 가 사람의 반응 시간이자, 승인이 도착했을 때
  루프가 아직 살아 있게 하는 여유다.
- "왜 확인 창을 띄워 진행을 멈추지 않나?" — 2026-07-09 사용자 결정으로 화면 차단
  타임아웃 모달을 이미 폐기했다. 멈추면 남은 20% 를 사람이 읽는 데 써버린다.

## §2. 대안 분기

- **Alt-A: 타임아웃 기본값을 크게 올린다.** 페르소나: 설정으로 해결하려는 운영자.
  안 고른 이유: 모든 요청에 큰 상한을 주면 진짜로 멈춘 run 도 오래 붙잡혀 워커 슬롯과
  비용을 먹는다. 문제는 "짧은 상한" 이 아니라 "사람이 기다리는 요청과 아닌 요청을
  구분하지 못하는 것" 이다.
- **Alt-B: 타임아웃 시 부분 추론을 저장해 보여준다.** 페르소나: 데이터 보존 우선 팀.
  안 고른 이유: 사용자가 원한 것은 "잘린 중간 산출물" 이 아니라 "완주한 답변" 이다.
  부분 보존은 이미 인터럽트 경로(`cancel_preserve`)에 있고, 소실 체감을 없애지 못했다.
- **Alt-C: 자동 연장(사용자 확인 없이).** 페르소나: 마찰 최소화 우선 팀.
  안 고른 이유: 사람이 자리를 뜬 요청까지 무한정 돌아 비용·슬롯이 새며, 사용자 요청
  자체가 "확인을 받은 후" 를 명시했다.
- **Alt-D: 즉시답변(finalize) 권한을 재사용.** 페르소나: 권한 추가를 피하려는 팀.
  안 고른 이유: "지금 멈추고 답해라" 와 "한도 없이 더 해라" 는 정반대 조작이다. 같은
  코드로 묶으면 감사 로그와 역할 설계에서 두 행위를 분리할 수 없다.

## §3. 가정된 사용 시나리오

DBA 담당자가 대량 스키마에 대해 복합 분석 질문을 던지고 다른 창에서 티켓을 처리하러
간다. 40초쯤 뒤 브라우저 알림이 뜬다 — "응답 시간 한도에 근접했습니다. 계속 추론할까요?"
탭으로 돌아와 컴포저 위 배너의 [계속 추론] 을 누르면 배너가 "한도 없이 추론 중" 으로
바뀌고, 잠시 후 잘리지 않은 완전한 답변이 도착한다. 다음 질문은 다시 평소 타임아웃으로
동작하므로, 이 한 번의 승인이 시스템 기본값을 바꾸지 않았다는 것도 화면에서 확인된다.
