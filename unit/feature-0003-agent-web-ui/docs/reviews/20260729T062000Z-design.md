## 1. Findings (발견)

### D-1 (CONCERN·회귀) `.attach-list-item-meta` 는 말줄임 방어가 없다 — 버전 체인 행에서 2줄로 터진다

브리핑 1번 항목의 답: **이름줄은 안전, 메타줄은 안전하지 않다.**

| 규칙 | 방어 | 판정 |
|---|---|---|
| `.attach-list-item-info` | `flex:1; min-width:0` (styles.css:3258) | OK — flex 축소 가능 |
| `.attach-list-item-name` | `overflow:hidden; text-overflow:ellipsis; white-space:nowrap` (3262) | OK |
| `.attach-list-item-meta` | **없음** — nowrap·overflow·ellipsis 전부 부재 (3269) | **취약** |

폭 예산(패널 기본 280px 기준, `.attach-side-panel-list` padding 12px×2 · 행 border 1px×2 +
padding 10px×2 → 행 내부 234px, `gap:8px`):

```
변경 전: 234 − icon(~19) − 8 − 8 − dl(~26)                = info ~173px
변경 후: 234 − icon(~19) − 8 − 8 − dl(~26) − 8 − del(~20) = info ~145px   (−28px, −16%)
패널 최소폭 240px 에서는  133px → 105px (−21%)
```

메타줄 최악 조합(= `verCount>1` 행)은
`12.3MB · 읽기 완료 · [버전 3개 ▾]` — 10.5px 기준 한글 full-width 로 계산하면 **~150px**.
즉 변경 전(173px)엔 들어가고 변경 후(145px)엔 **넘친다**. nowrap 이 없으므로 잘리지 않고
**줄바꿈**되어, ① 행 높이가 ~13px 커지고 ② 리스트의 균일 리듬이 깨지며 ③ 1행 끝에 구분자
` · ` 만 남고 `버전 3개 ▾` 토글이 2행으로 내려가는 고아 배치가 나온다.

영향 범위가 하필 **버전 체인이 있는 행 = AI 가 수정한 파일** 이라는 점이 나쁘다(가장 중요한 행).
`fmtSize` 가 `12.3MB` 처럼 5~6자를 뱉는 큰 파일 + `읽기 완료` 상태에서 가장 먼저 터진다.

### D-2 (CONCERN·회귀) `v2 · AI 수정` 배지가 이름줄 말줄임에 먹혀 사라지는 구간이 넓어졌다

`verBadge` 는 `.attach-list-item-name`(nowrap+ellipsis) **안쪽 마지막 인라인 요소**다(app.js:10107).
배지에 `flex-shrink:0` 류 보호가 없으므로, 파일명이 길면 배지가 통째로 잘려 **사라진다**.
컨테이너가 173px → 145px 로 줄면서, 이전엔 배지 일부라도 보이던 파일명 길이 구간
(대략 145~173px 폭 = 한글 파일명 12~14자 / 영문 23~28자)이 **전부 배지 소실 구간으로 이동**한다.
"AI 가 이 파일을 수정했다"는 유일한 시각 신호가 조용히 사라지는 것이라 단순 미관 문제가 아니다.
브리핑 4번 항목("배지 있는 행에서 무너지는가")의 답은 **예 — 무너지는 게 아니라 소리 없이 없어진다**.

### D-3 (CONCERN) 공유 문맥에서 파괴적 컨트롤인데 소유자 신호가 0이다 — 게다가 코드 주석의 권한 전제가 틀렸다

`app.js:9650` 주석과 신규 함수 주석은 "업로더 본인만 삭제할 수 있다" 라고 단언하지만,
실제 서버 판정은 업로더가 아니라 **대화 소유 OR 그룹 멤버십**이다:

```
routers/attachments.py:334-338  _account_can_access_attachment
    if _conversation_owned_by_account(...): return True
    # feature-0009: 그룹 대화 멤버도 첨부 접근 가능 (첨부는 전원 공유, REQ-GC-R6)
    return _account_is_conversation_member(conversation_id, acct_id)
```

즉 **그룹 대화에서는 아무 멤버나 다른 멤버가 올린 첨부를 지울 수 있다.** 그리고 이 변경은
"대화 전체 첨부"를 보여주는 목록 뷰(=남의 첨부가 정상적으로 섞여 있는 유일한 화면)에 그 삭제
버튼을 처음으로 붙였다. 그런데 화면에도, confirm 문구에도 **누가 올린 파일인지 단서가 없다**:

- 목록 payload(`_serialize_attachment_for_api`, `_conv_store.py:3473-`)는 `AccountId`/업로더를 **노출하지 않음** → 프론트가 표기하고 싶어도 데이터가 없다
- confirm 문구: `"X.csv" 을(를) 이 대화에서 삭제할까요? / 삭제하면 AI 가 더 이상 이 파일을 참조하지 않습니다.`
  → "이건 남의 파일" · "모든 멤버에게서 사라진다" 어느 쪽도 말하지 않는다

파괴적 동작을 공유 자원에 노출할 때 필요한 최소 정보(소유자·영향 범위)가 빠져 있다.

### D-4 (CONCERN) 거부 피드백이 틀렸다 — 403 분기는 죽은 코드, 실제 거부는 "재시도하면 될 것 같은" 토스트

```js
showToast(e && e.status === 403 ? "이 첨부를 삭제할 권한이 없습니다." : "첨부를 삭제하지 못했습니다.", true);
```

`DELETE /api/attachments/{id}` 는 라우트 데코레이터 없이 핸들러 안에서 권한 실패 시
**404** 를 돌려준다(`attachments.py:240` — "첨부를 찾을 수 없거나 삭제 권한이 없습니다.").
따라서 `403` 분기는 이 경로에서 도달 불가이고, 권한 거부는 항상 일반 실패 문구
`첨부를 삭제하지 못했습니다.` 로 표시된다. 사용자는 이를 **일시적 오류로 읽고 재시도**한다 —
confirm 을 다시 읽고, 다시 승인하고, 다시 실패하는 루프. 영구 상태에 재시도 유도 문구를 붙인
전형적 오류다(신규 코드는 아니지만, 이 변경이 노출면을 pill → 전체 목록으로 확장했다).

### D-5 (nit) 시각 위계는 **타당** — 다만 코드 주석이 CSS 와 불일치

브리핑 2번 항목의 답: **파괴적 동작이 더 강해 보이지 않는다. 위계는 옳다.**

| | 색(rest) | 크기 | hover |
|---|---|---|---|
| `⬇` `.attach-list-item-dl` | `--primary` #2563eb (강한 액센트) | 12px | 파랑 8% 배경 |
| `×` `.attach-list-item-del` | `--text-muted` #807d72 (억제) | 14px | 빨강 8% 배경 + `--danger` |

색 위계로 다운로드가 명백히 우세하고, 삭제는 hover 에서만 danger 를 드러낸다 — 프로젝트의 가장
가까운 선례인 `.attach-side-panel .composer-attachment-pill .pill-remove`(styles.css:3075-3085,
`color:var(--text-muted)` → hover `var(--danger,#dc2626)`, **font-size:14px; line-height:1**)와
정확히 같은 관용구다. 14px 은 `×`(U+00D7) 의 작은 글리프 폭(~0.55em)을 보정하는 프로젝트 표준값이지
"더 크게 보이게" 한 것이 아니다.

다만 신규 주석은 `다운로드와 같은 크기·리듬을 쓰되` 라고 적었는데 실제로는 12px vs 14px 로 **다르다**.
근거 문서가 코드와 어긋난 채 남으면 다음 사람이 "정렬 맞춰야지" 하며 잘못 고친다. 문구 정정 필요.

행 높이 영향은 없다: dl ≈ 4+4+`normal`(≈14.4) = 22.4px, del ≈ 4+4+`line-height:1`(14) = 22px 로
사실상 동일하고, 둘 다 info 블록(이름+메타)보다 낮아 행 높이를 지배하지 않는다.

### D-6 (nit) hover 배경이 토큰을 우회한다 — `--danger-soft` 가 이미 있다

신규: `background: rgba(220, 38, 38, 0.08)` (리터럴 #dc2626 을 손으로 복제).
프로젝트의 danger hover 관용구는 일관되게 토큰이다:

```
.tool-btn.danger:hover              { background: var(--danger-soft); }            (345)
.share-mgr-btn.is-danger:hover      { background: var(--danger-soft); }            (2659)
.share-participant-btn.is-danger:hover { background: var(--danger-soft,#fef2f2); } (2739)
```

인접 규칙 `.attach-list-item-dl:hover { rgba(37,99,235,.08) }` 과 국소적으로 맞춘 선택이라
이해는 가지만, `--danger` 가 소유한 리터럴을 CSS 안에 한 번 더 하드코딩한 것이라 팔레트 변경 시
색이 조용히 어긋난다. 최소한 `rgba(220,38,38,.08)` 대신 `var(--danger-soft)` 검토 권고.

### D-7 (note) 타깃 크기·간격 — 오클릭 유발 수준은 아니나 두 가지 단서

브리핑 3번 항목의 답: **간격 규칙은 있다.** `.attach-list-item { gap: 8px }`(3246)이 flex 자식
전체에 적용되므로 `⬇`↔`×` 사이는 8px 로 벌어져 있다.

- 실측 추정 타깃: `×` ≈ 20×22px, `⬇` ≈ 26×22px → 둘 다 WCAG 2.5.8(24×24) **미달**.
  단 중심 간 거리 ≈ 34px > 24px 이므로 **spacing exception 은 충족**한다. 그리고 이는 기존
  `.attach-list-item-dl` 이 이미 갖고 있던 성질이라 이 변경의 회귀는 아니다.
- 진짜 위험은 크기가 아니라 **근육 기억**이다: 지금까지 행의 최우측 = 다운로드였는데, 이제 그
  자리가 삭제다. 기존 사용자의 첫 클릭이 삭제로 착지한다. 파괴적 동작을 최우측에 두는 배치
  자체는 관례에 맞으므로 유지하되, confirm 이 유일한 방어선이라는 점을 인지해야 한다(→ D-8).
- 터치(패널 `max-width:92vw`)에서는 20×22px + 8px 간격이 편안한 타깃(≥44px)에 한참 못 미친다.

### D-8 (nit) 파괴적 동작 관용구가 프로젝트 안에서 두 갈래다 — 네이티브 `confirm` vs 인앱 undo

이 프로젝트는 되돌릴 수 있는 파괴적 동작에 대해 **인앱 6초 실행취소 배너** 관용구를 이미 갖고 있다
(`conv-folder-undo` / `undoFolderDelete()` / app.js:3159 "삭제 후 잠시 '실행 취소'로 되돌릴 수 있습니다").
반면 첨부 삭제는 디자인 시스템 밖의 **네이티브 `window.confirm()`** 이다. 첨부 삭제는 실제로는
soft-delete + `restorable_until`(기본 30일 retention, `_conv_store.py:3511-3520`) 이므로 기술적으로
undo 배너를 붙일 수 있는 대상이다. 기존 pill 경로에서 물려받은 것이라 이번 변경의 신규 결함은
아니지만, 이 변경이 confirm 노출 빈도를 "방금 첨부한 직후" → "목록의 모든 행"으로 곱했다.

### D-9 (nit) 접근 가능한 이름이 파일을 식별하지 못한다

`aria-label="첨부 삭제"` · `title="이 대화에서 삭제"` 가 **모든 행에서 동일**하다. 스크린리더
사용자는 N개의 구분 불가능한 "첨부 삭제" 버튼을 듣는다(다운로드 버튼도 `title="다운로드"` 로
같은 문제를 갖지만 파괴적이지 않다). confirm 이 파일명을 말해주므로 완전한 맹목은 아니나,
파괴적 컨트롤의 접근 이름에 파일명을 넣는 것은 비용이 거의 0이다.

### D-10 (PASS) 테마 — 이 콘솔은 LIGHT-ONLY 이므로 브리핑 5번 항목은 성립하지 않는다

`styles.css:76-77` 이 정책을 명시한다: *"이 콘솔은 LIGHT-ONLY — 서피스/시맨틱 태그 토큰의 다크
@media override 를 두지 않는다 ... 과거 다크 override 는 흰색 행 위에서 대비 저하 회귀를 유발해 제거함."*
`:root`(7-74) 에만 토큰이 있고 `--danger`/`--text-muted`/`--bg` 에 다크 override 가 없다.
파일에 남은 `@media (prefers-color-scheme: dark)` 3곳(1197·1230·8471)은 메시지 말풍선 국소 패치일 뿐
이 패널에 닿지 않는다. 따라서 OS 다크 모드에서도 행 배경은 `--bg #f7f7f4` 로 고정이고,
신규 규칙은 **테마 안전**하다. `var(--danger, #dc2626)` 의 fallback 은 잉여지만 인접 규칙들과
같은 표기라 무해.

대비(계산 추정):
- rest `#807d72` on `#f7f7f4` ≈ **3.8:1** → 1.4.11(비텍스트 3:1) 통과 / 1.4.3(4.5:1) 미달.
  아이콘 글리프이고 기존 `.pill-remove` 와 동일 토큰이라 신규 회귀는 아님.
- hover `#dc2626` on 빨강 8% 틴트 배경 ≈ **4.2:1** → 통과.

## 2. Risks (위험)

1. **행 리듬 붕괴가 가장 중요한 행에서 발생** (D-1) — 버전 체인 = AI 수정 파일. 패널을 최소폭
   240px 로 줄인 사용자에게는 거의 확정적으로 재현된다.
2. **AI 수정 배지의 무성(無聲) 소실** (D-2) — 사용자가 "AI 가 내 파일을 고쳤다"를 인지하지 못한 채
   원본으로 착각할 수 있다. 잘못된 파일을 신뢰하는 데이터 신뢰성 문제로 번진다.
3. **그룹 대화에서 남의 파일을 1클릭+confirm 으로 파괴** (D-3) — 소유자 표기 없음, 영향 범위
   고지 없음, 인앱 undo 없음. 삭제된 파일은 assistant 참조 스코프에서 즉시 빠지므로 다른 멤버의
   진행 중 작업에 즉시 영향을 준다.
4. **거부가 재시도를 유도** (D-4) — 404→일반 실패 문구. 사용자는 confirm 을 반복 승인하며
   같은 실패를 반복한다.
5. **최우측 버튼 교체로 인한 첫 오클릭** (D-7) — 기존 사용자의 다운로드 근육 기억이 삭제에 착지.
6. TASK 의 `[x] 라이브 재검증 (PB-0008)` 은 D-1/D-2 를 노출하는 조합(`version_count>1` +
   `status=ingested` + 긴 파일명 + 패널 240px)을 태우지 않았을 가능성이 높다.

## 3. Recommendations (권고)

우선순위 순.

1. **(D-1 필수)** `.attach-list-item-meta` 에 말줄임 방어 추가 —
   `white-space:nowrap; overflow:hidden; text-overflow:ellipsis;`.
   단 `버전 N개 ▾` 토글이 잘리면 기능 자체가 사라지므로, 메타를 flex 로 만들고
   토글에 `flex-shrink:0` 을 주는 편이 안전하다(텍스트만 줄고 토글은 유지).
2. **(D-2 필수)** 이름줄을 `display:flex; align-items:baseline; gap:4px` 로 바꾸고
   파일명 span 만 `min-width:0` + ellipsis, `.attach-list-item-ver` 에 `flex-shrink:0`.
   배지는 절대 사라지지 않고 파일명만 줄어든다.
3. **(D-3 / 사람 판단)** 두 갈래 중 택일 — ⓐ 목록 payload 에 업로더 표시(예: `uploaded_by_name`
   또는 `can_delete` 불리언)를 추가해 행에 소유자 표기 + 남의 파일이면 확인 문구 강화,
   ⓑ 스코프 유지(frontend-only) 하되 최소한 confirm 문구에 "이 대화의 모든 참여자에게서
   사라집니다" 한 줄 추가. ⓐ 는 §12.3 frontend-only 범위를 넘으므로 **승인 필요**.
4. **(D-4)** 에러 분기를 `e.status === 403 || e.status === 404` 로 넓히고 문구를
   "이 첨부를 삭제할 권한이 없습니다." 로. 지금의 403 전용 분기는 이 엔드포인트에서 죽은 코드다.
5. **(D-5)** CSS 주석의 `다운로드와 같은 크기·리듬` 을 사실에 맞게 정정 —
   "pill 의 × 와 같은 크기(14px/line-height:1)·색 관용구를 따르고, 다운로드보다 약한 색으로 억제".
6. **(D-6)** `rgba(220,38,38,0.08)` → `var(--danger-soft)` 검토(또는 왜 토큰을 안 쓰는지 주석).
7. **(D-9)** `aria-label` 에 파일명 포함 — `aria-label="${escapeHtml(name)} 삭제"`.
8. **(D-8, 후속)** 첨부 삭제도 `conv-folder-undo` 관용구(6초 실행취소)로 통일 검토.
   soft-delete + restorable_until 이 이미 있어 서버측 전제는 충족. 별 TASK 권장.
9. **(D-7, 선택)** `.attach-list-item-del` padding 을 `5px 7px` 로 올려 24px 타깃에 근접시키고,
   두 버튼 사이만 `margin-left:2px` 추가로 벌리는 것도 가능(단 D-1 폭 예산과 상충하므로
   1·2번 수정 후에 판단).
10. **재검증 케이스 지정**: `version_count ≥ 2` + `status=ingested` + 한글 15자 이상 파일명 +
    패널 폭 240px(최소) 에서 PB-0008 스크린샷. 이 조합이 D-1·D-2 를 동시에 노출한다.

## 4. Verdict rationale (판정 근거)

**CONCERN.** BLOCK 이 아닌 이유: 삭제는 soft-delete + 30일 retention 이라 비가역이 아니고,
기능 자체(안내 문구가 가리키는 컨트롤이 화면에 없던 불일치 해소)는 옳은 수정이며, 시각 위계
(D-5)와 테마 안전성(D-10) 은 실제로 잘 잡혀 있다 — `.pill-remove` 선례를 정확히 따랐다.

PASS 가 아닌 이유: 브리핑 1·4번이 지목한 폭 압박이 **실재하는 회귀**로 확인되었다.
`.attach-list-item-info` 는 `min-width:0` 으로 잘 보호돼 있지만 그 안의 두 자식 중
이름줄만 방어되고 **메타줄은 무방비**이며(D-1), 배지는 말줄임의 첫 희생자다(D-2).
28px(-16%, 최소폭에선 -21%)는 "조금 좁아짐"이 아니라 이 두 요소를 임계 밖으로 밀어내는 크기다.
여기에 공유 문맥의 파괴적 컨트롤이 소유자 신호 없이 노출되고(D-3), 거부 피드백이 사실과
다르게 재시도를 유도한다(D-4).

권고 1·2 는 CSS 몇 줄로 끝나고 이 변경의 스코프 안이다 — **머지 전 처리 권장**.
권고 3 은 스코프 확장 판단이 필요해 **사람 승인 대상**으로 올린다.
