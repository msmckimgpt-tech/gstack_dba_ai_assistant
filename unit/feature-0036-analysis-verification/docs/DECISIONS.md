# Decisions (feature-local ADR)

## ADR-0036-01 — 판정 실패는 "검증됨"이 아니다 (핵심 불변식)
- **결정:** LLM 오류·계약 위반 응답·근거 없는 응답·증거 부재·저장 실패는 **행을 만들지 않는다**.
- **근거:** 확인 도장이 잘못 찍히면 그 도장을 근거로 위층(요약·답변)이 더 확신한다. 검증층이
  틀린 확신을 증폭하면 없느니만 못하다. 이 모듈의 fail-soft 는 "통과"가 아니라 "침묵"이다.
- **강제:** 테스트 파일의 절반이 이 명제를 지킨다.

## ADR-0036-02 — 예산을 못 읽으면 중단한다 (fail-soft 방향 반전)
- **결정:** `llm_budget`·`resource_budget` 을 import 할 수 없으면 pass 를 중단한다.
- **근거:** 다른 fail-soft 와 방향이 반대인 이유는, 계량 장애로 기능이 멈추는 것보다 **상한을
  모른 채 자동 지출을 계속하는 쪽이 위험**해서다. "모르면 하지 않는다"는 원칙은 지출에 특히 강하게
  적용된다.

## ADR-0036-03 — red-team 재사용 금지, pass_no 재사용 금지
- **결정:** 신규 프롬프트 + 신규 테이블.
- **근거:** feature-0021 은 `question + draft + evidence` 답변 전용 구조다. `pass_no` 는
  back-refine 세대라 검증 세대와 직교한다. 억지로 겹치면 한쪽을 고칠 때 다른 쪽이 깨진다.

## ADR-0036-04 — analysis_hash 가 재판정의 축이다
- **결정:** 이전 판정의 해시를 조회해 현재 분석문 해시와 비교한다. 저장 시 같은 노드의 다른 해시
  행을 삭제해 노드당 1행을 유지한다.
- **근거:** "판정 행이 있으면 제외"로 두면 분석이 갱신돼도 옛 판정이 남아 **재판정되지 않는다** —
  문서에 적은 계약과 정반대다(codex P1). 1행 유지는 무한 증식과 LEFT JOIN 행 증가를 함께 막는다.

## ADR-0036-05 — 배치하지 않는다 (1건 1콜)
- **결정:** 판정은 분석문 1건에 LLM 1콜.
- **근거:** 배치하면 한 건의 오판이 같은 응답 안의 다른 건으로 번지고, 응답이 길어져 잘린다.
  L2 요약(feature-0033)이 배치 6인 것과 다른 판단인 이유는 **판정은 서로 독립이어야** 하기 때문이다.

## ADR-0036-06 — 근거 없는 판정은 기록하지 않는다
- **결정:** `reason` 이 비면 판정을 버린다.
- **근거:** 프롬프트는 "판정을 가른 구체적 숫자·필드"를 요구한다. 그것이 없으면 사람이 그 판정을
  재확인할 방법이 없고, 재확인할 수 없는 확인 도장이야말로 이 층의 최악의 실패다.
- **경계:** 길이 하한은 두지 않는다 — 자의적이고, 짧아도 숫자를 지목하면 유효한 근거다.

## ADR-0036-07 — 판정자는 모순 쪽으로 기울되 날조하지 않는다
- **결정:** 프롬프트에 "prefer contradicted over supported when a real conflict exists" 와
  "do not invent conflicts to look thorough" 를 함께 넣는다.
- **근거:** 한쪽만 있으면 rubber-stamp 판정자 또는 트집쟁이 판정자가 된다. 증거가 **표본**임을
  명시해 표본 유일성을 전역 제약으로 오해하지 않게 하는 것도 같은 균형이다.

## ADR-0036-08 — 대상은 노드당 최신 분석문 1건 (ADR-0036-04 의 짝, 2026-08-05)
- **결정:** `pending_targets` 는 `DISTINCT ON (scope_key, node_key)` 로 노드마다 가장 최근
  분석문 1건만 대상으로 삼는다. 바깥 정렬의 첫 키는 "한 번도 판정된 적 없는 노드 우선".
- **근거:** ADR-0036-04 가 **저장**을 노드당 1행으로 고정했는데 **대상 선정**은 `node_analysis_jobs`
  를 행 단위로 봤다. 두 정책이 어긋난 자리에서 판정이 무한 순환한다 — 같은 노드에 **여러 분석 run 의**
  done 행이 쌓이므로(라이브: done 2,682행 / 노드 2,052, 다세대 노드 489개 전부 run_id 상이),
  A세대를 저장하면 B세대가 미판정으로 남고 B세대를 저장하면 A행이 지워져 다시 미판정이 된다.
  (초판 서술은 이 중복을 back-refine 탓으로 적었으나 오귀속이다 — `_backrefine_neighbors` 는 행을
  만들지 않고 기존 행을 제자리 전이시킨다. 적대 패널이 라이브 데이터로 반증했다.)
- **실측(2026-08-05 라이브):** 7일간 `analysis_verify` 7,896콜 = 배경 LLM 호출의 **62.8%**,
  토큰 24.9M(38.3%). 그런데 대상 노드는 91개뿐 — **노드당 평균 87회 재판정**이고 판정 행 수는
  91개로 고정. 정보는 한 건도 늘지 않았다. 상위 8개 노드(전부 done 행 2개 이상)가 호출의 69%를
  소비했고, done 행이 1개인 노드는 1회 판정 후 조용했다 — 원인이 중복 세대임을 가리키는 대조군.
- **대안 기각:** ① 재판정 쿨다운(`created_at < now() - interval`) — 증상만 늦추고 순환은 남으며
  "분석 갱신 즉시 재판정" 계약을 훼손한다. ② `node_analysis_jobs` 중복 정리 — 다른 feature 의
  적재 정책이라 이 층에서 손댈 경계가 아니고, 정리해도 대상 선정의 취약성은 남는다.
- **관측:** telemetry 에 `attempted`(실제 LLM 콜) · `rejudged`(이전 판정이 있었는데 다시 판정)를
  `checked` 와 분리했다. 정상 운영에서 `rejudged` 는 분석 갱신 빈도만큼만 나온다 — pass 마다 cap 을
  채우면 순환 재발 신호다. `attempted ≫ checked` 는 판정 실패가 예산을 먹는 중이라는 뜻이다.

### ADR-0036-08 보강 — 적대 패널(2026-08-05, backend·qa) 반영

- **"최신"의 기준은 `id`, `updated_at` 아님.** 모든 UPDATE 가 updated_at 트리거를 올려 과거 run 행이
  재분석 행보다 최신으로 역전된다. 이 저장소는 그 결함을 이미 겪고 `id DESC` 를 정본으로 삼았다
  (`node_analysis.get_node_analysis` · `_latest_done_analysis`). 패널이 라이브에서 두 기준이 갈리는
  노드 13개를 찾았고 **전부 분석문 텍스트가 달랐다** — 기준이 어긋나면 사용자가 볼 수 없는 문장에
  확인 도장이 찍히고, 화면에 보이는 최신 분석문은 영영 판정되지 않는다.
- **순회는 "판정이 오래된 것부터"(미판정 NULLS FIRST), "미판정 우선" 아님.** 후자만 두면 갱신된
  분석문이 미판정 집합 전체 뒤로, 다시 stage 전체 뒤로 두 겹 강등돼 완충 구간(limit×5) 밖에서
  **재판정이 굶는다** — ADR-0036-04 계약이 커버리지 확대와 함께 조용히 죽는다. 판정하면 verdict_at
  이 갱신돼 큐 뒤로 가므로 라운드로빈이 된다.
- **판정 pass 도 advisory lock 안에서.** 이 pass 에는 `node_analysis.process_pending` 같은 행 단위
  claim 이 없다. 워커를 늘리면 모두 같은(결정론적) 큐 선두를 판정해 콜이 워커 수만큼 중복되고, 그
  중복은 `judged_hash IS NULL` 을 함께 읽으므로 `rejudged` 에도 안 잡힌다. domain_synthesis 와 동형.
- **계측은 allow-list 등재까지가 구현이다.** `scan_report` 의 dict 값은 `_telemetry_sweep` 의 스칼라
  필터가 통째로 버린다. 이 워커에서 같은 실패(계측을 만들고 payload 에 안 실어 무음)가 이미 두 번
  있었고, 이번이 하마터면 세 번째였다. 테스트로 등재를 고정했다.
- **연속 판정 실패 상한(5).** 실패 노드는 미판정으로 남아 큐 선두를 계속 무므로, 판정자가 특정
  입력에서 계약 위반 응답을 반복하면 pass 예산을 통째로 먹는다. 영속 실패 상태를 두는 대안은
  "실패는 아무것도 기록하지 않는다"(ADR-0036-01)와 충돌해 채택하지 않았다.
