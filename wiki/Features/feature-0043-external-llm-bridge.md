# feature-0043 — 서버 계정 LLM 차단 + 웹 대화 pull 브리지

## 한 줄

서비스가 보유한 Claude 계정으로는 더 이상 추론하지 않고, 웹 대화 질문을 **각 사용자의 개인 머신
AI 런타임**이 자기 계정 LLM 으로 처리한다.

## 왜

2026-08-07 `claude-corp` 7일 쿼터가 100% 소진돼 서비스가 멈췄다. 계정을 늘리는 대신 **추론 주체를
뒤집는다** — 서버는 도구·컨텍스트·데이터만 제공하고 토큰은 사용자 구독이 부담한다.

## 어떻게 (한눈에)

```
[웹 대화창] 질문 → WebAiTasks(Origin='web', 대기)  → "내 AI 가 처리 중" 말풍선
                          ↓ 개인 머신 AI 가 블로킹 대기(wait_for_request · 폴링 아님)
              list_open_requests → claim_request (점유·30분 lease)
                          ↓ 개인 계정 LLM 이 추론 + 기존 도구로 DB 조회
              submit_answer → 원 대화에 답변 저장 → 화면이 SSE 로 자동 갱신(폴링은 폴백)
```

## 알아둘 것

- **push 가 아니라 pull.** MCP `sampling` 은 프로토콜 2026-07-28 에서 폐기됐고(SEP-2577)
  Claude Code 가 미지원이라(anthropics/claude-code#1785) 서버→클라이언트 push 경로가 없다.

  alias 주석이 두 번째 자물쇠. 되돌리려면 **둘 다** 풀어야 한다.
- **로컬 임베딩은 살아 있다.** `titan-embed`(bge-m3)는 계정과 무관하고 KB 검색이 의존한다.
- **무설치(등록형 경로).** 등록형 경로는 `https://<host>/api/ai/mcp` 를 AI 클라이언트에 URL+토큰으로
  등록하는 것뿐이고, 러너(정본 `src/agent/` 19 모듈 · 배포되는 단일 파일 `bridge_agent.py` 는 빌드 산출물 · 수동 보조 `bridge_runner.py`)도 Python 표준 라이브러리만 쓴다.
  다만 **연결의 기본 진입점은 등록이 아니다** — 2026-08-28 에 원클릭 셸 명령(아래 P0-AC)으로
  옮겼고, **2026-09-03 다시 연결 프로그램**([[feature-0046-native-client]] · `DQA Connect`)으로
  옮겨 터미널 단계는 접힌 보조 경로가 됐다.
- **연결은 셸이 실행한다(2026-08-28, P0-AC/AD).** 연결 수단이 「AI 에게 지시문 붙여넣기」 하나뿐일
  때는 어떤 AI 는 MCP 로 등록하고 어떤 AI 는 러너를 안 띄워 **구축 방식이 매번 달랐다.** 기본
  진입점을 셸 명령(`bridge_setup.sh`/`.ps1`)으로 바꿔 해석층을 걷어냈고, 지시문은 지우지 않고
  `<details>` 로 접어 보조로 내렸다 — 대체가 아니라 **기본 경로의 교체**다. 셋째 길로 **환경
  판단만** 그 머신의 AI 가 `BRIDGE_PROBED_*` 네 칸을 채우고, 그 값을 스크립트가 실존·타입·범위·
  allowlist 로 다시 본다(실행 경로는 여전히 하나라 「같은 입력이면 같은 결과」가 유지된다).
  브라우저는 샌드박스라 로컬 프로세스를 못 띄우므로 재기동은 최초 1회 등록한 **URL 스킴 핸들러**를
  거치며, 그 등록물은 setup 에만 있고 러너에는 없다.
- **연결이 요청의 전제조건이다**(정본 FUNCTION §P0-AB「요청과 연결은 다른 흐름이다」 — 같은 파일에 동명 절이 3개라 제목으로 한정). `연결됨`(토큰) × `대기 중`(러너) 곱을 **서버**가
  판정한다(`compose_blocked` — 프런트가 조립하면 판정이 두 벌이 되고 갈리는 순간 느슨한 쪽이
  사용자가 보는 진실이 된다). 토큰이 없으면 `409 bridge_blocked` 로 거절하며 **아무것도 저장하지
  않는다**(유령 말풍선 방지). 사용자가 쓴 입력은 지우지 않는다.
- **폴링이 아니라 블로킹 대기.** `wait_for_request` 가 질문이 들어오는 그 순간 반환한다(55초 상한 ·
  만료는 오류가 아니라 200 + `timed_out: true`). 주기 폴링은 인지 지연이 사람마다 달라 '환경 차이'
  가 되므로 금지다. 자리를 비워도 처리하려면 상주 러너 `bridge_agent.py`(stdlib 전용 단일 파일 — 2026-09-02
  이후 **정본은 `src/agent/` 모듈군**이고 그 단일 파일은 빌드 산출물이다. 분할 시 18 · 같은 창의
  자기 갱신 `selfupdate.py` 추가로 **현재 19** — `__init__.py` 의 `_EMIT_ORDER` 가 번들 순서 정본)를
  띄우며, 지시문에서 이것이 **권장 기본 경로**다. 워커는 **1개로 시작해 수요를 따라간다**(P0-Y,
  2026-08-28 — 종전 고정 2개는 폐기): `wait_for_request` 가 돌려준 대기 질문 수가 슬롯 수를 넘으면
  그만큼 늘고(상한 `--max-workers` 기본 8 · 예측 확장 없음), 300초 넘게 쉰 슬롯을 오래된 것부터
  회수하되 **최소 1개는 남긴다**. tick 은 별도 타이머가 아니라 long-poll 반환 그 자체다.

  이름을 얻었다 — Windows 명령줄 상한이 죽이던 답변 · 기동 240초 침묵 · `cp949` 머신에서 자식
  입출력이 깨지던 것(UTF-8 못박음).
- **09-02 창 — 능력 질의가 «신속»해졌고, 그 대가를 같은 cycle 이 되찾았다.** 자기소개 질문을 받은
  에이전트가 작업 디렉토리를 뒤지고 웹을 검색하고 있었다(한 번의 질의에 `exec_command` 18회 ·
  `web_search` 29회) — 그것이 240초 예산을 태운 실체이지 추론 강도가 아니었다. 세 질의 프롬프트
  맨 앞에 **도구 금지 가드**를 붙이고 codex 에만 질의 전용 인자를 얹어 claude 66.3→6.6초 ·
  codex >300초(타임아웃)→9.0초. 배포 직후 실측이 **가드가 추론축을 죽인 것**을 자체 적발했다 —
  claude 가 도구 없이 「추론 등급이 없다」고 자신 있게 답하자 그 부정이 확정으로 굳어 선택기가
  화면에서 사라졌다(5단계 → 0단계). 그 부정을 `--help` **관측으로 반증**하게 순서를 바꿔 되찾았다
  (도구를 금지한 쪽은 우리이므로 그 「없다」는 관측이 아니라 기억이다). 알려진 대가는 숨기지 않는다
  — 한 회차의 응답 폭이 좁아진다(claude 6종→3종). 감당하는 근거는 계정 원장의 **합집합 누적**이다.
- **09-02 창 — 화면 쪽 3건.** 콘솔 작업의 모델·추론등급을 **계정이** 정하고(러너가 없어도 저장값은
  보존하고 사유를 표시한다), 프로필 「AI 작업」 탭은 **열 수 있는 작업만** 보인다. 답변이 완수되는
  순간 사라지던 **총 수행시간**은 표시가 아니라 **각인**의 부재였다 — 서버 LLM 경로만 그 값을 굳히고
  브리지 경로는 아예 담지 않아 `duration_ms` 를 가진 마지막 답변이 2026-08-26 이고 이후 브리지 답변
  104건이 전량 비어 있었다. 원장의 세 시각으로 end-to-end 와 «대기/실행» 분해를 각인해 되살렸고
  (과거 104건은 소급 각인하지 않는다 — 사후 삽입은 관측이 아니다), 원장이 `DATETIME` 이라 **초
  해상도가 상한**임을 한계로 적었다. 라이브 배포 `ec649a6e` → `64168d5b`.
- **09-03 창(18 커밋) — 러너가 제품 이름을 얻고, 화면이 「모른다」를 정상이라 말하지 않게 됐다.**
  ⓐ **개명 `mysql-ai-bridge` → `dqa-connect`**(사용자 결정 = 하드 컷오버 · 하위호환 별칭 없음).
  이름이 리터럴로 21곳에 흩어져 있었고 한 곳을 놓치면 **웹은 새 스킴으로 열고 OS 에는 옛 스킴이
  등록된** 상태가 되는데, 브라우저는 스킴 핸들러 부재를 감지하지 못한다 — 버튼이 조용히 죽는다.
  정본 `shared/dqa_identity.py` 를 신설하고 **축을 셋으로 갈랐다**: `DQA Connect`(사람) ·
  `dqa-connect`(머신 전역 스킴) · `com.masangsoft.dqa-connect`(역-DNS). 스킴을 `dqa` 로 줄이지
  않은 것은 보안 판단이다 — 이 URL 에 세션 베어러 토큰이 실리고 스킴은 **마지막 등록자가 이기는**
  머신 전역 네임스페이스다(반대로 MCP 키는 짧게 `dqa` — 사용자 자기 CLI 설정 안의 로컬 키라
  전역 충돌이 없고 대신 모든 도구 이름에서 매번 읽힌다). 자체 감사가 실 결함 1건을 잡았다:
  옛 설치 잔재 정리 가드가 문자열 비교라 **끝 슬래시 하나** 때문에 옛 이름을 계속 쓰겠다고
  명시한 사용자의 **현행 홈이 삭제 대상**이 됐다. 후속으로 `.ps1` 의 `Say "… ($DqaScheme://)"`
  가 `$Var:` 를 네임스페이스 한정 변수로 읽혀 **파일 전체가 파싱 불가**였던 회귀를 CI 가 잡았고,
  그 파서 검사가 로컬에서 `pwsh` 부재로 **항상 skip** 되던 것까지 고쳤다(「테스트가 있다」 ≠
  「테스트가 돈다」) — 굽힌 `launch.ps1` 을 아무도 파싱하지 않던 Windows 축의 빈 자리도 채웠다.
  라이브 배포 `c08047f8` POST-DEPLOY 대조: 딥링크 스킴·응답 본문 `mysql-ai` 4 → **0**.
  ⚠ 실 OS 핸들러 재등록·옛 잔재 삭제는 사용자 머신 setup 재실행 후에만 관측된다(미검증).
  ⓑ **「모른다」를 정상으로 말하지 않는다 — 연결 상태 3상태.** 한 변수(`_AI_READY`)가 게이트 축과
  표시 축을 겸했다. 게이트에서 옳은 fail-open 초기값(`True`)이 그대로 화면에 나가 **미확인을
  「대기 중」으로** 그렸고, 캐시된 caps 가 있으면 능력 협상이 아예 돌지 않아 관측 기회조차
  없었다(사용자 라이브가 정확히 그 경로였다). 원장을 `None`(미확인)·`True`(답을 받아냈다)·
  `False`(관측된 불가) 3상태로 바꾸고 `ai_health()`(표시)와 `ai_blocked()`(게이트)를 **별도
  함수로 갈랐다**. 「확인 중」이 영구 고착하지 않도록 생존 확인(상한 30초)이 반드시
  `True`/`False` 로 떨어뜨린다 — 없으면 종전 거짓이 **새로운 무용**으로 바뀔 뿐이다. 서버는
  「키 없음」(구 러너)과 「`null` 신고」(확인 중)를 구분하고 변경 판정을 NULL-safe(`<=>`)로
  바꿨다(종전 `<> NULL` 은 거짓이라 「정상 → 확인 중」 전이가 한 행도 갱신되지 않았다).
  그 앞 cycle 은 화면의 축을 「하트비트 살아있음」에서 **「답할 수 있음」**으로 옮겼다.
  ⓒ **응답하지 않는 AI 를 영원히 기다리던 구조를 닫았다** — 협상 실패가 「답할 수 없다」로
  취급되지 않고 · 러너 상한이 0(무제한)이며 · 서버 900초는 「표시 경계이지 종료 조건이 아니었다」
  · lease 만료 후 재배달에 시도 상한도 종결도 없었다. 관측 기반 AI 건강 원장 + **아픈 러너에만**
  유한 상한(건강한 러너 무회귀) + **성공 1회 즉시 복귀**(영구 잠김 없음). 이어서 아픈 러너를
  기다리게 하던 **150초를 체감 0초**로 바꿨다(사용자 답변은 AI 호출 없이 즉시, 회복 확인은
  배경 스레드 · 쿨다운 60초). ⚠ 러너가 **제출조차 못 하는** 경우의 서버측 종결은 이월이다.
  ⓓ **연결 단계 체크리스트 + 클라이언트 우선 안내**(ROADMAP ITEM-03·ITEM-06) — 화면이 「어디서
  막혔는지」를 말한다. 판정은 서버 한 곳(`_connect_steps.py`)이고 단독 페이지와 모달이 같은
  배열을 그리므로 문안도 갈리지 않는다. 첫 행동을 **연결 프로그램**([[feature-0046-native-client]])
  으로 옮기고 터미널 단계는 접었다(실패 시 자동 펼침 · CLI 안내는 유지). ⚠ 클라이언트 다운로드가
  없으면 클라이언트를 **권하지 않는다** — 없는 다운로드를 안내하면 사용자는 안내받은 대로 갔다가
  막힌다. 실측된 최악 사례가 이 모듈의 이유다: 능력 협상 실패로 **240초 침묵**인데 설치
  스크립트는 2초 뒤 「완료」를 선언하고 실패 사유는 러너 로그(터미널)에만 있었다.
  ⓔ **연결 퍼널 계측**(ITEM-00)과 그 라이브 0건의 원인 — `build_audit_change_json` 은 명시적
  allowlist 인데 미등재라 `ValueError` 가 나고 `_audit_user_action` 의 fail-open 이 그것을 삼켜
  **증상 없이 계측만 소실**됐다. 등재 후 2026-09-03 실측 4행 적재 확인.
  ⓕ **`finally` 블록 안의 `return` 이 삼키던 협상 실패 사유를 되살렸다** — `_probe` 예외를
  `reasons` + `caps.probe_crashed` 로 노출해 요약 줄까지 도달시키고, 한 런타임 사고가 나머지
  협상을 죽이지 않게 했다.
- **한계.** 개인 머신 AI 가 꺼져 있으면 답이 오지 않는다. 2026-09-03 이후 UI 는 이것을
  「대기 중」으로 뭉치지 않는다 — **미확인은 「확인 중」**(중립 회색), **관측된 불가는 「답할 수
  없음」 + 사유**로 갈라 말한다. 남은 것: 러너가 제출조차 못 하는 경우의 **서버측 종결**(이월) ·
  ~~WSL 런타임을 `--cmd` 로 넘기는 경로는 능력을 신고하지 않아 「답할 AI 있음」이 ❌ 로 남는다~~
  → **해소(2026-09-04)**. 러너가 WSL 안을 직접 조회한다 — 탐지 순서는 지정 경로 → PATH →
  표준 설치 위치 → **WSL 안**이고, POSIX 절대경로는 `wsl.exe -e` 로 확장하되 **런타임 종류를
  바꾸지 않아** 능력 협상이 그대로 돈다(그것이 `--cmd` 우회와 다른 점이다). 실측에서
  「답할 AI 있음」 ✅.
