### 3. Challenge to current spec

설계는 스펙이 말하지만 시스템이 붙들 수 없는 전제에 기댄다: **「낡은 러너는 이 이름을 모르므로 신고할 수 없다 — 자격의 부재가 구조적으로 보장된다.」** 부재는 구조적으로 보장된다. *존재*는 아니다. `caps_self_report` 는 클라이언트가 준 JSON 필드에 실린 자기단언이고 `bridge_agent.py` 는 사용자가 내려받아 실행하는 평문 파일이다. 로컬 사본을 편집하는 누구든 — 또는 튜플 항목을 유지한 채 폴백을 복원하는 미래 빌드(코드 주석이 명시적으로 경고하는 바로 그것) — 계약을 선언하고 위반하는 러너를 만들며, 서버는 저자 자신의 인정대로 그것을 탐지할 수단이 없다. 그러므로 게이트는 계약을 검증하지 않는다. **2026-09-01 이후에 협조적 빌드를 내려받았음**을 검증한다. 그것은 capability 의 옷을 입은 버전 검사다.

이것이 중요한 이유: 스펙은 버전 축을 명시된 이유로 기각했고(「버전은 날짜 단위라 같은 날 세 번 바뀐 러너를 구분하지 못한다」) 지문 축을 다른 이유로 기각했는데(「러너 파일을 고치는 모든 배포가 전 사용자의 선택기를 지운다」), 선택된 축이 버전 축의 약점을 새 형태로 상속한다: monotone 이고 만료되지 않으므로, *다음* 신고 포맷 변경에는 다섯 번째 capability 이름이 필요하고, 2026-09-01 의 러너는 잘못 조립한 신고에 대해서도 여전히 「신뢰」된다. 재발 클래스는 닫힌 것이 아니라 한 iteration 미뤄졌다. 실제로 닫는 설계는 신고를 자기서술적으로 만든다 — 러너가 런타임별로 각 모델 목록을 *어떻게* 얻었는지(`probe` vs `http` vs `builtin`)를 말하고, 서버가 provenance 가 라이브 답이 아닌 항목을 버린다. 러너는 이미 정확히 그 값을 계산한다: `caps["source"]` 가 생성 지점에서 `"probe"` 또는 `"builtin"` 으로 설정되고 `detect_runtimes` 가 신고 전에 버린다. 그 필드를 전선으로 승격해 런타임별로 게이팅하면 전역 불리언보다 엄격히 강하고, 우아하게 열화하며(나쁜 런타임 하나만 숨고 나머지는 남는다), 다음번 계약이 움직일 때 새 capability 이름이 필요 없다.

둘째, 「유일한 관문」이라는 스펙 주장은 호출 그래프의 우연으로만 오늘 참이며 스위트의 무엇도 그것을 붙들지 않는다. `test_gate_lives_in_the_store_so_every_consumer_inherits_it` 은 docstring 에서 소비처 셋을 이름하지만 둘을 실행하고, `conversations._bridge_model_offered` 가 `account_runner_capabilities` 를 경유하는지 전혀 단정하지 않는다 — 직접 SQL 로 능력을 읽는 mutation 은 무관한 기존 테스트가 겨우 죽였다. 관문이 load-bearing 주장이라면(§16.7 G8-a 가 그것을 위해 세 번 인용된다) 구조적으로 강제하라: `oauth_store` 밖 어떤 모듈도 `RunnerCapabilities` 컬럼을 참조하지 않음을 AST 로 단정하라. 그것이 실제로 원하는 성질이고 검사도 싸다.
