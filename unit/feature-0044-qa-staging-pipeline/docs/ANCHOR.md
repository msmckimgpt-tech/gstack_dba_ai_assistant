# ANCHOR: feature-0044-qa-staging-pipeline QA 스테이징 파이프라인

## §1. 외부 관점 요약

"이미 무중단 배포 스크립트가 잘 돌고 있는데 왜 파이프라인을 새로 만드나?" 가 첫 의문일
것이다. 이유는 현행 스파인이 **배포 대상 호스트에서 소스를 체크아웃하고 직접 이미지를
빌드하는 전제**로 만들어졌기 때문이다. QA 머신은 인터넷이 차단된 격리망이라 그 전제가
성립하지 않고, 사내 미러를 붙여 빌드하더라도 개발 머신과 다른 시점의 의존성을 받아
"검증한 바이트"와 "배포한 바이트"가 달라진다.

두 번째 의문은 "레지스트리도 없는데 어떻게 이미지를 옮기나?" 이다. 사내에 컨테이너
레지스트리가 없으므로 `docker pull` 이라는 표준 경로가 없다. 그렇다고 각 머신이 각자
빌드하면 첫 문제로 되돌아간다 — **전달 수단이 없다는 것이 각자 빌드하라는 뜻은 아니다.**
`docker save` tar 에 sha256(전송 무결성)과 image_id(설치 등가성)를 붙이면 레지스트리의
신원 보증을 대신할 수 있다.

세 번째는 "QA 인데 왜 이렇게 보안을 무겁게 잡나?" 이다. QA 머신이 라이브 데이터 복제본을
**마스킹 없이** 담기로 결정됐기 때문이다. 반출 승인이 불요하다는 것은 옮겨도 된다는 뜻이지
아무렇게나 둬도 된다는 뜻이 아니다 — 이름은 QA 지만 자산 등급은 운영이다.

네 번째는 "배포 성공인데 왜 완료가 아니라고 하나?" 이다. 이 서비스의 사용 경로가 웹 화면이
아니라 **사용자 개인 머신의 MCP 연결**이라, 컨테이너가 전부 healthy 여도 VPN DNS·사내 CA·
OAuth discovery 중 하나만 어긋나면 사용자는 진입 자체를 못 한다.

## §2. 대안 분기

- **Alt-A: 각 머신에서 빌드.** 페르소나: 전달 인프라를 만들기 싫은 팀. 안 고른 이유: 폐쇄망
  에서 빌드 재현성이 성립하지 않는다. 의존성 lock 없이 사내 미러를 쓰면 시점에 따라 다른
  이미지가 나오고, 그 차이는 늦게·이상하게 드러난다. "검증한 것과 배포한 것이 같다" 는
  보장이 사라지면 QA 단계 자체의 의미가 없어진다.

- **Alt-B: 빌드 머신이 대상에 직접 push.** 페르소나: 파이프라인 도구 없이 스크립트로
  해결하려는 팀. 안 고른 이유: 배포 자격증명과 인바운드 경로가 빌드 머신에 상주하게 되어,
  빌드 머신 침해가 곧 운영 등급 데이터 접근이 된다. 사용자가 확정한 전달 경로(사내 산출물
  저장소 경유)와도 어긋난다.

- **Alt-C: 컨테이너 레지스트리를 먼저 구축.** 페르소나: 장기적 정석을 원하는 플랫폼 팀.
  안 고른 이유: 방향은 옳지만 QA 도입 일정 앞에 인프라 과제를 하나 더 얹는다. 대신
  매니페스트의 `transport` 필드로 획득 경로를 추상화해, 나중에 레지스트리가 생기면 배포
  러너 무변경으로 전환되게 했다 — 지금 안 하는 것이지 못 하게 만든 것이 아니다.

- **Alt-D: SVN 을 소스 미러로도 사용.** 페르소나: 사내 표준이 SVN 인 조직. 안 고른 이유:
  git↔svn 변환이 상시 필요하고 브랜치·머지 이력이 단순화되어 사실상 정본이 둘이 된다.
  사용자 결정(산출물 저장소만)과도 정합한다.

- **Alt-E: Kubernetes + ArgoCD 로 GitOps 전면 도입.** 페르소나: 다중 노드·다중 환경을
  운영하는 플랫폼 팀. 안 고른 이유: 단일 호스트 23서비스 규모에 오케스트레이터 전환은
  QA 도입과 독립된 큰 결정이고, 현행 compose 스파인의 무중단 롤링·soak·last-good 롤백은
  이미 라이브에서 실증됐다. 다만 **pull + 선언적 매니페스트**라는 GitOps 핵심 아이디어는
  채택한다.

- **Alt-F: 라이브는 현행 호스트에 두고 QA 만 분리.** 페르소나: 이전 비용을 아끼려는 팀.
  안 고른 이유(사용자 결정으로 기각): 라이브만 "개발 머신에서 로컬 빌드" 라는 예외 경로가
  영구히 남는다. 예외 경로는 검증되지 않은 채 남고, 개발 활동이 서빙 자원과 계속 경합한다.
  분리하면 QA·라이브가 같은 절차를 공유해 오히려 유지 비용이 낮아진다.

## §3. 가정된 사용 시나리오

사내 DBA 담당자가 자기 노트북에서 VPN 에 접속한 뒤, Claude Code 에 QA 서비스의 MCP
엔드포인트를 등록한다. 브라우저가 열리고 사내 계정으로 로그인·동의하면 연결이 맺어진다
(사내 CA 서명 인증서라 별도 신뢰 설정이 필요 없다). 담당자는 "이번 주 특정 게임 스키마의
재화 지급 추이를 보고 싶다"고 자기 AI 에게 말하고, AI 는 MCP 도구로 QA 서비스의 스키마·
메타지식을 조회해 답을 만든다. 추론은 담당자의 계정 LLM 이 하고 서비스는 데이터와 도구만
준다. 조회 이력과 최종 답변은 QA 서비스 쪽 대화 기록에 남아 나중에 운영자가 열람할 수 있다.

이 시나리오에서 담당자는 배포 파이프라인의 존재를 전혀 모른다. 체감하는 것은 "연결이
되는가 / 도구가 답을 주는가" 둘뿐이며, 그래서 배포 완료 판정도 그 두 가지를 실제로
확인하는 것이어야 한다.

한편 배포를 수행하는 담당자 관점에서는, 릴리즈 태그를 자르고 빌드 스크립트를 한 번
실행하면 나머지는 QA 머신이 알아서 당겨가 설치하고 스모크 결과를 남긴다. 그가 하는 판단은
"QA 에서 실제로 써 보고 승격할 것인가" 하나이며, 승격은 재빌드가 아니라 표식을 다는 일이다.
