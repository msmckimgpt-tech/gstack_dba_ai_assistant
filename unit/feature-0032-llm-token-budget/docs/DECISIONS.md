# Decisions (feature-local ADR)

## ADR-0032-01 — 종결된 판단을 전제 변화로 되살린다
- **결정:** `TODOS.md` P3 의 "일일 cap 가치 0" 종결을 철회하고 토큰 상한을 도입한다.
- **근거:** 그 종결의 근거는 *결론*이 아니라 *전제*였다 — "라이브 100% edge → 과금 없음".
  2026-07-30 재실측에서 과금 lane 99.7%로 반전됐다. 전제가 바뀌면 결론도 바뀐다.
- **기록 방식:** `TODOS.md` 의 옛 disposition 을 지우지 않고 **반전 사실을 위에 덧붙였다**.
  왜 한때 그렇게 판단했는지가 남아야 다음 사람이 같은 재조사를 반복하지 않는다.

## ADR-0032-02 — rolling 24시간, 자정 리셋 아님
- **결정:** 창을 rolling 24h 로 둔다.
- **근거:** 자정 리셋은 (a) 타임존을 정해야 하고(서버 TZ vs 사용자 TZ), (b) 자정 직후 폭주가
  그대로 재개된다. rolling 은 둘 다 없다. knob 이름도 `..._CAP_24H` 로 정직하게 붙였다.

## ADR-0032-03 — 사용자 요청 경로는 세지도 막지도 않는다
- **결정:** `agent`·`redteam`·`topic`·`classify`·`prompt_gen` 을 집계와 게이트에서 제외한다.
- **근거:** 예산으로 사용자를 막으면 그건 비용 통제가 아니라 서비스 장애다. 비용 사고를 막으려다
  더 큰 사고를 만드는 교환이다.
- **강제:** 제외 목록이 실제 집계 SQL 에 반영되는지 테스트가 파라미터를 직접 검사한다 —
  상수 선언만 확인하면 쿼리가 바뀌었을 때 조용히 어긋난다.

## ADR-0032-04 — 블랙리스트(사용자 경로 열거), 화이트리스트 아님
- **결정:** 백그라운드 task 를 열거하지 않고, 사용자 경로만 열거한 뒤 나머지 전부를 백그라운드로 센다.
- **근거:** 화이트리스트면 새 백그라운드 작업이 예산 밖으로 조용히 샌다. 블랙리스트면 새 작업이
  자동으로 예산 안에 들어온다 — **보수적인 방향으로 틀린다**. 예산은 틀릴 때 조이는 쪽이 안전하다.

## ADR-0032-05 — 게이트는 진입점에, 커버리지는 정직하게
- **결정:** 백그라운드 진입점 3곳에만 게이트를 걸고, 나머지 경로는 계량만 한다. 그 사실을 코드
  주석·문서·콘솔 설명에 명시한다.
- **대안 기각:** LLM 호출 단일 choke-point 는 존재하지 않는다(`chat.completions.create` 15곳).
  전부에 게이트를 걸면 사용자 경로까지 침습하고 회귀 표면이 커진다.
- **원칙:** 커버리지가 96%면 "96%"라고 쓴다. 100%인 척하면 나중에 "상한이 있는데 왜 넘었나"라는
  더 나쁜 혼란이 생긴다.

## ADR-0032-06 — circuit-breaker 를 새로 만들지 않는다
- **결정:** 429/401 대응은 기존 `llm_provider_health` 에 맡기고, 없는 것(누적 소비 상한)만 만든다.
- **근거:** 같은 축의 두 번째 구현은 서로의 상태를 모르는 두 개의 진실을 만든다.

## ADR-0032-07 — fail-open 3중
- **결정:** 상한 0 · 조회 실패 · 모듈 부재 — 세 경우 모두 허용한다.
- **근거:** 상한은 안전망이지 필수 경로가 아니다. 계량이 고장 났을 때 백그라운드가 멈추면
  관측 장애가 기능 장애로 승격된다. 다만 콘솔은 "조회 불가"를 "상한 없음"과 **다른 문구**로
  표시해, fail-open 이 조용히 상한을 무력화한 상태를 숨기지 않는다.
