# Report

## 진행 요약 (2026-07-31)

ITEM-10(검증층) 구현 완료. codex 적대 리뷰 P1 4건·P2 1건 반영, 출하 중.

## 무엇을 만들었나

노드 분석문을 L0 통계 증거와 대조해 `supported`/`contradicted`/`unverifiable` 로 판정하고
근거 한 문장과 함께 저장한다. **AI 의 말을 AI 가 평가하는 게 아니라 AI 의 말을 실제 측정값과
대조**한다 — "이 컬럼이 레코드를 고유 식별한다"는 서술 옆에 `distinct_est=12, sampled_rows=100`
이 있으면 그 서술은 틀렸다.

## 이 기능의 전부는 정직성이다

```
판정 실패는 "검증됨"이 아니다.
```

LLM 오류·계약 위반 응답·근거 없는 응답·증거 부재·저장 실패·예산 소진 — 전부 **행을 만들지
않는다(미검증)**. 확인 도장이 잘못 찍히면 그 도장을 근거로 위층(요약·답변)이 더 확신하게 되고,
그러면 이 층은 없느니만 못하다. 그래서 fail-soft 가 "통과"가 아니라 "침묵"이다.

예외는 하나다: **예산 모듈을 못 읽으면 중단**한다. 계량 장애로 기능이 멈추는 것보다 상한을
모른 채 자동 지출을 계속하는 쪽이 위험하다.

## 리뷰에서 드러난 것

codex 가 P1 4건을 잡았고, 그중 하나가 특히 아팠다:

- **`c` 미정의 — 배선이 통째로 죽어 있었다.** 테스트 38건이 모듈 내부를 촘촘히 덮었지만
  `insight.py` 의 호출 한 줄이 정의되지 않은 변수를 쓴다는 사실은 잡지 못했다.
  **모듈 테스트가 배선을 보증하지 않는다.**
- **재판정이 안 됐다.** 저장 키에는 `analysis_hash` 가 있는데 대상 조회는 그것을 비교하지 않아,
  분석이 갱신돼도 옛 판정이 남았다 — 내가 문서에 적은 계약과 정반대로 동작했다.
- **근거 없이 `supported` 를 저장**할 수 있었다. 프롬프트는 reason 을 필수로 요구했지만 코드가
  강제하지 않았다. 재확인할 수 없는 확인 도장이 이 층의 최악의 실패인데 그 문이 열려 있었다.
- 실패한 증거로 판정할 수 있는 race.

그리고 `cursor()` 를 try 밖에 두는 실수를 **네 번째** 반복했다. 이제는 패턴이다 —
**자원 획득은 언제나 try 안**.

## 지금의 한계

판정 대상이 **7건** 수준이다. 분석문과 증거가 둘 다 있어야 대조가 되는데 증거 커버리지가
아직 낮다. 플래너(feature-0035)가 커버리지를 채운 뒤에야 이 층이 실질 값을 한다 — 인프라를
먼저 놓는 판단이었고, 그 사실을 숨기지 않는다.

## 남은 것

- 배포 후 판정 실측(TEST.md §4) — 특히 `contradicted` 의 `reason` 이 구체적 숫자를 지목하는지.
- ITEM-08(L3 lazy 도메인 합성) — 로드맵 마지막 항목.
- 후속: 판정 결과의 콘솔 표시·grounding 반영.

## Cycle 2 — 판정이 무한 순환하고 있었다 (2026-08-05)

사용자가 운영 현황 화면을 보고 물었다: "분석문 사실성 검증이 대부분의 분석 작업을 차지하는데,
이게 실제로 무슨 일을 하고 효용이 있느냐."

실측이 답을 대신했다. 7일간 이 task 가 **7,896콜** — 배경 LLM 호출의 62.8%, 토큰의 38.3%.
그런데 판정 대상은 **91개 노드**뿐이었고 판정 행 수는 91개로 **고정**돼 있었다. 노드당 평균
87회를 다시 판정하면서 정보는 한 건도 늘리지 않았다.

### 왜 그랬나

이 기능의 두 정책이 서로 다른 단위를 보고 있었다:

- **저장**(ADR-0036-04): 노드당 1행. 다른 해시 행은 지운다 — 무한 증식 차단.
- **대상 선정**: `node_analysis_jobs` 를 **행 단위**로. 같은 노드에 여러 분석 run 의 done 행이
  쌓인다(라이브 done 2,682행 / 노드 2,052 — 다세대 노드 489개 전부 run_id 상이).

A세대를 저장하면 B세대가 미판정으로 남고, B세대를 저장하면 A행이 지워져 다시 미판정이 된다.
각 정책을 따로 읽으면 둘 다 옳다 — 결함은 **정책 사이**에 있었다. 초기 cycle 의 codex 적대
리뷰도 이 축은 잡지 못했다(해시 비교 누락은 잡았지만, 그 비교가 어떤 행 집합 위에서 도는지는
묻지 않았다).

대조군이 원인을 확정했다: 호출 상위 8개 대상은 **전부 done 행이 2개 이상**이었고(합계 69%),
done 행이 1개인 노드는 1회 판정 후 조용했다. `tf_log_01_contents` 는 done 행 6개 → 단독 1,914콜.

LLM 응답 자체는 정상이었다 — 수동 1콜 재현에서 근거 문장까지 규격대로 나왔다. **대상 선정을
의심하기 전에 응답 품질을 의심했다면 한참 헤맸을 것이다.**

### 고친 것

- `pending_targets` → `DISTINCT ON (scope_key, node_key)` 로 **노드당 최신 분석문 1건**.
  저장 단위와 같아져 순환이 닫힌다 (ADR-0036-08). 라이브 쿼리 실측: 100행(중복 포함) → **92행
  (= distinct 노드 수)**.
- 바깥 정렬 첫 키를 "한 번도 판정된 적 없는 노드 우선"으로. 고정 정렬만 두면 이미 판정된 노드가
  완충 구간(limit×5)을 채워 미판정 노드가 영영 밀린다 — 증거 커버리지가 늘수록 심해진다.
- telemetry `rejudged` 분리 + 로그 노출. **"많이 도는 것"과 "같은 걸 또 도는 것"이 계기판에서
  구별되지 않았던 것**이 이번 결함이 오래 숨은 이유다.

### 남은 것 (이번 범위 아님)

- **판정 결과를 아무도 읽지 않는다.** `node_analysis_verdicts` 를 조회하는 코드가 생성 모듈·
  테스트·마이그레이션 밖에 0곳이다. ANCHOR §3 이 그리는 장면(분석문 옆에 `contradicted` 와 근거
  한 줄)이 아직 없다. 순환을 고쳐도 이 층은 여전히 "쓰이지 않는 판정"이다.
- **검증 범위가 4.5%.** 증거(`metadata_table_stats`)가 95개 테이블에만 있어 분석문 2,052 노드 중
  92개만 판정 가능하다. feature-0035 플래너가 커버리지를 올려야 이 층이 실질 값을 한다.
