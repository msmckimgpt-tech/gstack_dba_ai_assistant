# ANCHOR: feature-0045-zd-bridge-continuity 브리지 배포 연속성

## §1. 외부 관점 요약

"무중단 배포는 feature-0014 에서 이미 만들었잖아. Caddy 뒤 2-replica 롤링에 pre-drain
게이트까지 있는데 왜 또 손대지?"

→ 그 스파인이 보는 신호가 **바뀐 세계를 따라오지 못했다.** feature-0043 전환으로 추론 주체가
서버에서 개인 머신 AI 로 넘어가면서, 사용자 작업은 `ask_jobs`(서버 워커 큐)도 `active_streams`
(SSE/CSV 스트림)도 아닌 **`WebAiTasks` + 브리지 왕복** 위에서 일어나게 됐다. 게이트는 그 둘만
보므로, 개인 AI 가 붙어 대기하고 질문을 조사하는 그 순간에도 **0 을 읽고 "조용하다" 고 판정**한다.

무중단이 깨진 게 아니라, **무중단이라고 믿게 만드는 계기판**이 남은 것이다. 그쪽이 더 나쁘다.

여기에 더해 개인 AI 가 실제로 붙는 문(`/api/ai/mcp` → `ext-tool-mcp`)은 단일 컨테이너였고
워커 일괄 recreate 대상이라, 배포할 때마다 그 연결이 통째로 끊겼다.

## §2. 대안 분기

- **Alt-A: 대기(long-poll)도 in-flight 로 세고 끝날 때까지 기다린다.** 페르소나: "진행 중인
  것은 모두 기다린다" 는 단순 규칙을 선호하는 운영자. 안 고른 이유: 연결된 AI 는 **항상**
  대기 중이다. 그것을 기다리면 배포는 매번 최대 55초(연결 수만큼 겹치면 그 이상) 늦어지고,
  결국 상한을 넘겨 강행하게 된다 — 게이트를 붙이고도 매번 강행하는 결과. 대기는 끊겨도
  잃을 것이 없으므로 **기다릴 대상이 아니라 비울 대상**이다.

- **Alt-B: 배포 전에 브리지를 잠시 정지(admission fence)한다.** 페르소나: 확실한 정지 창을
  원하는 팀. 안 고른 이유: 전역 정지는 배포와 무관한 사용자의 새 질문까지 막는다. 게다가
  "언제 다시 여는가" 가 배포 성공에 결속되어, 배포가 중단되면 서비스가 잠긴 채 남는다.
  드레인은 **replica 단위**라 다른 replica 가 계속 받는다.

- **Alt-C: MCP 표면을 surge 교대(ask-worker 방식)로 교체한다.** 페르소나: 상시 자원 증가를
  피하려는 운영자. 안 고른 이유: surge 는 큐 소비자에게 성립하는 패턴이다("받는 쪽을 먼저
  세운다"). MCP 는 **HTTP 수신자**라 엣지 upstream 목록을 배포 중 동적으로 바꿔야 하고, 그
  reload 경계가 2-replica 상시보다 얇다. 사용자 결정(2026-08-27)으로 2-replica 채택.

- **Alt-D: 점유(claim)를 배포 시 전부 반납한다.** 페르소나: 배포를 지연 없이 끝내려는 팀.
  안 고른 이유: 살아남은 러너의 조사까지 버려져 사용자가 답을 다시 기다린다. `ClaimedBy` 를
  보존하고 lease 만 만료시키면 **먼저 끝내는 쪽이 이기므로** 어느 경우에도 손실이 없다.

## §3. 가정된 사용 시나리오

사내 직원이 `https://mysql-ai.company.local` 대화창에 질문을 보낸다. 그 사람의 개인 머신에서
Claude Code 가 MCP 로 붙어 있어 질문을 즉시 가져가고, 스키마를 훑고 `execute_sql` 을 몇 번
돌리는 중이다. 같은 시각 다른 개발자의 PR 이 머지되어 자동 배포가 시작된다.

배포는 `web-a` 에 문을 닫고, 그 사람의 대기 연결은 소리 없이 `web-b` 로 옮겨간다. 조사 중이던
`execute_sql` 왕복은 그대로 끝나고, 그 뒤에야 `web-a` 가 교체된다. MCP 표면도 하나씩 바뀐다.
개인 AI 는 답을 제출하고, 사용자는 배포가 있었다는 사실 자체를 알지 못한다.

(부득이 상한을 넘겨 강행한 배포라면, 끊긴 질문은 대기열로 되돌아가 곧 다시 처리된다. 사용자
화면에는 "가져갔습니다" 가 "기다리는 중" 으로 돌아갔다가 답변이 온다 — 늦어질 뿐 잃지 않는다.)
