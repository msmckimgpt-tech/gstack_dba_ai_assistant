### 1. Blocking issues

**B1 (critical) — "지문 미저장 = 신규 테이블" 오분류로, 자격 있는 스키마의 *전체 테이블*이 자동 시드된다**
- **Evidence**: `_auto_table_candidates` (`insight.py:341-366`) 의 baseline 가드는 `known = [t ... if stored.get(fp_key_of(t))]` 가 **1건이라도 있으면** 통과하고(`:353-355`), 이후 루프는 `prev_fp` 가 공란인 테이블을 전부 후보로 담는다(`:360-363`, `if prev_fp and prev_fp == cur_fp: continue`). 그런데 `table_fp` 는 `_publish_table_insight` 가 **artifact 발행 완료(`table_complete`)일 때만** 저장하고(`insight.py:291-297`), 발행 대상은 스캔당 `AGENT_SCHEMA_INSTANCE_SCAN_TABLE_LIMIT=12`(`config.py:1103`) 개뿐이며 스캔 자체는 기본 6h(`AGENT_SCHEMA_INSTANCE_SCAN_EVERY_SEC=21600`, `config.py:1101`)다. 반면 `current_table_fps` 는 `_compute_table_fingerprints_batch`(`insight.py:76-104`)가 **전 테이블**에 대해 산출한다. 신규 테스트 `test_table_candidates_detects_new_and_changed`(`tests/test_node_analysis_change_reanalysis.py:237-244`)가 `item_log`(stored fp 없음)를 후보로 **의도적으로 단언**하고 있어, 이는 버그가 아니라 설계 전제다.
- **Location**: `unit/feature-0002-agent-core/src/modules/insight.py:341-366` (+ 호출부 `:1784-1791`)
- **Reason**: 라이브 정상 상태는 "스키마의 극히 일부만 table_fp 보유"다(12 테이블/스캔/스키마로 채워지므로 500 테이블 스키마는 완충까지 수백 시간). 따라서 이 기능이 배포되는 순간, **사용자가 이미 수동 전체 분석을 마친 바로 그 스키마**에서 구조가 전혀 변하지 않은 수백 개 테이블이 "신규"로 판정돼 자동 LLM 재분석 시드가 된다. 수동 경로에는 있는 `only_missing`(이미 분석된 노드 제외)·`SCHEMA_CAP`(1000) 총량 캡이 자동 경로에는 없어, 사람이 한 번 승인한 비용을 **승인 없이 통째로 재지출**한다. 문서(FUNCTION.md §18 "baseline 가드")와 TASK.md TCR.4 는 이 가드가 전량 오탐을 막는다고 주장하지만, 실제로는 "완전 최초 스캔"만 막는다.
- **Action**: 후보 판정을 `prev_fp` 존재를 **필수 조건**으로 바꾼다 — `if not prev_fp or prev_fp == cur_fp: continue` (즉 "이전 지문이 있고 그것과 다를 때만 변경"). 진짜 신규 테이블은 `stored_table_fps` 대신 **직전 스캔의 `all_table_names` 스냅샷**(스키마 단위 KV 1건)과 대조해 검출하거나, 그래프 Table 노드 부재 + `get_scope_analysis_status().done_keys` 미포함을 조건으로 삼아야 한다. 아울러 스키마당 자동 시드 **누적 총량 캡**(예: 수동 `SCHEMA_CAP` 과 동일 예산)을 별도로 둔다.

**B2 (critical) — 진행 중 run 에 append 하는 경로가 쿨다운·시드 cap·node_budget 전부를 우회해 시드가 무한 증식한다**
- **Evidence**: `enqueue_change_analysis` 의 판정 순서에서 쿨다운은 `if active_run is None and cooldown:` 로 **신규 run 경로에만** 적용된다(`node_analysis.py:1048`). `active_run` 이 있으면 매 호출마다 `targets = present[:cap_v]`(cap=50) 을 **추가로** append 하고(`:1074-1090`), `_insert_seed_jobs`(`:1136-1165`)는 `node_budget` 을 전혀 검사하지 않고 무조건 INSERT 한다(예산 검사는 이웃 확장 `_enqueue_neighbors` 에만 존재). append 마다 `node_budget = LEAST(4000, GREATEST(nb+added, nb+added*4))` 로 예산까지 ratchet 된다(`:1082-1088`). 한편 `_scan_instance_schema_insights` 의 6h interval 게이트는 `force_scan`(= `missing` 스키마 존재 또는 pending repair) 이면 **완전히 건너뛰어진다**(`insight.py:1338-1356`), 그리고 insight-worker tick 은 기본 8초다(`config.py:1505`, `insight.py:3371`). `made_progress or missing` 이면 repair backoff 도 해제된다(`insight.py:2086-2089`).
- **Location**: `unit/feature-0002-agent-core/src/modules/node_analysis.py:1040-1095`, `:1136-1165`
- **Reason**: `missing` 스키마가 하나라도 있는 흔한 상태(신규 datasource, LLM 실패로 artifact 미완성, `MAX_SCHEMAS=20` 로테이션 밖 스키마)에서는 스캔이 **8초마다** 돌고, 자동 run 은 한 번 생성되면 소비 속도(`BATCH_PER_TICK` 기본 10)보다 시드 유입(50/tick)이 훨씬 빨라 **영원히 `running` 상태를 유지**한다. 그 결과 쿨다운 1800s 는 한 번도 발동하지 못하고 50 시드/8초 = 375 시드/분이 무기한 적재된다. 시드 자체는 node_budget 밖이므로 "예산 캡" 이라는 4중 가드의 마지막 방어선도 없다. 이것이 B1 과 결합하면 스키마당 전 테이블 + 이웃 4000 노드까지 수 분 내에 큐잉된다. 테스트 `test_append_to_running_auto_run` 은 이 경로를 "쿨다운 쿼리 미실행"으로 **정상 동작으로 단언**하고 있어(`tests/...:210-211`) 회귀 검출이 불가능하다.
- **Action**: (a) 쿨다운을 append 경로에도 적용하거나, 최소한 `(scope, root_key)` 단위 **시간창 시드 예산**(예: 쿨다운 창당 cap 1회분)을 도입. (b) `_insert_seed_jobs` 진입 전에 `SELECT enqueued, node_budget FROM node_analysis_runs FOR UPDATE` 로 잔여 예산을 확인하고 `min(cap, node_budget - enqueued)` 만 시드. (c) append 시 `node_budget` ratchet 을 제거하거나 run 생성 시점 예산으로 고정.

**B3 (high) — 자격 게이트가 "1개 노드만 성공한 run" 도 '전체 분석 완료'로 인정한다**
- **Evidence**: `schema_analysis_completed` 는 `root_label='Schema' AND status='done'` 1행만 확인한다(`node_analysis.py:966-969`). 그런데 `process_pending` 의 run 마감은 `final = "done" if int(r[0]) > 0 else "failed"` — 즉 **done 카운터가 1 이상이면 done**이다(`node_analysis.py:1408-1412`). 또 수동 run 은 `only_missing`/`SCHEMA_CAP`(1000)/`table_cap` 으로 일부만 분석했을 수도 있다.
- **Location**: `unit/feature-0002-agent-core/src/modules/node_analysis.py:949-981`
- **Reason**: 사용자가 500 테이블 DB 에 전체 분석을 걸었다가 LLM 장애로 499 실패·1 성공한 run 도 `status='done'` 이 되어, 그 스키마는 **영구히** 무인 자동 LLM 지출 대상이 된다. 게다가 `node_analysis_runs` 에는 보존/정리 경로가 없어(전 코드베이스에 retention DELETE 없음) 자격은 한 번 생기면 취소 불가다 — 사용자가 "이 DB 자동 분석 끄기"를 할 수단이 없다. 사용자 요청의 전제("'DB 전체 AI 능동 분석'이 이루어진 DB")를 SQL 이 충실히 구현하지 못한다.
- **Action**: 자격 판정을 done 카운터 유의미성 기준으로 강화한다 — 예: `SELECT 1 FROM node_analysis_runs WHERE ... AND status='done' AND done >= GREATEST(1, enqueued/2)`, 또는 `get_scope_analysis_status(scope).done_keys` 가 그 스키마 Table 노드의 일정 비율 이상을 덮을 때만 자격 인정. 스키마별 자동분석 opt-out 플래그(관리 콘솔)도 함께 제공.

**B4 (high) — 루틴 후보에는 baseline 가드가 없고, MSSQL 라벨 충돌로 `definition_hash` 가 매 사이클 진동해 영구 재트리거된다**
- **Evidence**: `_auto_routine_candidates`(`insight.py:325-339`)는 `_rt_changed` 를 그대로 후보화하며 "이전 지문 존재" 조건이 없다. `_rt_changed` 는 `routines.introspect_and_store` 가 `rc is None or rc != 0` 인 모든 upsert 를 담는다(`routines.py:328-334`) — 즉 **최초 INSERT 전량**이 "변경"이다. 더 심각한 것은 MSSQL: `_rel_store_schema = get_active_database()` 라 한 DB 의 **모든 실 스키마(dbo, sales …)가 같은 `schema_name` 라벨로 저장**되고(`insight.py:1462-1474`), `routine_objects` 의 유니크 키는 `(scope_key, schema_name, routine_name, routine_type)` 이다(`routines.py:311-320`). 코드 자신이 이 충돌을 인지하고 있다(`insight.py:1563-1566`, `_rt_prune_ok=False`).
- **Location**: `unit/feature-0002-agent-core/src/modules/insight.py:325-339`, `unit/feature-0002-agent-core/src/modules/routines.py:328-334`
- **Reason**: 동명 프로시저가 두 스키마에 있으면 스키마 순회마다 서로의 행을 덮어써 `definition_hash` 가 A→B→A 로 진동한다. 마커는 지문 대조 방식이므로 **매 사이클 마커 불일치 → 매 사이클 자동 재분석 트리거**가 영구히 반복된다(무한 재시도 루프 — 리뷰 축 1 이 지목한 바로 그 클래스). 또 루틴 introspect 가 새로 활성화되거나 `prune` 이 한 번 대량 삭제하면 다음 사이클에 전 루틴이 "신규"로 시드된다.
- **Action**: (a) `_auto_routine_candidates` 에도 테이블과 동형의 baseline 가드를 넣되, B1 의 수정 원칙(이전 지문이 있고 다를 때만)을 적용한다 — `routines.introspect_and_store` 가 `changed_sink` 에 `prev_definition_hash` 도 함께 실어 보내고(UPSERT 시 `RETURNING` 또는 사전 SELECT), 신규 INSERT 와 정의 변경을 구분한다. (b) MSSQL 라벨 충돌 구간에서는 자동 재분석을 억제하거나(`_rt_prune_ok is False` 를 신호로 사용) 후보 key 를 실 스키마 기준으로 분리한다.

**B5 (medium) — 마커 KV key 가 `agent_runtime.kv.key varchar(128)` 를 넘으면 저장이 조용히 실패해 영구 재트리거 루프가 된다**
- **Evidence**: 마커 key = `"na_auto_fp:" + node_key`(`insight.py:319-323`, prefix 11자), node_key = `<datasource>:<schema>.<table>`. KV 테이블은 `key character varying(128) NOT NULL`(`alembic/versions/20260602_0001_baseline_agent_kb_schema.py:98-104`)이고, `_save_fingerprint` → `save_memory_kv` 는 PG 쓰기 실패를 **warning 1줄로 삼킨다**(`insight.py:305-310`, `memory.py:229-239`). scope_key 는 96자까지, MySQL 스키마·테이블명은 각 64자까지 허용되므로 상한은 128 을 크게 초과한다.
- **Location**: `unit/feature-0002-agent-core/src/modules/insight.py:305-323`, `:378-397`
- **Reason**: node_key 가 117자를 넘는 노드는 마커가 **절대 저장되지 않는다**. 그 노드는 매 스캔마다 후보 → 시드 → 마커 저장 실패 → 다시 후보로 도는 무한 LLM 재분석 루프에 갇힌다. 기존 `table_fp:` 키도 같은 상한을 공유하지만 그쪽 실패의 대가는 insight 재발행이고, 이쪽은 사람 승인 없는 재귀 LLM run 이라 위험도가 다르다.
- **Action**: 마커 key 를 길이 안전하게 만든다 — `f"na_auto_fp:{hashlib.sha1(node_key.encode()).hexdigest()}"` (혹은 prefix + 앞 40자 + 해시 접미). 저장 직후 `stored_auto_fps` 반영 전에 read-back 또는 길이 사전 검사로 실패를 가시화한다.

**B6 (medium) — 기본 datasource 에서는 기능이 조용히 죽는다(그래프 key 는 `common:` 로 실재하는데도)**
- **Evidence**: `_auto_scope = get_active_datasource()`(`insight.py:1477`)가 None 이면 `_auto_reanalyze_changed_nodes`/`_auto_table_candidates` 가 즉시 return 한다(`insight.py:352`, `:384-386`). 그러나 그래프 정점 key 는 `_vkey(scope, fqn) = f"{scope or 'common'}:{fqn}"`(`metadata_graph.py:215-216`)이고, SSOT 인 `column_descriptions.scope_key` 의 DEFAULT 는 `'common'` 이다(`alembic/versions/20260624_0017_table_column_descriptions.py:48`). 즉 기본 DB 의 노드는 `common:<schema>.<table>` 로 **정상 존재**한다.
- **Location**: `unit/feature-0002-agent-core/src/modules/insight.py:1475-1477`, `:341-352`
- **Reason**: 코드 주석은 "None(기본 DS 미지정)이면 그래프 키를 확정할 수 없어"라고 하지만 키는 확정 가능하다(`common`). 등록 datasource 를 쓰지 않는 배포/기본 DB 에서는 사용자가 수동 전체 분석을 마쳐도 자동 재분석이 **한 번도 발동하지 않으며, 로그도 telemetry 도 남지 않는다**(후보 산출 이전에 return). 사용자 요청이 부분적으로 미구현이고 그 사실이 관측 불가하다.
- **Action**: `_auto_scope = get_active_datasource() or "common"` 으로 `_vkey` 폴백과 정합시키거나, 정말 skip 이 맞다면 `report["auto_reanalysis_skipped_no_scope"]` 계측을 남겨 침묵 저하를 가시화한다.

**B7 (medium) — `_insert_seed_jobs` 무-가드 + `enqueued` 사후 patch 로 고아 `running` run 과 예산 회계 구멍이 생긴다**
- **Evidence**: `_insert_seed_jobs`(`node_analysis.py:1136-1165`)에는 per-row try/except 가 없어 한 행의 INSERT 예외가 배치 전체를 중단시키고 바깥 `except` 로 빠진다(`:1122-1124`). 신규 run 경로는 `INSERT ... 'running',0,0,0` 로 **enqueued=0 으로 먼저 커밋**한 뒤(autocommit — `_rw_conn` 은 `_pg_connect(autocommit=True)`, `:339-345`) 시드를 넣고 마지막에 `UPDATE ... SET enqueued=%s` 로 덮어쓴다(`:1104-1117`). 비교 대상인 `enqueue_schema_analysis` 는 run INSERT 문 안에서 `enqueued=len(targets)` 를 원자적으로 세팅한다(`:881-894`).
- **Location**: `unit/feature-0002-agent-core/src/modules/node_analysis.py:1096-1124`, `:1136-1165`
- **Reason**: (a) 첫 INSERT 에서 예외가 나면 시드 0 인 run 행이 `running` 으로 **영구 잔존**한다 — `process_pending` 의 마감 판정은 `touched_runs`(잡이 있는 run)만 훑으므로 절대 finalize 되지 않고, 900s 동안 append 대상이 되고 1800s 동안 쿨다운을 점유한다. (b) `enqueued=0` 커밋과 `SET enqueued=added` 사이에 다른 워커 replica(롤링 배포 중 순간적으로 2개)가 시드를 claim 해 `_enqueue_neighbors` 의 `enqueued = enqueued + inserted` 를 수행하면 그 증분이 **덮어써져 소실**되고, `remaining = node_budget - enqueued` 가 과대평가돼 예산 초과 LLM 호출이 난다. `_enqueue_neighbors` 가 `FOR UPDATE` 로 지키려던 바로 그 불변식이다.
- **Action**: 시드 삽입을 행 단위 try/except 로 감싸고(실패는 debug 로그 후 continue), run INSERT 시점에 `enqueued` 를 확정값으로 넣도록 순서를 바꾼다(시드 목록 확정 → run INSERT with enqueued=len(targets) → 시드 INSERT → 실패분만 보정 UPDATE). 예외 경로에서도 `DELETE FROM node_analysis_runs WHERE run_id=%s` 로 정리한다(FK ON DELETE CASCADE 확인됨 — `alembic .../0028_node_analysis.py`).

### 3. Challenge to current spec

이 설계의 근본 문제는 **"insight 지문의 부재"를 "구조 변동"의 증거로 재사용한 것**이다. `table_fp`/`definition_hash` 는 원래 "이 객체의 insight 요약을 다시 만들어야 하나"를 판정하는 신호이고, 그 저장 시점은 LLM 발행 성공에 종속돼 있어 **커버리지가 태생적으로 희소하다**(12/스캔/스키마). 그 신호를 그대로 "AI 재귀 분석 시드" 로 승격하면, 신호의 희소성이 곧 비용으로 번역된다(B1). 사용자 요구는 "변경된 노드"였지 "아직 요약이 발행되지 않은 노드"가 아니다.

대안으로, 자동 재분석은 **자체 전용 스냅샷**을 갖는 게 맞다: 스키마당 KV 1건에 `{table: fp}` 전체 맵(또는 그 맵의 해시 + 테이블 목록)을 저장하고, 다음 스캔에서 그 스냅샷과 **전량 대조**해 신규/변경/삭제를 판정한다. 이러면 (a) 최초 저장이 곧 완전한 baseline 이라 "부분 커버리지" 오탐이 원천 제거되고, (b) 노드당 마커 수천 건(B5 의 128자 문제·C4 의 KV 팽창)이 스키마당 1건으로 줄며, (c) 삭제 감지까지 자연히 얻는다. 마커의 "시드된 것만 저장" 세밀함은 잃지만, 그건 스냅샷 갱신을 "이번에 시드 성공한 항목만 반영"하는 부분 갱신으로 보존할 수 있다.

두 번째 도전: **"진행 중 run 에 append" 는 비용 모델상 잘못된 기본값**이다. 코드 주석은 "이미 승인된 예산 안"이라고 정당화하지만, 자동 run 에는 애초에 승인이 없고 append 는 그 예산 자체를 곱해 늘린다(B2). 변경 누락이 걱정이라면 append 가 아니라 **마커를 남기지 않고 다음 쿨다운 창에서 처리**하는 편이 훨씬 안전하다 — 이미 "마커 미저장 = 자연 재시도" 메커니즘이 있으므로 append 없이도 누락은 0이다. 즉 append 경로는 순이익 없이 유일한 무제한 증식 통로만 열어 준 셈이다.

세 번째: 기본값 ON 은 사용자 결정이지만, **첫 배포 사이클만이라도 shadow 모드**(후보 산출·telemetry 만 기록하고 enqueue 하지 않음)를 거치는 것이 이 규모의 자동 지출에 맞다. `report["auto_reanalysis_candidates"]` 는 이미 계측되고 있으므로, `AGENT_NODE_ANALYSIS_AUTO_ON_CHANGE=shadow` 한 값만 추가하면 라이브 후보 규모(B1 의 실제 크기)를 비용 없이 측정할 수 있다. TCR.10 의 POST-DEPLOY 계획은 "변경을 가하면 run 이 생기는가"만 확인할 뿐, **변경을 가하지 않았을 때 run 이 생기지 않는가**(오탐 규모)를 검증하지 않는다 — 이 축의 검증이 계획에 반드시 추가되어야 한다.
