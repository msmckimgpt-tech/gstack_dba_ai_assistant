# Decisions (feature-local ADR)

## ADR-0035-01 — 플래너는 결정적이다 (LLM 아님)
- **결정:** 우선순위를 관계 차수 + 대화 조인 이력의 가중합으로 계산한다.
- **근거:** 신호가 이미 구조적 데이터로 있다. 결정적 규칙은 재현 가능하고 비용이 0이며 설명
  가능하다. ADR-0031-02(LLM 오케스트레이터 기각)와 같은 판단 — LLM 은 계획이 아니라 분석·합성에서
  값어치를 낸다.

## ADR-0035-02 — 대화 이력에 압도적 가중치(50 : 1)
- **결정:** 대화에서 조인된 이력 1건이 관계 차수 50건과 맞먹는다.
- **근거:** 차수는 "구조상 얽혀 있다"이고 대화 이력은 "사람이 실제로 이걸 물었다"이다. 후자가
  분석의 즉시 효용을 훨씬 잘 예측한다. 단순 허브(코드 테이블 등)가 실사용 테이블을 밀어내면
  커버리지 숫자만 오르고 답변 품질은 그대로다.

## ADR-0035-03 — 시드 큐잉을 재구현하지 않는다
- **결정:** `enqueue_change_analysis` 를 `reason` 만 바꿔 재사용한다.
- **근거:** 자격·그래프 실재·cap·쿨다운·busy 가드가 이미 거기 있다. 자동 LLM 지출의 안전장치를
  두 벌 만들면 서로를 모르고, 한쪽만 조여도 다른 쪽으로 샌다.

## ADR-0035-04 — 사이클 전역 상한을 별도로 둔다
- **결정:** 스키마당 상한(3) 위에 사이클 전체 상한(9)을 추가한다.
- **근거:** 시드는 effective-schema 루프 안에서 일어나고 재사용하는 큐잉 경로의 cap·쿨다운은
  **스키마 단위**다. 사이클 상한이 없으면 총량이 스키마 수만큼 곱해진다.
- **자기 지적:** feature-0033 에서 **정확히 같은 계열의 결함**(상한이 스키마 루프마다 적용)을
  지적받았다. 이번에는 "검증된 경로를 재사용하니 괜찮다"고 판단했는데, 그 경로의 가드가 어느
  단위인지 확인하지 않은 것이 실수였다. 재사용은 가드의 **범위**까지 확인해야 성립한다.

## ADR-0035-05 — 스키마 축은 object_key prefix 로 맞춘다
- **결정:** 후보 조회에서 `rag_objects.schema_name` 을 쓰지 않고 `object_key` prefix 를
  `strpos(…) = 1` 로 검사한다.
- **근거:** MSSQL 은 `schema_name` 이 리터럴 `dbo` 라 DB 차원이 소실돼 노드 키와 안 맞는다.
  `LIKE` 는 식별자의 `_` 를 와일드카드로 해석해 다른 스키마가 섞인다(feature-0034 와 같은 함정).

## ADR-0035-06 — 관계 점수는 datasource 단위 근사를 허용한다
- **결정:** 관계 집계를 스키마로 좁히지 않는다.
- **근거:** `table_relationships` 의 schema 는 원본이라 effective schema 와 어긋난다. 잘못
  맞추면 신호가 **통째로 0**이 되고, 그러면 플래너가 이름 순 순회로 퇴화한다. 동명 테이블 합산
  오차는 순위에만 영향을 주므로 훨씬 안전한 실패 방향이다.
- **한계 기록:** 같은 datasource 에 `sales.Customer` 와 `archive.Customer` 가 있으면 점수가
  합산된다. 스키마별 정확한 점수가 필요해지면 `table_relationships` 에 effective schema 를
  저장하는 별 슬라이스가 필요하다.

## ADR-0035-07 — 구조 변경이 있는 사이클에는 시드하지 않는다
- **결정:** `changes` 가 비었을 때만 커버리지 시드를 넣는다.
- **근거:** 구조 변경 재분석이 더 급하고, 같은 사이클에 둘 다 시드하면 자동 run 이 겹쳐
  busy 가드에 걸리거나 예산을 서로 잠식한다.
