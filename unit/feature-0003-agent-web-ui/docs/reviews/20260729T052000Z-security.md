## 1. Findings (발견)

### F-SEC-1 (BLOCK) — `read_attachment` 가 그룹 발신자 스코프(feature-0009 CSO F1)를 통과하지 못한다

`_load_scoped_attachment_rows` 의 SQL 에는 **AccountId(발신자) 술어가 없다**.

- `unit/feature-0002-agent-core/src/agent_core.py:551-601` — `WHERE Id IN (...) AND ConversationId = %s AND DeletedAt IS NULL AND DeletePending = 0`
  (`:573` 이 유일한 스코프 술어. sender/force_sender_scope 개념 자체가 없음)
- 대조군: 같은 파일의 메타 주입 경로 `_build_attachment_context_section` 은 `:983`
  `_scope_by_conv = bool(conversation_id) and not (force_sender_scope and account_id)` → `:1028`
  `AccountId = %s` 로 F1 을 **실제로 집행**한다. 즉 이 diff 는 F1 집행점이 없는 두 번째 첨부 열람
  경로(본문 반환)를 신설했다.

경계를 넘는 id 가 스코프에 들어오는 경로는 `_resolve_conversation_attachment_scope` 의 `client_ids`
합집합이다 — **client_ids 는 대화·발신자 어느 쪽으로도 검증되지 않고 그대로 append 된다**:

- `unit/feature-0003-agent-web-ui/src/routers/_conv_store.py:3083-3087`
  ```python
  merged = list(scoped)          # ← sender_scope 필터가 적용된 부분
  for aid in client:             # ← 검증 없이 그대로 합집합
      if aid not in merged:
          merged.append(aid)
  ```
- 호출부: `unit/feature-0003-agent-web-ui/src/routers/conversations.py:3110-3115`
  (`client_ids=client_attachment_ids + new_attachment_ids_clean`, `sender_scope=_conversation_is_group(...)`)

따라서 `agent_core.py:527` `_attachment_scope_ids()` 의 docstring —
“web ask 핸들러가 … 그룹 발신자 스코프(feature-0009 CSO F1)를 이미 적용해 넘긴 집합이라,
**이 목록 자체가 권한 경계다**” — 는 **사실이 아니다**. 목록의 절반(client 분)은 무검증 사용자 입력이다.

**악의 없이도 재현되는 경로** (그룹 대화, 멤버 A 가 올린 파일을 멤버 B 가 읽음):

1. `/api/conversations/{cid}/attachments` 는 ConversationId 단독 스코프 —
   `routers/conversations.py:2163-2176` (멤버 전원에게 타 멤버 첨부 노출: REQ-GC-R6 설계).
2. 프론트가 그 목록 전량을 `selected: true` 로 composer bucket 에 적재 —
   `src/static/app.js:9804-9824` (`:9821` `selected: true`).
3. `_composerAttachmentSnapshot` → `askBody.attachment_ids` 에 **타 멤버 id 포함**
   (`app.js:9336-9353`, `:10782-10784`).
4. 서버가 그대로 합집합(F-SEC-1 위 인용) → `ATTACHMENT_IDS` 에 타 멤버 id 진입.
5. `read_attachment(filename="…")` → `read_attachment_content`(`agent_core.py:626`) →
   `_load_scoped_attachment_rows`(AccountId 필터 없음) → `_load_attachment_bytes` → **원본 본문 반환**.

실행 확증(로컬 PoC, 본 리뷰에서 실측):

```
SQL:    SELECT Id, OriginalFilename, Kind, ObjectKey, UploadStatus, MetaJson
        FROM WebConversationAttachments WHERE Id IN (%s, %s) AND ConversationId = %s
        AND DeletedAt IS NULL AND DeletePending = 0 ORDER BY Id DESC
PARAMS: (10, 777, 'conv-group-1')          # 777 = 타 멤버(AccountId=99) 첨부
AccountId predicate present? False
read ok? True | text: 'salary,ssn\nalice,123-45'
```

그리고 스코프 해소 단계 확증:
`_resolve_conversation_attachment_scope(conn, 'conv-group-1', 5, client_ids=[777], sender_scope=True)`
→ `[10, 777]` (sender_scope=True 인데도 777 이 통과).

이는 FUNCTION `AC-GC-A6`(“멤버 A 의 첨부가 멤버 B 의 @assistant 실행 맥락에 주입되지 않는다”)와
`REQ-GC-R6`(LLM 맥락 주입은 발신자 본인 첨부 한정), 그리고 본 cycle 자신의
`AC-20260729T140200-attach-full-scope-2 ①` 을 정면으로 위반한다. csv/txt/sql/md 는 utf-8 로
디코드되어 전문이 반환된다(이미지·이진만 거부).

### F-SEC-2 (BLOCK 근접 / 동일 뿌리) — 공유창(share window) bounded 발신자에게 도구가 열린다

`_review_attachments` 는 bounded 발신자에게 첨부 근거를 넘기지 않는다(`agent_core.py:3363-3364`,
게이트 유지 확인 — 매니페스트 블록은 이 early-return **뒤**에 있다). 그 게이트의 근거는 같은 함수의
docstring 이 명시한다: “이 목록은 … 가려진 구간에서 첨부된 파일이 섞일 수 있고, **첨부 본문은
message id 로 clip 되지 않는다**”(`:3360-3361`).

그런데 `read_attachment` 노출 게이트는 `_suppress_conversation_context` 를 보지 않는다 —
`agent_core.py:4913-4921` 은 `bool(_attachment_scope_ids())` 만 본다(`_suppress_conversation_context`
는 `:4770` 에서 이미 계산되어 있다). bounded 멤버의 클라이언트는 (2)의 UI 경로로 창 밖 첨부 id 까지
전송하므로, **리뷰어에게는 감춘 그 파일을 답변 경로에서는 도구로 읽을 수 있다.** 억제 게이트가
방어하려던 자산이 우회 경로로 새는 구조다.

### F-SEC-3 (CONCERN) — cid 부재 시 `_load_scoped_attachment_rows` 가 **스코프 없이** 조회한다 (fail-open)

`agent_core.py:558-575`:

```python
conversation_id = str(_cfg.get_active_conversation_id() or "")   # 실패 시 ""
...
_scope_sql = " AND ConversationId = %s" if conversation_id else ""   # ← 스코프 술어가 사라진다
```

동종 소비자는 모두 **AccountId 폴백**을 갖는다:
`_build_attachment_context_section` `agent_core.py:1028`,
`_prepare_text_inline_attachments` `_conv_store.py:3127-3128`,
동기 ingest `conversations.py:3134-3135`, vision `conversations.py:3201-3202`.
신규 함수만 “스코프 없음”으로 폴백한다. `run_kwargs` 는 `conversation_id=conv_id or None`
(`conversations.py:3333`)이고 워커도 `payload.get("conversation_id") or None`
(`unit/feature-0002-agent-core/src/modules/ask.py:89`)이라 cid 가 비면 ContextVar 가 None 이 되고,
그때 `ATTACHMENT_IDS`(=무검증 client id, 요청당 최대 50)만으로 **시스템 전역 첨부 id 조회**가 가능해진다
= cross-account IDOR. 현재 ask 경로는 대부분 cid 를 만들어 넣으므로 즉시 착취 가능성은 낮지만,
방향이 fail-open 이라 TASK-0284 안전망의 설계 원칙(“ATTACHMENT_IDS 가 새도 스코프가 막는다”)과 반대다.

### F-SEC-4 (CONCERN) — 오류 메시지가 스코프 전체 파일명을 열거한다 (F-SEC-1 하에서 타 멤버 파일명 유출 + 탐색 도구)

`agent_core.py:650-653`, `:661-664` — 실패한 조회마다 `사용 가능: {…rows[:20]}` 로 파일명을 최대 20개
열거한다. F-SEC-1 로 rows 에 타 멤버·창 밖 첨부가 섞여 있으므로, 모델은 **아무 이름이나 한 번 틀리게
호출하는 것만으로** ATTACHED FILES 목록에 없는(=F1 이 감춘) 파일명 전량을 획득하고, 이어서 정확히
지목해 본문을 읽을 수 있다. 즉 이 메시지는 단순 편의가 아니라 F-SEC-1 의 **디스커버리 채널**이다.

### F-SEC-5 (CONCERN) — 파일명 부분 일치가 “다른 파일”을 조용히 반환한다

`agent_core.py:656-660`:

```python
exact   = [r for r in rows if r["filename"].lower() == want]
partial = [r for r in rows if want and want in r["filename"].lower()]
cands = exact or partial
target = cands[0]     # rows 는 Id DESC → 가장 최근 것
```

`want` 에 길이 하한이 없어 `"a"`, `"."`, `"report"` 같은 짧은 토큰이 광범위하게 매칭되고, 승자는
**Id 가 가장 큰 행**이다. 그룹 대화에서 타 멤버가 나중에 올린 동종 파일이 항상 우선한다
(F-SEC-1 과 결합하면 “의도치 않은 타인 파일 열람”이 모델의 통상 호출로도 발생). 헤더가 실제 파일명을
표기하는 것이 유일한 완화다.

### F-SEC-6 (CONCERN) — 스코프 해소가 적용하는 필터를 읽기 경로가 재적용하지 않는다

해소기는 `UploadStatus IN ('uploaded','ingested') AND SupersededAt IS NULL`
(`_conv_store.py:3063-3067`)을 걸지만, `_load_scoped_attachment_rows`(`agent_core.py:566-572`)는
둘 다 걸지 않는다. client 가 구버전(superseded) id 나 `failed` 행 id 를 보내면 **교체된 이전 버전의
본문**을 읽을 수 있다(사용자는 “새 버전으로 대체됨”으로 인지). 버전 체인 정책(TASK-0274)과 불일치.

### F-SEC-7 (INFO/CONCERN) — 인젝션 구획은 유지되나 헤더는 비신뢰 값이 평문이다

- 본문: `modules/tools.py:3336-3341` 에서 `_datamark_untrusted` 로 구획하고, 그와 무관하게 모든 도구
  결과가 `agent_core.py:5707`(및 `:5394`)에서 다시 `_datamark_untrusted(tool_result, …)` 로 감싸진다
  → **구획 자체는 성립**(질문 3 충족). 단, 내부 datamark 는 외부 wrap 이 sentinel 을 strip 하므로
  실질 무효(무해).
- 헤더(`tools.py:3329-3335`)와 오류 문자열은 파일명을 그대로/`repr()` 로 싣는다. `OriginalFilename` 은
  업로드 시 `.strip()` 만 거쳐 **CRLF 가 남을 수 있다**(`routers/attachments.py:120-123` 이 명시).
  오류 경로는 `repr()` 로 개행이 이스케이프돼 안전하지만, 성공 헤더는 평문이라 도구 결과 내부 구조
  위조가 가능하다. redteam 이 쓰는 `_flatten_untrusted` 같은 평탄화가 없다.

### F-SEC-8 (CONCERN, 가용성) — 본문 조회에 크기 가드가 없다

`_load_attachment_bytes`(`agent_core.py:604-621`)는 객체 전체를 메모리로 받고
`read_attachment_content`(`:669-681`)가 전량 decode + `splitlines()` 한다. 반환은 60k 자로 캡되지만
**입력은 캡되지 않는다**(per-file 상한 25MB — `app.py:1301`). 인라인 경로는 64KB 캡
(`_TEXT_INLINE_SIZE_CAP_BYTES`)을 쓰는 것과 대조적이며, 모델이 `start_line` 을 바꿔 반복 호출하면
호출마다 25MB 재다운로드 + 전량 디코드가 반복된다(ask-worker 메모리·MinIO 대역 압박).

### 유지가 확인된 경계 (통과 항목)

- **ConversationId 스코프(TASK-0284 IDOR)**: cid 가 있는 정상 경로에서는 유지
  (`agent_core.py:573`, `_conv_store.py:3061`). 타 대화 첨부 id 를 client 가 섞어도 rows 0행.
- **공유창 red-team 누출 게이트**: `_review_attachments` 의 `suppress` early-return 이 매니페스트
  **앞**에 있어 bounded 발신자에게는 여전히 빈 목록(`agent_core.py:3363`). 질문 5 = 깨지지 않음.
  (다만 F-SEC-2 로 같은 자산이 도구 경로로 샌다.)
- **ATTACHMENT_IDS 밖 접근 불가**: `Id IN (...)` 이 항상 걸려, 스코프 밖 임의 id 를 모델이 지어내
  읽을 수는 없다. object_key 는 DB 산출물이라 경로 조작 벡터 없음.
- **도구 인자 하드닝**: `start_line`/`max_lines` 클램프(1..5000, 60k 자), 이미지·이진 거부,
  저장소 실패 시 원인 단정 금지 문구 — 모두 적절.

## 2. Risks (위험)

- **R1 (Critical)**: 그룹 대화에서 타 멤버의 첨부 본문이 발신자의 LLM 실행 맥락으로 유입 →
  (a) 기밀 유출(그룹은 “열람 공유”이므로 다운로드는 원래 가능하지만, **LLM 실행 맥락 유입**은
  CSO 가 명시 차단한 별개 자산이다), (b) 타 멤버가 심은 지시문이 발신자 권한으로 datasource 를
  질의하게 하는 **indirect prompt injection → 권한상승**. F1 이 애초에 막으려던 시나리오 그대로다.
- **R2 (High)**: 공유창 bounded 멤버가 가려진 구간의 첨부 본문을 도구로 회수 → share-window
  격리(AR-1/AR-2)의 실효 약화. 리뷰어 억제 게이트만으로는 답변 경로를 막지 못한다.
- **R3 (Medium)**: cid 미확정 run 에서 스코프 술어 소멸(F-SEC-3) → 무검증 client id 로 전역 첨부
  열람. 현행 호출 그래프에서는 도달이 좁으나, 신규 caller(예: 배치·conversation API·재실행 경로)가
  cid 없이 run_agent 를 부르는 순간 즉시 cross-account IDOR 가 된다.
- **R4 (Medium)**: 오류 열거 + 부분 일치가 결합해 “목록에 없는 파일”을 탐색·지목하는 표준 절차를
  모델에게 제공한다(F-SEC-4 + F-SEC-5).
- **R5 (Low~Medium)**: superseded/failed 본문 회수(F-SEC-6), 파일명 CRLF 로 도구 결과 구조 위조
  (F-SEC-7), 대용량 반복 조회로 워커 메모리 압박(F-SEC-8).

## 3. Recommendations (권고)

1. **(필수, R1/R2 차단) 읽기 경로에 발신자 스코프를 집행한다.**
   `_load_scoped_attachment_rows` 가 `_build_attachment_context_section` 과 **동일한 스코프 계산**을
   쓰도록 한다 — `account_id` + `force_sender_scope`(그룹 판정)를 run 컨텍스트로 전달받아
   `AND AccountId = %s` 를 걸거나, 최소한 `_is_group_conversation(cid)` 가 True 면 AccountId 필터를
   강제한다. “경계를 한 곳에서만 계산” 이라는 REVIEW 의 설계 의도를 실제로 달성하려면 이 함수가
   그 한 곳을 **재사용**해야 하고, 지금은 두 번째 다른 계산이 되어 있다.
2. **(필수, 근본) `client_ids` 를 신뢰 입력으로 취급하지 않는다.**
   `_resolve_conversation_attachment_scope` 가 client 분도 **같은 WHERE 로 검증한 뒤** 합집합에
   넣도록 바꾼다(id 목록으로 1회 추가 조회 → 대화·발신자·최신본·상태 필터 통과분만 채택).
   “방금 업로드돼 목록에 안 잡힌 첨부” 라는 합집합의 실제 목적은, 같은 쿼리에 `Id IN (client)` 를
   OR 로 덧붙이면 필터를 유지한 채 달성된다.
3. **(필수, R2) 도구 노출을 `_suppress_conversation_context` 로 게이팅**한다 —
   `with_attachment_tools(_run_tool_defs, bool(_attachment_scope_ids()) and not _suppress_conversation_context)`.
   억제 대상 run 에서는 첨부 본문 자체가 창-clip 불가능하다는 것이 기존 판단이다.
4. **(필수, R3) cid 부재 시 fail-open 금지**: `conversation_id` 가 없으면 형제 소비자처럼
   `AccountId = %s` 폴백을 걸고, account_id 도 없으면 **빈 목록 반환(fail-closed)**.
5. **(권고, R4) 오류 열거를 축소**한다: 파일명 나열은 “ATTACHED FILES 섹션에 실제로 노출된 집합”
   (= 스코프 집행 후 목록)으로 제한하고, 개수도 소수(예: 5)로 줄인다. 부분 일치는 최소 길이(3자
   이상) + 유일 후보일 때만 채택하고, 다중 후보면 **후보 목록을 되묻는다**(임의 선택 금지).
6. **(권고, F-SEC-6) 읽기 SQL 에 `UploadStatus IN ('uploaded','ingested') AND SupersededAt IS NULL`**
   을 추가해 해소기와 필터를 일치시킨다.
7. **(권고, F-SEC-7/8) 헤더·오류의 파일명을 평탄화**(CRLF/제어문자 제거, 길이 캡)하고,
   `_load_attachment_bytes` 에 크기 가드(예: 2MB 초과는 거부 또는 ranged read)를 둔다.
8. **(테스트) 회귀 고정**: `test_read_attachment_tool.py` 에 “그룹 대화에서 타 멤버 첨부 id 가
   ATTACHMENT_IDS 에 있어도 읽히지 않는다”, “cid 부재 시 빈 목록”, `test_attach_full_scope.py` 에
   “sender_scope=True 이면 client_ids 의 타 멤버 id 가 결과에서 제외된다” 케이스를 추가한다.
   현재 테스트는 **스코프 밖 id 가 rows 에 없다는 전제**(`_patch_scope` 가 rows 를 직접 주입)로만
   경계를 검사해, 실제 결함이 있는 “스코프 안에 잘못 들어온 id” 축을 전혀 덮지 않는다.

## 4. Verdict rationale (판정 근거)

TASK/FUNCTION 은 “보안 경계 불변(AC-…-2)”을 이 cycle 의 명시 계약으로 선언하고, REVIEW 는
“`read_attachment` 의 권한 경계는 별도 검증이 아니라 **같은 스코프 집합의 재사용**”이라고 적었다.
코드에서는 그 재사용이 성립하지 않는다 — 기존 F1 집행은 `_build_attachment_context_section` 의
`AccountId` 술어였고(`agent_core.py:983,1028`), 신설 경로는 그 술어가 없는 **독립 SQL**
(`agent_core.py:566-575`)이며, 경계라고 선언한 `ATTACHMENT_IDS` 는 무검증 client 입력을 합집합으로
포함한다(`_conv_store.py:3083-3087`). 두 사실이 겹쳐 “멤버 A 의 첨부가 멤버 B 의 실행 맥락에 들어오지
않는다”(AC-GC-A6)가 **실제로 깨지며**, 이는 스톡 UI 동작(`app.js:9821` 전량 selected)만으로 도달한다.
PoC 로 SQL 술어 부재와 본문 반환을 실측 확인했다.

동일 결함이 공유창 억제 게이트도 우회한다(F-SEC-2): 리뷰어에게 감춘 자산을 답변 경로가 도구로
가져온다. 여기에 cid 부재 시 스코프 술어가 통째로 사라지는 fail-open(F-SEC-3)까지 더하면, 이 변경은
“노출 통제를 대화·그룹·공유창 경계가 담당한다”(ADR Consequences)는 전제 자체를 충족하지 못한다.

ConversationId 스코프와 red-team 억제 게이트의 **표면**은 유지되었고 도구 인자 하드닝·datamark 구획·
이진/이미지 거부는 적절하다. 그러나 권한 경계가 실제로 뚫리는 결함이 존재하므로 **BLOCK**.
권고 1~4 를 적용하고 회귀 테스트(권고 8)로 고정한 뒤 재검증을 요청한다. 그룹 첨부 정책은 CSO 가
명시 결정한 사안이므로, 만약 “그룹 전체 개방”으로 방향을 바꾸는 선택지를 검토한다면 코드 수정이
아니라 **사람의 재승인**이 선행되어야 한다(Human Approval Needed: yes).
