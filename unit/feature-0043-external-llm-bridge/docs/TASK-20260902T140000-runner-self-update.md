# TASK-20260902T140000 — 러너가 스스로 최신본으로 갈아 끼운다

## 1. 결정 (사용자, 2026-09-02 — 웹 리서치 후 선택)

사용자 요청으로 상용 서비스의 방식을 리서치한 뒤 두 축을 선택했다.

| 축 | 선택 |
|---|---|
| 낡음 판정 | **현행 유지 — 지문 완전 일치** |
| 화면 처리 | **조용한 자동 갱신** |

### 리서치 근거 (실 문서 대조)

| 출처 | 사실 |
|---|---|
| [Kubernetes 버전 스큐 정책](https://kubernetes.io/releases/version-skew-policy/) | kubelet 은 kube-apiserver 보다 **최대 3 마이너 낮아도 지원**. 금지는 «더 새로운 것» 뿐 — 정확한 일치를 요구하지 않는다 |
| [MCP Lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle) | 버전 협상(서버가 자기가 지원하는 다른 버전으로 응답) + **능력 협상**(`tools`·`resources`·`sampling` 선언으로 기능을 켠다) |
| [GitHub Actions 셀프호스티드 러너](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners) | 러너 애플리케이션은 **기본 자동 업데이트**(끌 수 있음). 사용자에게 재설치를 요구하지 않는다 |
| [Tailscale 클라이언트](https://tailscale.com/kb/1067/update) | 콘솔 Version 열에 회색=일반·빨강=보안·없음=최신. **심각도별 비차단 표시**, 자동 갱신은 권장이되 선택 |

공통 골자는 «판정은 호환 창 또는 선언된 능력으로, 표시는 비차단 넛지로, 수리는 자동으로» 이고,
**sha256 완전 일치를 요구하는 곳은 없었다.** 사용자는 그 중 **판정의 엄격함은 유지**하고
**수리만 자동화**하는 조합(GitHub 러너 형태)을 골랐다.

## 2. 왜 이 조합이 성립하는가

지문 일치는 정확하다. 문제는 러너 파일이 **거의 모든 배포에서 바뀐다**는 것이다 — 그래서 그
정확한 판정이 **러너와 무관한 배포**에도 하루에 몇 번씩 참이 된다.

라이브 실측(2026-09-02):

```
13:32:41  사용자 재설치 → build 4bdb0bace9b9 (그 시점 배포본과 일치)
13:33:01  run.ready — 연결 성립
~13:36:0x 다른 세션의 배포 66769688 착륙 → bridge_agent.py 가 바뀜
13:36:19  hb.stale_build ⚠  ← 사용자는 가만히 있었는데 「업데이트 필요」
```

사용자가 할 일은 없는데 화면은 조치를 요구했고, 연결 모달의 성공 조건에 `!stale` 이 있어
**창이 열린 채로 굳었다**. 판정을 무르게 하는 대신 **조치를 자동화**하면 두 문제가 함께 사라진다.

## 3. 러너 — `agent/selfupdate.py`

하트비트가 `stale_build` 를 받으면 신호만 세우고, **대기 루프가 유휴일 때** 갱신한다.
자리는 «물러남(`_SUPERSEDED`) → 갱신 → 대기» 순이다.

| 규율 | 왜 |
|---|---|
| **지문 일치로만 «단일 파일» 판정** | 개발 트리에서는 `_self_build()` 가 `events.py` 지문이라 배포본과 영원히 다르다. 경로만 보면 러너가 개발자 소스를 덮어쓴다 |
| **받을 곳은 모듈 상수** | 하트비트의 `download_url` 을 따르면, 응답을 바꿀 수 있는 누구든 러너가 **실행할** 파일을 지목한다 |
| **https + 기동 때 정한 CA** | 신뢰 앵커를 새로 정하지 않는다(`Api.ca` 를 그대로 쓴다) |
| **크기·문법 검사 후 교체** | 로그인 페이지·잘린 응답을 실행하면 러너가 죽는다 |
| **같은 디렉토리 임시 파일 → `os.replace`** | 원자성은 같은 파일시스템 안에서만 보장된다 |
| **지문이 같으면 재기동 안 함** | 「배포본을 못 따라잡는 러너가 영원히 재기동」 고리를 끊는 한 줄 |
| **최소 간격 120초** | 위가 «같을 때» 의 방어라면 이쪽은 «계속 다를 때» 의 방어 |
| **작업 중이면 미룸** | 최신이 되자고 방금 던진 질문을 죽이는 거래는 성립하지 않는다 |
| **재기동 전 하트비트 정지 → 점유 해제** | `os.execv` 는 `atexit` 를 부르지 않는다 |
| **실패는 조용히, 있던 파일로 계속** | 갱신하려다 멀쩡한 러너를 못 띄우는 것이 가장 나쁜 결말 |

`--no-self-update` 로 끌 수 있고, **끄면 신고에서도 빠진다**.

## 4. 신고 → 서버 → 화면

`self_update` 기능 신고는 **할 수 있을 때만** 나간다(단일 파일 ∧ 끄지 않음). 서버
`account_runner_self_updating()` 이 그 신고를 읽어 `connect_status.runner_self_updating` 으로
싣고, 화면은 `_actionableStaleOf()` **한 곳**에서 접는다:

```
낡음 ∧ ¬자기갱신  →  「업데이트 필요」 + 되돌아갈 명령 (종전 그대로)
낡음 ∧  자기갱신  →  아무 말도 하지 않는다 — 곧 스스로 풀린다
```

접는 자리를 하나로 둔 이유: 칩 문구·모달 성공 조건·자동 실행 자격·「재실행해도 그대로」
판정이 모두 이 축을 읽는다. 두 벌이면 하나만 고쳐지는 순간 화면이 자기 안에서 갈린다.

⚠ **모르면 종전 화면**(조치 안내)으로 떨어진다. 조회 실패·구 서버 응답·지문 판정 실패 모두
`false` 다 — 반대 방향은 스스로 못 고치는 러너의 사용자에게 아무 말 없이 낡은 동작만 남긴다.
