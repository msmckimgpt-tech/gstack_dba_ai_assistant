# Function

## 1. Summary

서비스가 보유한 Claude 계정(`claude-corp` · `root`)으로 LLM을 호출하는 경로를 **전면 차단**하고,
사용자 대면 질의는 **각 사용자의 개인 머신 AI 런타임**(Claude Code 등 MCP 클라이언트)이
**자기 계정 LLM**으로 처리하도록 전환한다. 서버는 도구·컨텍스트·데이터만 제공하고 추론은 하지 않는다.

웹 대화 화면은 유지하되 동작이 바뀐다: 질문은 서버 LLM으로 가지 않고 **대기 작업**으로 적재되며,
그 사용자의 개인 머신 AI가 MCP로 가져가 답변하고, 답변이 같은 대화창에 렌더된다.
이 "역방향" 경로는 MCP `sampling`(서버→클라이언트 push)이 아니라 **도구 기반 pull**로 구현한다 —
sampling 은 프로토콜 `2026-07-28`에서 폐기됐고(SEP-2577, "New implementations SHOULD NOT adopt it"),
Claude Code 가 미지원이기 때문이다(anthropics/claude-code#1785, 2025-06-08 이래 open).

feature-0041(외부 AI 도구 표면)의 인증·도구·원장·각인 인프라를 그대로 재사용하며,
서비스는 **어떤 사용자 LLM 자격증명도 보관하지 않는다**.

## 2. Goal

- REQ-20260828-ai-assisted-setup: 설치 경로의 **환경 판단**(파이썬·AI CLI·핸들러·워커 수)을
  그 머신의 LLM 이 조사해 채우게 하되, 채운 값은 설치 스크립트가 재검증하고 실행 경로는
  그대로 유지한다. 무결성 대조·명령 형태·성공 판정은 위임하지 않는다.
- REQ-20260828-tool-permission-friction: 브리지 답변이 웹 사용자에게 **도구 사용 승인**을
  요구하지 않는다. 러너 세션의 인증 표면을 task 결속 토큰 하나로 단일화하고(경합하는 상주 MCP
  표면 배제), 도구 실패 시에는 승인 요청 대신 실패 사실과 확인 범위를 답한다. 러너를 띄운
  사람의 권한 설정은 **낮추지 않는다**.
- REQ-20260826-external-llm-bridge: 서버 보유 계정의 LLM 호출을 fail-closed 게이트로 차단하고,
  웹 대화 질의를 개인 머신 AI 런타임이 자기 계정 LLM으로 처리하는 pull 브리지를 주 접근 경로로 구성한다.
  서비스는 사용자 LLM 자격증명을 보관하지 않고, 대화 기록은 서비스 측에 남는다.

- REQ-20260831-runtime-caps-restore: 연결된 개인 AI 로 답할 때 **쓸 수 있는 모델·추론등급이
  화면에 나타나고**, 사용자가 고른 값이 실제 CLI 호출 인자가 되며, 그 선택이 계정 기본값 +
  대화별 override 로 유지된다. 목록의 출처는 계속 **연결된 AI** 다(사용자가 직접 타이핑하지
  않는다).

## 3. In Scope

### P0-A. 서버측 LLM 전면 차단
- `shared/llm_gate.py` 신규 — fail-closed 게이트 단일 정본. **코드 기본값이 차단**이며 env 로 해제한다
  (설정 파일 미배포 환경에서도 차단이 유효하도록 기본값을 안전측에 둔다).
- chat 클라이언트 생성 chokepoint 2곳(`modules/llm._get_llm_client`, `agent_core` 의 직접 `OpenAI(...)` 생성)에 게이트.
- `litellm_config.yaml` 의 계정 alias 14종 주석처리(기존 Bedrock 토글 idiom 재사용).
- 차단 대상: 대화 답변 · 대화 보조 10단계 · insight 배치 · node_analysis · cluster_label · redteam · probe.
- **비대상(유지)**: KB 임베딩(로컬 `bge-m3`/ollama — 계정 무관).

### P0-B. pull 작업 브리지
- `WebAiTasks` 확장(멱등 ALTER): `Origin`(web|external) · `ConversationId` · `ClaimedBy` · `ClaimedAt`.
- 신규 MCP 도구 2종: `list_open_requests`(내 계정의 대기 질문 목록) · `claim_request`(점유 + 컨텍스트 반환).
- 라우팅: **본인 질문은 본인 계정 토큰을 가진 세션만** 집을 수 있다(계정 스코프 교차검증).
- `/api/ask` 분기: 게이트가 차단 상태면 LLM 실행 대신 브리지 task 적재 + 대기 상태 반환.
- 웹 프론트: 대기 말풍선 · 답변 폴링 · `/ai/connect` 연결 안내.

### P0-E. **사용감 패리티** — 전환이 기존 경험을 바꾸지 않는다 (사용자 결정 2026-08-27)

> "기존의 LLM 작동에 관련된 기능들(DB 요청사항 수행, 대화 내역 보존, 그룹 대화 Assistant 호출 등)에
> 대한 사용감은 동일하게 유지되어야 합니다." … "LLM 요청구조가 변경되면서 사용자 경험이 바뀐 부분이
> 기존의 동작 및 경험과 정합하도록 전수적으로 상세하게 수정 및 검증해주세요."

브리지는 `agent_core` 를 타지 않는다. 그래서 **기존 경로가 답변마다 하던 일을 브리지가 "그냥 안 하는"**
구멍이 생긴다. 계산이 아니라 **연결**이 끊긴 형태라, 헬퍼 단위 테스트로는 전부 통과한다.

| 축 | 계약 |
|---|---|
| 그룹 발신자 | 질문 meta 에 `sender_account_id`·`sender_username`·`group_chat` 각인 (기존 키와 동일) |
| 제품 귀속 | 답변 meta 에 `_answer_product_attribution` 각인 (`ProductMode` 를 task 에 굳혀 auto/pinned 구분) |
| 대화 내역 | 표시 store + **회수 store(`core_messages`)** 양쪽 기록. 순서는 표시 확정 → 회수 |
| 첨부 | task 에 `AttachmentIds` 적재 → `claim_request` 가 목록 반환 → `read_task_attachment` 로 본문 |
| 진입점 | `/api/ask` 를 재dispatch 하는 **모든 화면 동작**(전송·재답변·AI로 고치기)이 브리지를 처리 |
| 차단 안내 | 대화용 문구와 **다른** `feature_blocked_message()` — "고장이 아니다" 를 말한다 |
| 제한 배너 | 차단 중 provider health 는 non-restricted 로 표면화(거짓 경보·영구 고착 방지), 사유는 남긴다 |

**의도적으로 복원하지 않은 것** (정직한 잔여):

- ~~`attachment-edit` / `attachment-new` 블록 → 다운로드 첨부 변환~~ → **복원됨**(P0-AA).
  근거였던 「개인 AI 가 이 관례를 모른다」가 **사실이 아니었다** — 규약은 `system_prompt`
  (agent_core base)에 실려 이미 전달되고 있었고, 실측에서 개인 AI 는 블록을 정확히 만들어 냈다.
  빠진 것은 안내가 아니라 **서버의 처리**였다.
- 결과 CSV 다운로드. 외부 표면은 서버 CSV 경로를 응답에서 제거한다(경로 유출 + 외부 호출자에겐
  없는 다운로드 약속).
- ~~답변의 실행 단계(`AI 추론` 탭)~~ → **복원됨**(P0-N · P0-U). 「서버 run 이 없으니 단계도
  없다」는 절반만 맞았다 — 답을 만든 추론은 우리 밖이지만 **그 AI 가 무엇을 조사했는지는 우리
  안에 있다.**

### P0-F. 대기 안내는 **대화에 남아야 한다** (라이브 제보 2026-08-27)

브리지가 `agent_core` 를 우회한다는 것은 "답변을 만들지 않는다" 만이 아니라 **"답변을 저장하지도
않는다"** 는 뜻이다. 그 저장은 누군가 다시 해야 한다.

전환 직후에는 대기 안내를 동기 응답의 `answer` 로만 돌려주고 대화에 저장하지 않았다. 프런트는
**저장된 이력**을 그리므로 화면에는 질문만 남았고, 토스트는 몇 초 뒤 사라졌다 — 사용자에게는
"전송했는데 아무 일도 일어나지 않는" 상태였다(실제 제보).

| 시점 | 대화에 남는 것 |
|---|---|
| 전송 직후 | 질문(발신자 각인) + **대기 안내 assistant 말풍선**(`placeholder: true`) |
| 답변 도착 | 같은 말풍선이 **답변으로 덮어써짐**(`placeholder: false`) — 말풍선 2개가 아니다 |
| 안내를 못 찾음(구 task) | 답변을 새 말풍선으로 append(폴백) |

덮어쓰기 범위는 3겹으로 좁힌다 — 대화 · `role='assistant'` · **이 task 의** placeholder.
넓으면 남의 말풍선을 덮는다.

대기 안내는 **회수 store 에 넣지 않는다**. 시스템 안내이지 대화 내용이 아니다 — 넣으면 이후
LLM 문맥에 "AI 가 대기 안내를 했다" 는 가짜 turn 이 섞인다.

### P0-G. 안내는 **사용자의 언어**로, **상태에 맞게** (사용자 제보 2026-08-27)

> "가이드 메시지를 확인했지만, 일반적인 사용자는 '외부 AI 연결( /ai/connect )' 라는 의미 자체를
> 인지하지 못합니다."

맞는 지적이다. `MCP`·`/ai/connect` 는 **만든 사람의 언어**이고, 경로 문자열은 누를 수도 없다.
그리고 안내가 하나뿐이라 상태와 무관하게 같은 말을 했다.

**상태별 안내** — 하나로는 둘 중 한쪽에게 반드시 틀린 말이 된다:

| 상태 | 첫 줄 | 왜 |
|---|---|---|
| 연결 없음 | "답변할 AI 가 아직 연결되어 있지 않습니다" + `[AI 연결하기](/ai/connect)` | "기다리세요" 는 영원히 오지 않을 것을 기다리라는 말 |
| 연결 있음 | "연결된 AI 가 가져가면 여기에 답변이 표시됩니다" | 설정은 끝났다 — "연결하세요" 는 소음 |

판정은 요청당 **1회**(`_account_has_connected_ai`)이고, 저장 본문·응답 `answer`·토스트가 **같은
판정**을 쓴다. 조회 실패는 "연결됨" 으로 본다(fail-open) — 확신 없이 "연결이 없습니다" 라고
단정하면 이미 연결한 사용자에게 매번 설정하라고 떠드는 쪽이 된다.

**`/ai/connect` 화면도 같은 기준으로** 다시 썼다. 링크를 눌러 도착한 화면이 또 전문 용어투성이면
안내를 고친 의미가 없다:

- 추상적 "MCP 를 지원하는 도구" → **실제 이름**(Claude Desktop, Claude Code). 사용자는 자기 도구가
  MCP 를 지원하는지 스스로 판정할 수 없다.
- "주소만 등록하면" → **어디에** 넣는지(연결/커넥터 추가 설정)
- "1) / 2) 그 외" → "방법 ① **대부분 이 방법으로 됩니다**" / "방법 ② **①이 안 될 때만**"
- "토큰" 은 **버리지 않고 설명한다** — 새 이름을 만들면 정작 도구 설정의 `token` 칸과 매칭이 끊긴다.

문구를 고쳐도 **JS 가 잡는 DOM id 13개는 불변**이다(테스트로 고정 — 문구 수정이 버튼을 죽이지
않게).

### P0-H. 연결은 **한 덩어리 지시문**으로 — 나머지는 AI 가 (사용자 결정 2026-08-27)

> 방법 1, 2를 통합해주세요. AI가 각 방법을 스스로 시도하며 판단하도록 구성해주세요.
>
> 웹페이지에서 사람이 특정 텍스트(토큰을 포함)를 복사하여 AI에게 전달하면 나머지 인증과정이
> 모두 AI가 진행할 수 있도록 구성해주세요.

종전에는 두 경로를 나란히 놓고 사람에게 고르게 했다(① 커넥터 등록 / ② 토큰 수동 입력).
사용자는 **자기 AI 가 어느 쪽에 해당하는지 판정할 수 없다** — "MCP 를 지원하는 도구인가" 는
만든 사람이나 답할 수 있는 질문이다.

**사람의 몫**: `[연결 정보 만들기]` → `[복사]` → AI 에 붙여넣기. **끝.**
**AI 의 몫**: 어느 방법이 되는지 시도해 판단하고 인증까지 완료.

지시문 순서는 "간단해 보이는 순" 이 아니라 **사람을 다시 부르지 않는 순**:

| 순서 | 방법 | 사람 개입 |
|---|---|---|
| A | MCP 설정에 URL + `Authorization: Bearer` 헤더 | 없음 |
| B | HTTP 직접 호출 | 없음 |
| C | 커넥터 주소만 등록(표준 OAuth) | 브라우저 '허용' 1회 → **뒤로** |

커넥터 OAuth 는 가장 간단해 보이지만 사람을 다시 부른다. "복사만 하면 끝" 이라는 약속을
지키려면 토큰이 이미 손에 있는 경로가 먼저여야 한다.

지시문 끝에 **연결 직후 할 일**(`list_open_requests` → `claim_request` → 조사 → `submit_answer`)을
넣어, 붙여넣는 순간 대기 중인 질문이 처리되게 한다.

토큰은 지시문에 함께 실린다 — 세션 결합이라 로그아웃 시 즉시 무효이고, 1회 노출이다.

### P0-I. 발견 자료·가이드·엔드포인트가 **서로 어긋나지 않는다** (라이브 제보 2026-08-27)

외부 AI 는 이 셋을 순서대로 따라간다: 매니페스트 → 가이드 → 엔드포인트. 어느 한 곳이 다른 곳과
어긋나면 **AI 는 안내받은 대로 갔는데 막힌다** — 그리고 그것을 사람에게 보고할 뿐 스스로 우회하지
못한다. 실 연결 테스트에서 세 지점이 어긋나 있었다.

| 계약 | 어긋난 모습 |
|---|---|
| 노출 도구 = 가이드 열거 | 가이드가 "10종" 으로 브리지 3종 누락 → AI 가 그 축의 **존재를 모름** |
| 매니페스트가 안내한 URL = 토큰으로 도달 가능 | `/api/ai/capabilities` 가 쿠키 전용 → 토큰만 가진 AI 는 401 |
| 원장 기록 인자 = `record()` 시그니처 | `rows=` 오타 → `list_open_requests` **항상 500** → 브리지 축 전체 단절 |

세 번째가 가장 비쌌다. 등록·SQL·권한·어댑터 배선까지 테스트가 전부 있었고 green 이었는데,
마지막 줄의 인자명 하나가 틀려 100% 실패였다. **"도구가 등록됐는가" 와 "핸들러가 끝까지 도는가"
는 다른 사실이다.**

방어: `inspect.signature` × AST 호출부 전수 대조 · 가이드 도구 수 × 실제 노출 집합 대조 ·
capabilities 가 도구 표면과 **같은 토큰 해석기**를 쓰는지 검사(두 벌이면 갈린다).

### P0-J. **즉시 인지 · 폴링 금지 · 환경 차이 금지** (사용자 요구 2026-08-27)

> 대기열이 AI agent가 인지하는 시점은, 웹페이지에서 사용자가 요청을 보내는 즉시입니다.
> 또한, 주기적 폴링은 구성되어선 안됩니다. (환경 차이가 있어서는 안됩니다)

MCP 는 클라이언트→서버 단방향이라 서버가 AI 를 깨울 수 없다. 그렇다고 `list_open_requests` 를
N 초마다 부르면 질문이 최대 N 초 늦게 인지되고, **그 N 이 사람마다 달라 환경 차이가 된다.**

**`wait_for_request`** — 서버가 응답을 보류하다 질문이 들어오는 그 순간 반환한다.

| | 주기 폴링 | 블로킹 대기 |
|---|---|---|
| 호출 | N초마다 | **한 번** |
| 인지 시점 | 최대 N초 지연 | **즉시** |
| 간격 | 클라이언트마다 다름 | **서버 고정**(55초 상한) |

- 이미 대기 질문이 있으면 기다리지 않고 즉시 반환.
- 시간이 다 되면 **200 + `timed_out: true`** — 오류가 아니다. 곧바로 다시 부르면 된다
  (간격이 없으므로 폴링이 아니다).
- 루프마다 `conn.commit()` — 없으면 트랜잭션 스냅샷이 고정돼 **새 행이 영원히 안 보인다.**
- 클라이언트가 끊으면 즉시 중단(끊긴 응답을 위해 DB 를 두드리지 않는다).

### P0-K. 상주 러너 — 런타임 무관, 설치는 AI 가 (사용자 결정 2026-08-27)

블로킹 대기는 **AI 가 켜져 있는 동안만** 동작한다. 자리를 비워도 처리하려면 상주 프로세스가
필요하다. 이는 앞서 정한 무설치 원칙과 상충하므로, 설치물을 **stdlib 전용 단일 파일**로 최소화하고
**선택 사항**으로 둔다.

`bridge_agent.py` — `/static/agent/bridge_agent.py` 로 서빙, AI 가 직접 내려받아 띄운다.

- **sleep 이 없다.** 대기는 서버가 한다 — 그것이 '폴링 아님' 의 실체다.
- **런타임 무관**: claude·codex·gemini 는 "프롬프트 → stdout" 이라 명령 템플릿 하나로 덮인다.
  ollama 는 HTTP 어댑터. `--cmd` 로 임의 런타임.
- 프롬프트는 **argv 로** 넘긴다(셸 미경유) — 질문 본문의 셸 메타문자가 명령 주입이 되지 않는다.
- **AI 가 실패해도 답을 제출한다.** 침묵하면 사용자 화면은 30분간 대기 말풍선이고 아무도 이유를
  모른다 — 실패를 말하는 것이 침묵보다 낫다.
- 정본(`src/`)과 배포본(`static/agent/`)은 **해시 일치**를 테스트로 강제한다. 갈리면 사용자가
  받는 것과 우리가 테스트한 것이 달라진다.

### P0-L. 인증창은 **모달** (사용자 결정 2026-08-27)

안내 말풍선의 링크가 페이지를 이동시키면 질문을 써 놓고 화면을 벗어난다. 연결은 대화의
곁가지이지 목적지가 아니다.

- 문서 수준 위임으로 `a[href="/ai/connect"]` 를 가로챈다(메시지가 재렌더돼도 유지).
- **새 탭 의도는 존중**(중클릭·수식키·`target=_blank`) — 가로채면 사용자가 원한 동작을 빼앗는다.
- 단독 페이지는 **남긴다**. 모달은 가로채는 개선이지 유일 경로가 아니다.
- 열 때·닫을 때 본문을 비운다 — DOM 에 토큰을 남기지 않고, "다시 볼 수 없다" 를 참으로 만든다.
- 지시문은 **서버가 만든 것을 표시만** 한다(`handoff`). 화면이 조립하면 단독 페이지와 갈린다.

서버는 연결된 런타임이 claude 인지 codex·gemini·ollama 인지 **알 방법이 없다** — MCP 어댑터가
별도 컨테이너라 `clientInfo` 가 웹까지 오지 않는다. 알 수 없으니 목록을 그 런타임에 맞게
재구성할 수도, 고른 값을 맞는 이름으로 번역할 수도 없다.

그래서 **네 지점을 함께 닫는다**. 한 곳이라도 살아 있으면 사용자는 다시 "고를 수 있는데 반영은
안 되는" 상태를 만난다:

| 지점 | 하는 일 |
|---|---|
| 카탈로그(`/api/api-vault/options`) | 차단 상태면 목록을 비우고 `model_selector: "hidden"` 을 싣는다. 빈 목록만으로는 "로딩 중" 과 구분되지 않으므로 **상태를 값으로 말한다** |
| 조작면(컴포저) | 모델·추론 강도 항목을 DOM 에서 감춘다. 메뉴 열기 경로에도 가드를 둔다(키보드·직접 호출 우회 차단) |
| 전송(`/api/ask`·재답변) | 보여주지도 않은 값을 싣지 않는다 — 실으면 대화 KV 에 저장돼 나중에 **고른 적 없는 모델**이 그 대화 설정으로 되살아난다 |
| 적재·전달(task·`claim_request`·러너) | `RequestedModel`·`ReasoningLevel` 을 쓰지도 읽지도 않는다. 러너의 모델 인자 조립 경로를 제거 |

**이것은 제거가 아니라 조건부 숨김이다.** 게이트를 되돌리면(`AGENT_SERVER_LLM_ENABLED=1`)
같은 코드가 원래 카탈로그를 반환하고 선택기가 복원된다 — 테스트가 양방향을 모두 잠근다.

**컬럼은 남긴다**: `WebAiTasks.RequestedModel`·`ReasoningLevel` 의 과거 행 값은 그때의 사실이다.
쓰기만 멈추고 스키마는 보존한다.

**모델을 고정하고 싶은 사용자**의 길은 남아 있다 — 러너를 자기 런타임의 실제 모델 이름으로
띄운다: `--cmd 'claude --model opus -p {prompt}'`. 그 이름을 아는 것은 서버가 아니라 사용자다.

### P0-Z3. 아는 쪽이 말한다 — 러너가 신고하고 웹은 그것만 보여준다 (사용자 결정 2026-08-28)

> "웹브라우저 내 [모델 + 추론수준] 설정을 되살립니다. 해당 설정값에 따른 워커를 동작시키고
> (없다면 워커 확장) 요청을 전달하는 방식으로 구성해주세요. 이는 각 AI플랫폼에 대응되어야
> 하니 모델 종류의 확장도 염두해주세요. (claude 뿐만 아니라, codex 등...)"

P0-T 는 **"서버는 연결된 런타임을 알 수 없다"** 를 전제로 조작면을 지웠다. 그 전제는 참이었다 —
서버가 *혼자서* 알아낼 방법이 없었다. 그런데 알아낼 필요가 없다. **아는 쪽이 말하면 된다.**

상주 러너는 자기 머신에 무엇이 깔려 있는지 안다. 그것을 30초마다 가는 하트비트에 실어 보내고,
서버는 그 신고를 그대로 카탈로그로 쓴다. 그러면 화면에 보이는 이름이 **그 러너의 CLI 가 아는
이름**이 되고, 고른 값은 실제 인자가 된다. P0-M 이 실패한 지점(서버 alias ↔ CLI 어휘 불일치)이
구조적으로 사라진다 — 목록과 실행이 같은 출처를 갖기 때문이다.

| 지점 | P0-T 가 닫은 것 | P0-Z3 가 여는 방식 |
|---|---|---|
| 신고 | (없음) | 러너가 하트비트 본문에 런타임·모델·추론등급을 싣는다. 별도 채널이 아닌 이유: 살아 있음과 능력은 **같은 사실의 두 면**이라, 나누면 한쪽만 낡아 화면이 없는 모델을 보여준다 |
| 카탈로그 | 차단이면 무조건 `hidden` | 차단 + **신고 있음** → 신고 목록 + `visible`. 차단 + 신고 없음 → 종전대로 `hidden` |
| 조작면 | DOM 에서 감춤 + 열기 가드 | 같은 가드가 그대로 작동한다 — 서버가 `visible` 을 실을 때만 풀린다(프론트는 판정을 새로 만들지 않았다) |
| 전송·적재 | 값을 싣지도 굳히지도 않음 | `runtime:model` + 등급을 싣고 `RequestedRuntime`·`RequestedModel`·`ReasoningLevel` 로 굳힌다 |
| 전달·실행 | `claim_request` 미전달, 러너 인자 조립 제거 | `requested` 로 전달하고 러너가 그 CLI 의 실제 인자로 옮긴다 |

**"고를 수 있는데 반영은 안 되는" 상태는 어떻게 막는가.** P0-T 가 지운 것이 그 상태였으므로,
되살리면서 같은 함정을 다시 파지 않는 것이 이 설계의 핵심 제약이다. 세 곳에서 막는다:

1. **신고가 없으면 선택기도 없다.** 러너 미연결·구 러너·`--cmd` 직접 지정이 전부 이 경로다.
   특히 `--cmd` 사용자는 러너가 **스스로 신고를 포기한다** — 그 명령에 모델이 이미 박혀 있어
   웹에서 고른 값이 무시되기 때문이다. 고를 수 없는 상태를 화면이 정직하게 반영한다.
2. **없는 것은 신고하지 않는다.** 설치되지 않은 런타임, 모델이 0개인 런타임(ollama 미보유),
   추론등급 플래그가 없는 런타임(gemini)의 등급 목록 — 셋 다 신고에서 빠진다.
3. **낡은 선택은 복원되지 않는다.** 저장은 하되(대화별 기억), `/api/history` 의 hydration 이
   **지금 신고된 목록**과 대조한다. 러너를 바꾸거나 게이트를 되돌리면 옛 선택은 탈락한다.

**신뢰 경계 — 신고는 클라이언트가 준 값이다.** 그 값은 DB 에 저장되고, 다른 세션의 화면에
그려지고, 러너로 돌아가 `Popen` 인자가 된다. 셋 다 경계를 넘으므로 두 겹으로 막는다:

- **서버**(`_sanitize_runtimes`): 이름은 이름처럼 생긴 것만(공백·따옴표·세미콜론·선행 `-` 불허),
  라벨은 한 줄로 접고, 개수·길이에 상한. 어긋난 항목은 **그것만** 버린다(런타임 하나의 결함이
  나머지를 지우지 않게).
- **러너**(`build_cmd` 의 표 대조): 서버가 뭘 돌려주든 **자기가 신고한 값**만 인자가 된다.
  옵션처럼 보이는 문자열(`--dangerously-skip-permissions`)도, 다른 런타임의 모델 이름도,
  구 서버 alias(`claude-haiku-4`)도 조용히 버려지고 CLI 기본값으로 답한다.

**워커는 이미 수요를 따라간다** (P0-Y). 지정 조합은 슬롯이 아니라 **그 슬롯에서 실행할 명령**의
문제라, 워커 풀과 직교한다 — 요청마다 그 조합으로 프로세스를 띄우면 된다.

**새 플랫폼을 더하려면 러너의 `_RUNTIME_SPECS` 에 한 항목을 더한다.** 감지·신고·인자 조립·화면
렌더가 전부 그 표를 읽으므로 그 외에 손댈 곳이 없다. 서버는 이름을 하나도 모른 채 신고를
운반만 한다 — 그래서 **새 런타임 지원에 서버 배포가 필요 없다**.

**되돌리기**는 그대로 게이트 1개(`AGENT_SERVER_LLM_ENABLED=1`) — 해제하면 같은 코드가 원래
서버 카탈로그를 반환한다. 테스트가 세 갈래(신고 없음/있음/게이트 해제)를 모두 잠근다.

### P0-Z4. 목록을 정하는 것은 **그 AI 자신** (사용자 결정 2026-08-28)

> "실제 연결된 AI에 따라, '고를 수 있는 것' 을 제한하여 노출하도록 구성해주세요. 노출 기준을
> 설정하는것은 연결 중 시도된 AI 스스로입니다. … claude 및 codex 등 AI 플랫폼에 관계없이,
> 클라이언트 입장에서 자유롭게 서술한 모델과 추론레벨을 관대한 입장으로 수용할 수 있도록"

P0-Z3 는 목록의 출처를 서버에서 **러너**로 옮겼다. 그런데 러너가 신고한 것은 결국 우리가
`_RUNTIME_SPECS` 에 적어 둔 표였다 — 출처만 옮겼을 뿐 **내용은 여전히 우리 것**이었고, 그 표는
우리가 아는 시점에 멈춰 있다. 실측이 그것을 바로 보여줬다:

| 런타임 | 우리 표 | 그 AI 가 답한 것 |
|---|---|---|
| claude | opus · sonnet · haiku | opus · sonnet · haiku · **fable** (우리가 빠뜨림) |
| codex | `gpt-5.1-codex` · `-m` 플래그 | **`gpt-5.6-sol` · `gpt-5.6-terra`** · `--model` 플래그 (둘 다 우리가 틀림) |

그래서 한 겹 더 옮긴다 — **묻는다.** 기동 시 각 CLI 에게 "너는 어떤 모델과 추론 수준을 인자로
지정할 수 있나" 를 한 번 물어(`_CAPS_PROBE_PROMPT`) 그 답을 그대로 쓴다.

**호출법도 함께 묻는다.** 플랫폼마다 지정 방법이 다르다(`--model` / `-m` / `-c key=value`).
우리가 표로 갖고 있으면 새 플랫폼은 우리 배포를 기다려야 한다. AI 가 자기 호출법을 말하면
그 종속이 사라진다 — **우리 표에 없는 CLI 도 `--ai <이름>` 으로 지목하면 쓸 수 있다.**

#### 요구는 정확히, 수용은 관대하게

형식을 주지 않으면 파싱이 불가능하고, 엄격히 강제하면 조금만 어긋나도 그 런타임이 통째로
사라진다. 그래서 프롬프트는 정확한 JSON 스키마를 주되 받는 쪽이 관대하다:

| 받는 모양 | 처리 |
|---|---|
| 코드펜스(` ```json `) · 머리말 · 맺음말 | `_extract_json` 이 중괄호 균형으로 첫 완전한 객체를 찾는다 |
| `["opus","sonnet"]` (문자열 배열) | value=label 로 승격 |
| `[{"name":…}]` · `[{"id":…}]` | 흔한 키 이름 대체 수용 |
| `{"opus":"Opus"}` (매핑) | 목록으로 변환 |
| 항목 하나만 어긋남 | **그것만** 버린다(나머지는 산다) |
| 플래그 `"--model {model}"` (문자열) | `shlex` 로 분해 |

#### 그래도 모양은 본다

관대함은 **내용**에 대한 것이다. 어떤 모델이 있는지는 그 AI 의 소관이지만, 그 값은 곧
`Popen` 인자가 되므로 모양은 우리가 책임진다 — 선행 `-`(옵션 위장) · 공백 · 셸 메타문자는
거부한다. 실제 모델 이름은 이 집합 안에 다 들어온다(`gpt-5.6-sol` · `llama3:8b`).

#### 호출법은 서버로 나가지 않는다 (P0-Z3 경계 유지)

|  | 어디까지 |
|---|---|
| 모델·등급 **목록** (사람이 고를 것) | 서버 → 화면 → 선택 → 되돌아옴 |
| **플래그 형태** (`--model {model}`) | 로컬 `config.json` 에만. 서버는 모른다 |

서버는 **값을 고를** 수 있을 뿐 인자의 *형태* 를 바꾸거나 새 플래그를 만들어 넣지 못한다.
`detect_runtimes` 가 돌려주는 dict 에 `model`/`effort` 키가 없음을 직접 확인할 수 있다.

#### 기동 비용

질의는 사용자 계정의 토큰을 쓰고 시간이 걸린다(실측: claude 23초 · codex 112초). 그래서

- **병렬**로 묻는다 — 순차면 합(135초), 병렬이면 가장 느린 하나.
- 답은 `config.json` 에 **캐시**된다. 다음 기동은 묻지 않는다(`--refresh-caps` 로만 갱신).
- 질의는 **명시적 옵트인**(`detect_runtimes(probe=True)`)이다. 기본이 켜져 있으면 이 함수를
  부르는 모든 자리가 AI 를 호출한다 — 실제로 테스트 스위트가 그렇게 멈춘 적이 있다.
- 실패하면 **내장 표로 폴백**한다. 물어보지 못했다고 화면에서 사라지면, 종전에 잘 쓰던
  사용자가 이유 없이 기능을 잃는다.

### P0-Z5. `--ai` 는 그 실행의 제한이지 복원할 설정이 아니다 (라이브 실측 2026-08-28)

P0-Z3 이전에 `ai` 는 **"무엇으로 답할까"** 하나만 정했다. 그래서 자동 감지 결과를 저장해 두고
`--resume` 이 복원하는 것이 편의였다.

P0-Z3 이후 같은 값이 **신고 목록까지 좁힌다**(`detect_runtimes(only)`). 의미가 바뀌었는데
저장·상속 규칙은 그대로였고, 그 어긋남이 라이브 재기동에서 드러났다 — `--ai` 를 준 적 없는
사용자도 첫 기동의 감지 결과가 `config.json` 에 굳고, `--resume` 이 그것을 상속해
**codex 가 설치돼 있는데도 claude 만 신고**됐다(사용자 요청은 정확히 "claude 뿐만 아니라
codex 등" 이었다).

그래서 둘을 끊는다:

- **저장은 명시분만** — `save_conf(..., args.ai or "", ...)`. 자동 감지 결과를 저장하면
  그것이 다음 실행의 제한으로 승격된다.
- **상속은 하지 않는다** — `--resume` 이 복원하는 것은 `base`·`ca`·`cmd` 뿐이다.
  제한하려면 매번 명시한다. 그래야 "지금 무엇이 제한되고 있는가" 가 명령줄에 그대로 보인다.

잃는 것은 없다 — 실행 런타임은 `detect_ai()` 가 매번 다시 정한다.

> **일반화**: 한 값의 **의미가 넓어지면 그 값의 수명 규칙도 다시 봐야 한다.** 여기서는
> "실행 대상 하나" 였던 것이 "화면에 보일 목록의 필터" 가 됐는데, 저장·상속은 전자의 규칙을
> 그대로 쓰고 있었다. 그 어긋남은 단위 테스트로는 보이지 않고 **재기동해 봐야** 드러난다.

### P0-N. 실행 단계는 **원장에서 복원한다** (사용자 제보 2026-08-27)

브리지 답변에는 서버 run 이 없어 'AI 추론' 탭이 비었다. 처음엔 "없는 것을 있는 것처럼 그리지
않는다" 며 그대로 뒀는데, **절반만 맞았다**:

> 답을 만든 추론은 우리 밖에 있지만, **그 AI 가 무엇을 조사했는지는 우리 안에 있다.**

개인 AI 의 도구 호출은 전부 `tool_call_usage` 에 남는다. 제출 시 그것을 실행 단계로 옮기고
답변 meta 에 `run_id`(= task_id)를 각인한다 — 그 키가 없으면 기록해도 화면이 못 찾는다.

**옮기는 것**: 어떤 도구를 · 어떤 스키마에 · 언제 · 몇 행 · 얼마나 걸려. 관측한 사실뿐이다.
**옮기지 않는 것**: LLM 사고 과정(`reason_text`). 사용자 AI 안에서 일어났고 우리는 못 봤다.
브리지 자체의 진행 도구(wait·claim·submit)는 조사 내역이 아니므로 걸러낸다.

단계 기록 실패는 답변 전달을 막지 않는다(없으면 탭이 빌 뿐이다).

> **후속 정정 (P0-U)**: 이 절의 "사유는 비워 둔다" 는 그대로 두면 화면에 `SQL을 실행한다` 만
> 남는다 — **왜** 그 단계가 있었는지 읽을 수 없다. 지금은 개인 AI 에게 사유를 물어 받고,
> 없을 때만 서버가 파생하며, 둘을 `reason_source` 로 구분한다. 원장 이관은 **fallback** 이
> 됐다(구 task 전용).

### P0-O. 진행 상황은 **말풍선에 남는다** (사용자 제보 2026-08-27)

> 웹페이지 내에서는 AI가 연결이 완수되었는지, 답변을 진행중인건지 알 방법이 없습니다.

전송 직후 안내가 "가져가면 표시됩니다" 에서 멈춰 있었고, 실제로 누가 가져갔는지는 화면에 아무
흔적이 없었다.

점유 시 **말풍선 본문 자체**를 "가져갔습니다 · 조사·작성 중" 으로 바꾼다. 토스트가 아닌 이유:
토스트는 몇 초 뒤 사라지고 새로고침하면 없다. 사용자가 알고 싶은 것은 "지금 어떤 상태인가" 이고
그건 **화면에 남아 있어야** 한다.

국면은 **서버가 한 단어로** 정한다(프런트가 조합하면 화면마다 갈린다):

| phase | 뜻 |
|---|---|
| `not_connected` | 연결된 AI 가 없다 — **영원히 오지 않는다.** 기다리게 두지 않고 알린다 |
| `waiting` | 연결은 있고, 아직 아무도 안 집었다 |
| `working` | 누군가 가져가 처리 중 |
| `done` | 제출됨 |

프런트는 **전환된 순간에만** 다시 읽는다 — 매 tick 갱신은 스크롤을 흔들고 요청을 배로 만든다.

### P0-P. 5단계 시스템 프롬프트는 **서버가 조립해 넘긴다** (사용자 제보 2026-08-27)

브리지는 `agent_core` 를 우회하므로 `compose_system_prompt` 가 **아예 호출되지 않았다.**
운영자가 설정한 전역·제품·역할·계정·개인 지침이 브리지 답변에서만 사라졌고, **같은 질문이
경로에 따라 다른 규칙으로 답해졌다.**

- 개인 AI 는 우리 프롬프트 체계를 모르고, 안다 해도 DB 를 못 읽는다 → **서버가 조립**한다.
- 조립 로직을 여기서 다시 쓰지 않는다 — 내부 경로와 **같은 함수**를 부른다(두 벌이면 갈린다).
- 역할별 지침을 위해 `RoleId` 를 task 에 굳힌다.
- 러너는 이 지침을 **프롬프트 맨 앞**에 둔다. 뒤에 두면 앞의 지시가 이기고 운영자 설정이
  사실상 무시된다.
- 조립 실패는 빈 문자열 — 설정 하나가 서비스를 세우지 않게. 다만 로그로 남긴다.

### P0-Q. 제품·데이터소스는 **집행과 인지가 다르다** (사용자 제보 2026-08-27)

도구 호출의 제품 경계는 이미 `scoped_execution` 이 묶는다 — 그건 **집행**이고 정상이었다.
빠진 것은 **인지**다: AI 가 어떤 제품·어떤 DB 를 보는지 모르면 엉뚱한 스키마를 찾아 헤맨다.

`claim_request` 가 제품명·키·데이터소스 목록을 함께 준다. 러너는 프롬프트에 "대상 제품: …" 을
명시한다. 웹 화면의 표시는 기존 답변 제품 귀속 각인이 담당한다.

### P0-R. 로그아웃하면 AI 연결도 죽는다 (사용자 제보 2026-08-27)

> 재 로그인(로그아웃 후 로그인)해도 ai 간 연결이 끊기지 않는 이슈

**원인 둘이 겹쳤다.**

1. `revoke_for_session` 은 "웹 로그아웃 시 파생 토큰을 함께 죽인다" 는 목적으로 **이미 있었는데
   아무도 부르지 않았다**(테스트만 호출). 정의와 호출이 갈리면 그 함수는 없는 것과 같다.
2. 화면의 연결 판정이 인증 판정과 **다른 술어**였다. 라이브 데이터로 대조한 갈림:

   | 술어 | 결과 |
   |---|---|
   | 구(토큰 행만) | 연결 **1건** ← 화면이 본 것 |
   | 신(묶인 세션까지) | 연결 **0건** ← 실제 |

**데이터 경계는 지켜졌다** — 무효 토큰의 도구 호출은 401 이다. 틀린 것은 **화면의 말**이었다.

판정은 `oauth_store.account_has_live_token` 하나로 모은다. 같은 질문에 두 개의 답이 있으면
언제든 갈리고, **갈리는 순간 느슨한 쪽이 사용자가 보는 진실**이 된다.

**남은 것**: MCP `initialize` 는 토큰 값을 검증하지 않아(엣지는 헤더 *존재*만 확인) 클라이언트가
계속 "Connected" 로 표시한다. 데이터는 새지 않으나 상태 표시가 낙관적이다.

### P0-S. 연결이 없으면 **대기열에 올리지 않는다** (사용자 결정 2026-08-27)

종전엔 연결 여부와 무관하게 적재했다. 그러면 아무도 가져갈 수 없는 질문이 쌓이고, 나중에
연결하는 순간 **밀린 것이 한꺼번에** 처리된다(실측: 같은 질문 5건 누적). 사용자가 그때 원하는
것은 "그동안 쌓인 것 전부" 가 아니라 **지금 묻는 것** 이다.

| | 연결 없음 | 연결 있음 |
|---|---|---|
| 대기 작업 | **만들지 않음** | 적재 |
| 대화 기록 | 질문·안내 **남김**(표시·회수 양쪽) | 남김 |
| 폴링 | **안 함**(없는 task 를 물으면 404 만 쌓인다) | 함 |
| 안내 | "연결한 뒤 **다시 질문해 주세요**" | "가져가면 표시됩니다" |

버려지는 것은 **'대기 항목'이지 '내용'이 아니다** — 연결 후 다시 물으면 이전 질문이
`_recent_conversation_context` 로 함께 간다. 이미 적재된 것은 그대로 두며, 유기되어도 무방하다.

### P0-T. 연결 상태는 **묻기 전에** 보인다 (사용자 제보 2026-08-27)

> 웹브라우저 내 화면에서는 연결여부에 대한 메세지가 없어 연결이 1차적으로 완수되었는지
> 확인되지 않습니다.

종전엔 **질문을 보내야만** 안내 말풍선으로 간접 확인됐다. 순서가 거꾸로다 — 연결 여부는
묻기 전에 알아야 하는 사실이다.

컴포저 하단에 상시 표시(`● 내 AI 연결됨` / `○ 내 AI 연결 안 됨`). 누르면 연결 모달이 열린다
— **표시가 곧 조치 경로**여야 한다. '연결 안 됨' 만 보이고 방법이 없으면 소용없다.

갱신은 셋뿐이고 **주기 폴링은 없다**(연결은 자주 바뀌지 않고, 이 기능 전체의 원칙과도 맞춘다):

| 시점 | 왜 |
|---|---|
| 페이지 로드 | 기본 |
| 연결 정보를 만든 **직후** | 방금 연결했는데 표시가 낡으면 실패한 줄 안다 |
| 탭 복귀(`visibilitychange`) | 다른 창에서 연결하고 돌아오는 경로 |

판정은 인증과 **같은 함수**(`account_has_live_token`). 이 지점을 따로 셌다가 로그아웃 후에도
'연결됨' 이 됐던 결함을 반복하지 않는다.

조회 실패·미로그인은 **표시하지 않는다** — 틀린 상태를 보이느니 침묵이 낫다.
### P0-U. 대화 제목과 단계 사유 — **빠진 두 축** (사용자 제보 2026-08-27)

> "대화의 제목이 '새 대화' 인 상태로 바뀌지 않았으며, 기존에서 맥락에 따라 대화 제목이 바뀌는
> 기능이 누락되었습니다." / "실행 단계에서 '어떠한 이유로, 어떤 작업이 수행되었다' 라는 구조가
> 누락되었습니다."

둘 다 P0-E 가 말한 그 형태다 — **계산이 아니라 연결이 없다.** 헬퍼는 멀쩡하고 단위 테스트도
통과한다. 브리지가 그 헬퍼를 **부르지 않을** 뿐이다.

#### ① 대화 제목 — 2단 (서버 즉시 + AI 제안)

서버 LLM 경로(`agent_core._try_update_topic`)는 두 축으로 제목을 만들었다: 첫 메시지는 질문
앞머리로 즉시, 이후 턴은 LLM 이 다시 뽑아 갱신. 브리지는 그 함수를 타지 않으므로 **두 축이 다**
없었다. 그리고 두 번째 축은 그대로 복원할 수 없다 — 그 LLM 이 지금은 잠겨 있다.

| 축 | 시점 | 누가 |
|---|---|---|
| 즉시 | 질문 적재(`_enqueue_web_bridge_task`) | 서버 — 질문 앞머리 60자 |
| 맥락 | 답변 제출(`submit_answer` 의 `title`) | 개인 AI — 대화를 요약한 짧은 제목 |

정본 헬퍼는 `_conv_apply_auto_topic` 하나다(`core_conversations.topic` + kv `'topic'` 동시 갱신 —
한쪽만 쓰면 목록과 상세가 다른 제목을 말한다).

**사용자가 손으로 바꾼 제목은 덮지 않는다.** 서버 LLM 경로는 매 턴 무조건 덮어썼는데, 그건
되살릴 값이 아니라고 판단했다. 갱신 대상은 placeholder("새 대화") 이거나 **우리가 앞서 붙인
질문 기반 제목**일 때뿐이다(`supersedes` 로 판정).

#### ② 실행 단계 사유 — 「어떤 이유로 → 어떤 작업」

원장(`tool_call_usage`)에는 **인자가 없다**(`datasource_key`·`schema_name` 뿐). 그래서 이관으로
만든 단계는 표시층 fallback 을 타 `SQL을 실행한다`·`테이블 구조를 확인한다` 로 뭉뚱그려졌고,
사유 칸은 통째로 비었다.

이제 **도구 호출 그 시점에** 기록한다 — 인자와 사유를 동시에 가진 유일한 순간이다.

- MCP 어댑터 2종(stdio·HTTP)의 조사 도구 9종에 선택 인자 `reason` 을 열고, 도구 설명에
  「지금 이걸 왜 조사하는지 한 문장」을 요구한다(자리만 있고 설명이 없으면 선택 인자는 비어 온다).
- 상주 러너는 HTTP 직접 호출이므로 프롬프트에 같은 규약을 싣는다.
- 미제공 시 서버가 파생한다 — **내부 경로와 같은 헬퍼**(`_derive_step_work`/`_derive_step_reason`).
  문구를 새로 지으면 같은 도구가 경로에 따라 다르게 표현되고, 그때부터 한쪽은 반드시 낡는다.
- 출처를 구분해 각인한다: `external-ai`(AI 가 말한 사유) vs `derived`(서버 파생). 파생 문구를
  AI 의 사고인 양 표시하지 않는다 — P0-N 의 원칙은 이 구분으로 지킨다.

실패한 조사·상한 초과도 단계로 남긴다 — 감추면 "왜 답이 늦었나 / 왜 이 결론인가" 가 화면에서
사라진다.

**화면 노출 시점은 아직 답변 도착 후다.** 단계는 도구 호출 즉시 DB 에 쌓이지만, 프런트는 국면
전환(`working`) 때 한 번 이력을 다시 읽을 뿐이라 조사 중에는 "조사·작성 중" 만 보인다 —
기록 시점을 옮긴 것이 곧 실시간 표시가 되지는 않는다(codex 지적). 진행 중 단계 폴링은 별도
과제로 남긴다.

### P0-U. 상주 러너가 **기본 경로**다 (사용자 결정 2026-08-27)

> AI 인증을 통해 세션만 띄워두는 구조는 한계가 있는것이 확인되었습니다.
> 항상 상주 러너를 띄워두도록 가이드라인을 제공해주세요.

**실측된 한계**: AI 가 `wait_for_request` 를 10분간 반복하다(15:32~15:42, 각 55초),

원인은 구조적이다 — **대기 1회 = AI 의 도구 호출 1회.** 대화형 세션은 턴 예산이 있고 대기가

지시문에서 러너는 **필수 1단계**이고, 직접 대기는 "지금 당장 확인만" 하는 선택지로 내렸다 —
사용자는 앞의 것을 고른다. **왜 러너인가도 지시문에 적는다**(이유가 없으면 다음 사람이 되돌린다).

### P0-V. **연결됨 ≠ 대기 중** (재시작 케이스)

> 만약 사용자의 머신이 재실행하여 첫 환경에서 다시 사용되었을 경우도 고려하여

머신을 재시작하면 **러너만 사라지고 토큰은 DB 에 남는다.** 둘을 뭉쳐 표시하면 아무도 듣지 않는
곳에 질문하게 된다.

원장의 `wait_for_request` 최근성(150초 창)이 **살아 있는 귀**의 증거다 — 추측이 아니라 관측.

| 표시 | 뜻 |
|---|---|
| `● 내 AI 대기 중` | 토큰 있음 + 지금 듣는 중 |
| `◐ AI 대기 안 함` | 토큰은 있으나 아무도 안 듣는 중(재시작 후) |
| `○ 내 AI 연결 안 됨` | 토큰 없음 |

**판정 실패 방향이 서로 반대다**: 연결 조회 실패 → '연결됨'(과잉 경고 방지),
대기 조회 실패 → '대기 안 함'(헛된 기다림 방지). 각각 더 나쁜 쪽을 피한다.

러너는 설정(주소·CA·AI)을 `~/.mysql-ai-bridge/config.json`(0600)에 저장하고 `--resume` 을
지원한다. **토큰은 저장하지 않는다** — 비밀이고 어차피 세션과 함께 죽는다. 401 로 끝날 때도
다시 띄우는 명령을 그대로 출력한다(조용히 죽으면 "왜 답이 안 오지" 만 남는다).

### P0-X. 연결이 끊긴 동안의 질문은 **보관했다가 이어받는다** (사용자 결정 2026-08-28)

> 라이브 실측(2026-08-27, admin): 19:07:58 로그아웃 → **AI 연결 토큰 동시 폐기**(P0-R 의
> 의도된 동작) → 19:08 질문 → "연결되어 있지 않습니다. 다시 질문해 주세요" → 19:09 재연결.

판정은 **정확했다**. 문제는 그 다음이다 — 사용자는 재입력을 요구받았고, 그것을 "LLM 이 막혔다"
로 겪었다. 로그아웃이 AI 연결을 함께 끊으므로 **재로그인 직후가 정확히 그 창**이고, 그 창은
사용자가 예측할 수 없다.

#### 무엇을 바꿨나

| | 종전 | 지금 |
|---|---|---|
| 미연결 질문 | 적재 안 함 · 재입력 요구 | `Status='deferred'` 로 **보관**(대기열에는 비가시) |
| 연결 성립 시 | (없음) | **최근 1건만** `open` 승격, 나머지 `expired` |
| 밀린 질문 폭주 | 적재를 막아서 방지 | **승격을 1건으로 제한**해서 방지 |

폭주 방지는 그대로 지키면서 재입력만 없앤다. 사용자가 그 순간 원하는 것은 "그동안 쌓인 것
전부" 가 아니라 **마지막으로 물은 것**이다.

#### 경계

- **승격 지점** = `list_open_requests` · `wait_for_request`. 개인 AI 가 "가져갈 질문 있나" 를
  묻는 그 순간이 연결이 실제로 성립했다는 **유일한 증거**다(토큰 발급 시점에 올리면 발급만
  받고 오지 않는 클라이언트 때문에 질문이 늙는다).
- **승격과 만료는 한 문장**(`CASE WHEN`). 나누면 요청 커넥션이 autocommit 이라 두 세션이
  동시에 연결할 때 서로 다른 행을 각자 승격한다 — "1건" 약속이 깨진다.
- **24시간 상한**(`DEFERRED_MAX_AGE_HOURS`). 사흘 전 질문이 오늘 답변으로 돌아오면 그건
  이어받기가 아니라 **기억에 없는 응답**이다.
- **만료는 화면에 남긴다.** 상태만 바꾸고 말풍선을 두면 "연결하면 이 질문부터 처리합니다" 가
  영구히 박제된다. 정정은 idempotent 라 일시 장애 후 다음 연결에서 자동 복구된다.
- **보류는 폴링하지 않는다.** 언제 승격될지 모르는데 5초마다 물으면 연결하지 않은 브라우저가
  종일 빈 요청을 보낸다.

#### 남은 한계 (정직한 잔여)

- **"연결" 판정은 토큰 존재다.** 토큰은 살아 있는데 러너만 죽은 상태는 `connected=True` 라
  질문이 곧바로 `open` 으로 들어가고, 그때는 "최근 1건" 규칙이 적용되지 않는다(대기열이
  `CreatedAt ASC` 라 오래된 것부터 처리된다). 러너 생존 신호를 연결 판정에 넣는 것은 별도
  과제다 — `bridge_status` 의 `listening` 축이 이미 그 사실을 관측하고 있다.
- **대기 중 새 보류는 그 대기에서 인지되지 않는다.** `wait_for_request` 는 승격을 루프 진입
  전 1회만 한다. 다만 대기가 도는 동안은 토큰이 살아 있어 새 질문이 `open` 으로 들어오므로
  실제 창은 매우 좁다.

### P0-Y. 러너 타임아웃은 **서버 lease 와 짝**이다 (라이브 실측 2026-08-28)

PB-0008 실 브라우저 검증 중, 27단계 조사가 끝나기 전에 러너가 중단했다 — 화면에 남은 답변은
"AI 호출이 900초를 넘겨 중단했습니다" 였다.

900초는 서버 점유 lease(30분)의 **절반**이다. 서버는 아직 그 러너의 점유를 인정하는데 러너만
먼저 포기하는 구간이 15분 있었고, 그동안 개인 AI 는 답을 만드는 중이었다.

`_AI_TIMEOUT_SEC = 1700` = lease 1800 − 제출 여유 100. 여유를 남기는 이유: 타임아웃 직후의
`submit_answer` 도 lease 안에서 끝나야 답변이 원 대화에 붙는다(lease 밖이면 그 사이 다른
세션이 같은 질문을 다시 집는다).

러너는 stdlib 전용 단일 파일이라 서버 상수를 import 할 수 없다. 그래서 **두 값의 관계를 계약
테스트로 고정**한다 — lease 안일 것, 그리고 lease 의 80% 이상일 것(너무 이르게 포기하지 않을 것).

### P0-Z. 진행 표시는 **완료본과 같은 모양**이어야 한다 (사용자 제보 2026-08-28)

라이브 화면 제보 3건이 한 뿌리에서 나왔다:

> ① 도구 실행 단계만 나타나고 **추론에 대한 단계가 누락**
> ② 실행 단계 출력이 구조화되지 않고 **텍스트를 나열**하는 형식
> ③ AI 호출이 900초를 넘겨 중단

①②는 **진행 표시가 완료본과 다른 데이터·다른 렌더러를 쓰고 있었기 때문**이다.

| 축 | 종전(진행 중) | 종전(완료본) | 지금(둘 다) |
|---|---|---|---|
| 데이터 | `tool_call_usage` 원장 — 도구·스키마·행수뿐 | `agent_runtime.steps` — 작업·근거·소요 | **`agent_runtime.steps`** |
| 렌더러 | `_renderBridgeSteps` 문자열 조립 | `buildStepDetailEl` 카드 | **`buildStepDetailEl`** |
| 화면 | `list_schemas 3행` 나열 | 「작업 + 근거」 카드 | 카드 |

원장에는 작업·근거가 **없다**. 그래서 그 소스를 쓰는 한 진행 중 화면은 영원히 도구명 나열이
된다 — 표시층만 고쳐도 채울 값이 없다. 우리는 이미 도구 호출 시점에 같은 단계를
`agent_runtime.steps` 에 기록하므로(P0-U), 진행 중에도 **그 레코드를 그대로** 돌려준다.

말풍선 안의 비-SQL 단계도 같은 카드로 바꿨다(종전 `작업 — 근거` 한 줄 `<li>` 목록).
같은 사실이 자리마다 다른 모양이면 사용자는 그것을 "구조가 깨졌다" 로 읽는다.

#### 추론(내부 동작) 단계

내부 LLM 경로는 `agent_core._emit_activity` 로 "요청을 받았습니다 — 대화 맥락을 불러오는 중"
같은 진행을 남긴다(`action='activity'`). 브리지에는 그 축이 통째로 없어 실행 단계가 **DB 를
뒤진 기록**으로만 보였다.

브리지 생애주기 2곳에 activity 를 남긴다 — `claim_request`("질문을 가져왔습니다 — 대화
맥락과 첨부를 확인합니다")와 `submit_answer`("조사 결과를 정리해 답변을 작성했습니다").
**지어내지 않는다**: 여기 실리는 것은 우리가 관측한 브리지 생애주기이지 개인 AI 의 사고
과정이 아니며, `work_source='bridge-runtime'` 으로 출처가 구분된다(화면은 「내부 동작」
배지로 그린다).

#### ③ 타임아웃 — 시계가 아니라 **진행 신호**로 판정한다

> "기본적으로 time_out 은 진행되어선 안되며, 각 단계에 대한 갱신을 수신받는 부분을
> 기준으로. 연결은 살아있는 상태입니다."

고정 상한은 **일하고 있는 AI 를 끊는다**. 900초 벽에 27단계 조사가 걸린 것이 그 증거다.

- **서버**: 도구 호출마다 `ClaimedAt` 을 현재로 민다(`_renew_claim_lease`). lease 는 "마지막
  진행 이후 30분" 이 되어, 조사가 이어지는 한 만료되지 않는다. 정말 멈추면(러너 크래시·절전)
  마지막 호출로부터 30분 뒤 회수되어 안전망은 그대로다.
- **러너**: 고정 상한을 **기본 제거**(`_AI_TIMEOUT_SEC = 0`). 상한은 서버가 관측한 사실로
  집행되지 러너의 시계로 집행되지 않는다 — 회수되면 제출이 409 로 거절되어 스스로 하차한다.
  스스로 상한을 걸고 싶으면 `--ai-timeout` / `BRIDGE_AI_TIMEOUT_SEC` (opt-in).
- **취소는 그대로 즉시** 듣는다 — "무제한" 이 "사용자가 멈출 수 없다" 를 뜻하지 않는다.

### P0-AA. 진행 표시는 **말풍선 안에, 자기 run 으로** (사용자 제보 2026-08-28)

P0-Z 로 카드 구조는 맞췄는데 **자리와 귀속**이 틀려 있었다. 화면에는 이렇게 보였다:

    [새 질문]
    Assistant  연결된 AI 가 이 질문을 가져갔습니다. 조사·작성 중입니다.
               [단계 보기 (21)]        ← ① 직전 답변의 단계 수
    ─────────────────────────────      ← 말풍선 경계
    내부 동작  질문을 가져왔습니다 …    ← ② 카드가 말풍선 밖으로 흘러나옴

증상은 둘인데 뿌리는 셋이다.

| # | 뿌리 | 조치 |
|---|---|---|
| ① | 대기 말풍선 meta 에 `run_id` 각인이 없어, `_load_steps_for_message` 가 "이 시각 이전의 최근 run"(=직전 답변)으로 폴백 | placeholder 저장 시 `run_id = task_id` 각인 |
| ② | 진행 단계 앵커(`data-bridge-task`)가 **메시지 행**에 붙어 있었다 — 행은 아바타·메타·말풍선을 담는 바깥 컨테이너 | 앵커를 **말풍선(`.message-bubble`)** 으로 이동 |
| ③ | `/api/progress` 의 run 폴백이 **브리지 run 까지** 잡아 내부 경로용 progress-strip 을 깨움 | `run_id NOT LIKE 't\_%'` 로 브리지 run 제외 |

③ 은 P0-Z 가 만든 회귀다. 종전엔 브리지 단계가 사후 이관(`bridge-ledger`)뿐이라 그 필터
하나로 걸러졌는데, 도구 호출 시점 기록을 도입하면서 출처가 `derived`·`external-ai`·
`bridge-runtime` 로 갈려 필터를 그냥 통과했다. **브리지에는 전용 진행 표시가 이미 있다**
(`bridge_status`/`bridge_stream` → 대기 말풍선 안). 두 축이 같은 run 을 그리면 화면이 두 번
그려지고 자리도 갈린다 — 경계는 run_id 접두로 세운다.

### P0-AB. 진행 표시는 **자리를 새로 만들지 않는다** (사용자 제보 2026-08-28, 2차)

P0-AA 로 자리는 말풍선 안으로 들어왔지만, 여전히 `.bridge-live-steps` 라는 **제3의 블록**을
새로 만들고 있었다. 그래서 화면은 이렇게 갈렸다:

    말풍선:  ▶ 실행 단계        ← 접힌 드롭다운(1단계에서 멈춤)
             [단계 보기 (1)]     ← 개수가 멈춤
             ─────────────────
             내부 동작 …         ← 드롭다운 **밖**에 카드가 계속 쌓임
             describe_schema …
    사이드 패널: 1단계            ← 열어 둔 시점 그대로 멈춤

완료된 답변이 쓰는 자리(말풍선 details · 사이드 패널)를 **아무도 갱신하지 않았기 때문**이다.

지금은 자리를 만들지 않고 **그 둘을 갱신**한다:

| 자리 | 갱신 방법 |
|---|---|
| 말풍선 「▶ 실행 단계」 details | `renderMessageDetails({steps})` 로 통째 재구성(펼침 상태 유지) |
| 「단계 보기 (N)」 | 개수 + **클릭 대상(steps)** 을 함께 교체(개수만 고치면 옛 목록이 열린다) |
| 사이드 패널 | `refreshStepSidePanelForRun(runId, steps)` — **그 run 을 보고 있을 때만** |

사이드 패널의 판정 축이 내부 경로와 다른 이유: 내부 경로는 `stepSidePanelLive`(= `pendingBubble`
과 **같은 객체**)로 판정하는데, 브리지 대기 말풍선은 **저장된 메시지**라 그 객체가 아니다.
그래서 브리지는 `run_id` 로 같은 질문을 한다 — "지금 이 패널이 이 run 을 보고 있는가".

### P0-D. 인증 축 통일 — `mat_` 하나로 (사용자 결정 2026-08-27)

**모든 인증 및 사용은 `mat_`(OAuth access token) 를 통해서만** 이루어진다.

| 접두 | 축 | 상태 |
|---|---|---|
| `mat_` | OAuth access token — `/api/ai/tools/*` · `/api/ai/mcp` | **유일 축**. `/ai/connect` self-serve 발급, MCP 는 표준 OAuth 로 발급조차 불요 |
| `matk_` | 대화 API 토큰 — `/api/ask` | **신규 발급 중단**. 기존 토큰 인증은 유지(무회귀) |

`matk_` 축은 서버 계정 LLM 으로 답변을 만들던 경로다. 그 LLM 이 차단된 지금 그 토큰으로는
아무것도 완결되지 않으므로, **발급도 안내도 하지 않는다**. 폐기 *설명* 은 남긴다 — 사라지면
옛 토큰 보유자가 왜 안 되는지 알 수 없다.

도구 표면은 `WebOAuthTokens`(mat_)만 참조하고 `WebApiTokens`(matk_)를 보지 않는다(축 분리 불변식).

### P0-T. 대기 중에도 **멈출 수 있고, 되돌릴 수 있고, 무슨 일이 일어나는지 보인다** (사용자 결정 2026-08-28)

전환 이후 브리지 경로에는 기존 경로가 가지고 있던 **런타임 조작면 3종이 통째로 빠져 있었다**.
계산이 아니라 **연결**이 끊긴 형태라 헬퍼 테스트로는 전부 통과했다(P0-E 와 같은 부류).

| 축 | 기존 경로 | 브리지(전) | 왜 빠졌나 |
|---|---|---|---|
| 인터럽트 | `/api/cancel` → KV 플래그 → 루프가 폴링 | **UI 도달 불가** | `/api/ask` 가 즉시 반환해 `myAskInFlight` 가 곧바로 비고, 중단 버튼 자체가 안 뜬다 |
| 맥락 전환 | `_interruptCurrentRunForResend`(R3) | task 가 **추가**됨 | 이전 질문이 남은 채 `CreatedAt ASC` 로 먼저 처리 — 방금 정정한 질문이 뒤로 밀린다 |
| 진행 가시성 | 단계 폴링(1.2초) | 5초 폴링 + **답변 후에야 단계** | `_materialize_bridge_steps` 가 제출 시점에 일괄 이관 |

#### 취소는 **한 곳에서만** 판정한다

`_cancel_bridge_tasks` 하나를 정본으로 두고 `/api/cancel` · 재전송 supersede · 중단 버튼이
전부 그것을 부른다. 술어가 두 벌이면 "어디서 취소했느냐" 로 결과가 갈리고, **갈리는 순간
느슨한 쪽이 사용자가 보는 진실**이 된다(P0-R 에서 이미 한 번 겪었다).

| 대상 | 처리 | 왜 |
|---|---|---|
| 미점유(`ClaimedBy IS NULL`) | **DELETE** | 아무도 안 가져갔다 — 없던 일로 만들 수 있다 |
| 점유됨 | `Status='canceled'` (**협조적**) | 남의 머신에서 이미 돌고 있다. kill 권한이 없다 |
| 취소 후 도착한 답변 | **409 + 대화 미전달** | "취소하면 끝난다" 를 참으로 만든다 |

**정직한 계약**: *취소 즉시 화면은 풀린다. 남의 머신의 계산은 못 멈춘다.*
이것을 안내에 그대로 쓴다 — "중단했습니다" 라고만 하면 개인 계정 토큰이 계속 타는 것을 숨긴다.

#### 협조적 취소는 **기존 대기 채널**로 알린다

신규 도구를 만들지 않는다. `wait_for_request` 의 대기 루프가 이미 0.5초마다 재조회하므로,
**취소를 그 루프의 두 번째 조건**으로 넣고 응답에 `canceled_task_ids` 를 싣는다.

- 새 질문과 **똑같이 즉시** 인지된다 — P0-J 의 "환경 차이 금지" 가 취소에도 적용된다.
- 도구 **개수가 불변**이라 P0-I 계약(매니페스트·가이드 열거·`capabilities`·수 대조)이 흔들리지 않는다.
- 러너는 이 신호로 **제출 전에 하차**하고, 이 신호를 안 읽는 등록형 AI 는 `submit_answer` 409 가 받는다.
  인지(러너)와 집행(서버)은 층이 다르므로 이중 정의가 아니다.

#### 진행은 **스트리밍**으로, 다만 상한은 서버가 정한다

`GET /api/ai/bridge_stream` — `_sse_pack`·`_counted_stream`·`X-Accel-Buffering: no` 는 프롬프트
자동작성에서 이미 프로덕션 검증된 조합이라 **새 스트리밍 스택을 만들지 않는다**.

**55초 상한 + 프런트 재접속**으로 묶는 이유는 `wait_for_request` 와 같지 않다 — 여기선 **배포**다.
`deploy-web.sh` 의 pre-drain 이 `active_streams == 0` 을 최대 90초 기다린 뒤 남은 스트림을 끊는데,
30분짜리 스트림을 열어 두면 배포마다 replica 당 90초를 버리고 **그러고도 끊긴다**(fetch/getReader 는
자동 재접속이 없다). 55초로 자르면 배포 대기가 그 안에 들어가고 절단도 사라진다.

흘리는 것은 **관측한 사실뿐**이다 — phase 전환과 개인 AI 의 도구 호출 내역(`tool_call_usage`).
LLM 사고 과정은 여전히 비어 있다. `_materialize_bridge_steps` 가 그은 선을 그대로 지킨다.

**폴링을 지우지 않는다.** SSE 실패 시 기존 `_pollBridgeAnswer` 로 폴백한다 — 전송 방식이 바뀌었다고
답변 도달성이 나빠지면 개선이 아니다.

#### 병렬은 서버가 아니라 **러너**가 막고 있었다

서버는 이미 병렬이다: `wait_for_request` 가 최대 20건 반환, `claim_request` 는 원자적 점유,
프런트 폴링 복구도 대화별 배열. 직렬인 것은 러너뿐이었다(`limit=1` + 순차 `handle_one`).
그래서 **서버 계약 변경 0** 으로 워커 N개를 돌린다. 실질 상한은 개인 AI 런타임 동시성과
**개인 계정 쿼터**이며, 그것은 우리가 정할 수 없으므로 `--workers` 로 사용자가 정한다.


### P0-U. 취소 통보는 **한 번**이다 (라이브 실측 2026-08-28)

취소를 `wait_for_request` 로 알리는 설계(P0-T)는 맞았지만, **몇 번 알리는가**를 정하지 않았다.
그 빈틈이 라이브에서 가장 비싼 결함이 됐다.

취소된 행을 매 호출 다시 집으면 `timed_out = not canceled` 가 영원히 False 가 되어 대기가
즉시 반환되고, 호출측은 간격 없이 재호출한다 — **P0-J 가 없애려던 tight loop 가 우리 서버를
향해** 생긴다. 실측에서 러너가 20라운드 만에 spin 가드로 죽었고, 그때 **진행 중이던 다른
질문의 답변이 통째로 유실**됐다.

| | 알린 뒤 |
|---|---|
| 점유(`ClaimedBy`) | **놓는다** — 그래야 다음 조회에서 안 잡힌다 |
| 상태(`Status='canceled'`) | **유지한다** — `submit_answer` 409 집행과 화면 `canceled` 국면이 여기 걸려 있다 |

일반화하면: **알림은 상태가 아니라 사건이다.** 상태를 그대로 두고 알림만 소비하려면
"알렸다" 를 어딘가에 새겨야 하고, 여기서는 점유 해제가 그 자리다.

### P0-V. 상태를 바꾼 쪽이 **렌더를 책임진다** (라이브 실측 2026-08-28)

프런트의 재렌더 트리거를 "진행 중일 때만" 으로 최적화했는데, 정작 화면이 잘못 굳는 순간은
**막 진행이 끝났을 때**다. 그때 그 술어는 이미 false 라 트리거가 꺼져 있다 — 고쳐 줄 손이
정확히 필요한 시점에 사라진다(실측: 답변이 왔는데 버튼이 '중단' 에 박제, 글자를 넣어도 안 풀림).

취소 경로는 이미 렌더를 부르고 있었고 답변 경로는 아니었다. **그 비대칭이 결함이었다.**
대기를 지우는 모든 자리가 렌더를 부르고, 입력 핸들러에는 stale 상태를 푸는 backstop 을 둔다.

### P0-C. 개인 머신 접속 — **무설치 계약** (사용자 결정 2026-08-26)
개인 머신에 **어떤 패키지도 설치하지 않고** 동작해야 한다. 세 경로 모두 이 제약을 지킨다.
- **주 경로 (설치 0)**: `https://<host>/api/ai/mcp` — HTTP/SSE MCP 를 **서버가 호스팅**하므로
  AI 클라이언트에 URL + 토큰을 등록하기만 하면 된다(feature-0041 기구축).
- **REST 정본 (설치 0)**: `/api/ai/*` — `curl` 만으로 전 구간(`list_open_requests` → `claim_request`
  → 도구 → `submit_answer`) 가능.
- **보조 러너**: `src/bridge_runner.py` — 단일 파일, **Python 표준 라이브러리만** 사용
  (`urllib`; `mcp` SDK·`requests` 등 외부 패키지 import 금지). 상주시키면 대기 질문이 자동 처리된다.

### P0-W. 온보딩 지시문은 **스스로를 증명한다** (외부 AI 거절 제보 2026-08-27)

외부 머신의 AI 가 연결 지시문 실행을 거절했다 — "공인 IP 에서 사설 CA 를 받아 신뢰하고 같은 곳의
스크립트를 nohup 상주시키는 것은 무제한 원격 명령 채널이다. 평문 베어러 토큰 · '나한테 더 묻지
않아도 돼' · 자체 서명 CA 는 사회공학 전형." **그 거절이 옳다는 것이 이 계약의 출발점이다.**

코드는 실제로 훨씬 좁았지만(러너가 실행하는 명령은 소스에 하드코딩) 지시문이 그 사실을 **증명할
수단을 주지 않았다.** 좁게 만든 것과 좁다는 것을 보이는 것은 다른 일이고, 후자가 없으면 전자는
상대에게 존재하지 않는다. 그래서 지시문은 신뢰를 **요구하지 않고 검증 수단을 준다**.

| 축 | 계약 |
|---|---|
| 검증 값 | CA 지문(**인증서 DER** 기준 SHA-256)과 러너 체크섬을 서버가 런타임에 계산해 싣고, 대조 명령(`openssl x509 -fingerprint -sha256` · `sha256sum`)을 함께 준다 |
| 지문의 출처 | **AI 가 실제로 내려받는 파일**(`/trust/rootCA.crt` 서빙 번들)을 우선한다. 서버 보관본으로 계산하면 CA 회전 후 번들 재조립 누락 시 갈려 **정상 절차가 차단**된다 |
| fail-closed | 번들에 인증서가 여러 장이면 **값을 내지 않는다**(어느 장인지 말할 수 없으면 오경보가 된다). 계산 실패는 예외가 아니라 "운영자에게 확인" 으로 대체 — 무결성 값 때문에 토큰 발급이 죽지 않는다 |
| 신뢰 범위 | 사설 CA 신뢰가 **프로세스 한정**(`--cacert`/`NODE_EXTRA_CA_CERTS`)임을 명시. 시스템·브라우저 저장소를 건드리지 않고 전역 설치를 요구하지 않는다 |
| 부트스트랩 | CA 는 **평문 HTTP** 경로를 먼저 준다 — 엣지 인증서를 서명한 것이 그 CA 라 https 로만 주면 받을 방법이 없다(데드락). 평문의 위험은 지문 대조가 덮는다(지문은 https, 파일은 http — 바꿔치려면 두 채널을 동시에 잡아야 한다) |
| 단계 분리 | 내려받기+체크섬 → 소스 확인 → `--check` → `--once` → 상주. 종료(`kill`)·로그(`bridge.log`)를 함께 준다 |
| 출처 표시 | 발급자 계정명을 싣는다 — 받는 AI 에게 "이건 네 사용자가 로그인해서 만든 것" 이라는 유일한 표시 |
| **정직** | 러너 소스 상단 `## 보안 계약` 이 받는 것/실행하는 것/하지 않는 것을 **직접 확인할 명령과 함께** 적고, **남는 위험도 적는다** |

**정직이 이 계약의 알맹이다.** 초판은 "서버는 명령도 코드도 보내지 않는다" 와 "토큰을 디스크에
쓰지 않는다" 를 적었는데 **둘 다 사실과 달랐다** — 전자는 운영자 `system_prompt` 가 구획 없이
프롬프트 맨 앞에 실리는 것을 빠뜨렸고, 후자는 토큰이 프롬프트·argv 로 나가는 것을 빠뜨렸다.
우리가 지시문에 적어 준 확인 경로로 30초면 드러나는 것들이었다. 검증 가능한 문서에서 한 군데의
과장은 나머지 참인 주장까지 무너뜨리므로, **잔여 위험을 그대로 적는 것이 계약의 일부**다:

- 운영자 시스템 지침은 구획되지 않고 프롬프트 맨 앞에 실린다 → 운영자는 답변 방식에 영향을 줄 수 있다.
- 토큰은 프롬프트 본문·argv 에도 실린다 → `BRIDGE_TOKEN` 환경변수로 셸 히스토리만큼은 피할 수 있고,
  세션 결합·12시간 상한이 이 노출면의 상한이다.
- 서버가 보낸 텍스트가 상대 에이전트를 구동하는 여지는 남는다 → 그쪽 런타임의 권한 설정이 마지막
  방어선이고, 우리는 **그것을 낮추라고 요구하지 않는다**(TLS 검증 비활성화 포함).

### P0-X. 지시문은 **한 곳에서만 만든다** (라이브 PB-0008 발각 2026-08-28)

지시문을 표시하는 화면은 둘이다 — `/ai/connect` 단독 페이지와 대화 화면 모달. **조립은 서버
(`compose_connect_handoff`) 한 곳에서만** 하고, 두 화면은 응답의 `handoff` 를 표시만 한다.

이 계약은 처음부터 서버 함수 docstring 에 적혀 있었지만 **모달에만 테스트가 걸려 있었고**,
그동안 단독 페이지는 자체 조립본을 내보냈다. 서버 문안이 CA 지문·러너 체크섬·상주 러너 절차·
TLS 신뢰 범위를 담도록 여러 차례 개정되는 사이 그 사본은 몇 세대 뒤처졌고, 결국 보안 우려를
해소한 지시문이 **사용자 화면에 도달하지 않은 채** 배포까지 완료됐다.

| 축 | 계약 |
|---|---|
| 조립 | 서버 1곳. 화면은 `body.handoff` 를 표시·복사에 **그대로** 쓴다 |
| 검사 범위 | 표시하는 화면 **전부**를 parametrize 한다(하나를 빼면 그 화면만 조용히 갈린다) |
| 자체 조립 금지 | 프런트에 `mcpServers`·인증 줄 문자열 연결·가이드 URL 이 있으면 사본이 되살아난 신호 |
| 자격증명 보관면 | 화면은 토큰을 별도 변수로 붙들지 않는다 — 지시문 안에만 있고 닫으면 사라진다 |

**왜 서버인가**: 지시문은 도구 이름·발급자·무결성 값 같은 **서버 사실**을 담는다. 브라우저는
그 값들을 알지 못하므로, 화면에서 조립하는 한 그것들은 영원히 빠진다.

### P0-Y. 동시 처리는 **수요를 따라간다** (사용자 요구 2026-08-28)

> "워커는 1개부터 시작하고, 현재 실행중인 워커 개수를 초과하는 동시 요청이 구성될 때 마다
>  동적으로 확장 … 특정 시간 이상 사용되지 않는 오래된 워커부터 비활성화"

종전은 **고정 2개**였다. 고정값은 어느 쪽으로도 틀린다 — 질문이 하나뿐인 대부분의 시간에는
쓰지 않을 용량을 들고 있고, 몰릴 때는 모자란다. 실질 한계(개인 계정 쿼터·런타임 동시성)를
우리가 모르므로 **관측된 수요**를 따라가되 상한은 사용자가 정한다.

| 축 | 계약 |
|---|---|
| 시작 | **1개**(`--workers`, 기본 1). 안 쓸 용량을 미리 잡지 않는다 |
| 확장 | `wait_for_request` 가 돌려준 대기 질문 수가 현재 슬롯 수를 넘으면 그만큼. 상한 `--max-workers`(기본 8) — **예측 확장 없음**(빗나가면 비용이 사용자 쿼터로 나간다) |
| 축소 | `--worker-idle-sec`(기본 300초) 넘게 쉰 슬롯을 **오래된 것부터**(LRU). **최소 1개 유지** — 0이 되면 다음 질문을 받을 창구가 사라지고 스스로 풀리지 않는다 |
| 사용 중 보호 | 진행 중 슬롯은 회수하지 않는다(오래 걸리는 조사의 답이 사라진다) |
| tick | **서버 long-poll 반환**(최대 55초)이 곧 tick. 타이머 스레드도 추가 sleep 도 없다 — 폴링 금지(P0-J)와 정합 |
| 한 라운드 다건 | 확장한 그 라운드에 여러 건을 집는다. 하나씩 집으면 늘어난 자리가 다음 라운드까지 비어 "동시 요청이 오면 동시에 처리" 가 한 박자 늦는다 |

**LIFO 로 꺼내는 것이 축소의 전제다**: 유휴 슬롯 중 가장 최근에 쓴 것을 준다. 돌아가며 쓰면
(FIFO) 전부 조금씩 최근이 되어 idle 임계를 넘는 슬롯이 영영 생기지 않고, 그러면 "오래된
워커부터 비활성화" 가 **작동하지 않는다**.

### P0-AA. 첨부 **쓰기**를 되돌린다 — 안 여는 것보다 나쁜 상태였다 (사용자 제보 2026-08-28)

> "첨부파일 같은 경우는, assistant가 첨부된 파일을 수정하여 버전관리는 진행하거나 새로운
> 첨부파일을 추가하는 동작이 가능했습니다."

P0-E 는 이 축을 **의도적으로 열지 않았다**. 근거는 두 가지였고 **둘 다 틀렸다**:

1. 「개인 AI 가 관례를 모른다」 — 규약(```` ```attachment-edit ````/```` ```attachment-new ````)은
   `system_prompt`(agent_core base)에 실려 **이미 전달되고 있었다**. 라이브에서 개인 AI 는
   블록을 형식까지 정확히 만들어 냈다.
2. 「반쯤 만들면 '가끔 되는' 기능이 된다」 — 실제로 만들어진 상태가 그보다 나빴다.

**실측(2026-08-28, 첨부 1246 `sample.sql`)**: 개인 AI 가 `attachment-edit` 블록을 만들었으나

| 무엇이 | 어떻게 됐나 |
|---|---|
| 파일 | 만들어지지 않음 — `versions` 는 v1 그대로 |
| 답변 본문 | 블록이 strip 되지 않아 **원문 diff 가 채팅에 노출** |
| 사용자가 읽는 것 | "요청하신 두 곳만 수정했습니다" → **거짓 성공** |

「기능 없음」은 사용자가 대처할 수 있다. 「됐다고 말하는데 안 된 것」은 대처할 수 없다.

**한 벌로 합쳐서 되돌린다.** 이 시퀀스(materialize edit → new → 도구 전달분 바인딩 → strip →
미전달 고지 → content 갱신)는 ask-worker 경로에만 살아 있었다. 브리지에 두 번째 구현을 쓰면
소유권·kind·용량·확장자 allowlist 가드가 두 벌이 되고, **갈리는 순간 느슨한 쪽이 사용자가 보는
진실이 된다**. `_apply_assistant_attachment_blocks` 를 web 층에 두고 두 경로가 같이 부른다.

| 축 | 계약 |
|---|---|
| 쓰기 경계 | 내부 경로와 **동일**. 답변을 만든 주체가 밖에 있다는 사실이 가드를 넓힐 이유가 아니다 |
| 실패 | 답변 전달을 막지 않는다(fail-soft). 대신 **조용하지도 않다** — 블록 수 대비 생성 수가 모자라면 사유·건수를 답변에 덧붙여 본문의 성공 서술을 정정 |
| strip | materialize 성패와 **무관하게** 수행. 실패했다고 파일 전문을 채팅에 쏟아 두지 않는다 |
| 실패·취소 run | materialize 는 건너뛰되 strip 은 한다. 미전달 고지는 **붙이지 않는다**(이미 오류가 표면화돼 있어 같은 사실을 두 번 다르게 말하게 된다) |
| 회수 store | **정리본**을 넣는다. 원문 블록이 남으면 다음 턴 컨텍스트에 파일 전문이 통째로 재유입 |
| 영속 실패 | `answer_persisted=False` — 호출자가 자기 사본(result_json·회수본)을 바꾸지 않는다. 안 그러면 DB 메시지와 갈린다 |
| 러너 프롬프트 | 규약을 **다시 적지 않는다**. `system_prompt` 가 정본이고, 두 벌이면 형식이 갈릴 때 서버 파서가 아는 쪽만 파일이 된다 |

**codex 적대 리뷰가 드러낸 것**(REV-20260828T220000): 재사용한 기존 헬퍼에 결함 3건이 있었고
내 변경이 그것을 **새 경로로 확산**시켰다 — 0행 갱신을 영속으로 오보, 미전달 분모가 실 파서와
불일치, 블록만 있는 답변에서 원문 부활. "기존 함수를 그대로 쓰니 안전하다" 는 절반만 맞다:
재사용은 가드를 물려받지만 **결함도 물려받는다**. 추가로 제출 각인이 전달보다 먼저 커밋되는
구간(pre-existing)에 MinIO 왕복이 들어가 창이 넓어져, `done` 판정에 15초 유예를 붙였다.

**남은 잔여**: 동기 inproc 경로(`_ask_impl`)는 아직 자체 시퀀스를 갖고 있다 — materialize 사이에
step 기록이 끼고, 응답 body 에 첨부 목록을 실으며, `request` 로 audit 을 dispatch 한다. 그쪽까지
합치는 것이 옳지만 응답 shape 를 건드리므로 분리했다. **이번에 합친 것은 없던 경로(브리지)와
중복 구현(worker) 2개다.**

### P0-AB. **요청**과 **연결**은 다른 흐름이다 — 연결 전에는 요청이 열리지 않는다 (사용자 결정 2026-08-28)

> "[assistant 요청, 브릿지 연결] 을 각각 구분해주세요. 브릿지가 연결된 상태가 아니라면 요청이
> 막히고 브릿지 연결 가이드가 곧바로 제공되도록 구성해주세요. 요청이 막힘에 따라 메세지 박스
> 내 상호작용도 진행되지 않도록 처리해주세요. (연결 완수 후 활성화)"

지금까지 두 관심사는 **서로의 진입점**이었다. 연결 안내가 assistant 말풍선으로 대화에 저장되고
(P0-F·P0-G), 연결이 필요하다는 사실은 **질문을 보내야** 드러났으며(P0-T 가 상태 표시를 붙였지만
그건 *표시*였지 *게이트*가 아니었다), 연결 수단은 대화 상대인 AI 에게 지시문을 붙여넣는 것이었다.
그래서 "연결하려면 먼저 물어야 하고, 물으면 답이 안 온다" 는 순환이 남았다.

#### 게이트는 두 축의 **곱**이다

> "웹브라우저에서 접속 시, 머신 내 DQA프로세스가 실행중인지, 토큰이 연결되어 있는지 여부를
> 점검하여 허용합니다."

| 축 | 무엇을 보는가 | 없으면 |
|---|---|---|
| `connected` | `mat_` 토큰(=`account_has_live_token`) | 연결 자체가 없다 |
| `listening` | 러너 프로세스(=`account_is_listening`) | 토큰은 있으나 **아무도 듣지 않는다** |

P0-V 가 이 둘을 표시로 나눴고, 여기서 **허용 판정**으로 승격한다. 하나만 보면 각자의 사각지대가
그대로 사용자 화면의 거짓말이 된다 — 재부팅 후에는 토큰만 살아 있고, 그 상태로 열어 두면
아무도 듣지 않는 곳에 질문하게 된다.

**판정은 서버가 낸다**(`compose_blocked`). 프런트가 `connected && listening` 을 조립하면 그 순간
판정이 두 벌이 되고, 축이 늘거나 규칙이 바뀔 때 갈린다 — **갈리는 순간 느슨한 쪽이 사용자가 보는
진실**이 된다(P0-R 에서 이미 겪었다).

**게이트가 적용되는 전제도 서버가 본다**(`bridge_mode`). 서버 LLM 이 열려 있으면(`AGENT_SERVER_LLM_ENABLED=1`)
개인 AI 연결은 선택 사항이고, 그때 잠그면 **아무도 연결하지 않았다는 이유로 멀쩡한 서비스의
입력창이 잠긴다.**

#### 잠금은 표시, 집행은 서버

| 층 | 하는 일 | 실패 방향 |
|---|---|---|
| 화면(컴포저) | 입력·전송·첨부·모델 조작 비활성 + 안내 패널 | 조회 실패 시 **직전 판정 유지** (장애가 정지도 우회도 되지 않게) |
| 전송 경로(`sendPrompt`) | 잠금 반영 전 눌린 Ctrl+Enter 흡수 | **입력은 지우지 않는다** |
| 서버(`/api/ask`) | 토큰 없으면 `409 bridge_blocked`, **아무것도 저장 안 함** | 낡은 탭·직접 호출 차단 |

409 를 500 으로 내지 않는 이유: 이것은 고장이 아니라 **상태 불일치**다. 그리고 응답에 어느 축이
비었는지를 실어야(`bridge_connected`·`bridge_listening`) 프런트가 안내 문구를 고를 수 있다 —
`_json_error` 는 `{"error": …}` 뿐이라 그대로 쓰면 연결 패널을 열 근거가 없다.

**거절 시 대화에 아무것도 남기지 않는다.** 질문이나 안내를 저장하면 새로고침에 사라지는 유령
말풍선이 된다. 대신 프런트가 낙관적 말풍선을 걷고 **입력을 되돌려 준다** — 연결한 뒤 그대로 다시
보낼 수 있어야 한다(P0-X 의 취지).

#### 보관(`deferred`)은 남는다 — 다만 사유가 바뀌었다

> "이미 로그인 된 상태(연결 완료 상태)에서 질문이 진행되었다면 보관하여 다시 처리합니다."

| | P0-X (종전) | P0-AB (지금) |
|---|---|---|
| 보류 사유 | 토큰 없음 | **토큰은 있고 러너만 꺼짐** |
| 토큰 없음 | 보류 적재 | **차단**(적재·저장 없음) |
| 재입력 요구 | 없음 | 없음 (그 창에서 그대로) |

화면 게이트가 `러너 대기 중` 을 요구하므로 대부분 전송 자체가 막히고, 이 분기에 걸리는 것은
**잠금이 화면에 반영되기 직전에 눌린 전송**이다. 말풍선 문구도 사유에 맞춘다
(`_BRIDGE_NOTICE_NOT_LISTENING` — "연결하세요" 가 아니라 "실행하세요"; 토큰은 이미 있으므로
새로 만들 필요가 없다).

#### 잠긴 동안에만 재조회한다

P0-J 의 '주기 폴링 금지' 는 **대기열 인지** 축의 계약이고 `wait_for_request` 가 그것을 대체했다.
여기는 다른 축인데, 갱신 3시점(로드·연결 생성 직후·탭 복귀)만으로는 **러너 기동을 감지하지
못한다** — 사용자는 터미널에서 설치를 끝내고 이 탭으로 돌아오지 않을 수 있고, 그러면 입력창이
잠긴 채 "연결했는데 안 열린다" 가 된다.

그래서 **잠긴 동안에만** 5초로 돌고 풀리는 즉시 멈춘다(+ 배경 탭 skip). 잠기지 않은 사용자
(대다수·대부분의 시간)에게는 요청이 0 이라는 원래의 성질이 유지된다.

**잠금이 풀리면 컴포저를 다시 그린다** — 상태를 바꾼 쪽이 렌더를 책임진다(P0-V). 그 연결이 없으면
입력창이 잠긴 채 박제되고, 연결을 마친 사용자가 여전히 쓸 수 없다.

### P0-AC. 연결은 **셸이 실행한다** — AI 해석층을 걷어낸다 (사용자 결정 2026-08-28)

> "가능하다면 AI요청을 통한 연결보다 브릿지에 정형화된 형식으로 연결하는 방법을 구축하는 방법을
> 검토해주세요. 현재는 LLM에 요청함에 따라 구축하는 방식이 모두 달라 사용자의 경험이 일정하지
> 않은 이슈가 확인되었습니다."

정확한 진단이다. `compose_connect_handoff` 는 **AI 에게** 주는 지시문이고, 붙여넣는 순간부터
무엇이 일어날지는 그 AI 의 해석에 달렸다 — 어떤 AI 는 MCP 로 등록하고, 어떤 AI 는 curl 한 번으로
끝내고, 어떤 AI 는 러너를 안 띄운다(P0-U 가 실측한 그 형태다). 재현도 지원도 문서화도 되지 않는다.

**결정론적 산출물은 이미 있었다** — `bridge_agent.py`(stdlib 단일 파일). 없던 것은 **결정론적
진입점**이다. 그래서 셸에게 주는 명령을 만든다: 같은 입력이면 같은 결과다.

| | AI 지시문 (종전 유일) | 원클릭 명령 (지금 기본) |
|---|---|---|
| 실행 주체 | 사용자의 AI | 사용자의 셸 |
| 결과 | 해석에 따라 다름 | **항상 같음** |
| 화면 위치 | 유일 경로 | `<details>` 로 접힌 보조 |

지시문을 **지우지는 않는다** — 터미널을 못 쓰는 환경이 있고, 이미 그 경로로 잘 쓰던 사용자가 있다.
대체가 아니라 **기본 경로의 교체**이고, 보조 경로에는 그 성질("도구에 따라 설치 결과가 달라질 수
있습니다")을 밝혀 둔다.

#### 스크립트는 자기를 증명한다 (P0-W 계약 계승)

"모르는 주소에서 받아 실행하라" 는 요구는 그 자체로 사회공학과 구분되지 않는다. 그래서 대조할
값을 **명령 안에** 싣고(`BRIDGE_CA_SHA256`·`BRIDGE_AGENT_SHA256`), 스크립트가 CA·러너를 받은 뒤
그 값으로 대조하며, 어긋나면 **거기서 멈춘다.**

- 지문은 **인증서 DER** 기준 — 서버(`_ca_fingerprint`)·`openssl x509 -fingerprint -sha256` 과 같은
  기준이어야 대조가 성립한다. PEM 텍스트를 그냥 해싱하면 줄바꿈 차이로 갈린다(sh·ps1 양쪽 고정).
- 서버가 값을 계산하지 못하면 **대조 줄을 넣지 않고, 건너뛴 사실을 말한다.** 빈 값과 비교하면
  항상 불일치라 정상 사용자가 막힌다 — fail-closed 를 엉뚱한 곳에 적용하는 것이다.
- 러너 체크섬 불일치는 **1회 재시도** 후 판단한다(롤링 배포 교대 중일 수 있다 — 이 고지가 없으면
  정상 배포가 "침해 의심" 으로 읽혀 온보딩이 멈춘다).
- CA·설치 스크립트는 **평문 HTTP** 로 받는다. 엣지 인증서를 서명한 것이 그 CA 라 https 로만 주면
  받을 방법이 없다(부트스트랩 데드락). 평문의 위험은 지문 대조가 덮는다 — 지문은 https(화면)로,
  파일은 평문으로 오므로 바꿔치려면 두 채널을 동시에 잡아야 한다.
- 정본(`src/`)과 배포본(`static/agent/`)의 **해시 일치를 테스트로 강제**한다(러너와 같은 계약).
  갈리면 사용자가 받는 것과 우리가 테스트한 것이 달라지고, 서버가 알려 준 체크섬도 함께 갈린다.

#### 브라우저에서 실행하기 — 2단이 되는 이유 (정직한 제약)

> "웹브라우저 내에서 해당 프로세스를 실행시킬 수 있어야 하며, 해당 실행도 원클릭 명령으로
> 이루어져야 합니다."

**브라우저는 샌드박스라 로컬 프로세스를 직접 띄우지 못한다.** 우회로는 하나뿐이다 — OS 에 등록된
URL 스킴. 그래서 설치 스크립트가 `mysql-ai-bridge://` 핸들러를 등록하고, 웹의 `[내 AI 실행]`
버튼이 그 스킴을 연다.

| 시점 | 사람이 하는 일 |
|---|---|
| **최초 1회** | 명령 복사 → 터미널 붙여넣기 (설치 + 핸들러 등록 + 러너 기동) |
| **이후 (재부팅 등)** | 웹에서 `[내 AI 실행]` **클릭 한 번** |

등록은 **사용자 계정 범위**만 쓴다(`HKCU` · `~/.local/share/applications` · `~/.mysql-ai-bridge`
안의 `.app`). 관리자 권한을 요구하지 않고 시스템 전역을 건드리지 않는다.

##### 등록할 곳은 «셸» 이 아니라 «브라우저» 를 따른다 (2026-08-31 제보 반영)

> "'내 AI 실행' 을 통해 연결을 시도했지만, 연결이 진행되지 않는것으로 확인되었습니다."

초판은 `uname` 으로 갈라 **설치 셸이 도는 OS** 에 등록했다. 그런데 이 버튼을 누르는 주체는
셸이 아니라 **브라우저**다. 실측된 조합(브라우저 Windows · 러너 WSL)에서 등록은 성공하고,
스크립트는 "등록했습니다" 라고 말하고, 브라우저는 그 등록을 보지 못한다 — 사용자는 동작한다고
믿고 누르고, 아무 일도 일어나지 않는다.

| 셸 | 등록 위치 | 핸들러가 하는 일 |
|---|---|---|
| macOS | `~/.mysql-ai-bridge/MysqlAiBridge.app` (LaunchServices) | `launch.sh` 직접 |
| Linux (WSL 아님) | `~/.local/share/applications/*.desktop` (xdg) | `launch.sh` 직접 |
| **WSL** | **Windows `HKCU\Software\Classes\mysql-ai-bridge`** + xdg 양쪽 | `wsl.exe -d <배포판> -u <사용자> -- launch.sh "%1"` |

WSL 에서 판정 기준은 **Windows 쪽 등록의 성패**다 — 이 조합의 브라우저는 대부분 Windows 쪽이고,
xdg 만 성공한 상태가 정확히 이 결함의 모양이었다. Windows 등록이 실패하면 「등록했습니다」라고
말하지 않고, 사유와 함께 **버튼이 동작하지 않는다는 사실**을 말한다.

⚠ **`-d`/`-u` 값에 따옴표를 쓰지 않는다.** 레지스트리 커맨드라인은 ShellExecute 가 wsl.exe 에
원문 그대로 넘기고, wsl.exe 의 자체 파서는 그 두 옵션 값의 따옴표를 벗기지 않는다 —
`-d "Ubuntu"` 는 이름이 `"Ubuntu"` 인 배포판을 찾다 죽고, 그 오류는 즉시 닫히는 콘솔에
찍혀 사라진다(=버튼 무동작, 원래 결함과 화면상 동일). 따옴표를 못 쓰므로 공백이 든 배포판·
사용자 이름은 **표현할 수단이 없다** — 그때는 조용히 생략하지 않고 등록을 포기하고 사유를
말한다(생략하면 기본 배포판·기본 사용자로 러너가 떠서 `$HOME` 이 달라진다).

⚠ **러너의 「설치물 없음」 계약과 갈리는 지점**이다. 등록물은 **setup 스크립트에만** 있고 러너
본체에는 없다 — 러너만 받아 직접 띄우는 사용자의 계약은 그대로다. 해제 명령을 스크립트 종료
안내에 함께 출력한다.

핸들러 등록 실패는 **연결을 막지 않는다**(러너는 그대로 뜬다). 다만 조용히 실패하지도 않는다 —
버튼이 동작하지 않는다는 사실을 말하지 않으면 사용자는 눌러 보고 고장으로 읽는다.

##### 버튼은 «요청» 이 아니라 «결과» 를 말한다 (2026-08-31)

브라우저는 스킴 등록 여부를 알려 주지 않는다. 초판은 그 사실을 인정하면서도 「실행을
요청했습니다」를 성공 색으로 띄우고 4초 뒤 한 번 재조회하고 끝냈다 — 아무 일도 일어나지
않은 사용자에게 남는 것은 성공 문구 하나뿐이고, 되돌아갈 경로는 말해 주지 않았다.

이제 실제로 **대기 상태가 되는지 최대 30초 지켜본다**(누적 8회 재조회). 판정은
`refreshConnState()` 가 돌려주는 서버 응답 하나에서 난다 — 호출부가 따로 조회하면 판정이 두
벌이 되고 세대 번호(역순 도착 방어)도 우회된다.

- 대기 중이 되면 → "내 AI가 대기 중입니다."
- 30초 안에 응답이 없으면 → 실패로 말하고 **1단계 터미널 명령 블록을 가리킨다**(스크롤 + 강조).
  원인은 여럿이지만(핸들러 미등록 · 브라우저 확인 창을 닫음 · 러너 기동 실패) 사용자가 할
  일은 하나다.

대기 창이 긴 이유: 클릭 → 크롬의 외부 프로그램 확인 → 핸들러 프로세스 기동(WSL 콜드 스타트
실측 4초는 부족, 8초에 3/3 성공) → 러너의 토큰 확인 왕복이 순서대로 들어간다. 짧게 끊으면
**성공하는 중인 사용자에게 실패라고 말한다.**

⚠ **발사는 hidden iframe 이 아니라 최상위 이동이다.** 초판이 iframe 을 쓴 근거는 "미등록
스킴에서 페이지 이탈·오류 페이지가 뜨지 않는다" 였는데, 실 Windows 크롬 실측으로 둘 다
확인했다 — 미등록 스킴을 최상위로 열어도 페이지는 그대로고(URL·제목 불변), `location.href`
는 크롬의 외부 프로그램 허용 판정에 도달하는 반면(제스처가 없으면 "Not allowed to launch …
because a user gesture is required" 를 남긴다) iframe 경로는 그 판정에 **도달한 흔적조차
남기지 않는다**. 즉 iframe 은 얻는 것 없이 판정 경로만 흐린다. 최상위 이동은 클릭 핸들러
안에서 **동기적으로** 해야 사용자 활성화가 유지된다.

**명령·프로토콜 URL 은 서버가 만든다**(`compose_launch_commands`). 화면이 조립하면 무결성 값이
빠지고 — 브라우저는 그 값을 모른다 — 대조 없는 설치가 된다. P0-X 가 지시문에서 겪은 사본 drift 를
여기서 반복하지 않는다. **표시하는 화면은 둘이다**(대화 모달 · `/ai/connect` 단독 페이지) —
둘 다 `launch` 를 표시만 하고, 어느 쪽도 자체 조립하지 않는다. 그리고 모달을 닫으면 지시문뿐
아니라 **명령·프로토콜 URL 도 버린다** — 토큰이 거기에도 실려 있어, 한쪽만 지우면 "닫으면 다시
볼 수 없다" 가 절반만 참이 된다.

#### 대조 값이 없으면 **평문 경로를 닫는다** (codex 적대 리뷰 P1)

체크섬은 장식이 아니라 **평문 HTTP 로 받는 것을 정당화하는 유일한 근거**다. 초판은 값이 없을 때
"대조 줄만 빼고 그대로 실행" 했는데, 그러면 남는 것은 *모르는 주소에서 받은 스크립트를 검증 없이
실행* 이고 — 그게 P0-W 가 정당하게 거절당한 바로 그 모양이다. 게다가 이 스크립트가 하는 첫 일이
CA 를 신뢰시키는 것이라, 바꿔치기당하면 **이후 https 와 `mat_` 토큰까지** 그 CA 를 쥔 쪽으로 간다.

| 상황 | 지금 |
|---|---|
| 서버가 체크섬 계산 성공 | 평문 URL + 대조 줄 |
| 계산 실패 | **https URL** + "운영자에게 값을 확인하라" (CA 를 이미 신뢰하는 머신에서만 성공) |
| 스크립트가 CA 지문을 못 받음 | **중단**. 우회는 `BRIDGE_ALLOW_UNVERIFIED=1` 명시 opt-in |

"경고 후 진행" 은 경고가 아니라 승인이다. 못 받는 사용자를 막다른 길에 두지 않되(운영자 확인
경로·명시 우회), 기본값이 조용히 방어를 끄지는 않게 한다.

#### 토큰 노출면 — 줄인 것과 **남은 것** (정직 표기)

P0-W 가 이미 적었듯 토큰은 프롬프트·argv 에도 실린다. 원클릭 경로는 그 면을 **더한다**:

| 자리 | 상태 |
|---|---|
| 복사 명령 | 사용자가 터미널에 붙여넣는다 → **셸 히스토리에 남는다** |
| `mysql-ai-bridge://start?token=…` | 핸들러 프로세스의 argv 에 실린다 |
| 러너 프로세스 | 환경변수로 넘긴다(argv 아님) · 디스크에 쓰지 않는다 |
| `config.json` | 토큰 **없음** (주소·CA·런타임만) |

상한은 그대로다 — 세션 결합이라 로그아웃 시 즉시 무효이고, 러너가 꺼지면 마지막 생존 신호로부터
12시간 뒤 만료된다. **더 나은 설계는 일회용 교환 코드**(코드 → 서버에서 토큰 교환)이며, 그것은
발급 계약 자체를 바꾸므로 이번 cycle 범위 밖으로 남긴다.
### P0-AB. 답변은 **사용자가 할 수 없는 일**을 요구하지 않는다 (라이브 제보 2026-08-28)

> "assistant 작동에서 사용자가 '도구 사용 승인' 에 대한 과정을 직접 진행하는 부분은 전혀
> 의도하지 않았습니다. assistant는 제공된 모든 도구를 사용할 수 있지만, 현재는 사용자에게
> 권한을 요청하고 있는 상황이고 사용자는 이를 승인할 수 있는 방법도, 승인해야할 이유도
> 없습니다."

라이브 답변 그대로:

    첨부 파일 접근 권한이 필요합니다.
    웹 인터페이스의 권한 승인 대화에서 `mcp__mysql-ai__read_task_attachment` 도구 사용을
    승인해주신 후 "권한 승인했습니다" 라고 말씀해주세요.

**그런 승인 대화는 존재하지 않는다.** 러너는 다른 머신의 헤드리스 CLI 이고, 웹 사용자는 그
프로세스에 접근할 수단이 없다. 실행 불가능한 지시는 답이 아니다.

#### 원인은 권한이 아니라 자격증명 경합이었다

`claude -p` 직접 구동 실측: MCP 도구는 **권한 프롬프트 없이 호출됐고** 반환은
`HTTP 401 유효하지 않거나 만료된 토큰` 이었다. 러너 세션에는 인증 표면이 둘이다 —
프롬프트에 실린 task 결속 토큰과, 사용자 머신에 상주하는 같은 서비스 MCP 서버의 별개 토큰.
모델은 후자를 먼저 집었고 그것이 만료돼 있었다. 401 을 「권한 없음」으로 읽은 것이 그 답이다.

#### 계약

| 축 | 계약 |
|---|---|
| 실행 측 | claude 는 `--strict-mcp-config` 로 부른다 — 경합하는 두 번째 인증 표면을 없앤다. `--mcp-config` 미동반(배제이지 교체가 아니다) |
| 조사 능력 | 줄지 않는다 — 조사 도구 8종은 프롬프트의 HTTP 경로로 전부 제공된다. 줄어드는 것은 만료된 인증 경로뿐 |
| 권한 경계 | **낮추지 않는다.** `--dangerously-skip-permissions`·`bypassPermissions` 미사용을 회귀로 잠근다. 표면을 **좁히는** 변경이지 여는 변경이 아니다 (사용자 결정 2026-08-28) |
| 프롬프트 ① | 사용자에게 도구 승인을 요구하지 **않도록 지시한다** — 이유와 함께(그 사람은 승인 절차에 접근할 수 없다). ⚠ 이것은 지시이지 집행이 아니다 |
| 프롬프트 ② | 실패하면 침묵하거나 지어내지 말고 **무엇이 어떻게 실패했는지** 적은 뒤 확인한 범위까지 답한다 |
| 프롬프트 ③ | 프롬프트의 토큰이 **유일한 자격증명**이다. 다른 경로의 자격증명은 무관한 계정일 수 있다 |
| fail-safe | 계약을 따르지 않은 답(승인 요구)은 **제출 경로에서 감지**해 「할 일이 없다」 안내를 덧붙인다. 답을 지우거나 재생성하지 않는다 — 오탐 비용을 한 줄로 묶는다 (codex P1-4) |
| 학습 플래그 | AI 가 답한 모델·등급 플래그로 MCP·권한·도구·샌드박스 축을 **되열 수 없다**. 형태(토큰 수·치환자)만이 아니라 **축**을 본다 (codex P1-1) |
| 되돌리는 자리 | `BRIDGE_KEEP_MCP=1` — 배제는 mysql-ai 만이 아니라 그 사용자의 **모든** MCP 에 걸린다. 다른 MCP 를 쓰던 사람의 탈출구를 남긴다 (codex P1-3) |
| 잔여 ① | codex 에는 대응 플래그가 없다(실측) — 그 런타임은 프롬프트 계약 + fail-safe 가 방어선이다 |
| 잔여 ② | `--cmd` 는 사용자가 명령을 통째로 준 것이라 고치지 않는다 — 대신 **1회 경고**한다 (codex P1-2) |

### P0-AD. 환경 **판단**만 그 머신의 AI 에게 (사용자 결정 2026-08-28)

> "목적 자체는, LLM CLI에 연결시키기만 하면 됩니다. 그렇다면 해당 부분만, 각 머신에 설치된
> LLM의 도움을 받아 능동적으로 세팅되도록 구성해도 문제없을지 검토해주세요."

P0-AC 는 **실행**의 비결정성을 없앴다. 그런데 **판단**은 여전히 스크립트에 박혀 있었다 —
python 은 `python3 → python` 순으로 찍고, 핸들러는 `uname` 으로 갈랐다. 그 고정값이 틀리는
조합이 실측됐다: **브라우저는 Windows, `claude` 는 WSL 안.** 어떤 `uname` 분기도 그것을
맞히지 못하고, 조합은 열려 있어 열거할 수 없다.

#### 경계 — 무엇을 맡기고 무엇을 맡기지 않는가

    AI 가 채운다   → `BRIDGE_PROBED_*`   (조사해서 알아내는 값)
    스크립트가 한다 → 대조·설치·기동        (무엇을 할지는 고정)

| 축 | 계약 |
|---|---|
| 채우는 칸 | `BRIDGE_PROBED_PY` · `_AI` · `_ARGS` · `_HANDLER` **네 개뿐**. 명령 안에 빈칸으로 실재한다 — "채워라" 라고 말하면서 자리를 주지 않으면 AI 가 변수를 지어 붙이고, 오타 하나로 조용히 무시된다 |
| 검증 | `PROBED_` 접두 = **신뢰하지 않고 검증한다.** 실존·타입·범위·allowlist 를 스크립트가 다시 본다. 벗어나면 **버리고 기본 동작**(막지 않는다) |
| 거른 사실 | **stderr 로 도달**한다. 조용히 버리면 AI 가 채운 값이 반영된 줄 안다 |
| 실행 경로 | 조사 경로와 기본 경로가 **같은 스크립트**를 부른다 — P0-AC 의 「같은 입력이면 같은 결과」가 유지된다 |
| 맡기지 않는 것 | 무결성 대조 · 명령의 형태 · "됐다" 판정. 지시문이 직접 금지하고, 판정은 종료 코드다 |
| AI CLI 지목 | LLM 칸은 **알려진 이름만**(claude·codex·gemini·ollama). 실존 검사만 두면 `BRIDGE_PROBED_AI=rm` 이 통과해 러너가 그것을 AI 로 실행한다(codex 실측). 표 밖 CLI 는 사람 칸으로 |
| 수치 축 | 타입·범위로 본다(`--workers` 1~64 정수 · 시간 1~86400). `*[!0-9.]*` 하나로 뭉뚱그리면 `.` 과 `1..2` 가 통과해 러너 argparse 에서 죽는다 |
| 새 의존성 | **0.** 이 브리지의 전제가 이미 "그 머신에 LLM CLI 가 있다" 이다 |

#### 정직한 한계

- **provenance 를 강제할 수 없다.** 사람 칸(`BRIDGE_ARGS`)은 무검증인데 스크립트는 누가
  채웠는지 모른다. AI 가 그쪽에 넣으면 allowlist 를 우회한다 — 지시문이 선을 긋지만
  강제는 아니다.
- **결과의 동일성은 보장하지 않는다.** 같은 머신에서도 AI 마다 다른 값을 고를 수 있다.
  화면은 「스크립트가 같다」만 말하고 「결과가 같다」고 하지 않는다.
- **사람 칸의 따옴표 그룹은 보존되지 않는다**(비인용 전개 — 원래 동작). 숨기지 않고 적었다.
- **WSL↔Windows 핸들러 교차 등록은 하지 않는다.** 그 조합은 `_HANDLER=none` 으로 "등록하지
  않음" 을 고를 수 있을 뿐이다. 교차 등록은 실 브라우저 클릭 실측이 필요해 후속으로 남긴다.

## 4. Out of Scope

- MCP `sampling`(`sampling/createMessage`) 채택 — 폐기 기능 + Claude Code 미지원(§1).
- BYOK(사용자 API 키 서버 보관) — ADR-0026 · feature-0041 ANCHOR §2 Alt-B/C 에서 폐기된 결정.
- 팀 공용 큐(타인 질문 대리 답변) — 교차 노출면이 생기므로 별도 동의 절차 후 후속 cycle.
- feature-0023 `ask` API 축의 재설계 — 서버 LLM 차단으로 **동작이 멈추는 것**은 본 cycle 범위이나,
  외부 토큰 계약 자체의 변경은 하지 않는다.
- 기존 대화 기록의 마이그레이션 — 열람은 그대로 유지된다.

## 5. Inputs

- 웹 대화 질문(사용자 계정 세션) · `conversation_id` · 제품/폴더 지침 등 기존 ask 파라미터
- MCP 도구 인자: `task_id` · `limit` · `answer` (기존 0041 계약 준용)
- 게이트 knob: `AGENT_SERVER_LLM_ENABLED`(기본 `0` = 차단)

## 6. Outputs

- `WebAiTasks` 행 — 웹 질문(`Origin='web'` · `ConversationId` 결속) · 점유 이력 · 각인된 답변
- 웹 대화창의 대기 상태 → 답변 렌더
- 차단된 서버 LLM 호출: 호출측에 **정직한 사유 문자열**(무음 실패·폴백 금지)
- `tool_call_usage` 원장 행(기존 0041 계약)

## 7. Main Flow

1. 사용자가 웹 대화창에 질문을 보낸다.
2. `/api/ask` 가 게이트를 확인한다 → 차단 상태면 LLM을 호출하지 않는다.
3. 질문을 `WebAiTasks`(`Origin='web'`, `Status='pending'`, `ConversationId`)로 적재하고 대기 상태를 반환한다.
4. 사용자의 개인 머신 러너가 `list_open_requests` 로 대기 질문을 발견하고 `claim_request` 로 점유한다.
5. 개인 머신의 AI가 **자기 계정 LLM**으로 추론하며 기존 0041 도구로 스키마·데이터를 조사한다.
6. `submit_answer` 로 답변을 제출한다(인젝션 판정 → 각인 → 저장 → 원장 — 기존 계약).
7. 웹 대화창이 폴링으로 답변을 받아 렌더한다.

### P0-Z. 연결은 **명시적으로 끊을 때만** 끊긴다 (사용자 결정 2026-08-28)

> "브릿지와 DQA가 연결될 때 하트비트를 통해 지속적으로 연결이 보장되도록 구성해주세요.
>  명시적인 연결 해제(브릿지 프로세스 종료, 웹브라우저 내 로그아웃, 웹브라우저 종료)가
>  일어나지 않는다면 연결이 유지될 수 있도록"

종전 연결 수명은 **토큰 하나에 못박혀** 있었다. 콘솔 발급 `mat_` 토큰은 발급 시점부터 최대
12시간이고 refresh 가 없다. 그래서 아무도 로그아웃하지 않고 러너도 멀쩡히 도는데 하루 두 번
401 로 죽었다. 세션도 같은 형태였다 — 로그인 후 14일 **고정**(슬라이딩 없음)이라 매일 쓰는
사용자도 14일째에 로그아웃됐고, 그 세션에 묶인 브리지 토큰까지 함께 죽었다.

**끊기는 경로를 사건으로 분류한다.** 종전에는 "시간이 지났다" 도 해제와 같은 취급이었다.

| 사건 | 지금 |
|---|---|
| 러너가 살아 있다(하트비트 계속) | 토큰 만료가 계속 밀린다 — **끊기지 않는다** |
| 러너 종료 | 신호 중단 → 마지막 신호로부터 12시간 뒤 자연 만료 |
| 웹 로그아웃 | 세션 revoke 전파 → **즉시** 무효(하트비트가 되살리지 못한다) |
| 브라우저 종료 | **아무 일도 없다** — 세션은 살아 있고 러너는 계속 처리한다 |
| 웹을 계속 쓰는 중 | 세션 만료가 활동 기준으로 밀린다(절대 상한 90일) |

#### 하트비트는 **도구가 아니다**

`POST /api/ai/bridge_heartbeat` — 도구 표면(`/api/ai/tools/*`)에 넣지 않는다. 그 목록은
"노출 = 가이드 열거 = `capabilities` = 수 대조" 가 계약으로 묶여 있고(P0-I), 조사 도구 목록에
생존 신호가 끼면 AI 에게 "이걸 호출해 조사하라" 는 잘못된 신호를 준다. 대신 **같은 토큰
해석기**(`require_ai_token`)를 쓴다 — 인증 축이 갈리면 한쪽만 로그아웃을 반영한다.

원장(`tool_call_usage`)에도 남기지 않는다. 30초마다 오는 신호가 거기 쌓이면 화면의 실행
단계(P0-N)가 하트비트로 뒤덮이고, 시간당 호출 상한을 신호가 태운다. 흔적은 토큰 행의
`LastHeartbeatAt` 한 칸이다.

#### 연장에는 두 방향의 안전장치가 있다

- `GREATEST` — 이미 더 먼 만료를 **앞당기지 않는다**. 없으면 신호를 보낼수록 수명이 짧아진다.
- `LEAST(…, 세션 만료)` — 연장이 **세션 수명을 넘지 않는다**. 넘으면 "세션은 끝났는데 토큰만
  사는" 창이 생기고, 그것이 정확히 P0-R 에서 사용자가 겪은 결함이다.

#### '대기 중' 판정은 두 축의 OR

| 축 | 증거 | 혼자서는 무엇을 놓치나 |
|---|---|---|
| 하트비트(우선) | `LastHeartbeatAt` 최근성(90초) | 하트비트를 모르는 구 러너·등록형 MCP 클라이언트 |
| `wait_for_request` 원장(폴백) | 도구 호출 최근성(150초) | 러너가 **일하는 중**이면 호출이 없다 |

두 번째가 실제 결함이었다: 러너는 빈 워커 자리를 잡아야 대기하러 가므로, 긴 조사(최대 1700초)
동안 대기 호출이 한 번도 없다 — 그 구간에서 화면은 멀쩡히 돌고 있는 러너를 '대기 안 함' 으로
그렸다. 하트비트는 별도 스레드가 보내므로 일하는 중에도 끊기지 않는다.

### P0-Z2. 로그아웃하면 러너도 **스스로** 끝난다 (사용자 요구 2026-08-28)

> "웹브라우저 내 로그아웃 + 모든 요청사항이 완료되어 유휴상태가 확인된다면 더 이상 사용되지
>  않을 브릿지 프로세스도 안전하게 종료될 수 있도록"

로그아웃 뒤의 러너는 아무것도 할 수 없다 — 질문을 가져올 수도, 답을 제출할 수도 없다(둘 다
401). 그런 프로세스를 남겨 두면 사용자 머신에 **아무 일도 하지 않는 것**이 계속 떠 있는다.

| 그때 상태 | 하는 일 |
|---|---|
| 유휴(진행 중 0건) | 즉시 종료 |
| 진행 중 있음 | `BRIDGE_SHUTDOWN_GRACE_SEC`(기본 120초) 안에서 **끝나기를 기다린다** |
| 유예 초과 | 진행 중인 AI 호출을 **중단**시키고 종료 |

무한정 기다리지 않는 이유와 유예를 두는 이유가 같다: 그 답변들은 전달될 곳이 이미 없지만
(제출 401), 곧 끝날 일을 중간에 끊지는 않는다. 오래 붙잡으면 아무도 볼 수 없는 답을 위해
**개인 계정 토큰이 계속 탄다**(P0-T 에서 취소를 만든 것과 같은 이유).

'유휴' 를 물으려면 셀 수 있어야 한다 — 종전에는 워커 자리(세마포어)만 있고 누가 무엇을 하는지
아는 곳이 없었다. `ActiveTasks` 가 그 사실을 들고, 유예 초과 시 그 id 들을 취소로 전환한다.

### 8.x 진행 중 실행 단계 — 추론 구간과 갱신 연속성 (2026-08-31, R1·R2)

브리지 대기 말풍선의 「▶ 실행 단계」 details 와 「단계 보기」 사이드 패널은 **완료본과 같은
카드**로 그려진다(2026-08-28 정합). 그 위에 두 계약을 더한다.

**(1) 추론 구간이 단계로 존재한다.** 도구 호출 1회는 `agent_runtime.steps` 에 **두 행**을
남긴다 — 도구 단계(`action='step'`) + 그 직후의 추론 구간(`action='activity'`,
`work_source='bridge-runtime'`, 문구 「결과를 검토하고 다음 작업을 정합니다」). 화면의 소요
산출(`_computeStepTimings`)은 도구에 자기 실측(`result_summary.elapsed_ms`)을, 추론 구간에
`(다음 기록 − 이 시각) − 다음 도구 실측` 을 귀속한다. 이 행이 없으면 **도구 사이의 시간이
어느 단계에도 붙지 않아** 타임라인에서 사라진다(제보 2026-08-31).

기록하는 것은 **관측한 간격**뿐이다 — 개인 AI 의 사고 *내용*이 아니다. 사유 칸은 비운다.
겹쳐 실행된 도구(병렬 호출)에서는 뺄셈이 음수가 되어 0 으로 clamp 되므로, 겹친 시간이
추론으로 새지 않는다.

**(2) 진행 갱신은 회선 요동으로 끝나지 않는다.**

| 축 | 계약 |
|---|---|
| 스트림 결과 | 사용자 취소(`abort`)만 종결. 그 외 오류는 `"error"` → 재접속 |
| 예산 | **시간** 30분(단조 시계). 횟수 상한은 폭주 안전판이며 시간 예산보다 먼저 닿지 않는다 |
| 연속 오류 | 3회 누적 시 SSE 포기 → **폴링 강등**(커넥션을 붙들지 않는 경로) |
| 표시 창 | 최신 쪽 N건(`_BRIDGE_LIVE_STEPS_MAX`). 밀려난 앞 단계 수는 `steps_omitted` 로 동반 |
| 변경 감지 | `(길이, 생략 수, 마지막 step_index)` 서명 — 길이만 보면 창 상한에서 신호가 멎는다 |
| 절단 고지 | 「단계 보기 (N)」은 **총 단계 수**, 패널 상단에 생략 안내 1줄, 생략 시 '누적' 미표시 |
| 진행 중 표기 | 목록의 마지막 단계가 아직 끝나지 않았으면 소요 대신 「진행 중」 |

`bridge_status`(폴링)와 `bridge_stream`(SSE)은 **같은 필드**를 낸다 — 갈리면 폴백이 곧 화면
회귀다.

## 9. Constraints / Risks

- **가용성**: 개인 머신 AI 런타임이 꺼져 있으면 답변이 오지 않는다. 이는 설계상 수용된 한계이며
  (feature-0041 ANCHOR §2 Alt-D 가 지적한 "상시 도달 불가"), UI에서 **대기 상태로 정직하게 표시**한다.
- **즉시성**: 폴링 주기만큼 지연된다. 서버 LLM 즉답과 동등한 체감은 목표가 아니다.
- **blast radius**: insight·node_analysis·cluster_label 등 배경 산출물 생성이 멈춘다. 기존 산출물은 보존된다.
- **되돌리기**: 게이트 knob 1개 + `litellm_config.yaml` 주석 해제로 원복 가능하도록 구성한다.

### P0-Z6. 관리 콘솔도 같은 전환을 따라간다 (사용자 요청 2026-08-31)

> "프로젝트 내 서비스에서, LLM 동작 과정이 바뀐 구조에 따라 '관리 콘솔' 에서 작동하던 LLM의
> 동작도 정합하게 구성하고 싶습니다."

P0-A 가 서버 계정 LLM 을 끊고 P0-E~P0-Z5 가 **대화 화면**의 사용감을 되살렸다. 그런데 그
전환이 대화 화면에서 멈춰 있었다 — `static/admin/*.js` 전체에 차단 사실을 읽는 코드가
**0건**이었다. 그래서 관리 콘솔은 이렇게 보였다:

| 축 | 어긋난 모습 |
|---|---|
| 조작면 | 버튼은 그대로 있고 **눌러야** 503 을 안다 |
| 설정·권한 | 저장은 되는데 집행되지 않는 값이 "설정됨" 으로 보인다 |
| 관측 | `LLM 사용량` 0 이 "아무도 안 쓴다" 로 읽힌다 · `추론` 탭 영구 공백 |
| 부재 | 새 구조(연결된 러너·대기 큐)를 볼 자리가 관리자에게 없다 |

#### 판정은 하나, 축은 둘

`routers/_console_llm.py` 가 정본이다. **두 축을 접지 않는다**:

| 축 | 묻는 것 | 출처 |
|---|---|---|
| `server_llm_blocked` | 서버 계정으로 LLM 을 부를 수 있는가 | `shared.llm_gate` |
| `delegation` | 이 관리자의 개인 AI 가 대신할 수 있는가 | 러너 신고 |

차단+위임가능(정상 운영) · 차단+위임불가(안내 필요) · 차단해제(종전 경로)는 화면이 **서로
다르게** 말해야 하는 세 상태다. 한 값으로 접으면 그중 둘이 같은 말을 하게 된다.

#### 위임은 **작업 종류 단위**로 참이다

러너가 `console_jobs` 를 신고했다는 것과 *그 기능*의 전 구간(적재 호출부·프롬프트 조립·
산출물 반영)이 서 있다는 것은 다른 사실이다. 앞의 것만 보고 조작면을 열면 사용자는
"눌렀는데 아무 일도 없는" 버튼을 만난다 — P0-M·P0-T 가 두 번 지운 그 상태다.

그래서 `JOB_SPECS[...]["wired"]` 가 유일한 출처이고, 서버가 `delegable_jobs` 를 내려보내며
화면은 `jobDelegable(jobKind)` 로 종류마다 판정한다. **부분 배선을 True 로 적지 않는다.**

#### 콘솔 작업 = 대화가 없는 브리지 task

새 파이프라인을 만들지 않는다. 점유·lease·취소·원장·각인이 전부 `WebAiTasks` 위에 있고,
나누면 그 다섯이 두 벌이 된다. 갈리는 축은 `Kind` 하나다.

배급 자격은 **세 곳 모두**(목록·대기·점유 UPDATE)에 건다 — 목록은 방어이고 집행은 UPDATE 다.
배치(`Origin='batch'`)만 계정 스코프를 벗어나므로 거기에 권한(`kb.ingest.manual`)을 더한다:
신고는 클라이언트가 주는 값이라 그것만으로 자격이 될 수 없다.

- AC-20260831T100000-console-llm-parity-1: 관리 콘솔의 LLM 조작면이 **누르기 전에** 자기
  상태를 말한다(503 토스트로 처음 알게 되는 경로 0건).
- AC-20260831T100000-console-llm-parity-2: 집행되지 않는 설정·권한이 `미적용` 배지 + 사유
  dropdown 을 갖고, 설정 탭 최하단 집계에서 한 자리에 모인다.
- AC-20260831T100000-console-llm-parity-3: `AI 운영 현황` 이 브리지 축을 롤업에 포함하고,
  위임 작업의 **상태·소유 계정·수행 계정**을 표시한다.
- AC-20260831T100000-console-llm-parity-4: `features` 미신고(구) 러너에는 콘솔 작업이

- AC-20260831T100000-console-llm-parity-5: 배급 자격은 **그 토큰**의 신고에서 온다 — 같은

- AC-20260831T100000-console-llm-parity-6: 배치 점유분 조회는 **제출 경로만** — 조사 도구는

### P0-Z7. 위임은 **조립 뒤, 호출 앞** 한 지점에만 (사용자 결정 2026-08-31)

P0-Z6 가 관리 콘솔에 게이트 상태를 알렸다면, 여기서는 그 기능들이 **실제로 개인 AI 를 타고
돌아오게** 한다.

#### 왜 이음매가 하나여야 하는가

관리 콘솔의 네 기능(메타 자동완성 단건·일괄, 프롬프트 자동작성 3스코프)은 전부 **OpenAI
스타일 `messages` 를 조립한 뒤** LLM 을 부른다. 그 조립부가 이 feature 의 자산이다 —
스키마 grounding · 제품 바인딩 · 필드 제약 · 인사이트 수집이 전부 거기 있다.

그래서 위임은 조립 **뒤**, 호출 **앞** 한 지점에만 끼운다:

| 두는 위치 | 무슨 일이 생기나 |
|---|---|
| 조립 앞 | 조립부의 자산을 못 쓴다 — 프롬프트를 여기서 다시 써야 하고, 두 벌이 갈린다 |
| **조립 뒤 · 호출 앞** | 같은 프롬프트가 두 경로로 나간다. 갈릴 자리가 없다 |
| 호출 뒤 | 게이트가 닫혀 있으면 그 호출이 곧 503 이다 — 위임할 기회가 없다 |

`maybe_delegate` 가 `None` 을 돌려주면 호출부는 **종전 경로 그대로**다. 게이트가 닫혀 있으면
그 경로가 `feature_blocked_message` 로 안내하므로 위임 계층이 그 문구를 다시 쓰지 않는다.

#### 형식은 조립부가 정한다

`metadata_suggest` 의 기존 프롬프트는 "설명 본문만 출력" 을 지시한다 — 서버가 그 텍스트를
`{target, suggestion}` 봉투로 감쌀 뿐이다. 처음 이것을 `json` 으로 잡았는데, 그러면 위임
프롬프트가 조립부와 **모순된 형식**을 요구하고 AI 가 무엇을 내든 한쪽이 틀린다.

위임 결과는 **AI 가 낸 본문 그대로**이고 서버 봉투가 아니다. 그래서 화면이 봉투를
재구성하며, 그 재료(`target` 등)는 **적재 시점에 굳힌 payload** 에서 온다 — 폼 상태에서
다시 계산하면 그 사이 사용자가 서브뷰를 바꿨을 수 있다.

#### 러너는 콘솔 작업에 대화 프레이밍을 씌우지 않는다

`kind='job'` 이면 프롬프트를 그대로 쓴다. 대화용 프레이밍("너는 사내 DB 질의 어시스턴트다" ·
제목 마커 · 답변 규약)은 콘솔 작업에 전부 해롭다 — 서버가 이미 형식 요구를 포함한 완성
지시문을 보냈고, 덧씌우면 **두 지시가 충돌**해 JSON 을 요구했는데 산문이 오거나 끝에 제목
줄이 붙는다.

- AC-20260831T160000-console-job-wiring-1: 위임 훅이 `messages` 조립 뒤·LLM 호출 앞에 있다
  (네 경로 모두).
- AC-20260831T160000-console-job-wiring-2: 위임 대상이 아니면 `None` → 종전 경로가 그대로
  돈다(게이트 열림 / 러너 자격 없음 / 미배선 종류 / 적재 실패).
- AC-20260831T160000-console-job-wiring-3: 작업 종류의 `response` 형식이 조립부의 요구와
  일치한다.
- AC-20260831T160000-console-job-wiring-4: 러너가 `kind='job'` 을 대화 프레이밍으로 감싸지
