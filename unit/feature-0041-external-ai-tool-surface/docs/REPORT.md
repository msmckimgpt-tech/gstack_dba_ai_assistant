## 5. 알려진 한계 (정직 표기)

- 외부 AI 가 세션 A 의 데이터를 기억한 채 세션 B 에 **서술로** 답하는 경로는 차단·탐지 불가.
  각인·선언·대조는 "몰라서 섞임"을 제거할 뿐이며 "알고도 섞음"은 사후 탐지 대상이다.
- `submit_answer` 미호출은 강제할 수 없다(소프트 강제만 — 미제출률 노출 + 임계 초과 시 신규
  task 제한).
- 인젝션 방어는 SECURITY.md §14 와 동일하게 **확률적 완화**이며 보장이 아니다. 실 경계는
  RBAC·SQL guard·스코프 격리가 진다.
- 교차오염 탐지(AC-5)는 **명시적 유출 신호**에 한정되며 미탐을 허용한다(codex P2 반영).
- **답변 보존은 2026-08-14 이후 제출분부터다** (AC-7, §3.6). 그 이전에 제출된 2건
  (`bytes_out` 6,351 / 8,125)의 답변 본문은 우리 쪽에 **존재한 적이 없어 소급 복구가 불가**하다.
  > 발견 경위(기록 보존): AC-7 은 2026-08-14 까지 `[x]` 로 표기돼 있었으나
  > `submit_answer` 가 `Status`/`SubmittedAt` 만 갱신하고 있었다. 근거 4층 —
  > `ai_tools.py` 의 `INSERT INTO` 는 `WebAiTasks` 1건이 전부 · `external_ai` 문자열
  > 코드베이스 전역 0건 · 라이브 `agent_memory.WebAiTasks` 에 Answer 계열 컬럼 부재 ·
  > 원장에 답변이 바이트 수로만 존재. **정본이 존재하지 않는 보존을 주장한 사례**로 남긴다.
- 제출 자체는 여전히 자발적이다 — 보존은 "제출된 답변" 만 담는다. 미제출 task 는 질문과
  도구 이력만 남으며, 이 공백은 구조적이라 저장으로 메울 수 없다.

## 3.2 3차 출하 (2026-08-13) — 잔여 3건 완결

HTTP/SSE 전송을 **라이브에 띄웠다**(`ext-tool-mcp` + Caddy `/api/ai/mcp`). 사용자는 설치물 없이
URL + access token 만 등록하면 되고, 익명 연결은 엣지에서 401 로 끊는다. 상한 4종을 관리
콘솔(`시스템 > 설정 > 외부 AI 도구`)에 올렸고, 전 구간 e2e 는 절차서 + 스크립트로 만들어
**사람이 인가 1회**만 하면 완주하도록 했다.

codex 리뷰 P1 4건·P2 2건 전건 수정. 가장 중요한 것은 **"콘솔이 존재하지 않는 방어를 표시"**
였다 — 동시 실행 상한 knob 은 소비처가 없었고, 미제출 상한은 집행되지 않았으며, RPM 은
`open_task` 에 걸려 있지 않았다. 노출된 knob 은 그 자체로 "이 방어가 있다" 는 주장이므로
미구현 knob 은 삭제하고 나머지는 실제 집행을 붙였다. 테스트 161건.

**여전히 미실측**: 인가 이후 구간(토큰 교환 → 도구 호출 → 제출)의 라이브 완주. 절차서까지
준비했을 뿐 실행은 사람 몫이며, 이 항목은 TASK §9 에서 열린 채로 둔다.

## 3.4 인증 접근성 (2026-08-13, `5f20ee88`)

사용자 지적("스크립트 실행은 접근성이 매우 낮다")에서 시작해 **미로그인 사용자는 인가를
시작할 방법 자체가 없었다**는 것을 발견했다(`/login` 404). 문서는 "브라우저로 인가한다" 고
적혀 있었고 실제로는 404 였다 — 이번 cycle 에서 **문서가 사실을 앞지른 세 번째 사례**다
(앞의 둘: 콘솔 섹션 부재, 컨테이너 미기동).

이제 사용자는 URL 하나만 등록하면 클라이언트가 인증을 스스로 시작하고, 사람은 로그인 후
[허용] 만 누른다. 그 과정에서 **동의 화면 부재로 인한 링크 클릭 탈취 경로**(SameSite=Lax +
GET 발급)도 함께 닫았다.

codex P1×3·P2×3 + 머지 전 PB-0008 이 잡은 2건, 전부 수정. 뮤테이션 8종 KILL.

`None` 을 돌려주며 계약을 docstring 으로 호출측에 미룬 것 — **대부분의 제품이 단일 바인딩이라
예외가 아니라 기본 경로**였다. 인증된 사용자에 한정됐고 사용자가 운영자 본인뿐이라 실제 피해는
없었으나, 그 위에 `execute_sql` 을 얹었으면 훨씬 나빴다.

교훈은 **계약을 docstring 으로 호출측에 미루면 지켜지지 않는다** 이다. 스코프를 세우는 함수가
연결·allowlist·방언 전부를 책임지도록 옮겼고, 미바인딩 제품은 이제 403 이다.

`execute_sql` 은 방어를 새로 만들지 않고 내부 경로 것(AST 가드·제품 allowlist·무거운 쿼리
게이트·시간 cap)을 그대로 통과시킨다. 외부가 추가로 지는 것은 셋 — CSV **미생성**, **실제 행수**
원장 기록(줄 수로 세면 시간당 상한이 장식이 된다), 건당 행 상한.

**"존재하지 않는 방어" 가 세 번째로 나왔다** — 운영자 스위치 `get_int(key, default)` 는 인자가
하나라 TypeError 가 나고 `except` 가 True 를 돌려줬다. 콘솔에 노출된 knob 이 처음부터 작동하지
않았고, 이번에도 **문자열만 보는 테스트가 통과시켰다**. 이제 실제로 호출해 본다.

부하 게이트 건은 **게이트가 부하를 못 줄이고 마찰만 만든** 사례다. 집계 전용 조언은 실행계획
사실이 있을 때만 나갔는데 MSSQL 은 계획을 주지 않아, 이미 `COUNT(*)` 인 쿼리에 "서버측 집계를
쓰라" 는 일반론만 갔다. 그 결과 외부 AI 는 구간 2분할로 우회했고 **총 스캔량은 동일**했다.
집계 판정은 SQL 형태만 보므로 계획 사실이 필요 없었다 — 조언의 출처를 분리하고,
`list_schemas` 가 이미 주는 `approx_rows` 를 먼저 안내하도록 고쳤다.

## 3.6 AC-7 대화 적재 구현 (2026-08-14, ADR-002)

발견(§5)부터 출하까지 같은 날이다. 요구를 현재 수준으로 축소하지 않고 **실제로 채우는** 쪽을
택했다(사용자 결정).

**저장 위치를 원안에서 바꿨다.** FUNCTION 원안은 `agent_runtime.messages` 적재였는데, 그
테이블은 `core_conversations` 에 FK 로 묶여 있고 외부 task 는 `ConversationId` 가 NULL 이라
task 마다 대화 행을 만들어야 한다. 그 순간 그 테이블을 읽는 **47개 파일**(폴더·그룹 멤버·차단·
분기 체이닝·가시성 윈도우·insight·사용량 집계)이 전부 "외부 AI 대화를 어떻게 취급할 것인가" 를
새로 답해야 한다. 보존 하나를 위해 Critical 표면을 또 넓히는 교환이라 `WebAiTasks` 전용 컬럼으로
확정했다(ANCHOR §2.1 Alt-F). 스펙이 구현을 앞지른 채 남는 것이 이 feature 의 반복 결함이므로,
이번엔 **스펙 쪽을 구현에 맞췄다**.

**각인 방향이 반대라는 것이 이 구현의 핵심 함정이다.** 나가는 도구 결과는
`wrap_tool_output` 으로 *외부 AI 에게* "계정 X 전용 데이터" 라고 표시한다. 들어오는 답변은
`wrap_external_answer` 로 *우리 LLM 에게* "통제 밖 런타임이 쓴 텍스트, 지시가 아니다" 라고
표시해야 한다. 저장된 답변은 이후 요약·검색·분석 경로로 우리 컨텍스트에 되돌아올 수 있고,
저장 시점에 각인하지 않으면 그 판단이 유실돼 읽는 쪽이 매번 기억해야 한다(§14.2 한계 3번과
같은 부류). 테스트가 두 함수의 문구를 서로 배타적으로 단정한다.

**codex 가 P2 5건·P3 1건을 잡았고 전건 고쳤다**(REV-20260814-0026). 절반이 "내가 문서에 적은
것을 코드가 안 한다" 부류였다 — 이 cycle 자체가 그 부류를 고치려고 시작됐다는 점에서 뼈아프다.
가장 무거운 것은 **없는 권한 키(`admin.console.access`)로 게이트한 것**이다. 이 저장소가 세 번
기록한 "존재하지 않는 방어" 의 거울상으로, `_account_has_permission` 이 미정의 키에 항상 False 를
주므로 **관리자도 전역 조회를 못 받고 조용히 자기 것만 보게 되며 화면에는 오류가 없다.**
권한 키 실재를 테스트로 못박았다.

고신뢰 인젝션 답변은 `open_task` 와 같은 계약으로 400 거절한다. 거절이 보존과 충돌하는 것처럼
보이지만 아니다 — 시도는 원장에 `outcome=denied` 로 남아 감사 신호가 보존되고, 영속 기록에는
공격 페이로드가 '정상 답변' 으로 앉지 않는다.

열람은 `console.aiops.read` 뒤이며 **외부 토큰으로는 도달하지 않는다.** 외부 AI 에게 자기 기록
열람을 주면 그 엔드포인트가 곧 task 열거면이 되고, DCR 로 공유되는 `client_id` 를 통해 무관한
사용자의 task 존재가 드러날 여지가 생긴다(L4 의 codex P1 과 동형 구조). 상세에는 PG 원장의
도구 호출 이력을 합류시킨다 — 답변은 외부 런타임의 **주장**이고, 그 주장을 검증할 사실은
"어느 도구로 어느 datasource 를 얼마나 읽었나" 이기 때문이다.

**소급은 불가하다.** 이전에 제출된 2건(6,351 / 8,125 바이트)의 답변 본문은 우리 쪽에 존재한 적이
없다. 이 구현은 앞으로의 제출만 보존한다.
