WHY

"SQL 못 쓰는 현업"과 "DBA 병목" 사이의 다리

문제 지금까지

· 현업은 SQL 을 몰라 매번 DBA 에게 요청한다.
· DBA 는 단순 조회 반복 요청에 하루를 쓴다.
· 그렇다고 DB 계정을 직접 주면 — 실수로 UPDATE·DROP 사고 위험.

해결 DQA 가 중개

· 자연어를 받아 SQL 로 번역하고 실행한다.
· 세 겹의 방어로 읽기 전용을 강제한다.
· 역할별로 권한을 잘게 쪼개고, 모든 행위를 감사한다.

현업: 질문만 하면 끝 DBA: 반복 요청에서 해방 보안: 쓰기 불가 + 전수 감사

2단계 probe로 정확히 분류

① TCP 소켓 연결(빠른 실패) → ② 실제 DB SELECT 1. 빠르면 정상, 느리거나(≥1s) 1회 끊기면 불안정, 연속 실패면 끊김으로 분류합니다.

느린 연결도 작업은 계속

타-리전의 느린 DB 는 '불안정' 으로 표시만 하고 작업을 막지 않습니다. 빠른 차단(fast-fail)은 완전히 끊긴 경우에만 적용해, 정상 데이터소스가 굶지 않도록 circuit breaker 로 격리합니다.

SECURITY 1/2 — 구현된 방어

읽기 전용 3겹 방어 · 암호화 · RBAC · 전수 감사

✅ 읽기 전용 3겹 방어

①AST allowlist (sqlglot) — SELECT/CTE 만 허용. INSERT·UPDATE·DELETE·DDL·INTO OUTFILE·xp_cmdshell·다중문 거부.
②DB 최소권한 — datasource 계정은 read-only(MSSQL db_datareader, PG agent_kb_ro). 쓰기 SQL 이 통과해도 DB 가 거부.
③스키마 allowlist + 첨부 sandbox — 제품 허용 DB/스키마 밖은 요청 단위 차단.

✅ 그 외 핵심 통제

✓RBAC 43권한 + console.access 마스터 게이트 + 계정 override.
✓자격증명 envelope 암호화(KEK/DEK) — KEK 는 .env.secret 분리, 평문 비영속.
✓전수 감사(WebAuditEvents) — 관리 변경 same-tx fail-closed, 민감필드 redaction.
✓연결 격리(circuit breaker) + 메타데이터 IP 하드차단 + Caddy TLS + 서울 리전.

AI 가 어떤 SQL 을 만들든 — 문법·DB권한·스키마 화이트리스트 세 겹을 모두 통과해야 하고, 그래도 DB 계정 자체가 읽기 전용이라 쓰기는 물리적으로 불가능합니다.

SECURITY 2/2 — 잠재 이슈 + 대안 (정직성)

완벽한 시스템은 없다 — 잔여 위험과 대안을 함께

S1로그인 rate limiting 부재
현재 · 무제한 시도 가능(brute-force 노출)
계정·IP별 시도 제한 + 실패 N회 잠금/캡차 + 감사 알림
S2MFA(2단계) 부재
현재 · ID/PW 단일 인증
TOTP 등록 + 백업코드(암호화) · 역할별 강제
S3프롬프트 인젝션
현재 · 스키마명·결과가 LLM 맥락에 유입
결과/스키마 escaping·요약 + system prompt 방어문 + 행/시간 상한
S5공유 링크 만료 부재
현재 · 익명 토큰 무기한(수동 폐기)
기본 만료(7일) + 선택적 암호·IP allowlist
S6LLM 비용 quota 부재
현재 · per-user 토큰 상한 없음
일일 토큰 quota(429) + 비용 임계 알림
S8SSRF 사설망 경계 OFF
현재 · 사내 전제 토글 OFF(메타데이터 IP 는 하드차단)
외부 배포 시 토글 ON + host allowlist + 네트워크 세그멘테이션

단계별 보완: Phase 1 CSP·비밀스캔·SQL 미리보기 → Phase 2 rate limit·비밀번호 정책·공유 만료·첨부 검증 → Phase 3 MFA·비용 quota·외부 불변 감사 로그. secure-by-default 가 기본 자세입니다.

Q&A 1/2 — 예상 공격 질문 & 대응

날카로운 질문일수록 구조로 답한다

Q"AI 가 만든 SQL 을 어떻게 믿나? 틀리면 책임은?"
우려 · 환각·오답 → 잘못된 의사결정
단계별 근거+실행 SQL 그대로 노출(검증 가능) · read-only 라 파괴 0 · 로드맵: SQL/EXPLAIN 미리보기·승인. "신뢰하라"가 아니라 "검증 가능하게"
Q"DB 스키마·데이터를 외부 LLM 에 다 넘기는 것 아닌가?"
우려 · AWS 로 데이터 유출
전체 덤프 아님(질문+스키마 메타+결과 일부) · Bedrock 서울·학습 비사용 · 자격증명 게이트웨이 격리 · 필요시 on-prem LLM 교체
Q"프롬프트 인젝션으로 권한 우회·쓰기 가능?"
우려 · LLM 조작으로 가드 우회
권한은 LLM 이 아닌 앱·DB 계정에서 강제 · 인젝션이 성공해도 read-only 계정이 쓰기를 물리적 차단
Q"LLM 비용이 통제 안 되면 청구서 폭탄?"
우려 · 비용 폭주
사용량 대시보드가 모델·역할·계정별 실시간 회계 · 로드맵: 일일 quota+비용 알림 · 저비용 모델 라우팅
Q"그냥 ChatGPT wrapper 아니냐?"
우려 · 차별점 없음
본체는 LLM 이 아니라 거버넌스 인프라(read-only 3겹·RBAC·DB격리·전수감사·KB). LLM 은 교체 가능한 부품
Q"관리자가 다 보는 것 아닌가? 내부자 위협은?"
우려 · 권한 남용
43권한 RBAC + 마스터 게이트 + 모든 관리행위 same-tx 감사(기록 없는 변경 불가) · 로드맵: 외부 불변 로그
Q&A 2/2 — 규제·운영·도입 저항

미구현은 정직하게 로드맵으로, 회의는 파일럿으로

Q"개인정보가 해외로? PIPA 위반 소지?"
우려 · 데이터 잔류·규제
Bedrock 서울 + 결과 원문 비저장 · 일부 모델 global 라우팅은 정직히 명시 → 민감 PII 는 정책 제한·리전고정/on-prem 전환
Q"Bedrock 죽으면 전체 정지? 벤더 종속?"
우려 · 단일 장애점
litellm 추상화로 provider 교체 가능(로드맵: fallback 체인) · DB·관리·감사 등 비-LLM 기능은 무관하게 동작
Q"느린 쿼리로 운영 DB 에 부하?"
우려 · 운영 영향
EXPLAIN pre-gate + 실행시간·행 상한 + read-only + circuit breaker 격리 · 부담 시 replica 등록 권장
Q"DBA 를 대체해 일자리를 없애나?"
우려 · 대체 위협
대체가 아닌 위임 — 단순 조회 자동화로 DBA 가 튜닝·설계·거버넌스에 집중. SQL 검증·권한 설계는 사람의 영역
Q"데모만 잘 되고 실제론 안 되는 것 아니냐?"
우려 · 데모용 가짜
실제 read-only 계정 연결 파일럿(POC) 제안 · 멀티엔진(MySQL·MSSQL) 실연결·라이브 검증 이력
Q"보안팀 승인을 못 받을 텐데?"
우려 · 거버넌스 게이트
보안 섹션(통제+잔여위험·대안)을 검토 패키지로 제공 · 수용 기준에 맞춰 토글·우선순위 조정

대응 총칙 — ① 모르면 만들지 말고 로드맵으로 ② "믿어주세요" 대신 계층·증거로 ③ 회의적 질문은 POC 제안으로 마무리.
