## 1. Blocking issues

### P1-a — 게이트 없는 상한 knob = 거짓 컨트롤
- **Evidence:** `AGENT_WORKER_PG_BUDGET`/`AGENT_WORKER_DS_BUDGET` 가 `_PERF_SPECS` 에 등록되고
  description 이 "동시 커넥션 상한" 을 약속하지만, 그 자원을 `acquire()` 하는 호출 지점이 diff 에
  전혀 없다. `shared/db.py` 는 계측(`incr_conn`)만 하고 게이트가 없으며, 그 계측조차 **누적 생성
  횟수**여서 동시 점유를 표현하지 못한다.
- **Location:** `shared/resource_budget.py:47-50` · `shared/db.py:309-392,903-957`
- **Reason:** 운영자가 상한을 내려도 아무것도 강제되지 않는다. 이 repo 는 같은 이유로
  `attachment.execute_sql_on.*`(enforce 0)를 제거한 선례가 있다(TODOS Tier 3) — 거짓 컨트롤은
  관측·감사 신뢰를 직접 훼손한다.
- **Action(적용):** `RESOURCES` 를 `("llm",)` 로 좁히고 PG/DS knob 을 **제거**했다. 커넥션 총량
  게이트는 T0b(커넥션 수립 지점 배선)로 이연하고, 그 사유를 `RESOURCES` 주석과 `_PERF_SPECS`
  주석에 남겼다. 계측 문구는 "누적 생성 횟수"로 정직화. 회귀 단정 추가:
  `test_no_knob_without_an_enforced_gate`.

### P1-b — LLM 예산 게이트 우회 (기본 설정에서 무효)
- **Evidence:** `semantic_cluster._llm_content_labels` 는 `_cl_conc <= 1 or len(batches) <= 1` 인
  **직렬 경로**에서 `_llm.llm_cluster_label` 을 직접 호출한다(게이트 없음). 기본값이 concurrency==1
  이므로 배포 기본 설정에서 예산이 통째로 우회된다. `product_classify` 의 `llm_product_classify`
  호출도 kill-switch 만 있고 예산 게이트가 없다.
- **Location:** `unit/feature-0002-agent-core/src/modules/semantic_cluster.py:978-995` ·
  `unit/feature-0002-agent-core/src/modules/product_classify.py:179`
- **Reason:** "공유 LLM 총량" 이라는 계약이 실제로는 노드 분석에만 적용돼, 총량을 조여도 클러스터
  라벨·분류 제안이 그 밖에서 계속 호출한다.
- **Action(적용):** 직렬 경로와 `product_classify` 양쪽에 `acquire("llm")` 배선. 거절 시 각각
  affix 폴백 / 해당 datasource skip(멱등 적재라 다음 pass 재시도로 무해).

## 2. Cross-domain concerns

### P2-a — live 상한 상향이 대기자를 깨우지 않음
- **Evidence:** `_COND.notify()` 는 release 경로에만 있다. 상한을 live 로 올려도 깨울 이벤트가 없어
  `timeout>0` 대기자가 timeout 까지 잠든다.
- **Location:** `shared/resource_budget.py:155-168,185-187`
- **Reason:** 현재 호출자는 전부 비차단(timeout=0)이라 실해는 없으나, 후속 호출자가 timeout 을 쓰면
  상한 상향이 즉시 반영되지 않는다.
- **Action(적용):** `_COND.wait(min(remain, _WAIT_POLL_SEC))` — 상한 상향 반영 지연을 0.5초로 bound.

### P2-b — budget 이연이 무기한 pending 을 만들 수 있음
- **Evidence:** budget 분기가 `attempts` 를 증가시키지 않는다. tight loop 는 `next_attempt_at=30s`
  로 막히지만, 지속 contention 이면 그 잡이 영구 `pending` 으로 남는다.
- **Location:** `unit/feature-0002-agent-core/src/modules/node_analysis.py:1560-1567`
- **Reason:** 잡이 영구 pending 이면 run 이 영구 `running` 이고, `enqueue_analysis` 의 dedup 이
  그 run 을 계속 재사용해 **사용자 재트리거가 막힌다**(lease reclaim 대상도 아니다 — 워커
  heartbeat 가 `updated_at` 을 갱신하므로 stale 로도 판정되지 않는다).
- **Action(적용):** **연속** budget 거절이면 `attempts` 를 증가시키고 `max_attempts` 에서
  `budget_exhausted` 로 terminal 종결한다(첫 거절은 무료 — 일시 경합). 상한 도달은 WARNING 으로
  표면화해 운영자가 상한을 올리고 재트리거할 수 있게 한다.

### P3 — 커넥션 hot path 의 lazy import
- **Evidence:** `_worker_conn_incr` 가 매 호출마다 `from . import resource_budget` 를 실행.
  import cycle 은 없으나 커넥션 수립 hot path 에 작은 오버헤드.
- **Location:** `shared/db.py:35-49,903-957`
- **Action(적용):** 모듈 레벨 1회 import + 스텁 폴백(`_perf_counters` 와 동일 패턴)으로 교체.

## 3. Challenge to current spec

기본 설정에서 LLM 상한 16 > 현행 최대 병렬도 12 이므로 노드 게이트 거절은 발생하지 않는다 —
"배포 시점 byte-동치" 주장은 유효하다. 단 그 사실은 **게이트가 실전에서 검증되지 않았다**는 뜻도
된다. 라이브에서 상한을 12 미만으로 내려 `rejected > 0` 과 `budget_deferred` 증가를 1회 관측하는
것이 T0 의 실질 완료 조건이며, TASK-20260730T1235-11 로 남겼다.

`semantic_cluster` 의 `concurrency==1` 동작 순서·실패 처리는 기존과 동일하다(게이트 추가 후에도
배치 순차·실패 시 남은 배치 중단 계약 보존).
