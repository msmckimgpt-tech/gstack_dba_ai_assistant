# TASK-20260903T140000 — 응답하지 않는 AI 를 영원히 기다리던 구조

## 1. 요청 (사용자, 2026-09-03)

> 「결국, 모델을 탐색하는데 실패했다는거네요. 이러한 사실이 사용자에게는 알려지지 않고
>  영원히 기다리게 됩니다. 작동에 이슈가 나타난 사실이 해소되지 않았으니 명백한 오류입니다.
>  근본적인 원인을 해소해주세요.」

**이 지적이 맞고, 앞선 두 cycle 의 범위 설정이 틀렸다.** 그 머신의 `claude` 인증은 사용자
환경 문제지만, **그 실패가 화면에 도달하지 않아 무한정 기다리게 되는 것은 이 제품의 결함**
이다. 앞선 cycle 들은 그것을 「사용자 조작 영역」으로 밀어내고 증상을 열어 둔 채 종료했다.

## 2. 근본 원인 — 설계상 «종결» 이 존재하지 않았다

| # | 관측된 사실 | 근거 |
|---|---|---|
| 1 | 능력 협상 실패는 **모델 선택기만 숨긴다** — 「답할 수 없다」로 취급되지 않음 | `caps.detect_runtimes` 요약 루프 |
| 2 | 그래서 러너가 질문을 **정상 점유**하고 `claude.exe` 가 무한 응답 없음 | 라이브: 300초 timeout·출력 0바이트 |
| 3 | 러너 AI 호출 상한 `_AI_TIMEOUT_SEC` **기본 0 = 무제한** · 무진전 감시 0건 | `base.py` · `grep watchdog` 0건 |
| 4 | 서버 `BRIDGE_NO_PROGRESS_SEC=900` 은 **표시 경계이지 종료 조건이 아니다** | `bridge_tasks.py` 주석 명시 |
| 5 | lease 30분 만료 → **재배달**. 시도 횟수 상한·종결 상태 **없음** | `CLAIMABLE_SQL` · `grep ClaimAttempts` 0건 |

즉 **15분 안내 → 30분 재배달 → 반복**. 사용자 표현 그대로 「영원히」다.

그 머신의 `claude` 상태(참고, 우리 범위 밖): `claude.exe --version` 0.1초 정상이나 `-p` 는
argv/stdin × 플래그 유무 **4조합 전부 무응답**, 300초 여유에서도 **무한 hang**. 디버그 로그
**전 세션**에 `oauth/token status=400`(세션당 최대 26회 재시도).

## 3. 설계 — 되돌린 판단을 함께 적는다

초판 설계는 **「무출력 N초면 끊는다」** 였고 **틀렸다**:

- `claude -p` 는 답을 **끝에 한 번에** 낸다 → 무출력이 「생각 중」과 「멈춤」을 가르지 못한다.
- 고정 상한은 실제로 **27단계 조사를 죽인 이력**이 있다(그래서 기본값이 0이 됐다).

그래서 **시간이 아니라 관측된 건강 상태**로 가른다:

| 러너 상태 | 상한 | 근거 |
|---|---|---|
| 건강함(기본) | **종전 그대로 무제한** | 일하는 AI 를 끊지 않는다 — 회귀 0 |
| 응답 없음이 **관측됨** | `_AI_UNHEALTHY_TIMEOUT_SEC`(150초) | 유한 종결 + 다음 행동 안내 |

**자기 치유가 이 설계의 핵심**이다. 「못 쓴다」로 판정돼도 그 짧은 상한 안에서 **계속
시도**하므로, 실제로 복구되면 성공 1회로 **즉시** 정상 복귀한다 — 영구 잠김이 없다.
(「아프면 아예 거절」은 성공의 근거가 질문 처리뿐이라 **교착**이 된다. 그래서 채택하지 않았다.)

## 6. 검증에서 배운 것 (자기 실수 3건)

1. **뮤테이션 스윕이 중단되며 소스에 뮤테이션이 남았다**(`_cap = None`). 발견 후 복원하고,
   이후 스윕은 `finally` 로 전 파일 복원을 보장하게 바꿨다 — 실제로 다음 중단에서 그것이
   작동했다(앵커 전건·잔재 마커 0 확인). **검증 도구가 코드를 오염시킬 수 있다**는 것을
   실물로 겪었다.
2. **매달리는 테스트를 썼다.** 자식을 `sleep(600)` 으로 둬서, 상한이 사라지는 회귀에서 이
   테스트는 실패하지 않고 **600초 매달렸다**(스윕이 그 자리에서 죽었다). 매달리는 테스트는
   실패하는 테스트보다 나쁘다 — 무엇이 깨졌는지 말하지 않으면서 파이프라인을 멈춘다.
   자식 수명을 유한하게(25초) 두고 판정을 **경과 시간**으로 바꿨다.
3. **배선 공백 2건이 1차 스윕에서 살아남았다**(G3·G8). 판정 함수의 «계산»만 단정하면 그
   함수를 **부르는 자리**가 사라져도 전부 통과한다 — 이 저장소가 반복해서 겪은 부류이고,
   이번에도 같은 함정에 빠졌다. 행위 단정 2건을 추가해 닫았다.

## 7. 이월 — 이 cycle 이 닫지 않은 유한성 (명시)

**러너가 답을 제출조차 못 하는 경우**(프로세스 강제 종료·머신 절전·네트워크 단절)는 여전히
서버의 lease 만료 → 재배달 경로를 탄다. 그 축의 종결은 **서버가** 해야 한다(진행 신호를
보는 쪽이 서버뿐이므로):

- 점유 시도 횟수 상한(`ClaimAttempts`) 또는 무진전 하드 마감 → 정직한 안내로 **종결**
- ⚠ 스키마 추가가 필요하고, **fast path ALTER**(`_ensure_seed_catchup`)에 둬야 기존 운영 DB 에
  생긴다(`BridgeDefaultModel` 선례: slow path 전용이면 「테스트 전통과 + 기능 영구 폴백」)

이 cycle 은 **러너가 살아 있는 경우**의 무한 대기를 닫는다. 그것이 사용자가 실제로 겪은
경로다(러너는 멀쩡히 하트비트를 보내고 있었다). 남은 축은 별 cycle 로 둔다 — 여기서 함께
하면 스키마 변경까지 한 cycle 에 들어가 검증이 얕아진다.
