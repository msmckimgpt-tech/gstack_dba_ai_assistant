# Run 2026-09-07T18:00:00+09:00 — 라이브 배포 실측 (업데이트 채널)

`main` 697ffa84 배포본에서 **채널을 수신측 시선으로** 실측한 기록. 코드 완료(머지)와

## 무엇을 재려고 했나

배포 후 남는 미지수는 셋이었다. ① 호스트 릴리스 디렉토리가 컨테이너 안으로 **정말** 들어오는가
(compose 앵커를 고쳤을 뿐 실물을 본 적은 없다) ② 라우트가 **없는 것을 광고하지 않는가**
③ 올린 바이트가 **바뀌지 않고** 내려오는가. ①②는 릴리스 없이도 재지고, ③은 실물이 있어야 한다.

## 방법 — 그리고 그 방법이 실제로 연 창 (적대 리뷰 P1-1 정정)

실 설치기는 Windows 빌드 머신이 없어 없다. 그래서 **1.0.0** 으로 합성 파일(1,200,004 bytes,
`MZ` 매직)을 만들어 **실제 라이브 채널에** 퍼블리시하고, 검증 후 제거했다.
버전을 정본(`1.1.0`)보다 낮게 잡은 것은 의도였다 — `is_newer("1.0.0","1.1.0") = False` 이므로
`updater.py` 자동 갱신 경로는 그 합성물을 **집지 않는다**.

⚠ **그 안전판은 updater 경로만 덮는다. 사람용 다운로드 표면은 그 밖에 있었다.**
`client_release.download_url()` 은 릴리스가 **존재하면** URL 을 돌려주고 **버전을 비교하지
않는다**(`client_release.py:164`). `oauth_as._client_download_url` → `_connect_steps.py:45`
`if not connected and client_download:` 가 그것으로 「연결 프로그램 받기」 버튼을 만든다.
따라서 노출 창 동안 **미연결 사용자가 연결 화면을 열었다면 설치기가 아닌 파일을 받을 수 있었다.**

노출 창 실측(`docker compose logs web-a --timestamps`):

| 시각(UTC) | 사건 |
|---|---|
| 08:58:06 | `publish_release.py` 가 `manifest.json` 을 씀 — **여기서 창이 열린다** |
| 08:58:18.65 | `/api/ai/client/latest` **200** (첫 관측) · `/client/…-1.0.0.exe` **200** |
| 08:58:43.9 | 파일 2개 삭제 (릴리스 디렉토리 mtime) — **여기서 창이 닫힌다** |
| 08:58:44.87 | 두 경로 모두 **404** 로 복귀 확인 |

**창 = 약 38초**(200 관측 구간 26.2초). 그 창에 실제 사용자 세션이 라이브에 붙어 있었다 —
caddy 액세스 로그에 `remote_ip 172.26.144.1` / `Microsoft Edge WebView2`(= DQA Connect 내장 셸)
요청이 08:52:45 · 08:52:48 · 08:53:16 · 08:57:15 에 있고 09:01:59 에 새 세션이 붙었다.
그 38초 안에 연결 화면을 연 사람이 없었던 것은 **설계가 아니라 운**이다.
피해 여부는 실측으로 확인했다 — 그 창의 `/client/` 요청은 **내 프로브 1건뿐**이고 외부
클라이언트(`dqa-connect-agent/1`)의 매니페스트 요청은 **0건**이다.

**다음부터의 방법**: 라이브 릴리스 디렉토리를 쓰지 않는다. `CLIENT_RELEASE_DIR` 을 다른
디렉토리로 가리킨 **격리 인스턴스**에서 잰다 — 그러면 창 자체가 없다.

**#5 는 실패할 수 있는 축이 아니다 — PASS 로 세지 않는다.** 기록된 본문이 그것을 스스로
말하고 있었다: 이 라우트의 404 는 `{"error":"not_found"}` 인데(#4·#8·#9 가 받은 것) #5 가 받은
것은 `{"detail":"Not Found"}` = **Starlette 의 라우트 미매칭** 응답이다. `/client/{filename}` 의
`{filename}` 은 단일 세그먼트 컨버터라 다중 세그먼트 경로는 **어떤 코드 상태에서도** 이 핸들러에
닿지 않는다. 즉 이 칸은 내 가드를 한 번도 타지 않았고, 되돌려서 FAIL 시킬 수도 없다.
실제 traversal 방어는 `current_release()` 의 `target.resolve().parent != base.resolve()`
(`client_release.py:130`)이며 그것은 URL 이 아니라 **매니페스트가 선언한 파일명**으로만 도달한다 —
그 축을 재려면 traversal 파일명을 담은 매니페스트가 필요하고, 그건 재지 않았다.
**그래서 이 표의 실측 결론은 10 PASS + 1 미경유다.**

#9 가 이 표에서 가장 값이 나가는 칸이다. `StaticFiles` 마운트를 라우트로 바꾼 이유가 바로
그것이고, 마운트 시절이라면 `manifest.json` 은 **200 으로 내려갔다**. #10 도 축이 하나 더 있다 —
「모른다」와 「최신이다」를 같은 값으로 접으면 첫 판정이 오류로 위장하는데, 빈 이유 문자열이
그 둘을 갈라놓고 있음을 실측이 확인한다.

## 배포 중 관측한 두 가지 (둘 다 이 cycle 의 코드와 무관)

**(1) 1차 배포는 ABORT 했다 — caddy exec 채널 파손.** 로그의 표면 문구는
「web-b 가 엣지 후보로 복귀하지 않았다 — 지금 web-a 를 내리면 upstream 0」 이었다. 그러나
같은 순간 `https://localhost/healthz` 는 200 이고 caddy 프로세스도 살아 있었다(`/proc/<pid>/exe`).
실인과는 `docker compose exec -T caddy …` 가 `procReady not received` 로 죽는 것 —
uptime 4일 컨테이너의 **exec 채널만** 파손된 상태다. 스크립트는 그 채널로 Caddy admin API 를
읽으므로 「업스트림이 안 돌아왔다」로 보이고, 과거 같은 파손은 「rootCA 회전 누락」으로도
위장한 적이 있다. `restart caddy` 한 번으로 복구하고 재실행(멱등)해 완주했다.
**증상이 어느 쪽으로도 위장하니 deploy-web 의 ABORT 는 exec 채널부터 의심한다.**

**(2) 배포 창 안에 13초 엣지 정지가 한 번 있었다 — 행위 종류는 특정했고, 행위자는 못 했다.**
caddy 08:58:10.5Z SIGTERM → 08:58:23.6Z `serving initial configuration`(그 사이 :443 은 연결 거부).

**행위 종류는 특정된다** — `docker inspect` 가 `created=2026-08-28T09:01:12Z` ·
`RestartCount=0` · `StartedAt=2026-09-07T08:58:22Z` 이고 `docker ps -a` 에 caddy 컨테이너는
1개다. 즉 **기존 컨테이너의 stop/start** 이며 recreate 가 아니다. 이것이 `deploy-web.sh` 의
모든 `--force-recreate`/`up -d` 경로를 배제하고, 다른 컨테이너가 `Up 4 days` 를 유지했으므로
도커 데몬 재시작도 배제한다.

**남은 배제 논거를 정정한다** (적대 리뷰 P2-2):
- ① 배포 스크립트: 배제 근거는 로그 한 줄 —
  「Caddyfile 무변경(sha 일치) + 이미지 일치 — caddy 유지(blip 0)」 + 위 컨테이너 동일성.
  ~~「모든 compose 호출이 `--no-deps` 라서」~~ 는 근거가 못 된다 — `--no-deps` 는 *의존
  서비스* 를 안 건드린다는 뜻이고 caddy 는 아무의 의존 서비스가 아니다(오히려
  `depends_on: [web-a, web-b]`). 실제로 스크립트는 `--no-deps` 를 붙인 채 caddy 를 **직접**
  만지는 경로를 셋 갖는다(`:923` `:937` `:953`). 다만 그 셋은 전부 recreate 이므로 위
  컨테이너 동일성이 배제한다.
- ② 내 세션: **자기 배제는 성립하지 않는다.** 알려진 내 `restart` 는 08:50:48Z 1회이고 그
  짝(→08:51:01Z)이 로그에 따로 남아 있지만, 「짝이 하나 있다」에서 「두 번째는 내가 아니다」는
  나오지 않는다. 더구나 **같은 세션이 08:58:18~08:58:43 에 라이브 릴리스 디렉토리를 조작
  중이었다**(위 노출 창). 그 병존을 적지 않은 채 남의 세션을 지목하는 것은 정직하지 않다.
  내가 말할 수 있는 것은 「내가 낸 명령 중 caddy 를 재시작하는 것은 08:50:48Z 그 하나다」까지다.
- ③ 이 cycle 의 compose 변경: 배제 **성립**. `x-web-extra` 앵커는 web-a/web-b 만 참조하고
  caddy 서비스 블록은 그 앵커를 쓰지 않는다.
- ④ 탐색 범위: 호스트 cron·systemd timer·`bin/**` 에 caddy 재시작이 없다. ⚠ **`Makefile` 을
  빠뜨렸었다** — `Makefile:172`(`make up`) · `:539`(`web-down`) · `:567`(`web-tls-down`) 에
  `stop caddy` 가 있다. 즉 병행 세션의 `make up` 류가 그 stop/start 를 낼 수 있는 경로다.
  가능한 경로를 찾은 것이지 **그 경로가 발화했다는 증거는 없다**.

`docker events` 는 과거를 보관하지 않아 **행위자는 특정하지 못했다.** 추정을 실측으로 적지 않는다.

**사용자 영향**: 그 13초 창에 caddy 액세스 로그가 받은 요청은 **0건**이다(08:57:15 다음 요청이
09:01:59). 연결 거부를 실제로 만난 사용자는 관측되지 않았다.

⚠ **이 관측이 체크리스트 [5] 의 해석을 바꾼다.** `no upstreams available` 카운트는 **0** 이었지만
그 지표는 「Caddy 가 건강한 업스트림을 못 찾은 횟수」라서 **Caddy 자신이 죽은 구간은 애초에 셀 수
없다**. 그리고 뒤 절도 과했다 — 롤링 창(08:51~08:57)에 caddy 가 받은 요청은 정적 파일 4건뿐이므로
업스트림이 0 이었더라도 **그것을 발화시킬 요청이 거의 없었다.** 정확히 말하면: 0 은 **그 창에
요청이 있었다는 전제 아래에서만** 롤링 속도의 약한 증거이고, 요청 수를 함께 세지 않으면 아무
증거도 아니다. 동반 지표를 함께 세야 한다 —
`logs caddy --since <창> | grep -c 'handled request'`.

## 여전히 재지 못한 것

- ⛔ **엣지(caddy) 경유의 릴리스 200 / 다운로드 경로.** 위 표는 전부 컨테이너 내부 포트다.
  caddy 액세스 로그에 이 두 경로의 200 은 **한 건도 없다**(있는 4건은 전부 404). 재현하려면
  노출 창을 다시 열어야 하므로 **첫 실 릴리스 때 재는 것이 옳다** — 그때는 창이 정당하다.
- ⛔ **web-b 의 채널.** 프로브 0건. 두 replica 는 같은 이미지·같은 마운트 선언이지만
  「같은 선언」과 「같은 실물」은 이 cycle 이 통째로 구별하자고 만든 축이다.
- ⛔ **연결 화면의 「연결 프로그램 받기」 버튼 (배포 후 체크리스트 [4] — PB-0008).**
  체크리스트 [4] 는 「백엔드 API 뿐 아니라 사용자가 실제 쓰는 경로를 라이브 배포본에서 PB-0008
  로 검증한다」고 요구하는데, 위 표는 **전부 백엔드 fetch** 다. `Environment:
  Windows-browser 없음 — 웹 자산 변경 0건` 은 **check #13**(자산 변경 시각검증)의 면제 논거이며
  **[4] 의 면제가 아니다** — 둘을 같은 것으로 접었었다. 그리고 이 cycle 의 사용자 표면이 바로
  그 버튼이고, 그것은 위 38초 동안 **실제로 나타났다가 사라졌는데 아무도 브라우저로 보지 않았다.**
  릴리스 0 상태에서는 「미표시」만 관측 가능하므로, 표시↔미표시 **전환**은 첫 실 릴리스 때 잰다.
