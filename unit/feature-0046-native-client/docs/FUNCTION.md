# Function

## 1. Summary

**Windows 네이티브 클라이언트** — 사용자가 터미널을 열지 않고 자기 AI 를 이 서비스에 연결한다.
`bridge_setup.ps1`(669행 PowerShell)이 하던 일을 **같은 계약으로** 하되 껍데기를 GUI 로 바꾼다.

사용자가 하는 일: **설치 파일 실행 → 쓸 AI 선택 → [로그인] → [연결]**. 끝.

## 2. Goal

- REQ-20260903-native-client: 「AI 연결」의 터미널 의존을 제거한다. 근본 원인은
  `docs/improvements/onboarding-accessibility/RESEARCH.md` §9.1 — **연결을 우리가 만든
  배포물로 구현하고 런타임·설치 UX·설정 UI·업데이트 채널을 전부 자체 구현해 넷 모두가 마찰이 됐다.**

## 3. In Scope

### P0-A. 계약은 그대로, 껍데기만 교체

`bridge_setup.ps1` 과 **같은 순서·같은 대조·같은 중단 지점**:

1. 사내 CA 수신 → **DER 지문** 대조 (파일 해시가 아니다 — 그 혼동이 feature-0006 REQ-0286 의 실측 결함)
2. `bridge_agent.py` 수신 → sha256 대조
3. `--check` 로 연결 확인 (**상주 전에**)
4. 통과하면 러너 상주

CA 는 **평문 HTTP** 로 받는다(부트스트랩 데드락 — 엣지 인증서를 서명한 것이 그 CA 다).
그 위험은 지문 대조가 덮는다. 전역 신뢰 저장소는 **건드리지 않는다.**

### P0-B. 로그인은 **「위임」이 아니라 「대행 실행」** (ROADMAP §0.1 불변 제약)

2026년에 3사가 구독 OAuth 의 제3자 사용을 차단했다 — Anthropic 2026-04-04, Google 은
2026-02 에 **유료 구독자 계정을 정지**했다. 그래서 클라이언트는 **벤더 공식 명령을 subprocess 로
띄우고 종료코드로 판정할 뿐, 토큰을 읽지도 저장하지도 중계하지도 않는다.**

| CLI | 로그인 | 상태 | 로그인됨 | 미로그인 |
|---|---|---|---|---|
| claude | `claude auth login` | `claude auth status` | exit 0 + JSON `loggedIn:true` | exit 1 |
| codex | `codex login` | `codex login status` | exit 0 | exit 1 |
| gemini | — | — | **미실측** → 「감지·안내」로 강등 |

`test_client_never_touches_vendor_credentials` 가 이 경계를 잠근다.

### P0-C. 연결 축과 AI 축을 **갈라 말한다**

러너 `--check` 의 **종료코드 4 = 「서버 연결은 정상인데 쓸 수 있는 AI 가 없다」**. 이것을 「연결
확인 실패」로 뭉치면 사용자는 서버를 의심한다(feature-0043 REQ-20260901-win-ai-detect 의 실제 제보).

### P0-D. 감지는 **PATH 밖 표준 위치까지**

실측 2026-09-01: Claude Code 의 Windows 설치기는 `%USERPROFILE%\.local\bin\claude.exe` 에 넣는데
**그 폴더가 사용자 PATH 에 없었다.** `shutil.which` 만 쓰면 설치돼 있는데 「없음」이 된다.
Microsoft Store 앱 실행 별칭 스텁(`\WindowsApps\`)은 「있다」로 세지 않는다.

### P0-E. 토큰은 **환경변수로만**

명령줄에 실으면 프로세스 목록에 뜬다. `check_connection`·`spawn_runner` 둘 다 `BRIDGE_TOKEN` env.

### P0-F. GUI 앱은 **콘솔로 말하지 않는다** (실 Windows 실측 2026-09-03)

`--windowed` PyInstaller 빌드는 `sys.stdout` 이 `None` 이다. `print()` 를 부르면 예외 → 미처리
예외 대화상자 → **프로세스가 사용자 입력을 기다리며 멈춘다**(실제로 그렇게 걸려 강제 종료했다).
사용자 안내는 `tell()`(tkinter messagebox)로 한다.

### P0-G. 진입점은 **패키지 밖**이다 (실 Windows 실측 2026-09-03)

PyInstaller 는 진입 파일을 `__package__` 없는 최상위 스크립트로 돌린다. 따라서 진입점에
상대 임포트가 있으면 **exe 는 실행되지 않는다** — 종전 빌드가 그 상태였고 오류 대화상자만
띄웠다. 진입점은 `src/dqa_connect.py`(패키지 밖·절대 임포트)이고 빌드는 `--paths src` 를 준다.
`client/__main__.py` 는 `python -m client` 전용으로 남는다 — 그 경로는 부모 패키지가 있다.

### P0-H. 무결성 값은 **서버 봉투를 받아들인다**

서버는 CA 지문을 OpenSSL 관례(대문자·콜론)로 내고 클라이언트는 `hashlib` 기본(소문자·
구분자 없음)으로 계산한다. 두 모양을 `normalize_fingerprint()` 로 줄여 비교한다 — CA 축과
러너 체크섬 축 **둘 다**. 정규화는 표기만 지우고 값은 지우지 않는다(다른 인증서·잘린 지문은
여전히 거부). 이것이 없어 클라이언트는 **한 번도 연결에 성공할 수 없었다**(2026-09-03).

### P0-I. 빌드는 **레거시 콘솔 코드페이지에서도 성공을 성공이라 보고한다**

빌드 스크립트는 Windows 를 강제하는데, 비영어권 Windows 의 기본 콘솔은 UTF-8 이 아니다.
표준 스트림의 `errors` 를 `replace` 로 낮춰, 출력 때문에 종료 코드가 실패가 되지 않게 한다.
`encoding` 은 바꾸지 않는다 — 바꾸면 한글이 통째로 깨진다.

### P0-J. 배포 형식 = **설치 마법사 + 런타임 동봉** (사용자 결정 2026-09-03)

포터블 단일 exe(`--onefile`)를 버리고 중소 데스크톱 앱의 표준 형식으로 옮겼다.

    DQAConnect-Setup-1.0.0.exe        ← Inno Setup, per-user(관리자 불필요)
      └ %LOCALAPPDATA%\Programs\DQA Connect\
          DQAConnect.exe · _internal\ · runtime\python.exe

**러너용 인터프리터 동봉이 종속성 문제의 근본 해소다.** 러너는 파이썬 스크립트인데
`sys.executable` 은 동결 시 파이썬이 아니라 앱 실행 파일 자신이라, 종전 배포본은 러너를
실행하지 못했다(실측 exit=2 → 화면엔 「연결 확인에 실패했습니다(코드 2)」). 옆에 진짜
`python.exe` 를 두면 그 함정도, PyInstaller 가 못 보는 러너 모듈을 추측하는 일도 사라진다.

⚠ **동봉하는 것은 인터프리터지 러너가 아니다.** 러너는 여전히 서버에서 받아 체크섬을
대조한다 — 동봉하면 서버 배포와 클라이언트 배포가 갈려 「고쳤는데 그대로」가 재발한다.

부수 효과: onefile 의 매 실행 임시폴더 압축해제가 사라져 시작이 빨라지고 백신 오탐이 줄며,
시작 메뉴·제거 프로그램·자동 시작(기본 꺼짐)이 표준으로 붙는다. SmartScreen 경고는 설치
1회로 끝난다 — 단일 exe 를 매번 실행하던 종전보다 나아진 점이다.

### P0-K. AI 는 **Windows 와 WSL 양쪽**에서 찾는다

사용자 제보 2026-09-03: 「기존에 쓰던 LLM 접근 수단(WSL)에 진입할 수 없다」. 클라이언트가
Windows PATH·설치 폴더만 봐서, WSL 안의 CLI 에 도달하지 못했다.

`discover_runtime(name)` 이 두 자리를 **모두** 돌려준다. 첫 자리에서 멈추지 않는 이유:
하필 그 자리가 못 쓰는 쪽일 때 **쓸 수 있는 것이 있는데도** 「없다」가 된다.

WSL 런타임은 러너가 직접 부를 수 없다(러너는 Windows 파이썬으로 돈다). 그래서 러너가 이미
가진 계약 `--cmd 'my-ai -p {prompt}'` 로 넘긴다 — **러너를 고치지 않는다**.
⚠ 대가: `--cmd` 를 주면 러너는 능력을 신고하지 않아 웹의 「답할 AI 있음」이 ❌ 로 남는다.
답변은 정상으로 오간다. 이 간극은 러너가 WSL 자리를 직접 아는 날 사라진다.

### P0-L. **인증 상태는 가용성의 증거가 아니다**

종전 화면은 `auth status` 만 보고 「연결할 준비가 되었습니다」라고 했다. 실측에서 그 판정이
틀렸다 — 로그인돼 있는데 답을 받지 못하는 런타임이 있었다.

`verify_answers()` 가 **실제로 한 번 물어보고** `answers` 를 채운다. 화면·선택은 `usable`
(= 설치됨 + 답함)만 본다. 답하지 못한 런타임은 **감추지 않고** 그 사실을 말한다.

⚠ 이 호출은 사용자의 AI 사용량을 쓴다. 그래서 질문을 최소로 한다.

⚠ 질문 인자는 **런타임마다 다르다**(`_ASK_ARGV`). 정본은 러너 `_RUNTIME_SPECS` 이고 여기는
사본이며 테스트가 대조한다. 실측: 전부 `-p` 로 뭉뚱그렸더니 `codex` 가 0.1초에 실패해
**쓸 수 있는 런타임이 배제**됐다(codex 는 `exec` 하위명령).

### P0-M. 웹의 인계를 **받는다** — `dqa-connect://`

설치기가 스킴을 HKCU 에 등록하고(제거 시 삭제), 진입점이 URL 을 파싱한다. 받아들이는 것은
연결 4값뿐이고 그마저 이후 단계가 다시 검증한다.

⚠ 이것이 없어 실제로 일어난 일: 사용자가 [연결 준비] → [내 AI 실행] 을 눌렀는데
**「연결 정보가 없습니다」**만 떴다. 브라우저는 스킴 핸들러 부재를 감지하지 못한다.

### P0-N. 테스트도 **명칭 정본을 읽는다**

옛 스킴·옛 이름을 테스트에 리터럴로 적지 않는다. `feature-0043/tests/test_name_ssot.py` 가
허용 목록 밖 소스에서 옛 이름을 찾으면 실패시키는데, 거기에 예외를 뚫으면 그 파일이 개명
게이트의 **사각지대**가 되어 다음 개명 때 조용히 남는다. 정본에서 읽으면 함께 따라간다.

### P0-O. 딥링크는 **연결에 필요한 값을 모두** 싣는다

`dqa-connect://start?token=…&base=…&ca_sha256=…&agent_sha256=…`.

⚠ 종전에는 토큰만 실렸다. 그 딥링크는 **셸 설치본용**이고, 그 경로는 설치 때 서버 주소와
CA 를 디스크에 심으므로 토큰만 받으면 됐다. 네이티브 클라이언트에는 그 사전 상태가 없어
서버가 어디인지 몰랐고, 화면에는 「연결 정보가 없습니다」만 떴다.

조립은 정본 `shared/dqa_identity.scheme_url()` 한 곳이다. 셸 핸들러는
`[?&]token=([^&]+)` 로 토큰만 뽑으므로 파라미터 추가에 영향받지 않는다(테스트로 잠금).

### P0-P. 서버 주소는 **처음 연결한 곳으로 고정**한다 (TOFU)

딥링크의 `base` 를 그대로 믿으면, 남이 만든 링크를 클릭한 사용자가 공격자 서버에서 러너를
받게 된다. CA 지문 대조는 이 경우 방어가 되지 않는다 — 지문도 같은 URL 에서 오기 때문이다.

그래서 처음 연결한 서버를 홈에 적어 두고(**연결 성공 후에만**), 다른 주소가 오면 두 주소를
나란히 보여 주고 묻는다. 물을 수 없는 환경이면 **아니오**로 읽는다.

첫 연결은 물을 근거가 없어 통과시킨다 — 종전 복사·붙여넣기 경로와 같은 신뢰 수준이다.
이것은 완전한 해소가 아니라 **위험을 첫 1회로 좁힌** 것이다.

### P0-Q. 웹은 **클라이언트를 주 경로**로 보인다

터미널 1·2·3단계는 접는다(사용자 결정 2026-09-03). ⚠ **없애지 않는다** — 연결 프로그램을
설치하지 않은 사용자에게는 그것이 유일한 길이다. 그리고 실행 실패 안내가 「1단계 명령」으로
되돌려 보내므로, 그 경로는 접힌 블록을 **자동으로 펼친다**. 되돌아갈 길을 가리키면서 그
길을 닫아 두면 막다른 길이다.

### P0-R. 안내가 가리키는 것은 **그 화면에 실재해야** 한다

「[내 AI 실행] 을 누르면」 이라고 쓰면 그 화면에 그 버튼이 있어야 한다. 문구만 바꾸고 버튼을
안 넣으면 사용자는 없는 것을 찾는다 — 실제로 그렇게 냈다(2026-09-03).

테스트는 문구를 찾으면 **버튼 실재 + 배선 + 기본 숨김**까지 확인한다. 문구가 있다는 것과
그것이 가리키는 대상이 있다는 것은 다른 축이다.

### P0-S. 화면은 **서비스에 하나** — 클라이언트는 로컬 능력만

「Slack 같은 웹 기반」 요구의 답은 UI 를 클라이언트에 넣는 것이 아니다. 이 프로젝트는 러너에
대해 이미 그 구조를 기각했다 — *동봉하면 서버 배포와 클라이언트 배포가 갈려 「고쳤는데
그대로」가 재발한다*. UI 도 같다.

그래서 클라이언트는 `127.0.0.1` 에 브리지를 열고, **서비스 페이지가 그것을 부른다**. 화면을
고칠 때 설치본을 다시 배포하지 않아도 된다.

⚠ 이것은 **새 공격 표면**이다. 방어 네 겹: loopback 바인딩 + 임의 포트 · 실행마다 새 nonce ·
origin 고정 · **프로세스를 띄우는 동작은 네이티브 확인창**. XSS 가 생기면 앞의 셋은 뚫리므로
마지막 겹이 실질 방어선이며, 그 동작 집합이 실제 위험 동작을 덮는지 테스트가 대조한다.

### P0-T. 앱 창은 **기본 브라우저**로 연다

화면은 서비스에 있고 그 화면은 로그인 세션을 요구한다. 사용자가 방금 그 서비스를 보던
브라우저의 **기본 프로필**로 열어야 세션이 따라온다. `--user-data-dir` 를 주면 새 프로필이라
세션이 없다 — 「터미널을 없앤다」고 해 놓고 로그인을 하나 더 만드는 셈이다.

기본 브라우저 이름을 추측하지 않는다 — Windows 가 기록한 https 핸들러에서 읽는다.
`--app` 을 모르는 기본 브라우저면 크로미움 계열로 내려가되 **세션이 없을 수 있다고 말한다**.
아무것도 없으면 tkinter 폴백 — 창이 안 뜨면 사용자는 프로그램이 죽은 줄 안다.
### P0-AC. **상주는 알림 영역에서** — 창은 선택 사항이다 (사용자 요청 2026-09-04)

이 프로그램은 연결이 유지되는 동안 **계속 떠 있어야** 한다(러너가 자식 프로세스다). 종전에는
그 상주가 **창 하나**로만 표현돼, 쓰지도 않는 창을 작업 표시줄에 계속 두어야 했고 닫으면
연결이 끊겼다. 상주 프로그램의 표준 자리는 알림 영역이다.

`client/tray.py` — **표준 라이브러리만**(`ctypes` → `Shell_NotifyIconW`). `pystray` 는
아이콘 비트맵 때문에 `Pillow` 를 끌고 오는데, 알림 영역 아이콘 하나에 번들 수십 MB 와
백신 오탐 표면을 치를 값이 아니다(ANCHOR §1 「부품 하나로 끝난다」와 같은 근거). 아이콘은
**우리 exe 안에 이미 있는 것**을 꺼내 쓴다(`ExtractIconW`) — 새로 그리지 않는다.

- [X] → **숨는다.** 연결은 유지된다. 어디로 갔는지 풍선으로 **한 번만** 알린다.
- 오른쪽 클릭 → `창 열기` · `연결 끊기`/`다시 연결`(상태에 따라 라벨이 바뀐다) · `종료`.
- 두 번 클릭 → `창 열기`(기본 항목, 굵게).
- 툴팁이 현재 상태를 말한다 — 창을 열지 않고도 「연결됨」인지 보인다.
- 아이콘은 **배포본 exe 안의 것**(`ExtractIconW`)이다. 동결 빌드에서 실측 확인했다
  (`icon_count=1`, 유효 핸들). 추출이 실패하면 `IDI_APPLICATION` 으로 폴백하므로
  **아이콘이 사라지지는 않는다** — 최악이 「기본 아이콘으로 뜬다」다.

⚠ **트레이를 못 세우면 그 동작을 켜지 않는다.** `Tray.start()` 가 거짓을 내면 [X] 는 종전대로
**종료**이고, 화면 문구도 「이 창을 닫으면 연결이 끊깁니다」로 남는다. 트레이 없이 숨기면
사용자는 프로그램을 잃는다 — 화면에도 알림 영역에도 없고 작업 관리자로만 끌 수 있다.
그래서 「닫아도 유지됩니다」는 **트레이가 실제로 떠 있을 때만** 하는 말이다(P0-R).

#### P0-AC-1. 상주는 **두 껍데기 공통**이다 (사용자 요청 2026-09-04 재구성)

화면은 서비스에 하나(P0-S)이고 껍데기는 둘이다 — 웹 셸(주)과 tkinter(폴백). **사용자에게
이 프로그램은 하나이므로 상주 규약도 하나여야 한다.** 어느 껍데기로 떴는지는 우리 사정이지
사용자 사정이 아니고, 두 표면이 다르게 굴면 그 차이를 배우는 비용을 사용자가 낸다.

| | 웹 셸 (주) | tkinter (폴백) |
|---|---|---|
| 창을 닫으면 | 알림 영역에 남는다 | 알림 영역에 남는다 |
| 메뉴 | 창 열기 · 연결 끊기 · 종료 | 창 열기 · 연결 끊기/다시 연결 · 종료 |
| 완전 종료 | 아이콘 [종료] | 아이콘 [종료] |
| 트레이 불가 시 | **유휴 90초 뒤 종료**(종전 계약) | **닫기 = 종료**(종전 계약) |

⚠ **상주 중에는 유휴가 종료 사유가 아니다.** 웹 셸의 수명 신호는 「패널이 말을 걸어오는가」
인데, 패널을 닫아 두고 쓰는 것이 바로 상주의 의미다. 그래서 아이콘이 살아 있는 동안에는
유휴 한도를 적용하지 않고, **아이콘이 없거나 뜬 뒤 죽으면 종전 계약으로 되돌아간다** —
상주할 표면이 없는데 계속 살아 있으면 사용자가 끌 수단이 없다.

⚠ **웹 셸 트레이에 「다시 연결」이 없는 것은 의도다.** 이 경로에서 연결을 거는 곳은
**패널**(`bridge._do_connect`)이다. 트레이가 자체 재연결을 가지면 같은 동작의 입구가 둘이
되고 그 둘은 서로 다른 코드패스로 갈라진다. 트레이는 **패널을 다시 열어 주고**(창 열기),
연결은 거기서 건다. 끊는 것만 트레이가 한다 — 패널이 없어도 해야 하는 동작이기 때문이다.

⚠ **패널의 「닫아도 유지됩니다」는 껍데기가 세운 사실만 근거로 삼는다.** 브리지의
`resident` 플래그를 껍데기가 세우고(`br.resident = tray is not None`) 패널은 `status.resident`
를 받아 그린다. 프런트가 추정하면 트레이 없는 머신에서 **거짓**이 되고, 사용자는 창을 닫고
연결을 잃는다(P0-R).

⚠ 메뉴 콜백은 **트레이 스레드**에서 불린다. 거기서 tkinter 를 만지는 것은 정의되지 않은
동작이라, 콜백은 큐에 넣기만 하고 실제 조작은 `_drain` 이 도는 GUI 스레드가 한다.

### P0-AD. AI 를 찾고 물어볼 때 **검은 창을 띄우지 않는다** (사용자 제보 2026-09-04)

「AI 플랫폼과 연결을 진행할 때 그 윈도우가 켜지고 꺼지는 깜빡임」의 정체는 **콘솔 앱 자식에게
할당되는 새 콘솔 창**이다. 이 프로그램은 `--windowed` 라 자기 콘솔이 없고, 그 상태에서
`claude.exe`·`codex.exe`·`wsl.exe` 를 띄우면 Windows 가 자식에게 콘솔을 새로 만든다.
출력은 파이프로 받으므로 그 창은 **비어 있다** — 정보가 0인데 불안은 100이다.

탐지 한 번에 그 창이 8~12개 뜬다(런타임 3종 × `wsl -l -q` · `command -v` · `auth status` ·
가용성 질문). `core.hidden_child_kwargs()` 가 `CREATE_NO_WINDOW` + `SW_HIDE` 를 주고,
**자식을 띄우는 모든 함수**가 그것을 쓴다.

⚠ **GUI 자식에는 쓰지 않는다.** 이 인자는 콘솔 앱 자식용이고, 자기 창을 보여 줘야 하는
자식(브라우저 앱 창)에 주면 `SW_HIDE` 가 그 창을 숨겨 **아무것도 안 뜬다**. 그런 자식은
`CREATE_NO_WINDOW` 만 준다 — `appwindow.open_app_window()` 가 그 형태이며 **의도된 중복**이다
(통합하면 앱 창이 뜨지 않는다).

⚠ 종전에도 가드는 있었다 — `spawn_runner` **한 곳에만**. 즉 가드가 없었던 것이 아니라
**모수가 노출면보다 좁았다**(§16.7 G12). 사용자가 본 깜빡임은 전부 그 가드 밖의 호출이었다.
그래서 판정을 함수 하나(`hidden_child_kwargs`)로 모으고, 「자식을 띄우는 함수 전체」를 모수로
잡는 테스트를 걸었다.

### P0-U. 브리지 수명은 **패널 생존 신호**로 판정한다

「창이 열려 있는가」를 **프로세스가 살아 있는가**로 대신 읽지 않는다. 브라우저는 창을 자기
프로세스 모델대로 다루고 그 모델은 상황마다 다르다 — Chrome 이 이미 떠 있으면 `--app` 런처는
새 창을 기존 인스턴스에 위임하고 **즉시 종료한다**(실측 2026-09-04: exit=0).

패널이 20초마다 `ping` 하고, 브리지는 90초 유휴면 스스로 끝난다. **모든 요청**이 생존
신호다 — `ping` 만 세면 탐지가 오래 걸리는 동안 죽는다. 주기가 한도보다 길면 정상 사용 중에
죽으므로 두 상수의 관계를 테스트가 고정한다.

### P0-V. 앱 창은 **그 자체가 DQA** 다

앱 창은 연결 화면을 보여 주는 보조 창이 아니라 서비스 루트를 여는 제품 창이다(사용자 결정
2026-09-04). 연결 능력은 그 안의 대화 모달에서 쓰인다 — 창을 두 개 쓰게 하지 않는다.

브리지 좌표는 로드 때 읽어 보관하고 **주소에서 지운다**(앱이 라우팅하며 주소를 갈아 끼운다).
브리지 클라이언트는 `app/client-bridge.js` 로 **분리**한다 — `connect-modal.js` 에는 브라우저
저장소 금지·상시 폴링 금지 가드가 걸려 있고, 지키는 성질이 다른 코드를 같은 파일에 두면
다음 사람이 구분하지 못한다.

### P0-W. 「했다」는 **시도가 아니라 결과**로 기록한다

1회성 초기화 플래그를 호출 **전에** 세우면, 그 초기화가 실패해도 다시 시도하지
않는다 — 실패를 성공으로 굳힌다. 초기화 함수가 성립 여부를 돌려주고 호출부가
그 값으로 기록한다(실측 2026-09-04: 이 한 줄 때문에 패널이 끝내 안 켜졌다).

### P0-X. 커밋 전 신호는 **둘**이다

`verify-completion` 은 문서·구조 게이트이고 테스트를 돌리지 않는다. 그것이 PASS 라도
회귀는 적색일 수 있다 — 실측 2026-09-04: 게이트 PASS 를 보고 밀었는데 테스트 1건이
깨져 있었다. 밀기 전에 **게이트와 회귀를 함께** 본다.

### P0-AE. 상주 안내는 **사용자가 실제로 보는 화면**에 있어야 한다 (2026-09-04)

앞선 재구성은 상주 안내를 `ai-connect.html`/`ai-connect.js` 에 넣었다. 그런데 앱 창이 여는
것은 **서비스 루트**(`index.html`)이고, 그 화면의 연결 패널을 그리는 것은
`app/client-bridge.js` 의 `initClientPanel()` 이다. 즉 **저장은 됐는데 읽히지 않는 자리**에
넣었다 — 「주 경로와 정합하게」라는 요구가 한 층 아래에서 그대로 반복됐다.

- `#connectClientResidency` 는 `index.html` 의 연결 패널 **안에** 있고, **비운 채** 렌더된다.
- 채우는 것은 `bridgeCall("status")` 의 `resident` 뿐이다 (§P0-R 과 같은 이유: 프런트가
  추정하면 트레이 없는 머신에서 거짓을 말한다).
- `status` 는 `discover` **앞에** 묻는다. `discover` 는 실제 응답을 확인하느라 수십 초
  걸리는데, 「이 창을 닫아도 되는가」는 그 전에 알아야 하는 안내다.

⚠ **표면이 둘이면 둘 다 말해야 한다.** 별도 페이지(`ai-connect.*`)도 계속 존재하므로 그쪽
안내를 지우지 않는다 — 지우면 그 경로 사용자가 아무 안내도 못 받는다.

⚠ **상주 안내는 주입받지 않는다** — 상태 한 줄(`_status`)과 다르다. 저것은 모달이 이미 갖고
있던 헬퍼라 호출부가 주는 것이 옳지만, 이 안내는 **이 패널에만 있는 요소**이고 다른 호출부가
달리 그릴 이유가 없다. 주입 인자를 늘리면 호출부가 알아야 할 것만 늘어난다.

### P0-AF. 부르는 헬퍼는 **그 모듈이 갖고 있어야** 한다 (실측 2026-09-04)

`client-bridge.js` 가 `_status(...)` 를 8곳에서 불렀는데, 그 정의는 `connect-modal.js` 의
**export 되지 않은 지역 함수**였고 import 도 없었다. ESM 모듈 스코프는 파일마다 닫혀 있으므로
이것은 자유변수이고, 첫 호출에서 `ReferenceError` 로 던진다. 예외는 호출부
`openConnectModal()` 까지 전파돼 **연결 창 자체가 안 열린다**.

- **소스 검사로는 안 보인다** — 이름이 «있어» 보인다(정의가 저장소 안에 존재한다).
- **증상이 §P0-W 결함과 같다** — 화면상 「패널이 안 켜진다」로 똑같이 보이므로, 그쪽을 고쳐도
  이쪽이 남으면 증상이 그대로다. 실제로 그랬다.
- **처방은 호출부 주입**이다 — `initClientPanel(setStatus)`, 모달이 자기 `_status` 를 준다
  (병렬 세션 PR #1572 가 채택했고 본 cycle 이 그리로 수렴했다). 나는 처음에 **지역 중복
  정의**로 고쳤는데, 주입이 더 낫다: 중복이 없고, 순환도 없고, 이 모듈이 모달의 내부 헬퍼를
  **알지 못한다**는 사실이 시그니처에 드러난다. ⚠ 콜백을 안 주는 호출부를 위해 기본값(noop)을
  둔다 — 없으면 「주입을 잊었다」가 다시 `TypeError` 가 된다.
- ⚠ **같은 결함이 한 층 위에도 산다**: 주입하는 **이름 자체가 그 모듈에 없으면** 예외가
  호출부로 옮겨 갈 뿐이다. 그래서 「주입하는 이름이 실재하는가」를 따로 잠근다.
- 자유변수 판정은 「`function` 선언이 있는가」로 하면 안 된다 — 이름은 `const`/`let`/`var`·
  **매개변수**로도 묶인다. 실측: 주입으로 바꾸자 그 판정이 **거짓 양성**을 냈다.


### P0-Y. 앱 창 «안»에서는 프로그램을 다시 띄우지 않는다

`_connectEntry()` 의 기존 분기들은 「연결 프로그램이 없다」를 전제로 만들어졌다. 앱 창은 그
전제가 거짓인 유일한 맥락이므로, `clientBridge` 가 있으면 **곧바로 모달**로 간다. [내 AI
실행] 버튼도 감춘다 — 이미 실행 중이라 눌러도 아무 일이 없다.

⚠ 기능을 새 맥락에 넣을 때는 **기존 분기의 전제**를 되짚는다. 틀리는 것은 새로 넣은 코드가
아니라 기존 코드다(실측 2026-09-04).

### P0-Z. 옮긴 코드는 **실행해서** 확인한다

함수를 다른 모듈로 옮길 때, 그 함수가 부르던 «옮기지 않은 것»은 구문 검사·린트에 걸리지
않는다 — 부르는 시점에만 드러난다. 그래서 가짜 DOM 위에서 모듈을 import 해 실제로 호출하는
하네스를 둔다(). 실측 2026-09-04: 이 종류로 패널 목록이
영원히 비어 있었다.

### P0-Z. 옮긴 코드는 **실행해서** 확인한다

함수를 다른 모듈로 옮길 때, 그 함수가 부르던 «옮기지 않은 것»은 구문 검사·린트에 걸리지
않는다 — 부르는 시점에만 드러난다. 그래서 가짜 DOM 위에서 모듈을 import 해 실제로 호출하는
하네스를 둔다(`tests/test_client_bridge_runtime.py`). 실측 2026-09-04: 이 종류로 패널
목록이 영원히 비어 있었다(`_status is not defined`).

### P0-AA. 러너는 **WSL 안의 AI 도** 찾는다

Windows 파이썬으로 도는 러너가 WSL 쪽을 보지 않아, 실제로 쓰던 AI 에 닿지 못했다. 연결
프로그램이 `--cmd` 로 우회했지만 그 경로는 **능력 협상을 돌지 않아** 웹의 「답할 AI 있음」이
❌ 로 남았다(답변은 정상, 신고만 없음).

탐지 순서는 **지정 경로 → PATH → 표준 설치 위치 → WSL 안**이고, POSIX 절대경로는
`wsl.exe -e` 로 확장한다. ⚠ 이 확장은 **런타임 종류를 바꾸지 않으므로** 협상이 그대로 돈다 —
그것이 `--cmd` 우회와 다른 점이다.

같은 CLI 가 양쪽에 있을 때 어느 쪽인지는 **연결 프로그램이 정한다**(`BRIDGE_AI_PATH_<NAME>`).
그쪽이 각 후보에게 실제로 물어보고 답한 것을 골랐기 때문이다.

### P0-AB. **아이콘만 눌러도 앱이 뜬다** — 인자 없는 실행

사용자가 그대로 적어 보낸 두 문장이 이 절의 근거다(2026-09-04):

> 테스트를 위해 설치된 DQA를 삭제 후, 다시 실행해봤지만 스크린샷과 같은 화면과 함께 반응이
> 없는것으로 확인되었습니다. … 여전히 해당 서비스를 사용하기 위해서는 해당 주소에
> 들어가야하는것으로 확인됩니다.

이 프로그램은 **웹의 부속물**이었다. 딥링크로 켜질 때만 성립했고, 시작 메뉴·바탕화면·설치
직후의 [지금 실행]·자동 시작은 전부 「연결 정보가 없습니다」로 끝났다. 앱이라면 아이콘을
눌러 켜지고 그것이 곧 제품이어야 한다.

**어느 서버를 여는가**를 인자 없이도 알아야 한다. 세 출처를 이 순서로 본다 — 강한 근거가
이긴다:

| 순서 | 출처 | 무엇을 뜻하는가 |
|---|---|---|
| 1 | `server.json` 의 `base` (고정) | **연결에 성공한** 서버 |
| 2 | `server.json` 의 `last` | 사용자가 **받아들인** 딥링크의 주소 (연결 성공은 미지) |
| 3 | 설치 폴더의 `service.json` | 이 설치본이 어느 배포의 것인가 (빌드가 적는다) |

⚠ 2를 1과 **같은 키에 쓰지 않는다.** 고정은 「연결에 성공한 뒤에만」이라는 규율을 갖고 있고
그것이 TOFU 경고의 근거다 — 실패한 주소를 거기 적으면 다음번에 그 주소가 「전에 쓰던 곳」으로
신뢰받는다. **창을 여는 근거와 러너를 내려받는 근거는 세기가 다르다.**

⚠ 읽어 온 문자열은 그대로 **브라우저 창의 목적지**가 된다. `http(s)` 와 호스트를 확인하지
않으면 디스크를 만질 수 있는 상대가 한 줄로 로컬 파일 열람(`file://`)이나 창 안 스크립트
실행(`javascript:`)을 얻는다. 망가진 출처는 **건너뛰고 다음을 본다** — 거기서 멈추면 앱이
영영 열리지 않는다.

⚠ 인자 없는 실행에는 **서버 변경 확인을 묻지 않는다.** 그 주소는 우리가 적어 둔 것이지 남이
만든 링크가 아니고, 매 실행마다 뜨는 확인창은 사용자가 습관적으로 넘기게 만든다 — 그러면
정작 딥링크가 왔을 때의 확인도 같이 넘어간다.

### P0-AB.1 연결값은 **이 창의 로그인 세션**이 발급한다

인자 없이 켠 창에는 토큰이 없다. 토큰을 발급하는 주체는 원래부터 로그인 세션이고 앱 창은 그
세션을 갖고 있으므로, 값을 주는 쪽은 **패널**이 자연스럽다. 딥링크가 실어 온 값은 이제
**폴백**이다(창을 여는 사이 만료됐을 수도 있다).

봉투는 서버가 딥링크용으로 이미 만드는 `launch.protocol` **문자열 그대로** 넘긴다. 여기서
필드를 새로 조립하면 같은 뜻의 봉투가 둘이 되고, 한쪽만 고쳐지는 드리프트가 난다. 파서도
하나다(`core.parse_scheme_url`) — OS 딥링크와 패널이 **같은 코드로** 뜯는다.

⚠ 봉투의 `base` 는 **우리가 아는 그 서버여야 한다.** 그 값으로 CA·러너를 내려받으므로,
여기가 열려 있으면 XSS 한 번이 「고정(TOFU)을 우회해 남의 서버에서 러너 실행」이 된다.
거절은 **네트워크가 나가기 전에** 한다.

### P0-AB.2 두 벌이 뜨지 않는다

인자 없는 실행이 **실제로 무언가를 하게 되면서** 생긴 문제다. 종전에는 두 번째 실행이
대화상자 하나로 끝났지만 이제는 브리지·앱 창·트레이·러너가 한 벌 더 뜬다. 러너가 둘이면 같은
계정에 두 워커가 붙고 트레이 아이콘도 둘이 되어, 사용자는 어느 쪽을 끄는지 알 수 없다.

⚠ **PID 파일로 판정하지 않는다.** 죽은 PID 가 재사용되면 「떠 있다」로 오판하고, 비정상 종료
뒤에는 파일이 남아 **영영 실행되지 않는** 상태가 된다(이 저장소가 stale sentinel 로 이미 겪은
형태). OS 잠금은 프로세스가 죽으면 커널이 푼다.

⚠ 잠금은 **편의이지 안전 장치가 아니다.** 잠글 수 없는 환경(읽기 전용 홈 등)에서 실행을
막지 않는다 — 잠금 파일 하나 때문에 앱이 죽으면 안 된다.

### P0-AB.3 아이콘을 다시 눌러도 창이 돌아온다

사용자가 앱 창을 닫고(브라우저 창이라 닫는 것이 자연스럽다) 아이콘을 다시 누르는 것은 흔한
경로다. 거기서 「이미 실행 중입니다 — 트레이에서 [창 열기]」라고 답하면 **아이콘을 눌렀는데
앱이 안 뜨는** 경험이 한 번 더 난다 — 이 절이 고치려던 바로 그것이다.

두 번째 실행은 대화상자 대신 `show.req` 를 남기고 조용히 끝난다. 먼저 뜬 쪽이 그것을 읽어
창을 다시 연다. ⚠ 읽으면 **지운다**(안 지우면 0.5초마다 창이 열린다). ⚠ 30초가 지난 요청은
무시한다 — 아무도 읽지 않은 요청이 남아 있다가 다음 실행에서 창을 하나 더 열면 안 된다.

⚠ **두 껍데기가 모두 읽는다.** 웹 셸 루프와 tkinter 폴백 양쪽에 있다. 한쪽만 알면 그 화면에서
아이콘이 죽은 채로 남고, 사용자에게 이 프로그램은 하나다.

### P0-AC. 앱 창을 **이 프로그램이 직접 그린다** (사용자 요청 2026-09-04)

> 이제 DQA는 클라이언트로 작동하니, 'DQAConnect.exe' 를 별도로 열지 않고 클라이언트 내장으로
> 동작시키도록 구성해주세요.

그 전까지 앱 창은 «기본 브라우저를 앱 모드로 띄운 **별도 프로세스**» 였다. 화면은 서비스
하나라는 원칙(P0-S)은 지켜졌지만 사용자에게는 프로그램이 둘로 보였다 — 작업 표시줄에 아이콘이
둘 뜨고, 연결 프로그램은 「창을 띄우기 위해 따로 여는 것」이었다.

이제 WebView2(Edge Chromium)를 **이 프로세스가 호스팅한다.** 렌더링은 그대로 크로미움이고
화면은 여전히 **서비스가 서빙하는 그것 하나**다 — 동봉하는 것은 화면이 아니라 **창틀**이다.
그 구분이 P0-S 를 깨지 않는 근거다.

**껍데기는 셋이고, 아래로 내려갈수록 사용자가 잃는 것이 분명하다.**

| 껍데기 | 언제 | 다음으로 내려가는 조건 |
|---|---|---|
| **내장 창** | 기본 | WebView2 런타임 부재 · 창 생성 실패 |
| 브라우저 앱 모드 | 내장이 안 될 때 | 크로미움 계열 부재 |
| tkinter | 웹 화면을 띄울 수 없을 때 | — |

⚠ **닫기는 종료가 아니다 — 트레이가 살아 있을 때만.** 트레이가 없는데 숨기면 창도 아이콘도
없는 프로그램이 남고 사용자는 그것을 끌 수단이 없다(§P0-R). 그 판정 규약은 §P0-AG 다.

⚠ **주 스레드는 창의 것이다.** `webview.start()` 는 돌아오지 않는 GUI 루프다. 그래서 브리지·
트레이·「창 열어 달라」 폴링이 전부 워커 스레드에 있고, 확인창은 `MessageBoxW`(부른 스레드에
자기 모달 루프를 세운다)로 받는다. 브라우저 껍데기는 tkinter 시절의 주-스레드 큐를 그대로
쓴다 — 검증된 경로이고 이번 변경으로 건드릴 이유가 없다.

⚠ **로그인 세션이 브라우저와 갈린다.** `private_mode=False` + 고정 `storage_path` 라 한 번
로그인하면 유지되지만, 브라우저에 이미 로그인해 두었어도 **앱에서 한 번 더** 해야 한다.
그것이 내장의 대가다.

⚠ **동결본이 창을 그릴 수 있는지는 빌드가 실행으로 확인한다**(`--selftest`). 파일이 담겼는지
보는 검사로는 「담기긴 했는데 임포트가 깨진」 상태를 못 본다 — 이 저장소는 그 구분을 못 해서
**한 번도 실행된 적 없는 exe** 를 배포한 적이 있다.

### P0-AC.1 보이는 이름은 «DQA» 하나다

`APP_NAME`(설치 폴더·제거 항목 등 패키징 층)과 `DISPLAY_NAME`(창·트레이·대화상자·바로 가기)을
가른다. 사용자에게 이 프로그램은 「연결 도우미」가 아니라 **DQA 자체**이고, 화면에 «Connect»
가 남으면 서비스와 별개의 무언가로 읽힌다. 반대로 설치 폴더·레지스트리 키까지 바꾸면 기존
설치본의 업그레이드 경로가 갈리므로 **보이는 이름만** 바꾼다.

⚠ 웹 문구는 **어디서 보느냐로 갈린다.** 브라우저로 방문한 사람에게는 「받아서 설치할 것이
있다」가 사실이므로 그 안내는 남고, **앱 창 안의 문구**에서만 별도 프로그램이라는 표현을
없앤다.

### P0-AC.2 업그레이드는 **옛 이름의 잔재를 남기지 않는다** (실측 2026-09-04)

보이는 이름을 «DQA Connect» → «DQA» 로 바꾼 뒤 덮어 설치했더니 시작 메뉴에 **두 벌**이
남았다: `DQA Connect.lnk` · `DQA Connect 제거.lnk` · `DQA.lnk` · `DQA 제거.lnk`.

Inno 는 **자기가 더 이상 만들지 않는 바로 가기를 알아서 치우지 않는다** — 제거 프로그램이
돌 때만 지운다. 그래서 이 결함은 **덮어 설치한 머신에서만** 나타나고, 깨끗한 환경에 새로
설치해 보는 검증으로는 절대 보이지 않는다.

`[InstallDelete]` 로 옛 이름의 그룹 폴더·바탕화면 아이콘·자동시작 항목을 먼저 지운다.

⚠ **`AppId` 와 설치 폴더는 그대로 둔다.** 그것까지 바꾸면 업그레이드가 아니라 **두 벌 설치**가
되고, 옛 설치본이 제거 목록에 영원히 남는다.

⚠ 그리고 `UsePreviousGroup=no` 가 있어야 **폴더 이름까지** 도달한다. Inno 는 업그레이드에서
레지스트리에 적어 둔 지난 그룹 이름을 재사용하므로, `DefaultGroupName` 만 바꾸면 덮어 설치한
머신은 «DQA Connect» 폴더 **안에** «DQA» 바로 가기를 두게 된다 — 이름을 바꾼 의미가 절반만
도달한다(실측 2026-09-04). 그룹 선택 화면은 이미 감춰 두었으므로 사용자가 고른 값을 무시할
걱정은 없다.

### P0-AG. 닫기는 **트레이로**, 종료는 **아이콘 우클릭 [종료]** (사용자 요청 2026-09-04)

> DQA 클라이언트 윈도우를 닫을 때, 기본적으로 트레이 아이콘으로 남겨두도록 구성해주세요.
> 실제 프로세스를 종료하려면 트레이 아이콘 우클릭을 통해 종료를 진행하는 방향으로 …

**세 껍데기 공통 계약**이다 — 사용자에게 이 프로그램은 하나이고, 어느 껍데기로 떴는지는 우리
사정이다.

| 행동 | 아이콘이 살아 있을 때 | 아이콘이 없거나 죽었을 때 |
|---|---|---|
| 창 [X] | **숨는다** — 프로세스·연결 유지 | **종료** (종전 계약) |
| 아이콘 더블클릭 / [창 열기] | 창 복귀 | — |
| 아이콘 우클릭 → **[종료]** | **프로세스 종료** | — |

**(a) 판정은 «닫는 순간» 묻는다 — 값이 아니라 호출이다.** 아이콘은 뜬 뒤에도 사라진다(탐색기
재시작 후 재등록 실패). 기동 시점의 bool 을 들고 있으면 그 뒤 아이콘이 죽어도 계속 숨겨,
사용자는 **창도 알림 영역 아이콘도 없는** 프로세스를 갖는다 — 이 기능이 막으려던 상태가 시점만
뒤로 밀려 재현되는 형태다. 그래서 `Shell.can_hide` 는 `Callable[[], bool]` 이고,
판정 정본은 `gui._tray_alive` **하나**다(tkinter `_tray_live` 도 그것을 부른다).
판정할 수 없으면(`can_hide()` 가 던지면) **숨기지 않는다** — 모르는 채 숨기는 쪽의 실패가
훨씬 나쁘다.

**(b) 「닫아도 유지됩니다」도 같은 판정을 본다.** 브리지의 `resident` 는 **읽기 전용
property** 이고 껍데기가 넘긴 `resident_probe()` 를 매번 새로 부른다. 대입 자리를 없애
「기동 시점 bool」 형태를 구조적으로 불가능하게 했다(§16.7 G10) — 종전에는
`br.resident = tray is not None` 이라 아이콘이 죽은 뒤에도 패널이 계속 유지된다고 말했다.

**(c) 처음 닫았을 때 1회 안내한다 — 닫힘을 «이벤트로 받는» 껍데기에서만.** 아무 말 없이
사라지면 사용자는 **종료된 줄** 안다. 문구는 공유 상수 `gui.HIDDEN_NOTICE` 하나이며 **어디로
갔는지 + 어떻게 진짜로 끝내는지**를 같은 자리에서 말한다 — 닫기가 곧 종료가 아니게 된 이상
종료 경로를 모르면 사용자는 작업 관리자로 간다. 매번 띄우면 소음이므로 **1회**이고, 숨김이
**성립한 뒤에만** 알린다(실패 경로에서 알리면 「알림 영역에 있습니다」를 말해 놓고 창이
닫힌다 — §P0-R).

⚠ **브라우저 껍데기는 안내를 내지 않는다 — 낼 근거가 없다.** 그 창은 브라우저의 것이라
`WM_CLOSE` 가 우리에게 오지 않는다. 무신호(`idle_seconds`)를 「닫혔다」로 **추정**하면 틀린다:
패널의 20초 ping 은 `initClientPanel` **안에서** 시작하므로(`client-bridge.js` L178, L96 의
조기 반환 뒤) **연결 모달을 한 번도 열지 않은 사용자는 ping 을 아예 보내지 않고**, 배경·
최소화된 브라우저는 타이머를 스로틀한다 → **창이 열려 있는데** 안내가 뜬다. 이 껍데기 사용자는
