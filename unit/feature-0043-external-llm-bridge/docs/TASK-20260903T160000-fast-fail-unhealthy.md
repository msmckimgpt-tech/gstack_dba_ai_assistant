# TASK-20260903T160000 — 아픈 러너를 기다리게 하던 150초

## 1. 요청 (사용자, 2026-09-03)

> 「사용자 입장에서, 150는 너무 깁니다. (사실, 10초 이상 소요되는 부분도 길다고 체감됩니다.)
>  해당 부분도 고려해주세요.」

## 2. 직전 cycle 의 설계가 뒤바뀐 자리

`TASK-20260903T140000` 은 「응답 없음이 관측된 러너」에 **150초 상한**을 뒀다. 무한 대기는
없앴지만, **이미 못 쓴다는 것을 아는 상태에서 150초를 더 기다리게 했다.**

그 150초의 정체는 «사용자를 위한 시간»이 아니라 **«회복됐는지 확인하려는 우리 편의»** 였다 —
아픈 러너도 계속 시도해야 자기 치유가 성립하므로 그 시도를 사용자 질문에 얹은 것이다.
**그 비용을 사용자 대기 시간으로 지불하고 있었다.**

## 3. 조치 — 얽힌 두 목적을 분리한다

| 목적 | 종전 | 이제 |
|---|---|---|
| 사용자 답변 | 150초 기다린 뒤 안내 | **AI 를 부르지 않고 즉시** 안내(체감 0초) |
| 회복 감지 | 그 150초로 겸용 | **배경 스레드**(`caps.schedule_health_recheck`, 쿨다운 60초) |

- 게이트는 `ask_local_ai` **가장 앞**에 둔다 — 프롬프트·명령 조립 뒤에 두면 그만큼 사용자가
  기다리고, 그 시간은 어차피 버릴 준비 작업에 쓰인 것이다.
- 회복 확인을 **없애지 않았다**. 없애면 「못 쓴다」가 영구 잠김이 되어 복구된 러너가 영원히
  막힌다(직전 cycle 과 같은 판단). 바뀐 것은 **누가 기다리는가** 뿐이다.
- 회복 확인은 **협상 경로를 재사용**한다(`detect_runtimes`) — 「응답하는가」의 기준이 두 벌이
  되면 한쪽은 반드시 낡는다.
- ⚠ 회복 확인은 **실제로 AI 를 호출**한다(사용자 계정 토큰). 그래서 쿨다운을 둔다 — 아픈
  동안 매 질문마다 호출하면 남의 계정 쿼터를 우리가 태우는 셈이다.
- **건강한 러너는 이 경로를 타지 않는다**(무제한 유지) — 정상 질문이 안내문으로 바뀌면 안 된다.

## 5. 함께 관측한 별개 결함 — 자동 갱신이 발동하지 않는다

이 cycle 의 수정도 사용자가 러너를 재기동해야 도달하는데, **자동 갱신(`try_self_update`)이
동작하지 않고 있다**:

| 관측 | 값 |
|---|---|
| 러너 신고 지문 | `d69d7da6928a` (2026-09-03 10:28 기동) |
| 그 시점 배포본 | 동일(당시엔 최신) |
| **현재** 배포본 | `4669f0192526` — 이후 2회 배포로 stale |
| 러너 기능 신고 | `console_jobs,self_review,**self_update**` (코드 보유) |
| 감사 원장의 `stale_build`·self-update 사건 | **0건** (어제 구 러너의 `stale_build` 3건만) |

즉 서버가 stale 을 알리지 않거나 러너가 그 신호로 갱신을 시도하지 않는다. **조사·수정은 별
cycle** 로 둔다(이 cycle 의 범위는 대기 시간이고, 두 축을 한 cycle 에 넣으면 검증이 얕아진다).
그 전까지는 **수동 재기동이 필요**하며, 그 사실을 사용자에게 숨기지 않는다.
