# ANCHOR: feature-0033-analysis-synthesis 클러스터 합성 요약(L2)

## §1. 외부 관점 요약

"클러스터마다 이미 라벨이 있는데 왜 또 요약을 만드나?"
→ 라벨은 **평균 9자**다("몬스터 스폰", "아이템 효과"). 그건 이름이지 설명이 아니다. 라이브에는
테이블 클러스터가 818개, 그 안에 15,365개 객체가 있고, 각 객체에는 개별 분석문이 있다. 그런데
그 분석문들이 상위 의미로 접히는 층이 없어서, "이 DB 의 결제 관련 구조가 어떻게 되나" 같은 질문에
답하려면 개별 분석문 수백 개를 훑어야 한다. GraphRAG 계열이 계층 요약으로 전역 질의 비용을 크게
줄이는 지점이 정확히 여기다.

"그럼 기존 라벨 생성기를 확장하면 되지 않나?"
→ 그 함수는 32자 라벨 계약이고 저장소가 `agent_runtime.kv`(짧은 값)다. 요약은 2~4문장이고
"멤버 20개 중 3개만 상세분석 근거" 같은 메타를 함께 들고 있어야 하므로 저장 계약 자체가 다르다.
확장하면 두 계약이 한 함수에 섞여 둘 다 나빠진다.

"요약이 틀리면 클러스터링까지 오염되나?"
→ 아니다. 그게 이 설계에서 가장 조심한 지점이다. 요약은 클러스터링 시그니처에 **절대 유입되지
않는다**. 유입되면 요약 갱신 → 재임베딩 → 재클러스터 → 요약 갱신의 순환이 생긴다. 증거·분석의
변화는 오직 **요약 캐시 키**로만 전파된다.

## §2. 대안 분기

- **Alt-A: 클러스터 id 를 캐시 키로.** 페르소나 — 자연스러운 좌표를 쓰려는 팀. 안 고른 이유:
  `semantic_cluster_id` 는 pass 마다 MDS 배치 순서로 재부여되어 churn 한다. 클러스터 내용이
  그대로인데도 id 가 바뀌면 캐시가 통째로 미스 나 818개를 매번 재생성한다. **멤버셋 지문**이
  클러스터의 진짜 정체성이다.
- **Alt-B: 전량 사전 생성(818개 한 번에).** 페르소나 — 빨리 채우고 싶은 팀. 안 고른 이유:
  한 pass 에 818콜이 몰리면 토큰 예산(feature-0032)을 즉시 소진해 다른 백그라운드가 굶는다.
  pass 당 40개 상한으로 나눠 채운다 — 며칠 걸리지만 아무것도 굶기지 않는다.
- **Alt-C: 요약을 라벨처럼 kv 에.** 페르소나 — 테이블 추가를 피하려는 팀. 안 고른 이유:
  `member_count`/`analyzed_count`/2중 버전을 kv 한 칸에 직렬화하면 조회·부분갱신이 불가능하고,
  콘솔·상위 합성(L3)이 쓸 수 없다.

## §3. 가정된 사용 시나리오

운영팀에 새로 합류한 기획자가 "이 게임 DB 에서 우편/선물 관련 데이터가 어디에 있냐"고 묻는다.
지금은 그래프 뷰에서 "메일 시스템" 이라는 9자 라벨이 붙은 묶음을 찾은 뒤, 그 안의 테이블 30여 개를
하나씩 열어 분석문을 읽어야 한다.

요약이 있으면 묶음 하나를 열었을 때 "우편함 보관·수령·만료 처리를 담당하는 묶음이다. 우편 정의
테이블이 마스터이고 수령 이력이 로그 성격으로 붙는다. 미수령 보상 문의나 만료 정책 조정 시
찾게 된다" 같은 서술이 먼저 보인다. 그리고 그 서술 옆에 "멤버 32개 중 7개 분석 근거"가 붙어 있어,
읽는 사람이 이 요약을 얼마나 믿을지 스스로 판단할 수 있다.
