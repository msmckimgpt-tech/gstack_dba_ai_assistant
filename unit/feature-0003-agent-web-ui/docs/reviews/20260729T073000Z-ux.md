## 1. Findings (발견)

### PASS-1. append-only 계약 자체는 성립한다 (핵심 요구 충족)
- 렌더 게이트와 함수 가드가 **정확한 논리 여집합**이다.
  - `app.js:9599` `const isPendingLocal = !(Number(it.id) > 0) || it.status !== "ready";` → 버튼 노출
  - `app.js:9647` `if (Number(item.id) > 0 && item.status === "ready") return;` → 제거 차단
  - 즉 `노출 ⇔ ¬(id>0 ∧ ready)`, `차단 ⇔ (id>0 ∧ ready)`. **"보이는데 no-op 인 죽은 ×"도, "안 보이는데 함수로 뚫리는 경로"도 없다.** 리뷰 지시가 지목한 두 엣지(`id>0 ∧ uploading`, `id≤0 ∧ ready`) 는 양쪽 판정이 동일하게 "pending-local" 로 떨어져 불일치가 없다.
- `id>0 ∧ status≠"ready"` 가 실제로 만들어지는 유일한 경로는 `app.js:9964` (`status === "deleted" → "failed"`) 인데, 이 값을 공급하는 `GET /api/conversations/{cid}/attachments` 는 `conversations.py:2232` `WHERE ... DeletedAt IS NULL AND SupersededAt IS NULL` 로 삭제분을 애초에 반환하지 않는다 → **도달 불가 분기**(잠복 위험 낮음, 아래 R-3).
- 서버 상태를 바꾸는 프론트 경로는 0건이다. `_discardPendingAttachmentPill` 은 **로컬 bucket splice 만** 한다(`app.js:9648`). 호출처는 pill × 하나뿐(`app.js:9609`).
- ready 항목을 bucket 에서 빼는 다른 경로도 파괴적이지 않다: `_loadConversationAttachments`(서버 재동기화, `app.js:9957`), `_flushStagedAttachmentsToCid`(업로드 성공 후 target bucket 으로 이관, `app.js:9916`), 전송 후처리는 `source` 만 `session` 으로 바꾸고 항목을 남긴다(`app.js:10943`). → **첨부는 쌓이기만 한다.** 사용자 지시 이행 확인.

### PASS-2. 잔재 없음 (grep 실사)
- `_deleteConversationAttachment` / `_canDeleteFromAttachList` / `.attach-list-item-del` / 프론트의 `DELETE /api/attachments` : **src·tests 전체 0건**. `method: "DELETE"` 잔존 호출은 folders·share·members·avatar 뿐(첨부 무관).
- 죽은 CSS 아님: 남은 `.pill-remove` 규칙(`styles.css:3075`, `:hover` 3085)은 새 취소 버튼이 그대로 쓴다(`cancelBtn.className = "pill-remove"`). `.attach-list-item-del` 규칙은 마크업과 함께 제거됨 → 고아 CSS 없음.
- 유지 주장 검증: `.attach-list-item-name-text`(`styles.css:3274`)·`.attach-list-item-meta` 말줄임(`3287-3289`)은 그대로 남아 AC-4 유효 주장과 일치.

### F1 (BLOCK). "업로드 취소" 버튼은 업로드를 취소하지 않는다 — 그리고 이제 되돌릴 수단이 사라졌다
이번 diff 가 `aria-label="업로드 취소"` / `title="업로드 취소"`(`app.js:9604-9605`)를 **새로 붙였는데**, 그 아래 로직은 이전 코드와 동일하게 로컬 splice 뿐이다. in-flight `fetch` 에 `AbortController` 가 없다(`app.js:9803`, `apiFetch` 는 `options` 를 spread 하므로 `signal` 전달은 가능 — `app.js:836`).

`uploading` pill 의 ×를 누르면 실제로 일어나는 일:
1. pill 은 사라진다(사용자: "취소됐다").
2. 업로드는 계속 진행돼 **서버에 첨부가 생성된다**.
3. 성공 분기의 `showToast(_attachUploadDoneMessage(...))`(`app.js:9826`, lazy 경로 `9762`)가 그대로 실행 → 취소 직후 **"첨부 업로드 완료: foo.csv"** 토스트가 뜬다(정면 모순).
4. 그 첨부는 `_resolve_conversation_attachment_scope`(`conversations.py:3173-3181`)에 의해 **이후 모든 턴에서 AI 참조 스코프에 포함**된다. 클라이언트 selection 과 무관하다.
5. 대화 재진입/`_loadConversationAttachments` 시 `status:"ready"` pill 로 되살아나며 이번 변경으로 **×가 아예 렌더되지 않는다** → 사용자에게 **회수 수단 0개**.
6. 부가 증상: `uploadingCount` 는 finally 에서야 감소하므로(`app.js:9841`), "취소" 후에도 전송이 `"파일 업로드가 완료될 때까지 기다려주세요."`(`app.js:10737`)로 막힌다 — 화면엔 업로드 중 항목이 하나도 없는데 막힌다.

직전 cycle 까지는 같은 non-abort 동작이어도 라벨이 "삭제"였고 실제 회수 경로가 있었다. 이번 cycle 은 **라벨을 "취소"로 격상하면서 유일한 구제책을 제거**했다 — 잘못된 약속 + 비가역 결과의 결합이라 회귀로 판정한다.

### F2 (CONCERN). staged flush 중 취소하면 파일이 pill 로 부활한다 (F1 의 확정 변종)
lazy-create 전송 경로에서 `_flushStagedAttachmentsToCid(earlyCid, pendingKey)` 는 `state.activeConversationId` 가 `earlyCid` 로 바뀌기 **전에** 실행된다(플러시 `app.js:10977` → 전환 `app.js:11000`). 따라서 플러시 동안 pill 은 pending bucket 기준으로 렌더되고, `staged.status = "uploading"`(`app.js:9904`)이라 ×가 붙는다. 이때 ×를 누르면:
- `bucket.items` 에서는 빠지지만 루프는 `stagedItems` 배열이 잡은 **객체 참조**로 업로드를 계속하고(`app.js:9901-9908`),
- 성공 시 `findIndex` 가 -1 이라 splice 만 건너뛴 채 `targetBucket.items.push({... status:"ready" ...})`(`app.js:9918`) 로 **다른 버킷에 다시 넣는다**,
- `uploadedIds` 에 실려 `askBody.attachment_ids` 에도 union 된다(`app.js:10978-10982`).
→ 취소한 파일이 **바로 그 턴에 사용되고**, 전환 후 ×없는 영구 pill 로 화면에 다시 나타난다.

### F3 (CONCERN). append-only 안내가 "업로드 전"에 도달하지 않는다
지시 3번 항목 검증 결과, 문구 자체보다 **노출 시점**이 문제다.
- `#attachSidePanelNote` 를 보이게 만드는 코드는 `_loadConversationAttachmentList` 안의 단 한 줄(`app.js:10055`)뿐이고, 그 앞줄(`10050-10052`)에서 **첨부 0건이면 early-return** 한다 → **첫 업로드 전에는 문구가 구조적으로 표시 불가**.
- 이 함수는 사용자가 `첨부파일 목록` 메뉴를 눌러 패널을 열 때만 호출된다(`app.js:10608-10615`). 드래그&드롭(`app.js:10601-10607`)·클립 업로드 경로에서는 호출되지 않는다.
- 게다가 업로드 후 `_renderAttachmentPills` 가 **같은 `#attachSidePanelList` 를 `innerHTML=""` 로 덮어쓴다**(`app.js:9536,9545`) — 두 렌더러가 한 컨테이너를 공유한다.
→ 결과: "첨부는 대화에 계속 쌓입니다" 는 **이미 쌓인 뒤에, 그것도 사용자가 직접 목록을 열어봐야** 보인다. 비가역성 고지로서는 사후·수의(隨意) 고지다.
- 문구 자체도 "쌓입니다"는 축적의 서술이지 **"지울 수 없다"는 제약의 고지가 아니다**. 직전 문구가 회수 방법을 명시했던 만큼, 그 자리를 서술문으로 바꾸면 "빼는 방법은 어딘가 있겠지"로 읽힐 여지가 남는다. (과한 경고는 불필요 — 업로드 확인 모달은 반대. 문구 한 줄 강화 + 노출 시점 교정이면 충분하다.)

### F4 (CONCERN). 유일하게 남은 ×가 가장 안 보이는 상태에만 붙는다
`.attach-side-panel .composer-attachment-pill[data-uploading="true"] { opacity: .6; }`(`styles.css:3087`) + `.pill-remove { color: var(--text-muted); padding: 0 2px; }`(`3075-3084`). 이제 ×가 존재하는 상태는 `uploading`(전체 0.6 투명)과 `failed`(muted) 뿐이다 — muted 색을 다시 0.6 으로 깎으면 대비가 사실상 남지 않고, 히트 영역도 `padding: 0 2px` + `font-size:14px` 로 접근성 최소 타깃(24px)에 못 미친다. 삭제 ×가 사라지면서 **남은 취소 ×의 발견 가능성이 함께 떨어졌다.**

### F5 (CONCERN). 문서 서술의 과장 — "이월 이슈 해소"
- TASK.md 진행 체크박스 `- [x] 이월 이슈 해소 — ... UI 경로가 사라져 제품 표면에서 무효` 는 과장이다. 실측: `DELETE /api/attachments/{id}` 의 인가는 `conversation.attachment.upload.{own,any}` + `_account_can_access_attachment`(`attachments.py:232-240, 309-338`)이며, 마지막 줄이 `_account_is_conversation_member` 로 **그룹 멤버 누구나 타인 첨부를 삭제 가능**한 상태 그대로다. 바뀐 것은 **UI 어포던스 소멸(오클릭 위험 제거)** 이지 인가 결함의 해소가 아니다. 게다가 이 프로젝트는 Conversation API 토큰(feature-0023) 등 **UI 아닌 제품 표면**을 갖고 있어 "제품 표면에서 무효"는 성립하지 않는다. ADR 본문은 "정책 자체는 별도 판단 대상으로 유지"라고 정직하게 hedge 하고 있으므로, **TASK 체크박스 문구만 ADR 수준으로 낮추면 된다**(예: `- [x] 이월 이슈 — UI 오클릭 경로 소멸로 노출 위험만 제거, 인가 결함은 미해소·별도 판단 대상`).
- ADR 의 "`DELETE /api/attachments/{id}` 는 존치하되 ... **관리·보존정책 경로의 수단으로 남김**" 도 부정확하다. 이 엔드포인트의 권한은 관리 권한이 아니라 일반 사용자 권한(`upload.own`)이고, 관리/보존 경로는 별 엔드포인트(reconciliation·admin purge)로 설계돼 있다(`attachments.py:225-230` docstring). 정확히는 "**호출자 없는 일반 사용자용 엔드포인트로 잔존**" 이다.
- 반대로 누락은 없다: FUNCTION 의 AC-1~3 supersede·AC-4 유지 주장, MODIFY 의 변경 목록, DESIGN-entry-points 의 갱신은 코드와 일치함을 확인했다(위 PASS-2). `.attach-list-item-meta` 의 CSS 주석만 사라진 삭제 버튼을 이유로 들고 있어(`styles.css:3284-3286`) 근거가 stale — 규칙 자체는 버전 토글 줄바꿈 방어로 여전히 유효하니 주석 한 줄만 갱신하면 된다.

## 2. Risks (위험)

- **R-1 (높음, F1/F2)**: 사용자가 "취소"를 신뢰 → 잘못 올린 파일(오탈자 스크립트, 민감 데이터, 대용량 CSV)이 **영구히 대화에 남고 매 턴 AI 참조 스코프**에 들어간다. 회수 수단이 UI 에 없으므로 사용자 문의는 곧바로 운영/DB 개입 요청이 된다. append-only 결정이 옳더라도, **"취소했는데 남았다"는 첫 사례 하나로 append-only 자체가 버그로 인식**된다.
- **R-2 (중간, F3)**: 비가역 축적을 사전 고지 없이 학습시키는 구조 → 첨부 남발 → `_check_attachment_size_caps` 상한 도달·프롬프트 메타 목록 팽창이 사용자 눈에는 "갑자기 첨부가 안 된다"로 보인다.
- **R-3 (낮음, 잠복)**: `app.js:9964` 의 `deleted → failed` 매핑은 현재 도달 불가지만, 목록 엔드포인트가 언젠가 삭제분을 포함하도록 바뀌면 **서버 실재 첨부에 ×가 붙어 로컬에서만 사라지는** 옛 거짓말이 재발한다. (현재는 이미 삭제된 행이라 실피해는 없음.)
- **R-4 (낮음, F5)**: TASK 체크박스가 인가 결함을 "해소"로 기록하면 후속 cycle·감사에서 재점검 대상에서 빠진다.

## 3. Recommendations (권고)

1. **[BLOCK 해소, 택1 필수]**
   - (a) **진짜 취소**: 업로드마다 `AbortController` 를 만들어 bucket item 에 보관하고, ×에서 `ctrl.abort()` 후 splice. `apiFetch` 는 `options` spread 라 `signal` 만 넘기면 된다(`app.js:836`). abort 시 성공 토스트가 뜨지 않도록 `AbortError` 를 실패 분기에서 조용히 흡수하고 `uploadingCount` 도 즉시 감소. 서버에 이미 커밋됐을 수 있음을 감안해 abort 후 `_loadConversationAttachments` 로 재동기화하면, 서버가 이미 받은 경우 ready pill 로 정직하게 되살아난다(거짓말 없음).
   - (b) **라벨 정직화(최소 수정)**: `aria-label`/`title` 을 `"목록에서 치우기"` 로 바꾸고, `uploading` 상태에서는 ×를 아예 렌더하지 않는다(= `failed`/`staged` 에만 노출). staged 는 아직 업로드 전이라 진짜 취소가 맞고, failed 는 서버에 없다. 이러면 F1·F2 가 동시에 닫히며 append-only 서술과도 어긋나지 않는다. **F2 는 (b) 로만 해도 닫힌다** — flush 중 pill 은 `uploading` 이므로 ×가 사라진다.
2. **[F3]** 안내 노출을 업로드 시점으로 앞당긴다: `_renderAttachmentPills` 에서도 `#attachSidePanelNote` 의 `hidden` 을 항목 유무에 맞춰 토글(현재 `_loadConversationAttachmentList` 단독 소유). 문구는 비가역성을 한 마디로 명시 — 예: `"AI 는 이 대화에 올린 파일 전체를 참고합니다. 올린 파일은 대화에 계속 남습니다(삭제 불가)."` 업로드 확인 모달은 **권하지 않는다**(드래그&드롭 흐름 파괴, 과함).
3. **[F4]** 남은 ×에 최소 히트 영역(`padding: 4px 6px`)과 대비 보정을 준다. 최소한 `[data-uploading="true"]` 의 `opacity:.6` 이 버튼에 상속되지 않게 `.pill-remove { opacity: 1; }` 로 되돌린다.
4. **[F5]** TASK 체크박스를 "인가 결함 미해소, UI 오클릭 경로만 제거"로 낮추고, ADR 의 "관리·보존정책 경로의 수단" → "호출자 없는 일반 사용자 엔드포인트로 잔존(권한 `upload.{own,any}`)" 으로 정정. `styles.css:3284-3286` 주석의 stale 근거 1줄 갱신.
5. **[R-3, 선택]** `app.js:9964` 의 `deleted → "failed"` 매핑을 제거하거나(목록은 삭제분을 주지 않음) 주석으로 "도달 불가·유지 이유" 를 못 박아 후속 회귀를 막는다.

## 4. Verdict rationale (판정 근거)

사용자가 지시한 **핵심 계약(서버 저장 첨부는 UI 에서 제거·삭제 불가)은 코드로 성립**하며(렌더 게이트 ⇔ 함수 가드 여집합, 삭제 호출 0건, 잔재 0건), 문서도 대체로 정합하다. 그럼에도 BLOCK 인 이유는 하나다: 이번 diff 가 **새로 도입한 "업로드 취소" 라벨이 실제로 취소하지 않고**, append-only 전환으로 **되돌릴 수단까지 동시에 제거**되어 — 취소를 누른 사용자가 영구·비가역적으로 AI 참조 스코프에 파일을 남기게 된다(F1). 취소 직후 "업로드 완료" 토스트가 뜨고, 전송은 보이지 않는 업로드 때문에 막히며(F1-6), lazy-create 경로에서는 취소한 파일이 pill 로 되살아나 그 턴에 실제로 사용된다(F2 — 코드 경로 확정). 이는 사용자가 지시한 "삭제 기능 없음" 을 지키면서도 사용자를 속이는 상태이며, 수정 비용은 라벨 2줄 + 렌더 조건 1줄(권고 1-b)로 매우 낮다. F3~F5 는 단독으로는 CONCERN 이나, 비가역 계약을 제품에 심는 변경이라 안내 도달 시점(F3)과 문서 서술 정확도(F5)는 같은 cycle 에서 함께 닫는 것이 옳다.
