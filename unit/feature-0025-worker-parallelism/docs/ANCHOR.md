# ANCHOR: feature-0025-worker-parallelism 워커 성능·병렬 처리 설정

## §1. 외부 관점 요약
"백그라운드 워커(그래프 노드 분석·cluster_label)와 사용자 답변이 왜 이렇게 느리지? 서버는
놀고 있는데?" — 조사 결과 세 워크로드 모두 **단일 컨테이너·직렬 루프**로 실효 병렬도 = 1이었다
(insight-worker 는 tick 당 노드를 순차 LLM 호출, ask-worker 는 답변을 한 번에 하나씩 처리).
이 기능은 그 병렬도·페이싱·배치를 **관리 콘솔에서 조절**할 수 있게 열되, 기본값은 현행(직렬)과
byte-동치로 두어 opt-in 으로만 공격적으로 만든다. "왜 기본을 1로 두나?"의 이유: 병렬도를 올리면
pgbouncer 커넥션 풀(2026-07-14 §82 사건에서 20 소진→전역 장애)과 Bedrock LLM RPM/TPM(능동
rate-limit 부재)이 먼저 병목이 되므로, 운영자가 관측하며 신중히 올리도록 한다.

## §2. 대안 분기
- **Alt-A: 기존 knob 노출만 (배치·주기만 조절, 신규 병렬 코드 없음).** 페르소나: 최소 위험을
  우선하는 보수적 운영팀. 안 고른 이유: 사용자가 "더 공격적인 병렬도로 처리"를 명시적으로
  요구했고, 직렬 루프의 배치/주기만으로는 "동시 처리"가 안 된다(노드마다 순차 LLM, 답변 1건씩).
- **Alt-B: docker replicas 수평 확장으로만 병렬화.** 페르소나: 컨테이너 오케스트레이션 성숙 팀.
  안 고른 이유: deploy-web.sh 의 무중단 롤아웃(feature-0014/0020)이 서비스명 단위라 replicas
  자동 스케일은 배포 스파인 재설계가 필요(고위험). 프로세스 내 스레드 동시성이 claim 설계
  (SKIP LOCKED+lease)와 이미 정합하고 배포 스파인 무변경. (수평 확장은 여전히 병행 가능 — 인프라
  여력으로 pgbouncer/PG 상향만 선반영.)
- **Alt-C: 전역 LLM 세마포어로 동시 호출 상한 강제.** 페르소나: rate-limit 방어를 코드로
  강제하려는 팀. 안 고른 이유: 정당한 대화 병렬성까지 직렬화할 위험 + 복잡도. 대신 각 knob 의
  보수적 상한 clamp(node 8/cluster 4/ask 8) + 설명의 자원 경고 + 인프라 여력으로 방어.

## §3. 가정된 사용 시나리오
DBA 관리자가 대량의 데이터소스를 새로 등록한 뒤 "AI 운영 현황 > 최근 활동"에서 그래프 노드
분석이 tick 당 10건씩 순차 처리돼 대기열이 며칠째 줄지 않는 것을 본다. 시스템 리소스는 여유가
있어, `시스템 > 설정 > 성능·병렬 처리`에서 '노드 분석 동시 처리 수'를 1→4, 'tick 당 처리량'을
10→30 으로 올린다(즉시 반영). 며칠 뒤 사용자 답변이 몰리는 시간대에 답변 대기가 길어지자
'답변 동시 처리 수'를 1→3 으로 올리고 워커를 재배포한다. pgbouncer 풀 소진 경보가 없는지
운영 현황을 보며 조정한다. — 6개월 후 이 코드를 인수받는 개발자는 각 knob 이 어느 워커 루프의
어느 지점을 조절하는지 FUNCTION.md 표에서 즉시 파악하고, 기본 1=현행 동치임을 신뢰한다.
