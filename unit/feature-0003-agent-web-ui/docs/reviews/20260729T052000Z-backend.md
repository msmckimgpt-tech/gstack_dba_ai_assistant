## 1. Findings (발견)

### F1 [BLOCK · 실측 확증] red-team evidence digest 가 통째로 소멸한다 — 매니페스트가 상한 없이 예산을 선점

`modules/redteam.py:553-555`
```python
manifest_txt = "\n".join(manifest_lines)
body_budget = max(0, cap_chars - (len(manifest_txt) + 1 if manifest_txt else 0))
body_txt = "\n".join(lines)[:body_budget]
```
`manifest_txt` 에는 **상한이 없다**. 반환값에도 `[:cap_chars]` 재적용이 없다(종전 코드에는 있었음 —
diff 가 `return "\n".join(lines)[:cap_chars]` 를 제거했다). 그리고 그 결과가 그대로 상위로 전파된다:

`modules/redteam.py:571-572`
```python
attach_block = build_attachment_digest(attachments)
tool_cap = max(0, cap_chars - (len(attach_block) + 2 if attach_block else 0))   # cap_chars = 6000
```

`_review_attachments` 가 넘기는 매니페스트 항목 수는 이번 cycle 이 정한 스코프 상한과 같은
**최대 200건**(`agent_core.py:3379-3399` → `_load_scoped_attachment_rows`, 상한
`_ATTACHMENT_SCOPE_COUNT_CAP=200`)이고, 항목당 파일명은 `_flatten_untrusted(..., 120)` 까지 허용된다.

실측(worktree 코드 그대로 실행):

| 입력 | attach digest | 결과 |
|---|---|---|
| 본문 1건 + manifest 120건(평균 파일명) | **5,529자** (cap 2,500 의 2.2배) | 본문 발췌 전량 소실 (`'SELECT 1;' in out == False`) |
| 본문 1건 + manifest 200건(장문 파일명) | evidence digest **20,641자** (cap 6,000 의 3.4배) | `'EVIDENCE DIGEST' in ev == False`, `'execute_sql' in ev == False` |

즉 첨부가 많은 대화에서 리뷰어는 **① 첨부 발췌 0 + ② 도구/SQL 실행 근거 0 + ③ "EVIDENCE DIGEST" 헤더조차 없는
파일명 나열 20KB** 를 받는다. 이 cycle 이 고치려던 실패 모드(“digest 에 없으면 창작”)를 grounding 축까지
확대 재생산하는 방향이며, 동시에 리뷰 1회당 토큰이 3배 이상 튄다(REDTEAM 은 매 답변 경로).

신설 테스트 `test_manifest_survives_budget_pressure` 는 manifest 1건만 두어 이 구간을 지나간다 —
"매니페스트가 예산을 선점한다" 는 성질만 고정하고 **선점의 상한 부재**는 고정하지 않는다.

### F2 [BLOCK · CONFIRMED] 스코프 확대로 "방금 첨부한 이미지" 가 매 턴 탈락하게 된다

vision 선별은 두 백엔드 모두 **가장 오래된 5장**을 고른다:
- `routers/_conv_store.py:2765-2766` — `ORDER BY Id ASC ... LIMIT %s` (`_VISION_IMAGE_COUNT_CAP = 5`)
- `modules/attachment_pg_mirror.py:447` — `ORDER BY id ASC LIMIT %s` (라이브 경로)

종전에는 후보 집합이 프론트 selection 이라 "방금 올린 이미지만 보낸" 진입 경로에서는 문제가 드러나지
않았다. 이번 변경으로 후보가 **항상 대화 전량**이 되면서, 이미지가 6장 이상인 대화에서는 사용자가 지금
올린 이미지(가장 큰 Id)가 **모든 턴에서 구조적으로 탈락**한다.

같은 결함이 텍스트 경로에서는 이미 사용자 불만으로 발견돼 고쳐졌고, 그 주석이 코드에 남아 있다
(`routers/_conv_store.py:3134-3136`: "count cap 초과 시 … 이전엔 ASC 라 한 대화에 cap(20) 초과 첨부 시
방금 올린 파일이 조용히 누락됐다(사용자 불만)"). vision 만 ASC 로 남았다.

이번 diff 가 이 표면을 악화시킨다: 새 프롬프트 지시는 "목록의 어떤 파일이든 읽을 수 있다 / 접근 불가라
말하지 말라"(`agent_core.py:1069-1078`)이고, `read_attachment` 는 이미지에 대해 **"이미지는 지원 모델에서
화면으로 함께 전달됩니다"** 라고 단정한다(`agent_core.py:159-163`). 전달되지 않은 이미지에 대해 모델이
"전달됐다"고 믿게 만드는 지시가 새로 들어간 셈 — 첨부 관련 환각의 재발 경로다.

### F3 [CONCERN] 라이브에서 실행되는 분기(PG)가 신설 테스트 7건 전부에서 미검증

`.env:239-240` 이 `AGENT_RUNTIME_ATTACHMENTS_DUAL_WRITE=1` · `AGENT_RUNTIME_ATTACHMENTS_READ_BACKEND=postgres`
이므로 `_resolve_conversation_attachment_scope` 의 **실행 분기는 PG**(`routers/_conv_store.py:3030-3053`)이고,
MySQL 분기(3055-3081)는 PG 장애 시에만 돈다. 그런데 `tests/test_attach_full_scope.py` 7건은 전부 fake conn
기반이라 **MySQL 폴백만** 검증한다 — `"ConversationId = %s" in sql`, `"SupersededAt IS NULL" in sql`,
`"AccountId = %s" in sql` 같은 단언은 라이브 경로에 대해 아무것도 보장하지 않는다.

특히 그룹 권한상승 가드는 PG 분기에서 파이썬 한 줄로만 존재한다:
```python
# routers/_conv_store.py:3043
if sender_scope and int(r.get("account_id") or r.get("AccountId") or 0) != int(account_id):
```
`pg_list_conversation_attachments` 는 PascalCase alias(`"AccountId"`)로 돌려주므로 지금은 동작하지만,
alias 계약이 한쪽만 바뀌면 `0 != account_id` 로 전부 걸러지거나(가용성 붕괴) 키 부재로 가드가
사실상 무력화되는 방향으로 조용히 깨진다. 회귀 그물이 없다.

### F4 [CONCERN] PG 스코프 조회가 필요한 것의 22배를 읽는다 (필터·정렬·상한이 SQL 밖)

`modules/attachment_pg_mirror.py:340-353` 은 `LIMIT` 없이 22개 컬럼 전량을 읽는다 —
`meta_json::text`(sandbox sheets, `version_diff.unified_diff` 등 수십~수백 KB 가능),
`attachment_derived_messages::text` 포함. 스코프 해소가 실제로 쓰는 값은 `id` 하나다.

두 경로의 비용이 크게 갈린다:
- MySQL 분기: `SELECT Id ... AND UploadStatus IN (...) ... ORDER BY Id DESC LIMIT 200` — 필요한 만큼만.
- PG 분기(라이브): 대화 전체 행 × 전체 컬럼 → 파이썬에서 status 필터 → `scoped.sort(reverse=True)` →
  `merged[:200]`. 첨부 1,000건 대화면 매 ask 마다 1,000행 전량 + 대용량 JSON 을 끌어와 버린다.

선택 결과 자체는 두 경로가 같다(정렬·상한 모두 Id DESC top-N). 갈리는 것은 **비용과 필터 위치**다.

### F5 [CONCERN] "동기 ingest 대기를 이번 턴 첨부로 한정했다" 는 주장이 코드로 성립하지 않는다

`routers/conversations.py:3123-3126`
```python
_sync_ingest_ids: list[int] = []
for _v in (client_attachment_ids + new_attachment_ids_clean):
```
`client_attachment_ids` 는 "이번 턴 첨부" 가 아니라 **프론트 selection bucket 전체**다. 그 bucket 은
`_loadConversationAttachments`(`static/app.js:9804-9827`)가 서버 목록으로 채우며 **모든 항목을
`selected: true` · `status:"ready"`** 로 넣는다(`deleted` 만 예외). 따라서 정상 진입(switchConversation)
에서는 `client_attachment_ids` = 대화 전량이고, 이전 턴의 `failed` csv/xlsx 는 **종전과 똑같이 매 턴
재-ingest 시도 + 최대 25s join** 을 유발한다.

→ 회귀는 없다(변경 전과 동일). 그러나 TASK.md·FUNCTION.md 불변식·REVIEW.md "지연 회귀 차단" 세 문서가
"봉인했다"고 기술한 완화는 **실제로 존재하지 않는다**. 문서와 코드 중 하나를 고쳐야 한다.

### F6 [CONCERN] `failed` 첨부가 스코프에서 빠져 AC-1 불변식(진입 경로 무관 동일 집합)이 깨진다

스코프 필터는 `UploadStatus IN ('uploaded','ingested')` 인데(`_conv_store.py:3045-3047` · `3065`),
라이브에서 쓰이는 상태값은 `uploaded` / `ingested` / `failed` / `deleted` 4종이다
(`_conv_store.py:2584` · `2685` · `4600`, `modules/attachment_reconciliation.py:213`).
즉 **ingest 실패 첨부는 스코프 밖**이다. 반면
- 목록 엔드포인트는 상태 무관 노출(`routers/conversations.py:2172-2176` — `DeletedAt IS NULL AND SupersededAt IS NULL` 뿐),
- 프론트는 `deleted` 외 전부 `ready`(`app.js:9819`)로 매핑해 client 합집합에 실어 보낸다.

결과: bucket 이 살아 있으면 `failed` 첨부가 보이고, 새로고침/랜딩 복귀 후에는 사라진다 — 이 cycle 이
없애려던 "진입 경로에 따라 첨부 집합이 달라지는" 성질이 `failed` 상태에 그대로 남는다. 게다가 사용자는
사이드패널에서 그 파일을 계속 보고 있는데, 프롬프트는 "이 목록이 이 대화에서 이용 가능한 전량" 이라고
선언하고 "접근 불가라 말하지 말라 / 재첨부 요구하지 말라" 고 지시한다(`agent_core.py:1069-1078`) —
`read_attachment` 는 그 파일을 "이 대화의 첨부가 아니다" 로 거부한다. 모델을 모순 상태에 두는 조합이다.

### F7 [NIT] 상한 포화 시 "방금 올린 첨부"(합집합의 존재 이유)가 잘려 나간다

`routers/_conv_store.py:3083-3087`

```python
merged = list(scoped)
for aid in client:
    if aid not in merged: merged.append(aid)
return merged[:_ATTACHMENT_SCOPE_COUNT_CAP]
```
`scoped` 가 이미 200이면 뒤에 붙은 client id 는 전부 절단된다. client 합집합의 명시 목적이
"목록 쿼리에 아직 안 잡힌 이번 턴 첨부 보존" 인데, 정확히 그 항목이 먼저 버려진다.
`test_scope_is_capped` 는 `client_ids` 없이 도라 이 조합을 지나간다. client 를 앞에 두면 해소된다.

### F8 [NIT] ask 당 추가되는 왕복·주입량 (질문 2에 대한 정량 답)

이번 diff 가 **직접** 추가하는 것:
1. `app._conversation_is_group(conv_id)` (`conversations.py:3114`) — PG 커넥션 1 + 쿼리 1~2.

2. 스코프 해소 PG 조회 1회(F4 의 전량 읽기).
3. red-team 경로: `_review_attachments` → `_load_scoped_attachment_rows` 가 **매번 새 MySQL 연결**을

4. `read_attachment` 호출당: MySQL 연결 1 + **MinIO 객체 전체 재다운로드**(`agent_core.py:604-624`).

- text inline: 최대 20 MinIO GET + 파일당 최대 64KB 주입, **총량 상한 없음**

- sandbox allowlist: `Id IN (…200…)` (LIMIT 없음) → 최대 200개 MetaJson 파싱, allowlist 에 최대 200 스키마.
- `_build_attachment_context_section`: 메타 조회 1 + **SANDBOX SAMPLE ROWS 최대 20테이블 × 2쿼리 = 최대 40 MySQL 쿼리**
  (`agent_core.py:1290-1330`, information_schema + `SELECT * LIMIT 5`) + 그 컬럼·샘플 5행이 매 턴 프롬프트에 실림.

ADR 의 "매 턴 인라인되는 본문량은 종전과 동일하다(상한 불변)" 는 **상한 기준으로만** 참이다.
실제 주입량·왕복은 대화 첨부 수에 따라 상한까지 올라간다.

### F9 [NIT] PG/MySQL 필터 비대칭 — `delete_pending`

`pg_list_conversation_attachments` 는 `deleted_at IS NULL AND superseded_at IS NULL` 만 건다(`delete_pending` 무필터).
MySQL 분기는 `DeletePending = 0` 을 명시한다(`_conv_store.py:3066`). 현행 코드에서 `DeletePending=1` 은 항상
`DeletedAt` 과 동시에 세팅되므로(`routers/attachments.py:258`, `attachment_reconciliation.py:60-66`)
지금은 무해하지만, 두 경로가 서로 다른 가정 위에 서 있다. 그 암묵 불변식이 깨지면 삭제 대기 첨부가
스코프 → **sandbox allowlist**(`conversations.py:3204-3206` — `DeletedAt IS NULL` 만, `DeletePending` 무필터)
까지 흘러가 삭제 요청된 데이터의 sandbox 스키마가 쿼리 가능해진다.

### F10 [NIT] `content_available` 는 아무도 읽지 않는 계약(테스트만 고정)

`build_attachment_digest` 의 분기는 `content` 공백 여부만 본다(`redteam.py:524-525`). 새로 추가된

한쪽만 바뀌면 조용히 어긋난다.

### F11 [NIT] `read_attachment` 이어읽기 안내가 제자리 루프를 유도할 수 있음

`start_line > total_lines` 면 `chunk` 가 비고 `truncated = (start-1+0) < total` 이 True 라(`agent_core.py:709`)

또 파일명 부분일치(`want in filename`, `agent_core.py:147`)는 후보 다수 시 조용히 첫 항목을 고른다 —
정확 일치가 아니었다는 신호가 응답에 없다.

## 2. Risks (위험)

- **R1 (F1)**: 첨부가 수십 건 이상 쌓인 실사용 대화에서 red-team 리뷰가 SQL 근거를 못 보고
  grounding BLOCK 을 남발 → 잘못된 revise 루프 + 리뷰 토큰 3배. 배포 즉시 발현하고,
  발현 조건(첨부 누적)이 시간이 갈수록 흔해진다. 관측 지표: `redteam_reviews` 의 grounding 사유 급증,
  `llm_usage` 리뷰 호출 토큰 상승.
- **R2 (F2)**: "방금 올린 이미지를 못 본다" 는 사용자 가시적 회귀. 이번 cycle 의 원 리포트(첨부 접근 실패)와
  같은 계열의 불만으로 되돌아온다.
- **R3 (F3)**: 그룹 대화 발신자 가드가 라이브 경로에서 미검증 — CSO F1(권한상승) 가드가 무테스트 상태로
  형태만 유지된다.
- **R4 (F4/F8)**: 첨부 많은 대화에서 ask latency·DB/MinIO 부하가 대화 규모에 비례해 증가.
  최악의 경우 text inline 총량이 컨텍스트 상한을 밀어내 LLM 400(요청 과대)로 답변 자체가 실패할 수 있다
  (총 바이트 예산이 없다).
- **R5 (F6)**: UI 에는 보이는데 assistant 는 모르는 파일 + "접근 불가라 말하지 말라" 지시 = 환각 유도 조합.

**위험 아님으로 확인한 항목**
- 커넥션 누수(질문 4): `_load_scoped_attachment_rows` 는 connect 실패 시 즉시 return, 이후 `try/except/finally`
  구조라 `return []` 경로에서도 `finally: mem_conn.close()` 가 실행된다(`agent_core.py:551-602`). 누수 없음.
  단 풀 미사용이라 호출당 신규 연결(F8-3/4).
- 계약 변경(질문 5): 서버는 `data.get("attachment_scope_all")` 을 읽은 적이 없고 요청 본문은 미지정 키를
  무시하는 dict 접근이라, 구버전 프론트(캐시된 app.js)가 이 필드를 계속 보내도 서버는 깨지지 않는다.
  index.html 에서 제거된 `#attachScopeAllRow`/`#composerAttachmentsScopeAll` 는 구버전 app.js 가 모두
  `if (el)` 로 가드하므로 JS 예외도 없다. 롤링 중 구버전 web 으로 라우팅된 요청은 client selection 만 쓰는
  **기능 격하**(오류 아님)로 끝난다 → mixed-version 안전.
- contextvar/env(질문 6): `run_agent` 가 `_ATTACHMENT_IDS_CTX` 를 set/finally-reset 하고
  (`agent_core.py:4293-4296`, `4334-4337`), 워커 경로도 enqueue payload 에 `attachment_ids` 를 실어
  `run_agent` 로 복원한다(`_conv_store.py:2861`). 도구 실행(`execute_tool`, `agent_core.py:5664`)과
  red-team(`_review_attachments`, `agent_core.py:5240`)은 모두 `_run_agent_core` 와 같은 스레드/컨텍스트라
  ctx 조회가 정상이며, `cfg.set_active_conversation_id` 도 같은 구간에서 유효하다(`agent_core.py:4877`).
  → in-process·worker 양쪽 정합. web·ask-worker 는 동일 이미지(`agent-common` 빌드, `/app/web` 동봉)라
  `web.modules.storage_minio` / `import agent_core` 폴백 체인도 두 런타임에서 성립.
- 스코프 SQL 의 정본 필터(`SupersededAt IS NULL` · `DeletedAt IS NULL` · `ConversationId` · 그룹 `AccountId`)는
  두 경로 모두 존재하고, 정렬·상한 적용 결과(Id DESC top-200)도 동일하다.

## 3. Recommendations (권고)

1. **[F1 필수]** `build_attachment_digest` 에 매니페스트 상한을 도입하고 최종 절단을 복원한다.
   예: `_ATTACH_MANIFEST_CAP_CHARS = 600` + 항목 수 상한(예: 40) + `"… 외 N건"` 요약 1줄,
   그리고 `return (…)[:cap_chars]`. 회귀 테스트는 "manifest-only 200건에서도
   `len(out) <= cap` 이고 본문 발췌와 `EVIDENCE DIGEST` 헤더가 살아남는다" 를 고정할 것.
2. **[F2 필수]** vision 선별을 `ORDER BY Id DESC LIMIT n` 후 표시 시 reverse 로 되돌리는
   text 경로와 동형 패턴으로 바꾼다(`_conv_store.py:2765` + `attachment_pg_mirror.py:447` 둘 다).
   그렇지 않다면 `read_attachment` 의 "이미지는 화면으로 함께 전달됩니다" 단정을 완화해야 한다.
3. **[F3]** PG 분기 테스트 최소 1건 추가 — dict rows(PascalCase alias) fixture 로 `sender_scope` 필터,
   status 필터, DESC 정렬, 상한을 검증. 라이브에서 도는 코드가 무테스트인 상태를 해소.
4. **[F4]** id-only PG 헬퍼 신설(`SELECT id … AND upload_status IN (…) AND delete_pending = 0
   ORDER BY id DESC LIMIT %s`)로 필터·정렬·상한을 SQL 로 내리고 MySQL 분기와 동형화 — F9 의 비대칭도 함께 해소.
5. **[F5]** `_sync_ingest_ids` 를 `new_attachment_ids_clean` 기준으로 실제로 좁히거나,
   TASK/FUNCTION/REVIEW 3문서의 "이번 턴 첨부로 한정/봉인" 서술을 사실에 맞게 정정한다(둘 중 하나는 필수).
6. **[F6]** 스코프에 `failed` 를 포함(메타에 `degraded_reason` 이 이미 실려 모델이 상태를 알 수 있음)하거나,
   최소한 목록 라인에 "이 파일은 처리 실패로 본문 조회 불가" 를 명시해 UI 와 프롬프트의 진술을 일치시킨다.
7. **[F7]** `merged = client + scoped` 순으로 뒤집어 상한 포화 시 이번 턴 첨부가 우선 보존되게 한다.
8. **[F8]** text inline 에 **총 바이트 예산**(예: 256KB) 도입 검토 + `_conversation_is_group` 결과를
   요청 스코프로 1회 캐시(같은 핸들러에서 2회 조회 중).

## 4. Verdict rationale (판정 근거)

설계 방향(참조 범위 결정 주체를 프론트 selection → 서버 대화 스코프로 이동, 본문은 on-demand 도구)은
타당하고, 보안 경계(ConversationId IDOR·그룹 발신자 가드·공유창 bounded 억제)와 fail-safe 폴백,
contextvar/worker 패리티, 커넥션 정리, 계약 제거의 mixed-version 안전성은 모두 검증 결과 **정합**했다.

BLOCK 판정의 근거는 두 가지 **측정된** 결함이다.

- **F1** 은 이 diff 가 새로 만든 결함이고(종전 `return "\n".join(lines)[:cap_chars]` 의 절단을 제거),
  이 cycle 이 정한 상한(200)이 그대로 입력이 될 때 evidence digest 가 cap 의 3.4배로 부풀고
  **도구 실행 근거와 첨부 발췌가 동시에 0** 이 되는 것을 코드 실행으로 확인했다. 목적(첨부 오판 제거)과
  정반대 결과를 내는 경로이고, 배포 후 첨부가 쌓일수록 확률이 올라간다 — 사후 관측으로 잡기 어려운
  "리뷰어가 조용히 잘못된 근거로 판정" 유형이라 배포 전 차단이 옳다.
- **F2** 는 기존 결함이지만 이 diff 가 그것을 **모든 진입 경로에서 상시화**하고, 동시에
  "이미지는 함께 전달된다" 는 새 단정을 프롬프트/도구 응답에 넣어 환각 표면을 키운다.
  원 사용자 리포트와 같은 계열의 불만(첨부를 못 본다)으로 되돌아올 확률이 높다.

F5·F6 은 기능 회귀는 아니나 **문서가 주장하는 완화·불변식이 코드로 성립하지 않는** 경우라,
정직성 축에서 병합 전 정정이 필요하다(코드를 고치든 문서를 고치든).

사람 승인이 필요한 사유: F2 의 vision 정렬 수정과 F6 의 `failed` 포함 여부는 노출 정책(무엇을 몇 개
모델에게 보일 것인가)에 대한 결정이 얽혀 있어 리뷰어 단독으로 뒤집지 않는다. F1 은 정책 결정 없이
수정 가능하므로 승인 대기 없이 즉시 고칠 것을 권고한다.
