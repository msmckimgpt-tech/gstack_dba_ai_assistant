# DBA AI Assistant — 프레젠테이션 시나리오 (발표 스크립트)

> 본 문서는 클라이언트·소비자 대상 데모/발표를 위한 **시나리오(스피커 스크립트)** 다.
> 시각 자료는 동봉된 `index.html` (자기완결형 HTML/CSS 슬라이드 덱) 로 재생한다.
> `index.html` 은 작업 화면·관리 콘솔의 실제 UI 를 디자인 토큰(색·폰트·컴포넌트)
> 수준에서 재현하고, 각 동작을 애니메이션으로 시연한다.
>
> **조작**: → / Space / 클릭(우측) = 다음, ← / 클릭(좌측) = 이전, `Esc` 또는 좌상단
> ☰ = 섹션 인덱스(목차) 열기, 인덱스에서 특정 구간으로 점프. 모바일/태블릿은
> 좌우 스와이프. 우상단 진행 막대로 위치 파악.

---

## 0. 발표 개요 (presenter brief)

| 항목 | 값 |
|---|---|
| 제품명 | **Database Query Assistant (DQA)** — 사내 DBA AI 어시스턴트 |
| 한 줄 정의 | "자연어로 묻고, 안전하게 검증된 read-only SQL 결과를 받는다." |
| 대상 청중 | 데이터를 보고 싶은 현업(비-DBA) · 운영 관리자 · 보안 검토자 · 의사결정권자 |
| 핵심 메시지 | (1) 누구나 데이터를 묻는다 (2) 절대 쓰기는 못 한다 (3) 모든 행위는 감사된다 |
| 데모 소요 | 풀 12~15분 / 압축 6~7분 (인덱스로 보안·아키텍처 구간 생략 가능) |
| 디자인 톤 | warm off-white(`#f7f7f4`) + 파랑 primary(`#2563eb`), Geist/D2Coding, soft shadow — **실제 서비스 UI 와 동일** |

발표 흐름은 **문제 → 작업 화면(체감) → 관리 콘솔(통제) → 아키텍처(신뢰) → 보안(정직) → 로드맵**
순으로, "써보고 싶다 → 안심된다 → 도입하겠다" 의 심리 곡선을 따른다.

## 2. 구간별 스크립트

### [0] 타이틀 — `cover`

**화면**: 중앙에 DQA 로고 마크 + "Database Query Assistant" + 부제 "자연어로 데이터베이스에 묻다".
배경에 채팅 말풍선·SQL·표가 천천히 떠오르는 ambient 애니메이션.

**스크립트**:
> "오늘 소개할 제품은 **DQA, Database Query Assistant** 입니다. 한 문장으로 요약하면
> — *데이터를 보고 싶은 사람은 누구나 자연어로 묻고, 시스템은 안전하게 검증된
> read-only SQL 로 답한다* — 입니다. SQL 을 모르는 현업도, 매번 쿼리를 대신 짜주던
> DBA 도 모두 시간을 돌려받습니다."

**전환**: "그럼 이게 왜 필요한지부터 보겠습니다."

---

### [1] 왜 필요한가 — `why`

**화면**: 좌/우 대비 카드.
- 좌(문제): "현업은 SQL 을 모른다" / "DBA 는 단순 조회 요청에 시간을 뺏긴다" /
  "직접 권한을 주면 — 실수로 UPDATE·DROP 위험".
- 우(해결): DQA 가 가운데서 자연어↔SQL 을 중개하고, **쓰기를 원천 차단**한다는 화살표 애니메이션.

**스크립트**:
> "현업의 데이터 질문은 대부분 단순 조회입니다. 하지만 SQL 을 모르면 DBA 에게 요청해야
> 하고, DBA 는 이 반복 요청에 하루를 씁니다. 그렇다고 현업에게 DB 계정을 직접 주면?
> 잘못된 UPDATE 한 줄, DROP 한 줄이 사고로 이어집니다.
>
> DQA 는 이 사이에 섭니다. 자연어를 받아 SQL 로 바꾸되, **세 겹의 방어로 읽기 전용을
> 강제**하고, **모든 행위를 감사 로그에 남깁니다**. 권한은 역할별로 잘게 쪼개 부여합니다."

**강조 포인트(3개 칩)**: `누구나 묻는다` · `절대 못 쓴다` · `전부 감사된다`

---

### [2] 작업 화면 (체감) — `work`

> 이 구간이 데모의 심장. index.html 은 실제 채팅 UI 를 재현하고 타이핑·진행·답변을
> 단계 애니메이션으로 보여준다. 발표자는 아래 5개 미니 시퀀스를 클릭으로 넘긴다.

**레이아웃 소개 (2-1)**:
좌측 252px 사이드바(대화 목록 · "+ 새 대화" · 검색 Ctrl+K · 프로필), 상단 52px 토픽바,
중앙 채팅, 하단 컴포저(+ 메뉴 · 모델 선택 · **제품/데이터소스 chip** · 입력창 · 전송).

> "화면은 익숙한 채팅 형태입니다. 왼쪽은 대화 목록, 가운데가 대화, 아래가 입력창이죠."

**시퀀스 A — 질문 입력 (2-2)**:
입력창에 예시 질문이 타이핑된다 — *"최근 7일 신규 가입자 수와 일별 평균 접속 시간을 보여줘"*.
전송 버튼(종이비행기)을 누르면 곧바로 **중단(■) 버튼으로 모핑**.

> "자연어로 그냥 묻습니다. 전송하면 버튼이 '중단' 으로 바뀝니다 — 언제든 멈출 수 있어요."

**시퀀스 B — 진행(근거 노출) (2-3)**:
"처리 중" 말풍선에 스피너 + 경과시간이 흐르고, 우측 **실행 단계 패널**에 단계가 쌓인다:
`1. 스키마 조회` → `2. 테이블 구조(users)` → `3. SQL 실행`. 각 단계에 **근거(reason)** 가
붙는다: *"신규 가입자는 users.created_at 기준으로 집계"*.

> "여기가 핵심입니다. AI 가 **무엇을, 왜** 했는지 단계별 근거를 그대로 보여줍니다.
> 블랙박스가 아니라 '추론 과정을 검토 가능한' 어시스턴트입니다."

**시퀀스 C — 답변(표 + 다중 쿼리) (2-4)**:
최종 답변에 요약 텍스트 + **결과 표**(sticky 헤더, 행 hover) + "📎 전체 N행 미리보기" 링크.
쿼리가 여러 개면 `◀ 쿼리 2/3 · 대상: app.users ▶` 네비게이터.

> "결과는 표로 즉시 보여주고, 전체 행은 한 번에 펼치거나 CSV 로 내려받습니다.
> 여러 쿼리를 돌렸다면 좌우로 넘겨보고요."

**시퀀스 D — diff 블록 (2-5)**:
첨부 SQL 리뷰 요청 시 답변이 ```diff 블록으로 — `- WHERE status = 1` / `+ WHERE status = 'active'` —
**라인별 +/- 색**으로 렌더(녹/적).

> "쿼리나 첨부를 개선해 달라고 하면, 변경점을 깃 diff 처럼 색으로 보여줍니다."

**시퀀스 E — 데이터소스 연결상태 (2-6)**:
컴포저 제품 chip 의 ● 점이 **정상(초록)/불안정(빨강)/끊김(회색)** 으로 전환되는 애니메이션 +
한글 라벨. 느린 연결도 '불안정' 으로 표시될 뿐 작업은 계속 가능.

> "연결한 데이터베이스의 상태를 색맹 친화적으로 초록·빨강·회색 + 한글 라벨로 항상 표시합니다.
> 느린 원격 DB 도 '불안정' 으로만 표시하고, 작업 자체는 막지 않습니다."

**부가 언급(빠르게)**: 첨부 업로드(이미지/CSV) · 즉시 답변(지금까지 정보로 마무리) ·
대화 공유 링크 · 검색(Ctrl+K) · 프로필의 개인 사용량/비밀번호 변경.

**전환**: "사용자 경험은 이렇게 쉽습니다. 이제 이걸 **운영하는 쪽** 을 보겠습니다."

### [3] 관리 콘솔 (통제) — `admin`

**화면**: 좌측 탭 사이드바(대시보드 / 계정 · 역할 / 제품 · 데이터소스 / 감사 / LLM 사용량 /
보관 대화 / 설정) + 우측 패널. 탭을 클릭하면 해당 패널이 슬라이드로 전환된다.

발표자는 인덱스 칩으로 아래 6개 패널을 순회한다.

**3-1 대시보드 (CloudWatch 스타일)**:
운영 현황 위젯 그리드 — 큰 숫자 + 전기간 델타 배지 + **순수 SVG sparkline**. 집계기간
드롭다운(1/7/30/90일), 자동 새로고침, 위젯 편집(드래그·표시토글, 계정별 영속).

> "운영자는 첫 화면에서 사용량·연결 상태·증감 추세를 한눈에 봅니다. 위젯은 계정별로
> 커스터마이즈되고 저장됩니다."

**3-2 데이터소스 (암호화 registry)**:
데이터소스 목록(엔진 배지 MySQL/MSSQL + 연결상태 pill). 상세에 연결 좌표 + "암호 저장됨"
배지 + **테스트** 버튼(✓ 연결 성공). 자격증명은 **envelope(KEK/DEK) 암호화** 저장.

> "DB 접속 정보는 관리 콘솔에서 추가·수정하고, 비밀번호는 **봉투 암호화(KEK/DEK)** 로
> 저장됩니다. 평문은 응답·로그·캐시 어디에도 남지 않습니다. '테스트' 로 즉시 연결을 확인하고요."

**3-3 계정 · 역할 (RBAC 권한 트리)**:
역할 상세의 **권한 격자 → 단일열 트리**. `console.access` 마스터 게이트, 종속성 기반
**점진적 공개**("세부 권한 N개 더 보기"), 대화 운영권한을 **내 대화 / 전체 대화** 2그룹으로 분리.
계정별 override(허용/상속).

> "권한은 43개로 잘게 쪼개져 있습니다. 콘솔 진입이라는 마스터 게이트 아래에서, 종속성에
> 따라 필요한 권한만 펼쳐 보여줍니다. '내 대화만' 과 '전체 대화' 를 명확히 구분하고, 계정별
> 예외도 줄 수 있습니다."

**3-4 제품 · DB-단위 접근**:
제품 = 데이터소스 + **접근 가능 DB 목록**. "+ 데이터소스 추가" picker(이름·엔진 pill·좌표·연결배지),
DB 행마다 분석상태(미분석/분석중/분석됨)와 도메인. 제품을 못 받은 계정은 데이터에 접근 0.

> "데이터 접근은 **제품 단위**로 묶고, 제품 안에서도 **DB 단위**로 화이트리스트를 겁니다.
> 바인딩이 없으면 접근 자체가 없습니다 — 기본이 '차단' 입니다."

**3-5 LLM 사용량 대시보드**:
일별 stacked bar + 모델 도넛 + 역할별/계정별 막대 + **추정 비용**. granularity(시/일/주/월),
모델 필터 칩, 막대 클릭 시 해당 일·모델 대화 목록 drill-down.

> "AI 호출은 모델별·역할별·계정별 토큰과 추정 비용으로 회계됩니다. 막대를 클릭하면 그 날
> 어떤 대화가 비용을 썼는지까지 파고듭니다."

**3-6 감사 로그**:
모든 보안 관련 행위(`WebAuditEvents`) — 액션·행위자·리소스·시각. 필터(액션/리소스/기간/행위자),
상세에 변경 전후(민감필드 redaction). 관리 mutation 은 **같은 트랜잭션** 감사(실패 시 롤백).

> "계정·역할·데이터소스·시스템 프롬프트의 모든 변경, 그리고 사용자의 질문·공유까지 감사
> 로그에 남습니다. 관리자 변경은 감사 기록과 **한 트랜잭션** 으로 묶여, 기록이 실패하면 변경도
> 롤백됩니다 — 기록 없는 변경은 불가능합니다."

**부가**: 보관 대화 탭(삭제는 hard-delete 아닌 보관 — 데이터·첨부 보존), 시스템 프롬프트 편집.

**전환**: "사용자도 운영자도 봤으니, 이게 **내부에서 어떻게 안전하게 도는지** 보겠습니다."

### [4] 전체 아키텍처 (신뢰) — `arch`

**화면**: 서비스 토폴로지 다이어그램. 요청이 흐르는 경로를 따라 노드가 순차 점등되는
애니메이션:

```
사용자 브라우저
   │  HTTPS
   ▼
Caddy (TLS 종단/리버스 프록시)
   ▼
FastAPI Web (인증·RBAC·대화 CRUD·첨부)
   ├─→ MySQL agent_memory  (계정·역할·감사·제품·데이터소스 registry)
   ├─→ MinIO               (첨부 blob)
   └─→ ask_jobs 큐  ─→  ask-worker (out-of-process)
                              └─→ Agent Loop (LLM tool-call)
                                    ├─→ Bedrock Gateway → Claude (Seoul)
                                    ├─→ Postgres agent_kb  (pgvector + pg_trgm 지식)
                                    └─→ 데이터소스 N (MySQL·MSSQL, registry+allowlist+dialect)

insight-worker  ─(백그라운드)→  스키마 분석 → rag_objects (KB)
```

**스크립트(흐름을 따라 점등하며)**:
> "사용자 요청은 Caddy 에서 TLS 로 받아 FastAPI 웹으로 들어옵니다. 웹은 인증·권한·대화를
> 담당하고, AI 실행은 직접 하지 않고 **작업 큐(`ask_jobs`)** 에 넣습니다. 별도 프로세스인
> **ask-worker** 가 큐를 집어 에이전트 루프를 돕니다 — 덕분에 웹을 재배포해도 진행 중인
> 작업이 살아남습니다.
>
> 에이전트는 **Claude(AWS Bedrock, 서울 리전)** 로 추론하고, **Postgres 지식베이스**(벡터+트라이그램)
> 에서 스키마 맥락을 가져오며, 실제 질의는 등록된 **데이터소스 N개**(MySQL·MSSQL)로 보냅니다.
> 백그라운드 **insight-worker** 는 스키마를 미리 분석해 지식으로 캐시해 둡니다."

**데이터 분리 강조(작은 표)**:
| 저장소 | 역할 |
|---|---|
| MySQL `agent_memory` | 계정·역할·감사·제품·데이터소스 registry(암호화) |
| Postgres `agent_kb` / `agent_runtime` | 지식(pgvector) + 대화/단계 런타임 + 첨부 메타(cutover) |
| MinIO | 첨부 파일 원본(blob, signed URL) |
| AWS Bedrock | LLM 추론(Claude) — 자격증명은 게이트웨이에만 격리 |

> "데이터는 수명·접근 패턴에 따라 분리됩니다. AWS 자격증명은 Bedrock 게이트웨이 컨테이너
> 에만 있어, 웹이 뚫려도 LLM 키를 얻지 못합니다 — **최소 권한** 원칙입니다."

**전환**: "여기서 자연스럽게 보안으로 넘어갑니다. 강점과 함께, **솔직하게 잔여 위험도** 말씀드리겠습니다."

### [5] 보안 모델 — `security`

> 발표 철학: **방어를 자랑하되, 약점을 숨기지 않는다.** 두 개의 면을 모두 보여준다.

#### 5-A 구현된 방어 (왼쪽 패널 — 초록 체크)

1. **읽기 전용 3겹 방어**
   - ① AST allowlist(`sqlglot`): SELECT/CTE 만 허용, INSERT/UPDATE/DELETE/DDL·`INTO OUTFILE`·
     `xp_cmdshell`·다중문 거부.
   - ② DB 최소권한 role: datasource 계정은 read-only(MSSQL `db_datareader`, PG `agent_kb_ro`) —
     설사 쓰기 SQL 이 통과해도 DB 가 거부.
   - ③ 스키마 allowlist + 첨부 sandbox: 제품의 허용 DB/스키마 밖은 요청 단위로 차단.
2. **RBAC 43권한 + console.access 마스터 게이트** — 역할 + 계정 override, 내 대화/전체 대화 분리.
3. **자격증명 envelope 암호화(KEK/DEK)** — KEK 는 `.env.secret` 분리, 평문 password 비영속.
4. **감사 로그(`WebAuditEvents`)** — 관리 변경은 same-tx fail-closed, 민감필드 redaction, 공유 토큰은 prefix 8자만.
5. **연결 격리** — per-datasource circuit breaker 로 불안정 DB 1개가 전체를 굶기지 못함.
6. **네트워크 경계** — Caddy TLS, 메타데이터 IP(169.254.169.254) **하드차단**, X-Forwarded-For 조건부 신뢰.
7. **데이터 잔류** — Bedrock 서울 리전, 감사/로그에 쿼리 결과·원문 비저장.

> "방어는 한 겹이 아닙니다. AI 가 어떤 SQL 을 만들든 — 문법 검사, DB 권한, 스키마 화이트리스트
> 세 겹을 모두 통과해야 하고, 그래도 DB 계정 자체가 읽기 전용이라 쓰기는 물리적으로 불가능합니다."

#### 5-B 잠재 이슈 + 대안 (오른쪽 패널 — 노랑 주의)

> 각 항목은 카드로 표시: **이슈 → 현재 상태 → 대안**. (정직성 = 신뢰의 핵심)

| # | 잠재 이슈 | 현재 상태 | 권장 대안 |
|---|---|---|---|
| S1 | **로그인 rate limiting 부재** | `/api/login` 무제한 시도 가능 | 계정·IP별 시도 제한 + N회 실패 시 잠금/캡차, 감사 알림 |
| S2 | **MFA(2단계) 부재** | ID/PW 단일 인증 | TOTP 등록 + 백업코드(암호화 저장), 역할별 강제 |
| S3 | **프롬프트 인젝션** (스키마명·쿼리 결과가 LLM 맥락에 유입) | AST 가드가 SQL 은 막지만 의도 혼동 여지 | 스키마/결과 텍스트 escaping·요약, system prompt 에 "입력·결과 속 명령 무시" 명문화, 결과 행/시간 상한 |
| S4 | **LLM 생성 SQL 의 의미 정확성** | 문법·권한은 강제, 정답 보장은 LLM 책임 | 실행 전 SQL/EXPLAIN 미리보기·승인, 결과 1000행·`MAX_EXECUTION_TIME` 상한 |
| S5 | **공유 링크 만료 부재** | 익명 공유 토큰 무기한(수동 폐기) | 기본 만료(7일) + 선택적 암호·IP allowlist |
| S6 | **LLM 비용 quota 부재** | per-user 토큰 상한 없음 | 일일 토큰 quota(429) + 비용 알림(임계 초과) |
| S7 | **감사 로그 변조 방어** | 앱 DB 내 저장(서명 없음) | 외부 불변 로그(syslog/CloudTrail) 스트리밍 + 행 HMAC 체인 |
| S8 | **SSRF 사설망 경계 OFF** | 사내 전제로 토글 OFF(메타데이터 IP 는 하드차단 유지) | 외부 배포 시 토글 ON + host allowlist, 네트워크 세그멘테이션 |
| S9 | **비밀번호 정책·재설정 응답** | 길이 위주, 임시비번 응답 평문 | 복잡도/길이≥14, 임시비번은 보안채널(메일) 전송·응답 비노출 |
| S10 | **임의 첨부 파일 검증** | MIME·크기 위주 | magic number 검증·압축폭탄 차단·(선택) 바이러스 스캔 |

> "어떤 시스템도 완벽하지 않습니다. 우리는 강점만큼이나 **잔여 위험을 문서화**하고, 각각에
> 대한 대안과 우선순위(Phase 1 빠른 보완 → Phase 3 전략)를 갖고 있습니다. 외부망 배포처럼
> 위협 모델이 바뀌면, SSRF 경계를 켜는 등 토글로 강화합니다 — **secure-by-default** 가 기본
> 자세입니다."

#### 5-C 단계별 보완 로드맵 (한 줄)

- **Phase 2(고임팩트)**: 로그인 rate limit, 비밀번호 정책, 공유 만료, 첨부 검증.

## 3. 예상 공격 질문 & 대응 (Objection Handling)

> 클라이언트·소비자·보안검토자·의사결정자가 던질 법한 **공격적·회의적 질문**을 미리
> 예측하고 대응 라인을 준비한다. 원칙: **(1) 우려를 인정한다 → (2) 구조적 근거로 답한다
> → (3) 미구현이면 정직하게 로드맵으로 넘긴다.** 방어적으로 부인하지 않는다.
> 덱의 `qa` 섹션(슬라이드)이 이 표의 압축본이다.

### 3.1 신뢰 · 정확성

**Q1. "AI 가 만든 SQL 을 어떻게 믿나? 틀린 결과로 잘못된 의사결정을 하면 책임은?"**
- 숨은 우려: 환각·오답 → 의사결정 오류, 책임 소재.
- 대응: 설계 철학은 *"AI 를 신뢰하라"가 아니라 "AI 의 작업을 검증 가능하게 만든다"* 입니다.
  ① 모든 단계의 **근거(reason)와 실제 실행 SQL** 을 그대로 노출 → 사용자가 즉시 검증.
  ② 결과 표·CSV **원본 제공**으로 추적성. ③ **read-only** 라 틀려도 '잘못된 조회'일 뿐
  데이터 파괴 0. ④ 로드맵(S4): 실행 전 **SQL/EXPLAIN 미리보기·승인**. 최종 판단·책임은
  사람에게 — DQA 는 근거를 투명하게 제공하는 도구입니다.

**Q2. "환각으로 없는 테이블·컬럼을 지어내면?"**
- 대응: insight-worker 가 **실제 스키마를 사전 분석**해 grounding(KNOWN SCHEMAS)으로
  주입합니다. 없는 객체를 참조하면 AST/스키마 allowlist 단계에서 **실패가 단계 패널에 그대로
  노출** — 거짓 성공이 아니라 명시적 에러로 드러납니다.

### 3.2 보안

**Q3. "결국 우리 DB 스키마·데이터를 외부 LLM(AWS)에 다 넘기는 것 아닌가? 데이터 유출?"**
- 대응: LLM 에 가는 것은 *사용자 질문 + 관련 스키마 메타 + 처리에 필요한 결과 일부* 이지
  **전체 DB 덤프가 아닙니다.** Bedrock **서울 리전**, 모델 학습 비사용(Bedrock 정책),
  자격증명은 게이트웨이 컨테이너에만 격리. 더 엄격한 요구엔 **on-prem/리전고정 LLM** 으로
  교체 가능(litellm 추상화). 데이터 거버넌스 수준에 맞춰 조정합니다.

**Q4. "프롬프트 인젝션으로 권한 우회나 쓰기가 가능한 것 아닌가?"**
- 대응: 권한은 LLM 이 아니라 **앱·DB 계정 레벨**에서 강제됩니다. LLM 이 무엇을 생성하든
  ① AST allowlist ② 스키마 allowlist ③ **read-only DB 계정** 3겹을 못 넘습니다. 프롬프트
  인젝션은 '의도 혼동' 리스크로 정직하게 인정하고(S3) escaping·방어 프롬프트·결과 상한으로
  완화합니다. 핵심 — *인젝션이 성공해도 쓰기는 DB 계정이 물리적으로 막습니다.*

**Q5. "관리자가 마음대로 다 보는 것 아닌가? 내부자 위협은?"**
- 대응: 43권한 RBAC + `console.access` 마스터 게이트 + **모든 관리 행위 same-tx 감사**(기록
  없는 변경 불가) + 민감필드 redaction. 내부자도 감사 로그에 남습니다. 로드맵(S7): **외부
  불변 감사 로그**로 변조 방어 강화.

### 3.3 비용 · 차별점

**Q6. "LLM 호출 비용이 통제 안 되면 청구서 폭탄 아닌가?"**
- 대응: 사용량 대시보드가 **모델·역할·계정별 토큰/추정비용**을 실시간 회계합니다. per-user
  quota 는 현재 미구현이나(S6) 로드맵에 **일일 토큰 quota + 비용 알림** 포함. 저비용 모델
  (Haiku) 라우팅으로 단가도 절감합니다.

**Q7. "그냥 ChatGPT 붙이면 되는 것 아닌가? / 이거 ChatGPT wrapper 아니냐?"**
- 대응: ChatGPT 는 ① 사내 DB 에 연결 안 되고 ② read-only 강제·스키마 allowlist·감사가 없고
  ③ 데이터가 외부로 나갑니다. DQA 의 본체는 LLM 이 아니라 **데이터 거버넌스 인프라** —
  read-only 3겹 가드, RBAC·DB-단위 격리, 전수 감사, 스키마 insight·KB(pgvector), 연결 격리.
  LLM 은 **교체 가능한 한 부품**입니다. "AI 채팅"이 아니라 "통제된 데이터 접근 계층".

### 3.4 규제 · 개인정보

**Q8. "개인정보가 해외로 나가는 것 아닌가? PIPA 위반 소지?"**
- 대응: Bedrock **서울 리전** 사용. 단, 일부 모델은 global inference profile 로 라우팅될 수
  있음을 **정직하게 명시** → 민감 PII 워크로드는 운영 정책으로 제한하고, 필요시 리전고정/
  on-prem LLM 으로 전환합니다. 감사·로그에 **쿼리 결과 원문 비저장**. 거버넌스팀과 데이터
  분류 기준 합의를 권장합니다.

### 3.5 운영 · 대체

**Q9. "AWS Bedrock 이 죽으면 서비스 전체가 멈추는 것 아닌가? 벤더 종속?"**
- 대응: litellm 게이트웨이 추상화로 **provider 교체 가능**(현재 Bedrock 단일은 사실 —
  로드맵 S13 에 fallback 체인/로컬 LLM). DB 연결·관리콘솔·감사 등 **비-LLM 기능은 LLM 장애와
  무관**하게 동작합니다.

**Q10. "느린/무거운 쿼리로 운영 DB 에 부하를 주는 것 아닌가?"**
- 대응: **EXPLAIN pre-gate + `MAX_EXECUTION_TIME` + 결과 행 상한 + read-only 계정** + circuit
  breaker(불안정 DS 격리). 운영 DB 직결이 부담되면 **replica 를 데이터소스로 등록**하길
  권장합니다.

**Q11. "DBA 를 대체해 일자리를 없애는 것 아닌가?"**
- 대응: **대체가 아니라 위임**입니다. 단순 반복 조회를 자동화해 DBA 가 고부가(튜닝·설계·
  거버넌스)에 집중하게 합니다. AI 가 만든 SQL 검증·권한 설계·데이터소스 운영은 여전히 사람의
  영역입니다.

### 3.6 회의 · 도입 저항

**Q12. "데모만 잘 되고 실제 우리 데이터에선 안 되는 것 아니냐?"**
- 대응: **파일럿(POC)** 으로 실제 read-only 계정을 연결해 검증하실 것을 제안합니다. 멀티
  엔진(MySQL·MSSQL) **실연결·라이브 검증 이력**이 있습니다 — '데모용 가짜'가 아니라 실제
  운영 중인 시스템입니다.

**Q13. "보안팀/데이터 거버넌스 승인을 못 받을 텐데?"**
- 대응: 이 자료의 **보안 섹션(구현된 통제 + 잔여 위험·대안)** 을 그대로 검토 패키지로
  제공합니다. secure-by-default 자세 + 단계별 hardening 로드맵으로, 보안팀이 **수용 기준을
  명시**하면 그에 맞춰 토글(SSRF 경계 ON 등)·우선순위를 조정합니다.

### 3.7 대응 총칙 (presenter)

- **모르면 만들지 말 것** — 미구현은 "로드맵 Phase N" 으로 정직하게. 구현된 것처럼 답하면
  신뢰가 무너진다.
- **구조로 답하라** — "믿어주세요" 가 아니라 "이 계층이 이렇게 막습니다 + 증거(단계 패널·
  감사 로그·read-only 계정)".
