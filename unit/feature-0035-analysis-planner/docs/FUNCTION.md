# Function: 결정적 분석 플래너 — 중요도 기반 커버리지 자동 시드 (ITEM-11)

## 개요

구조 변경이 없는 점검 사이클에, **아직 분석되지 않은 테이블 중 중요한 것부터** 소량씩 분석
대기열에 넣는다. 중요도는 이미 있는 구조 데이터로 결정적으로 계산한다 — LLM 을 쓰지 않는다.

라이브 실측(2026-07-31): 분석 완료 테이블 **2,040 / 17,192 = 11.9%**. 그 11.9%가 중요도와
무관하게(사용자가 우연히 클릭한 것) 뽑혀 있어, 클러스터 요약의 85%가 "상세분석 근거 없음"으로
만들어지고 대화 grounding 에 주입되는 요약 대부분이 추정이다. **아래 층을 중요도 순으로 채우면
위 세 층이 함께 올라간다.**

## 1. 우선순위 신호

| 신호 | 원천 | 가중치 | 왜 |
|---|---|---|---|
| 대화 조인 이력 | `table_relationships.source='conversation'` | **50** | 사람이 실제 질문에서 조인해 썼다는 직접 증거. 분석해 두면 다음 질문에서 바로 값을 한다 |
| 관계 차수(degree) | `table_relationships` 양방향 등장 수 | 1 | 허브일수록 먼저 이해해 두면 이웃 분석의 맥락이 된다 |

`점수 = 대화이력 × 50 + 차수 × 1`. 동점은 **이름 오름차순**으로 가른다 — tie-break 가 없으면
사이클마다 다른 테이블이 뽑혀 어떤 테이블은 영영 분석되지 않고 어떤 테이블은 반복 시드된다.

**AGE 실시간 중심성은 쓰지 않는다** — multi-hop 이 라이브 최악 82초라 tick 안에서 감당할 수 없다.
우리에게 필요한 건 정확한 중심성 값이 아니라 **순서**다.

## 2. 왜 LLM 플래너가 아닌가

무엇을 분석할지 고르는 데 LLM 은 필요 없다. 신호가 이미 구조적 데이터로 있고, 결정적 규칙은
재현 가능하며, 비용이 0이고, "왜 이 테이블이 뽑혔나"를 점수로 설명할 수 있다. LLM 이 값어치를
내는 자리는 계획이 아니라 분석과 합성이다 — 이 initiative 의 첫 결론(ADR-0031-02)과 같다.

## 3. 시드 경로 — 재구현하지 않는다

선정만 하고 큐잉은 `node_analysis.enqueue_change_analysis` 에 맡긴다. 거기에는 이미
**자격**(사람이 한 번 전체 분석한 DB만) · **그래프 실재 확인** · **cap** · **쿨다운** ·
**진행 중 run 차단**이 있다. 자동 LLM 지출의 안전장치를 두 벌 만들면 서로를 모른다.
`reason="coverage_priority"` 로만 구분한다.

## 4. 비용 경계 — 2중 상한

| 상한 | 기본값 | 범위 |
|---|---|---|
| `AGENT_ANALYSIS_COVERAGE_SEED_CAP` | 3 | **스키마당** |
| `AGENT_ANALYSIS_COVERAGE_CYCLE_CAP` | 9 | **사이클 전체** |

⚠ 사이클 상한이 load-bearing 이다. 시드는 effective-schema 루프 안에서 일어나고 큐잉 경로의
cap·쿨다운은 **스키마 단위**라, 사이클 상한이 없으면 스키마 수(라이브 수백)만큼 곱해진다.
feature-0033 에서 같은 계열의 결함을 지적받았고 "검증된 경로를 쓰니 괜찮다"고 넘겼다가
여기서 다시 만났다.

그 위에 백그라운드 토큰 예산(feature-0032)과 전역 kill-switch 가 있다.

## 5. 스키마 축 정합

- 후보 조회는 `rag_objects.schema_name` 이 아니라 **`object_key` prefix** 로 맞춘다 —
  MSSQL 은 그 컬럼이 리터럴 `dbo` 라 DB 차원이 소실되고, 그래프 노드 키는 effective schema
  (=DB명)를 쓴다. 두 엔진 모두 `object_key` 가 `<ds>:<db>.…` 로 시작한다.
- prefix 검사에 `LIKE` 를 쓰지 않는다. 식별자에 `_` 가 흔한데(`dk_data_release`) LIKE 는
  그것을 "임의의 1문자"로 해석해 **다른 스키마의 테이블이 섞인다**. `strpos(…) = 1` 을 쓴다.
- `DISTINCT` 필수 — `rag_objects` 유니크 키에 `conversation_id` 가 포함돼 같은 테이블이 여러
  행일 수 있다. 중복을 두면 상한 3이 같은 테이블 3개가 되어 실제로는 하나만 시드된다.

**알려진 근사**: 관계 점수는 스키마로 좁히지 않고 datasource 단위로 집계한다.
`table_relationships` 의 schema 는 원본이라 effective schema 와 어긋나므로, 같은 datasource
안의 동명 테이블이 합산되는 오차를 감수한다 — 스키마를 잘못 맞춰 **신호가 통째로 0이 되는 것**
보다 안전한 실패 방향이다. 우선순위는 순서만 정하면 되는 근사 신호다.

## 6. fail-soft

선정·조회 실패는 빈 목록, 시드 경로 전체가 예외를 흡수한다. insight 스캔은 이 기능과 무관하게
계속 돈다. RO 연결·커서는 finally 에서 닫는다.
