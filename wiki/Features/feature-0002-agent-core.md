## 1. 개요

자연어 요청을 받아 **LLM tool-call loop** (SQL 작성·실행·메모리·지식·복구) 를 수행하는 핵심 에이전트 feature. Postgres `agent_kb` (pgvector, runtime + KB 단독 정본) 위에서 step loop 가 작동하며, insight worker 가 백그라운드로 schema/table 인사이트를 캐시한다.

> **2026-06 멀티 데이터소스 시대**: 단일 MySQL replica → **N 개 데이터소스 (MySQL·MSSQL)** 동시 분석으로 일반화. dialect 추상화 + datasource registry (envelope 암호화) + DB-단위 접근 + datasource-aware insight 가 배포·라이브검증 완료. §2.5 참조.

## 2. 상세

### 2.1 책임 경계

- **입력**: 사용자 질문 + `.env` agent 설정 + MySQL/MCP 런타임
- **출력**: CLI 응답 (Rich Markdown) / Web UI JSON / 메모리·지식·로그 기록 / SQL 실행 결과
- **side-effect**: `agent_memory` MySQL DB write · `agent_kb` Postgres dual-write (M2~) · `artifacts/shared/logs/insight_worker.log` 등

### 2.2 핵심 흐름 (FUNCTION §7)

1. `agent_core.run_agent()` 진입 → OpenAI SDK client 준비 (Bedrock gateway 경유)
2. `agent_memory` 대화/메시지/KV 보장 + `origin_request` / `thread_goal` 3-state 판정
3. `_build_knowledge_context()` 로 SCHEMAS / RELEVANT TABLES 블록 주입
4. **Step Loop**: `tool_calls` 최대 3 개씩 실행 (`execute_sql` / `describe_table` / `describe_routine` / `search_tables` / `get_sample_rows`), 결과 메모리 기록. tool_calls 없으면 최종 답변.
5. 루프 상한 = `AGENT_MAX_STEPS` + `AGENT_TIMEOUT_SEC * 3`, Web UI "중단" / "즉시 답변" 감지.

### 2.4 RBAC role

- `agent_kb_rw` — SELECT/INSERT/UPDATE/DELETE on 4 tables + VIEW SELECT (M2+ 사용)
- `agent_kb_ro` — SELECT only (read-only audit / debug)
- Application-level: `kb.read.own` / `kb.read.any` / `kb.mutate.any` / `kb.export` (별 cycle)

## 3. 특징

- **fail-soft**: PG unavailable 시 `_pg_available()` False → MySQL only path 자연 fallback.
- **fail-loud (`AGENT_KB_PG_REQUIRED=1`)**: M2-b+ 부터 깨진 schema 위 시작 차단.
- **cross-DB audit (best-effort)**: KB mirror write 가 MySQL `WebAuditEvents` 에 `kb.write.mirror` row append.
- **`pg_branch` tag**: `RETURNING id, (xmax = 0)` 패턴으로 INSERT vs UPDATE 구분 — `_pg_op_local` threadlocal capture.
- **insight worker fail-safe**: heartbeat stale 시 `_should_run_inline_insight_scan()` 가 인라인 scan 트리거.
- **insight 효율·안정성 (2026-07-03, 정본 REPORT — 비사용자향)**: ① 동일구조 테이블 그룹화(insight-table-grouping) — 날짜/번호 suffix 만 다른 샤드를 (base_stem, fingerprint)로 묶어 **대표 1회 LLM 분석 + 형제 LLM-free fan-out**(신규 일자 샤드는 KV 상속으로 LLM 0), per-table `table_insight` fact 유지로 NL→SQL 무회귀. ② 부하 분산(insight-load-spread, cross-feature 0016) — 실패 대상 격리·재시도 backoff + graph sync batched commit/incremental(57,000+ 요소 개별 MERGE WAL fsync ~5.7만 → ~114). ③ healthcheck false-negative 해소(insight-heartbeat-liveness) — 긴 cycle 중 진행-중 heartbeat throttle 갱신. ④ 요청레벨 LLM fallback(claude-corp→root→edge gemma, 정본 feature-0007).

- **예약 작업(SQL Server Agent) 조회가 구조적으로 도달 불가였다 — 정제기 비대칭 + 거부 안내 파생** (2026-08-31, conversation_audit) — 구조화 도구의 이름 인자는 **두 문맥**으로 나뉘는데 한 정제기만 쓰였다. 식별자 문맥(뷰·트리거·시퀀스·스키마·테이블)은 인용 구분자를 **제거**해야 한다(SQL 이 `[…]` 로 인용하므로 `]` 를 남기면 인용을 닫고 2차 SQLi 가 된다 — 완화 금지 영역). 그러나 SQL Server Agent 작업명은 `msdb.dbo.sysjobs.name` 의 **임의 문자열 리터럴**이라 같은 정제기를 쓰면 `[DK] Ranking Update` 가 `DK Ranking Update` 로 훼손돼 **영구 미매칭**이 된다 — 관측 서버 작업 83개 중 **73개(88%)가 `[` 접두**였다. 리터럴 문맥에는 문자를 보존하고 역슬래시·제어문자만 제거하는 별도 정제기를 쓰며, 따옴표 이중화는 **삽입 지점 한 곳**(방언 SQL 빌더)이 1회만 한다(caller 가 함께 이중화하면 따옴표가 두 번 늘어 다시 미매칭). 두 번째 축은 **거부 안내**다 — 차단 메시지가 대체 도구를 지목하지 않으면 모델은 대안이 없다고 판단해 우회를 자작하다 "확인 불가" 로 단정한다. 안내 목록을 단일 출처에 두고 **상시 노출 도구 세트와의 정합을 테스트로 강제**해(새 `search_*`/`describe_*` 도구가 추가되면 스위트가 깨져 안내 갱신을 강요한다 — 옛 4개 고정으로 feature-0040 의 두 도구가 누락돼 있던 drift 의 재발 봉인), 확장 전용 도구는 **광고하지 않는다**(모델이 부를 수 없는 이름을 권하면 새 마찰이 된다). 보안 경계는 불변 — freeform 의 msdb 하드 차단·허용 DB fail-closed·작업 단계의 제품 경계 필터는 그대로이고, 시스템 DB 차단에 붙는 것은 **안내 문자열뿐**이며 그 안내가 가리키는 경로는 이미 존재하던 고정 투영 도구다. 파서 기준 봉쇄를 적대 입력 13종(리터럴 노드 갇힘 · 문장 수 1 · 고정 조인 4뷰 밖 테이블 0)으로 잠갔다. 배포 기록 + 마찰 원장 2항목 · 학습 2건 동반.
- **용어 통용범위(`term_tier`) 축 — 전역 용어와 제품 용어를 가른다** (2026-09-01, `glossary-term-tier`, Major §12.3 · alembic 0058): 축이 비대칭이었다 — 읽기는 `[제품 → common → '']` 2단 캐스케이드인데 쓰기는 **항상 제품 scope 하나**였고, 프롬프트가 confidence 를 「얼마나 재사용 가능한가」로 정의해 **범용일수록 점수가 올라 가장 좁은 자리에 박혔다**(라이브 `kb_glossary` 732행 중 auto 722행이 11개 제품 scope 에 흩어지고 `멱등성` 한 개념이 4 scope 7행). tier ∈ {product · org · general} 로 저장 위치를 가르되 `general` 은 저장하지 않고 되살릴 수 있게 남기고(`skipped_general`), `org` 후보는 confidence 와 무관하게 항상 검토 큐다(전역 사전은 모든 제품 프롬프트에 실려 blast radius 가 N배). 표기변형 정규화는 alembic 0058 함수 인덱스 식과 **한 벌이어야 한다**. 소급 정리는 별도 실적용(105행 · 되돌리기 검증 동반).
- **큐레이션의 소비자가 사라져 있었다 — 지식베이스가 외부 AI 프롬프트에 실린다** (2026-09-01, `kb-external-reach`, Major §12.3): 서버 계정 AI 시절 `_build_knowledge_context()` 가 주던 **9개 grounding 층**이, 외부 AI 전환 뒤 **그 시점** 유일한 컨텍스트 진입점이던 MCP `get_task_context` 에서는 **클러스터 요약 1개 층**뿐이었다 — 「등록했는데 AI 가 모른다」의 출처다. 용어사전 · ENUM 코드 · 테이블/컬럼 설명 · 샘플 쿼리 · 관계를 번들에 싣고(층별 fail-soft · 빠진 층은 **이름을 밝혀** notes 에 · 번들 상한과 절단 표기), product 축은 주변 상태가 아니라 **그 task 의 ProductId** 에서 해석한다. L0 통계 수집은 LLM 게이트와 분리했다 — 전환일 이후 `metadata_table_stats`·`metadata_column_stats` 신규 0행이었고 직접 호출 경로를 가진 `table_relationships` 는 같은 기간 719건 갱신(대조군).
- **grounding 매칭 — 한도는 «후보»에, 판정은 «낱말»로** (2026-09-01, `kb-grounding-match`, Major §12.3): ① 용어 조회가 scope 전체를 `길이 내림차순 LIMIT 200` 으로 잘라 읽어 **언제나 가장 짧은 것부터** 빠졌다(239행 중 39행 상시 누락 — `AID`·`CCU`·`PvE`·`재화` 등 DBA 가 가장 자주 쓰는 약어) ② 판정이 부분 문자열이라 한 제품의 `BillingType` 이 다른 제품 ENUM 컬럼 `Type` 을 끌어왔다. 한도를 **매칭 후보**에만 걸고 낱말 경계로 판정하되 경계 규칙은 **비대칭**이다 — 뒤쪽 한글까지 막으면 `재화를`·`증분 복제와` 같은 정상 표현이 전부 깨진다. 한도에 닿으면 무음 절단 대신 로그로 말한다.
- **KB 근거는 «자동 주입»이다 — 도구 호출에 기대지 않는다** (2026-09-02, `kb-prompt-grounding`, Major §12.3) — 부트스트랩 계정에 AI 를 연결해 **실제 대화를 완주**시켜 보니 직전 두 cycle 이 만든 KB 도달 경로가 **라이브에서 여전히 0 기여**였다(질문: `steam_billing_log` 의 status 코드값 → 답변: 「등록 메타데이터 어디에도 없습니다」). 서버는 옳았다 — 같은 시각 같은 제품에서 `get_task_context` 를 직접 부르면 그 정의가 분명히 나온다. 문제는 **AI 가 그 도구를 한 번도 부르지 않았다**는 것이고, 러너가 안내하는 도구 목록에 그것이 없었기 때문이다(`list_schemas`·`describe_table`·`execute_sql` 등 **조사** 도구만 나열). 즉 전환이 바꾼 것은 위치가 아니라 **성격**이다 — 무조건 주입이 「AI 가 부르면 받음」이 됐다. `claim_request` 응답에 `kb_context`·`kb_notes` 를 실어 **자동 주입으로 되돌렸고**, 매칭은 가드 래퍼가 붙지 않은 **원문**으로 한다(marked 로 하면 canary·각인 안의 낱말이 용어에 걸린다). 러너는 받은 근거를 질문보다 앞에 놓고 「이미 조회된 것이니 다시 조사하지 마라」를 덧붙이며, 값이 없으면 블록 자체를 생략한다(서버·러너 버전 조합이 어긋나도 안 깨진다). ⚠ 정직: 배치가 러너 `compose_prompt` 에 있어 **구버전 러너에는 안 실린다** — 「서버에만 두면 러너 버전과 무관」은 사실이 아니었고, 서버가 `hb.stale_build` 로 갱신을 안내하는 것이 그 경로다. 라이브 전후 대조: 프롬프트 3,535 → 4,659자, 「어디에도 없습니다」→ ENUM·관계 층까지 인용하고 미정의분은 「미확인」 유지.
- **datasource health 텔레메트리가 매 사이클 통째로 유실되고 있었다** (2026-09-02, `ds-health-persist`, Minor §12.3) — insight 사이클이 `datasource_health_persist_failed err=AmbiguousParameter` 만 남겼다. upsert SQL 한 줄에서 같은 파라미터가 **두 타입 문맥**(`IS NULL` / `to_timestamp()`)에 쓰여, 값이 float 이면 드라이버가 타입을 실어 통과하지만 `None` 이면 타입 없는 NULL 이 가 Postgres 가 추론에 실패한다(42P08). **한 번도 체크되지 않은 datasource 가 섞인 사이클에서만** 터졌고 그 한 행이 batch 전체를 되돌려 health 가 통째로 사라졌다 — 「가끔 되고 가끔 안 되는」 형태라 더 안 보였다. 양쪽 자리표시자에 `::double precision` 명시 캐스트. ⚠ 뮤테이션 1차에서 한쪽만 `::text` 로 바꾼 뮤턴트가 **생존**했다(`"::double precision" in sql` 포함 검사가 부분 결함을 못 잡는다) — 모든 캐스트의 타입 **집합**을 단언하도록 강화해 5/5 KILL.
- **임베딩 없이 KB 를 외부 AI 에 잇는다 — 문자 후보 + 외부 판단** (2026-09-07, `kb-external-search`, Minor §12.3 · ADR-20260907T185500): 로컬 임베딩이 철거되자 샘플의 vector 필수 반환과 편집 시 stale 강등이 **KB 전달을 끊었다**. 새 임베딩 API 를 들이는 대신 서버가 `pg_trgm` 으로 문자 후보를 찾아 `claim_request.kb_context` 와 `get_task_context(focus=…)` 로 전달하고 **의미 적합성 판단·질문 재구성은 외부 AI 가 수행**한다. 샘플은 제품+common 의 **승인·active** 행만 문자 검색하며 **벡터 NULL 도 검색된다**(질문 수정 시 해당 벡터는 무효화 · SQL 신선도 active/stale/retired 유지 · 기존 벡터·볼륨 일괄 삭제 없음 · 모델 간 벡터 혼용 없음). 기존 MySQL schema/table 인사이트는 **엔진을 포함한 endpoint hash** 와 제품의 허용 DB 로 제한한다(schema 키는 DB 정확 비교 · table 키는 점으로 나눌 수 있는 **모든 DB 접두**를 인가 · hash 로 잘린 키 제외 · 점이 포함된 이름은 보수적으로 제외될 수 있다). **MSSQL 레거시 인사이트는 catalog 출처가 불명확해 원문 검색에서 제외**하고 `list_schemas`/`describe_schema`/`describe_table` 로 확인하도록 안내한다. ⚠ **문자 검색은 의미 검색과 동등하지 않고 무매칭은 객체 부재의 증거가 아니다** — 식별자·구체 용어로 focus 를 좁혀 재검색하도록 안내하고 문서별 1,200자 발췌 위치를 표시한다. 문서 검색은 **읽기 전용 연결 + 5초 statement timeout** 이고 층별 장애는 notes 로 전달하며, 현재 대화·제품 권한을 재확인하고 응답은 **비신뢰 근거로 각인**한 뒤 전체 JSON 크기를 원장에 기록한다. `titan-embed`·`bge-m3[:latest]`·`ollama/*` 잔존 설정은 **네트워크 호출 전에** 비활성화된다. 검증 203 PASS(`test-runs.d/TASK-20260907T181510-kb-external-search.md`).
