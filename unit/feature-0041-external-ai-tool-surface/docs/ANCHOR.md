# ANCHOR: feature-0041 external-ai-tool-surface

## §1. 외부 관점 요약

처음 코드를 여는 사람은 이렇게 묻는다. **"이 제품엔 이미 외부 AI용 Conversation
API(feature-0023)가 있는데 왜 또 만들지? `ask` 하나면 되는 것 아닌가?"**

답: 0023에서 외부 AI는 *질문하는 사람* 역할이고 추론은 우리 LLM이 한다 — 토큰 비용·
가용성·쿼터가 전부 우리 것이다. 본 기능은 그 관계를 뒤집는다. 우리는 **도구와 컨텍스트만
제공하고, 추론 루프는 사용자 머신의 AI 런타임에서 돈다.** 그래서 LLM 비용이 호출자에게
귀속되고, 우리 계정 쿼터 소진(2026-08-07 claude-corp 7일 쿼터 100% 소진 사례)이 서비스를
멈추지 않는다. 대신 답변 품질·검증 통제권을 잃으므로, **그동안 프롬프트에 주입하던
grounding 층을 조회 가능한 도구로 다시 노출하는 것**이 이 기능의 실질적 무게중심이다.

두 번째 의문: **"왜 신원과 비용 주체가 다르지?"** 로그인 세션(사용자별)이 권한·감사·데이터
스코프를 정하고, LLM 토큰은 그 세션을 호출하는 **머신의 AI 런타임**이 부담한다. 한 머신에서
A·B·C 계정 세션을 동시에 열 수 있으므로 신원:비용 = N:1이다. 이 비대칭이 본 기능의 거의 모든
설계 제약(세션 격리·원장 이원화·자기신고 대조)의 출처다.

## §2. 대안 분기

- **Alt-A: feature-0023을 확장해 `ask` 옆에 원시 도구를 추가.** 페르소나: 표면을 늘리지
  않으려는 운영팀. 안 고른 이유: 0023 ANCHOR §1/§3이 "외부 AI가 *assistant 답변*을 받는다"를
  목적으로 못박고 있고, 원시 데이터 도구는 신뢰경계(우리 LLM → 통제 밖 LLM)·비용 주체·품질
  책임이 전부 다른 축이다. 같은 unit에 두면 절대 denylist와 토큰 안전 기본 scope 설계가 두
  목적 사이에서 흔들린다. 0023은 `ask` 축으로 유지하고 본 feature와 상호 참조만 둔다.

- **Alt-B: BYOK — 사용자별 Anthropic API 키를 서비스가 보관하고 서비스가 호출.** 페르소나:
  기존 대화 UI를 그대로 두고 비용만 옮기고 싶은 팀. 안 고른 이유: ADR-0026이 동형 구조(API
  Vault)를 "사내 한정 운영에서 사용자별 키 입력 진입 장벽 부적합 + 두 trust 모델 병존 부담"으로
  이미 폐기했다. 자격증명 보관 책임이 되살아나고, prompt cache가 사용자 수만큼 파편화돼
  **총 토큰 비용이 오히려 오른다**(캐시 read 0.1× 이점 상실 + write 1.25× 중복).

- **Alt-C: 사용자 Claude 구독 계정의 OAuth 토큰을 서버가 보관·대리 호출.** 페르소나: "다들
  구독이 있으니 그걸 쓰자"는 팀. 안 고른 이유: refresh token 장기 보관은 **계정 지속 접근권**
  보관이라 API 키보다 보안 등급이 낮고, 구독은 자사 인터페이스 사용 전제라 지원되는 통합
  경로가 아니며, 구독 쿼터는 과금이 아니라 **제한**이라 소진 시 "비용 이전"이 아니라 그
  사용자의 서비스 정지가 된다. 계정 2개로도 겪은 회전·소진 운영 부담이 N배가 된다.

- **Alt-D: 우리가 MCP 클라이언트가 되어 사용자 AI 엔드포인트를 역호출.** 페르소나: 기존 웹 UI를
  유지한 채 비용만 옮기려는 팀. 안 고른 이유: 사용자 AI 엔드포인트 접근 자격증명이 필요해져
  Alt-C의 보관 문제가 그대로 돌아오고, 사용자 로컬 런타임은 상시 도달 가능하지 않다.

### §2.1 AC-7 답변 보존의 저장 위치 (2026-08-14, ADR-002 후속)

- **Alt-E(원안): `agent_runtime.messages` 적재.** 페르소나: 외부 AI 기록도 일반 대화처럼
  읽고 싶은 운영자. FUNCTION §6 이 원래 지목한 경로다. 안 고른 이유: `messages` 는
  `core_conversations` 에 **외래키로 묶여** 있고 외부 task 는 `ConversationId` 가 NULL 이라,
  task 마다 대화 행을 만들어야 한다. 그 순간 그 테이블을 읽는 **47개 파일**(폴더·그룹 멤버·
  차단·분기 체이닝 `active_leaf_message_id`·가시성 윈도우·redteam·insight·사용량 집계)이
  전부 "외부 AI 대화를 어떻게 취급할 것인가" 를 새로 답해야 한다. **보존 하나를 위해 Critical
  표면을 한 번 더 넓히는** 교환이고, 이 feature 는 이미 표면 확장 때마다 결함을 냈다.

- **Alt-F(채택): `WebAiTasks` 전용 컬럼.** 원 질문이 이미 사는 자리에 답변을 함께 둔다.
  변경 반경이 `ai_tools.py` + 부트스트랩 스키마 + 테스트로 닫히고, FK 가 없어 대화 계약과
  무관하다. 사용자 요구의 1차 목적은 **보존**이며 열람은 전용 뷰로 별도 충족한다
  (사용자 결정 2026-08-14: 열람도 같은 cycle 에 포함). FUNCTION §6 을 이 설계로 수정한다 —
  스펙이 구현을 앞지른 채 남는 것이 이 feature 의 반복 결함이었으므로, 스펙 쪽을 맞춘다.

- **Alt-G: `WebAiTasks` 저장 + `messages` 투영(이중 기록).** 안 고른 이유: 두 원장의 정합을
  영구히 져야 하고(편집·삭제·분기 시 어느 쪽이 정본인가), Alt-E 의 47경로 문제를 그대로
  물려받으면서 정합 부채만 추가된다.

## §3. 가정된 사용 시나리오

6개월 후, 데이터 분석가 P가 자기 노트북에서 Claude Code를 쓰고 있다. 사내 DB에 물어볼 게
생겨 이 서비스의 공개 가이드 문서를 AI에게 알려주면, AI가 스스로 클라이언트 등록을 하고 인가
URL을 만들어 제시한다. P는 브라우저에서 사내 계정으로 로그인하고 동의한다 — 이 사람 승인
단계가 본 기능의 신원 축을 성립시키는 지점이다.

이후 AI는 `open_task("작년 4분기 환불 사유 top10")`으로 시작해 `get_task_context`로 관련
스키마·도메인 개요·클러스터 요약·통계 증거를 한 번에 받고(우리 LLM 호출 0), `execute_sql__P`로
몇 차례 조회한 뒤 답을 만들어 `submit_answer`로 제출한다. 그 대화는 사내 웹의 P 계정 대화
목록에 남아 나중에 브라우저에서 열어볼 수 있다. 소비된 LLM 토큰은 전부 P의 노트북 Claude
Code 구독에서 나갔고 우리 `llm_usage`에는 한 줄도 남지 않는다 — 대신 `tool_call_usage`에
조회 부하가 기록된다.

같은 노트북에서 동료 Q의 계정으로도 세션을 열면 도구 이름이 `execute_sql__Q`로 갈라지고 반환
데이터마다 `account=Q` 각인이 붙어, AI가 두 세션을 섞지 않도록 유도된다. 그럼에도 섞였다면
`submit_answer`의 `source_tasks` 선언과 실제 결과셋 대조에서 걸려 원장에 남는다.
