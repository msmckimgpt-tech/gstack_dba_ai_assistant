# TASK-20260903T160000 — 아픈 러너를 기다리게 하던 150초

## 1. 요청 (사용자, 2026-09-03)

> 「사용자 입장에서, 150는 너무 깁니다. (사실, 10초 이상 소요되는 부분도 길다고 체감됩니다.)
>  해당 부분도 고려해주세요.」

## 2. 직전 cycle 의 설계가 뒤바뀐 자리

`TASK-20260903T140000` 은 「응답 없음이 관측된 러너」에 **150초 상한**을 뒀다. 무한 대기는
없앴지만, **이미 못 쓴다는 것을 아는 상태에서 150초를 더 기다리게 했다.**

그 150초의 정체는 «사용자를 위한 시간»이 아니라 **«회복됐는지 확인하려는 우리 편의»** 였다 —
아픈 러너도 계속 시도해야 자기 치유가 성립하므로 그 시도를 사용자 질문에 얹은 것이다.
**그 비용을 사용자 대기 시간으로 지불하고 있었다.**

## 3. 조치 — 얽힌 두 목적을 분리한다

| 목적 | 종전 | 이제 |
|---|---|---|
| 사용자 답변 | 150초 기다린 뒤 안내 | **AI 를 부르지 않고 즉시** 안내(체감 0초) |
| 회복 감지 | 그 150초로 겸용 | **배경 스레드**(`caps.schedule_health_recheck`, 쿨다운 60초) |

- 게이트는 `ask_local_ai` **가장 앞**에 둔다 — 프롬프트·명령 조립 뒤에 두면 그만큼 사용자가
  기다리고, 그 시간은 어차피 버릴 준비 작업에 쓰인 것이다.
- 회복 확인을 **없애지 않았다**. 없애면 「못 쓴다」가 영구 잠김이 되어 복구된 러너가 영원히
  막힌다(직전 cycle 과 같은 판단). 바뀐 것은 **누가 기다리는가** 뿐이다.
- 회복 확인은 **협상 경로를 재사용**한다(`detect_runtimes`) — 「응답하는가」의 기준이 두 벌이
  되면 한쪽은 반드시 낡는다.
- ⚠ 회복 확인은 **실제로 AI 를 호출**한다(사용자 계정 토큰). 그래서 쿨다운을 둔다 — 아픈
  동안 매 질문마다 호출하면 남의 계정 쿼터를 우리가 태우는 셈이다.
- **건강한 러너는 이 경로를 타지 않는다**(무제한 유지) — 정상 질문이 안내문으로 바뀌면 안 된다.

### 5.1 (폐기된) 당시 서술

러너 지문 `d69d7da6928a` vs 배포본 `4669f0192526` 인데 감사 원장에 `stale_build`·self-update
사건이 **0건**이라, 「서버가 stale 을 알리지 않거나 러너가 갱신을 시도하지 않는다」고 적었다.

### 5.2 실측 정정 — 자동 갱신은 정상 동작했다

```
11:48:56  run.selfupdate  local_build=d69d7da6928a → new_build=4669f0192526
                          "러너를 최신본으로 갱신했습니다 — 지금 다시 시작합니다"
11:48:56  run.stop        reason=selfupdate  uptime_sec=4828
11:48:57  run.start       build=4669f0192526  pid=40968
11:48:58  run.ready       startup_ms=987
```

서버 하트비트도 `RunnerBuild=4669f0192526` 로 갱신됐다(실측 02:56 UTC).

### 5.3 왜 틀렸나 — **부재를 근거로 결론 냈다**

두 가지가 겹쳤다:

1. **로그 침묵은 설계된 것이다.** `stale_build` 신호는 self-update 가 가능하면 **신호만
   세우고 로그를 남기지 않는다**(2026-09-02 사용자 결정 — 러너 파일은 거의 매 배포에서
   바뀌므로 매번 경고하면 로그가 «할 일» 로 가득 차는데 정작 할 일은 없다). 그 침묵을
   「신호가 오지 않았다」로 읽었다.
2. **스냅샷으로 영구 상태를 단정했다.** 11:35 에 관측하고 「미발동」이라 적었는데 실제
   발동은 11:48 이었다. 자기갱신은 **유휴 + 협상 종료 + 최소 간격**을 모두 만족할 때
   일어나므로 관측 시점에 아직 조건이 안 맞았을 뿐이다.

같은 부류의 오판을 이 세션에서 **두 번** 했다(`TASK-20260903T110000` §2 의 `exit` 필드
부재 판독은 맞았지만, 여기서는 부재가 «설계된 침묵»이었다). 교훈: **부재를 신호로 읽기 전에
「그 신호가 이 조건에서 기록되도록 설계돼 있는가」를 먼저 확인한다.**
