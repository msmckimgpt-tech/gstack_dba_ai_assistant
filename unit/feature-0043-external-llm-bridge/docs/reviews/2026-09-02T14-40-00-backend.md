### 2. Cross-domain concerns

- 스키마(fast/slow 양 경로 호출)·commit(autocommit=True)·첫 협상 동시성은 **정상**으로 확인.
- `prune_stale` 의 while 루프는 종료를 보장한다(실행으로 확인). 단 바이트 예산이 개수 예산보다
  먼저 물린다 — 정제 최대 런타임 1개가 14,189B 로 `BASELINE_MAX_BYTES=16384` 에 근접해
  **2개면 조용히 1개로 절단**된다(`BASELINE_MAX_RUNTIMES=8` 보다 훨씬 낮다). 두 상수가 서로
  일관되지 않는다.
- 협상은 **1회**만 돈다 — 첫 하트비트 실패가 그 프로세스 생애 전체의 baseline 경로를 죽인다
  (기능 강등이지 hang 은 아니다).
- 서버 병합 실패 시 `caps_baseline: []` 가 실리고, 러너의 제자리 갱신이 **모든 키를 pop** 한다
  → 일시적 서버 실패 한 번이 러너 원장을 지운다. 옆 주석의 「키가 없으면 건드리지 않는다」가
  빈 목록 케이스를 덮지 않는다.
- `connect_status` 가 폴링마다 `account_runner_profile` 질의를 하나 더 낸다 — 결함 #1 과
  곱해지면 stale 러너 탭 하나가 5초마다 ~2질의를 무한히 낸다.

### 3. Challenge to current spec

- **`caps_pending` 에는 「진행 중」을 관측할 수단이 없다.** 러너 협상은 1회이고 서버는
  `not _reported` 로만 추론한다. 협상이 실패한 러너(라이브 실제 사유 =
  `OAuth access token has expired`)에서는 화면이 「곧 표시됩니다」를 **영원히** 말한다.
  이 cycle 은 근거 없는 *지시* 를 없애고 근거 없는 *약속* 을 설치했다 — 사용자는 이제
  다음 행동을 아예 잃는다. 러너가 협상-종료(성공/실패 + 이미 포착한 사유)를 신고하고
  서버가 그 사실로 pending 을 닫는 것이 옳은 축이다.
- **「사용일 기준 만료」가 실제로는 「러너가 켜져 있었는지 기준」이다.** `last_used_at` 은
  하트비트 신고로 갱신되고, 사용자가 그 런타임을 고른 사실과는 무관하다. 그것이 결정된
  의미일 수 있으나 코드·주석은 「사용일」이라 적고 있고 둘은 같은 사실이 아니다.
