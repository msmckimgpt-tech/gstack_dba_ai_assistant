# ANCHOR: feature-0044-qa-staging-pipeline QA 스테이징 파이프라인

## §1. 외부 관점 요약

"이미 무중단 배포 스크립트가 돌아가고 있는데, 왜 파이프라인을 새로 설계하나?" 라는 의문이
가장 먼저 나올 지점이다. 이유는 현행 스파인이 **배포 대상 호스트에서 소스를 체크아웃하고
직접 이미지를 빌드하는 전제**로 만들어졌기 때문이다. QA 머신은 인터넷이 차단된 격리망이라
그 전제가 성립하지 않고, 사내 미러를 붙여 빌드하더라도 개발 머신과 다른 시점의 의존성을
받아 "검증한 바이트"와 "배포한 바이트"가 달라진다.

두 번째 의문은 "QA 인데 왜 이렇게 보안을 무겁게 잡나?" 이다. 이유는 QA 머신이 라이브 데이터
복제본을 **마스킹 없이** 담기로 결정됐기 때문이다. 이름은 QA 이지만 자산 등급은 운영이다.

세 번째는 "배포 성공인데 왜 완료가 아니라고 하나?" 이다. 이 서비스의 사용 경로가 웹 화면이
아니라 **사용자 개인 머신의 MCP 연결**이라, 컨테이너가 전부 healthy 여도 VPN DNS·사내 CA·
OAuth discovery 중 하나만 어긋나면 사용자는 진입 자체를 못 한다.

## §2. 대안 분기

- **Alt-A: 소스만 미러하고 QA 머신에서 빌드.** 페르소나: 레지스트리 등 새 인프라 없이 최소
  변경으로 끝내려는 팀. 안 고른 이유: 폐쇄망에서 빌드 재현성이 성립하지 않는다. 의존성 lock
  없이 사내 미러를 쓰면 시점에 따라 다른 이미지가 나오고, 그 차이는 늦게·이상하게 드러난다.
  "검증한 것과 배포한 것이 같다"는 보장이 사라지면 QA 단계 자체의 의미가 없어진다.

- **Alt-B: 개발 머신이 VPN 으로 QA 에 직접 push (push-based CD).** 페르소나: 파이프라인 도구
  도입 없이 스크립트로 해결하려는 팀. 안 고른 이유: 배포 자격증명과 인바운드 경로가 개발
  머신에 상주하게 되어, 개발 머신 침해가 곧 운영 등급 데이터 접근이 된다. 사용자가 확정한
  전달 경로(사내 GitLab 미러 경유)와도 어긋난다.

- **Alt-C: Kubernetes + ArgoCD 로 GitOps 전면 도입.** 페르소나: 다중 노드·다중 환경을 운영하는
  플랫폼 팀. 안 고른 이유: 단일 호스트 23서비스 규모에 오케스트레이터 전환은 QA 도입과
  독립된 큰 결정이고, 현행 compose 스파인의 무중단 롤링·soak·last-good 롤백은 이미 라이브에서
  실증됐다. 다만 **pull + 선언적 매니페스트**라는 GitOps 의 핵심 아이디어는 채택한다.

- **Alt-D: 별도 QA 없이 라이브를 검증 환경으로 겸용.** 페르소나: 리소스가 빠듯한 팀.
  안 고른 이유: 사용자가 QA 머신 도입을 이미 결정했고, MCP 표면이 외부 AI 런타임에 열리는
  만큼 검증 없는 라이브 직행의 위험이 크다.

## §3. 가정된 사용 시나리오

사내 DBA 담당자가 자기 노트북에서 VPN 에 접속한 뒤, Claude Code 에 QA 서비스의 MCP
엔드포인트를 등록한다. 브라우저가 열리고 사내 계정으로 로그인·동의하면 연결이 맺어진다.
담당자는 "이번 주 특정 게임 스키마의 재화 지급 추이를 보고 싶다"고 자기 AI 에게 말하고,
AI 는 MCP 도구로 QA 서비스의 스키마·메타지식을 조회해 답을 만든다. 추론은 담당자의 계정
LLM 이 하고, 서비스는 데이터와 도구만 준다. 조회 이력과 최종 답변은 QA 서비스 쪽 대화
기록에 남아 나중에 운영자가 열람할 수 있다.

이 시나리오에서 담당자는 배포 파이프라인의 존재를 전혀 모른다. 담당자가 체감하는 것은
"연결이 되는가 / 도구가 답을 주는가" 둘뿐이며, 그래서 배포 완료 판정도 그 두 가지를
실제로 확인하는 것이어야 한다.
