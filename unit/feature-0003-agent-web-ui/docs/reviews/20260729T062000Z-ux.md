## 1. Findings (발견)

### F1 (BLOCK) — 목록 뷰의 ×는 **자기 자신의 계약을 지키지 않는다**: bucket·배지 미동기화 → 삭제한 파일이 되살아나 보인다

이번 변경이 스스로 선언한 계약은 TASK.md 에 이렇게 적혀 있다:

> "성공 여부를 **반환해 caller 가 로컬 상태를 조건부로 갱신**한다"

그런데 새로 추가된 caller 는 반환값을 **버린다**(`app.js:10114-10123`):

```js
delBtn.addEventListener("click", async () => {
  delBtn.disabled = true;
  try {
    await _deleteConversationAttachment(a.id, a.original_filename);  // 반환값 미사용
  } finally {
    delBtn.disabled = false;
  }
});
```

pill 쪽 caller 는 계약을 지킨다(`app.js:9649-9652` — splice + `_renderAttachmentPills()`).
목록 쪽은 **`state.composerAttachments.byConv[key].items` 를 전혀 건드리지 않는다.**
`_deleteConversationAttachment` 안에서 하는 사후 처리는 `_loadConversationAttachmentList` 재호출
하나뿐이고(`app.js:9673-9675`), 그 함수는 `#attachSidePanelList` 만 다시 그린다 — bucket 도,
개수 배지도 손대지 않는다.

두 가지 관측 가능한 결과:

**(a) 첨부 개수 배지가 즉시·확정적으로 틀어진다.**
`#composerAttachCountBadge` 를 쓰는 코드는 앱 전역에서 `_renderAttachmentPills` **단 한 곳**
(`app.js:9534`, `9538`, `9544`)뿐이다. 목록에서 4개 중 3개를 지워도 "+" 메뉴의 배지는 계속 `4` 다.
사용자가 방금 수행한 파괴적 조작의 결과가 화면 다른 곳에서 부정된다.

**(b) 지운 파일이 같은 패널에 pill 로 되살아난다 — × 까지 달고.**
목록 삭제 직후 `_renderAttachmentPills()` 가 한 번이라도 호출되면(파일 추가 업로드
`app.js:9740/9749/9805`, 전송 후 동기화, pending 컨텍스트 전환 등) bucket 에 남아 있는
**삭제된 항목**이 다시 pill 로 그려진다. 그리고 이건 예외 시나리오가 아니라 **가장 흔한 흐름**이다:

> 잘못 올린 파일을 목록에서 × 로 지운다 → 바로 올바른 파일을 첨부한다
> → 패널이 pill 뷰로 전환되면서 **방금 지운 파일 + 새 파일**이 나란히 뜬다.

되살아난 pill 의 × 를 다시 누르면 confirm → `DELETE` → 백엔드가 idempotent 200
(`attachments.py:246-253`, `already_pending: true`) → **"첨부를 삭제했습니다." 토스트가 또 뜬다.**
사용자 입장에서는 "지웠는데 안 지워졌다가, 다시 지우니 또 지워졌다고 한다."

선행 cycle 의 ux BLOCK 은 "×가 로컬만 지우고 서버가 되살린다(거짓 어포던스)" 였다.
이번 결함은 그것의 **정확한 거울상** — 서버는 지웠는데 로컬이 되살린다. 같은 패널, 같은 버튼,
정반대 방향의 같은 종류의 거짓말이다. 수정 대상 surface 한복판에서 발생하므로 BLOCK.

수정은 한 줄 수준이다(목록 caller 도 성공 시 bucket 에서 splice 하고 `_renderAttachmentPills()`
대신 배지만 갱신하거나, `_deleteConversationAttachment` 안에서 bucket 정리를 공통화).

### F2 (BLOCK) — 남의 첨부에도 ×가 뜨고, **실제로 삭제된다**. 목록 응답에는 판단 근거가 없고, 실패 메시지는 잘못된 상태코드를 본다

지시문 #3 의 전제("타인 첨부는 눌러야 403")를 코드로 확인한 결과 **전제가 틀렸다. 실제는 더 나쁘다.**

- `DELETE /api/attachments/{id}` 의 게이트는 `_account_can_access_attachment(row,
  "conversation.attachment.upload.own", "...upload.any")` 이고, 그 함수는
  **`AccountId`(업로더)를 한 번도 보지 않는다**(`attachments.py:309-338`).
  통과 조건은 `upload.any` 보유 **또는** `upload.own` + (대화 소유자 **또는 대화 멤버**):

  ```python
  if app._conversation_owned_by_account(conn, conversation_id, acct_id):
      return True
  # feature-0009: 그룹 대화 멤버도 첨부 접근 가능 (첨부는 전원 공유, REQ-GC-R6).
  return app._account_is_conversation_member(conversation_id, acct_id)
  ```

  → **그룹 대화의 아무 멤버나 다른 멤버가 올린 파일을 삭제할 수 있다.**
  app.js 의 주석 `// 업로더 본인만 삭제할 수 있다(conversation.attachment.upload.{own,any})`
  (`app.js:9669`) 는 **사실과 다르다**. 이번 변경이 이 주석을 그대로 옮겨 심었다.

- 목록 API(`conversations.py:2194`)는 `read.{own,any}` 만 보고 **대화의 첨부 전량**을 돌려준다 —
  업로더 스코프 없음. 즉 목록 뷰는 남의 파일을 **반드시** 보여주는 뷰다. (반면 pill 뷰는 방금 첨부
  직후·전환 직후에만 살아 있는 과도기 뷰다.) 이번 변경은 **파괴적 컨트롤을, 남의 파일이 확실히
  보이는 상시 뷰에 붙였다.** 백엔드 관용성 자체는 기존이지만, 그것을 일상 동선으로 끌어올린 것은
  이 변경이다.

- **응답에 권한 판단 근거가 없다.** `_serialize_attachment_for_api`(`_conv_store.py:3469-3528`)
  가 내보내는 필드에 `account_id` / `uploader_name` / `can_delete` 가 **전부 없다.** 그래서
  프론트는 × 를 숨길 수도, disabled 로 만들 수도, "○○○ 님의 파일" 이라고 알려줄 수도 없다.
  행에는 아이콘·이름·크기·상태·버전만 있고 **누가 올렸는지 표시가 없다** — 남의 파일을 자기
  파일과 구분할 단서가 화면에 0개인 상태에서 삭제 버튼만 붙었다.

- 그리고 실패 경로의 문구가 안 맞는다. 권한 거부 시 백엔드는 **404** 를 준다
  (`attachments.py:240`: `"첨부를 찾을 수 없거나 삭제 권한이 없습니다.", 404`).
  프론트는 **403 만** 특별 처리한다(`app.js:9670`):

  ```js
  showToast(e && e.status === 403 ? "이 첨부를 삭제할 권한이 없습니다." : "첨부를 삭제하지 못했습니다.", true);
  ```

  → 실제 권한 거부(=404)에서는 **아무 설명 없는 "첨부를 삭제하지 못했습니다."** 만 뜬다.
  준비해 둔 친절한 문구는 도달 불가능한 분기에 있다. 거꾸로 진짜 403 이 오는 경우엔
  `apiFetch` 가 이미 토스트를 띄우므로(`app.js:855-857`) **토스트가 2개 겹친다.**

- **되돌릴 방법이 없다.** soft-delete 이지만 **restore/undelete 엔드포인트가 존재하지 않는다**
  (`attachments.py` 전역에 복구 route 0건 — `DeletePending = 0` 은 UPDATE 의 WHERE 절뿐).
  직렬화기는 `lifecycle_state` / `restorable_until`(기본 30일)을 응답에 실어 보내는데
  (`_conv_store.py:3502-3524`) **UI 도 API 도 그 복구 가능성을 쓸 수 없다.** 사용자에게 삭제는
  사실상 영구다.

종합: 그룹 대화에서 멤버 A 가 멤버 B 의 파일을 — 소유자 표시 없이, 되돌릴 수 없이, 실패해도
이유를 알 수 없는 문구로 — 지울 수 있는 동선이 상시 뷰에 생겼다. 삭제된 파일은 AI 참조 스코프에서도
빠지므로(`_conv_store.py:2991~`) **대화 전원의 답변 품질에 영향**을 준다. 이 허용 범위가 의도인지는
제품 결정 사항이라 사람 승인이 필요하다.

### F3 (CONCERN) — pill 뷰에서 삭제하면 패널이 **목록 뷰로 바뀐다**(지시문 #1 확인 결과: 부작용 실재)

코드로 확인했다. `_deleteConversationAttachment` 는 caller 가 누구든 무조건
`_loadConversationAttachmentList` 를 호출한다(`app.js:9673-9675`). 그 함수는 시작하자마자
**동기적으로**

- `noteEl.classList.add("hidden")` — 안내 1줄을 숨기고 (`app.js:10070-10071`)
- `listEl.innerHTML = '<div class="attach-list-empty">불러오는 중...</div>'` — 컨테이너를 비운다 (`app.js:10072`)

그 뒤 `await apiFetch(...)` 로 넘어간다. pill 경로에서 사용자가 실제로 보는 전이는:

```
pill 뷰(이번 요청에 첨부 / 세션 파일 헤더) → "불러오는 중..." → pill 뷰(동기 재렌더) → 목록 뷰
```

**최종 상태는 목록 뷰**다. 사용자는 pill 뷰에서 × 를 눌렀을 뿐인데 화면 구성이 통째로 바뀌고,
pill 뷰가 제공하던 "이번 요청에 첨부 / 세션 파일 (이전 첨부)" 구분(`app.js:9614-9628`)이 사라진다.
목록 뷰에는 그 구분이 **없다** — 방금 올린 파일과 3일 전 파일이 동일하게 나열된다.

부수 효과 하나 더: 마지막 pill 을 지우면 `_renderAttachmentPills()` 가 items 0 을 보고
**패널 전체를 `hidden` 처리**한다(`app.js:9535-9540`). 그 직후 in-flight 였던 목록 재로드가
**숨겨진 컨테이너에** 행을 그린다 — 낭비된 왕복이고, 그 대화에 (bucket 미수화 상태의) 다른 첨부가
남아 있으면 사용자는 패널이 그냥 사라진 것으로 본다.

이 전이 자체는 선행 cycle 이 들여왔지만, 이번 변경은 "pill 의 ×와 목록의 ×가 **같은 계약**을 쓴다"고
선언하면서 두 뷰의 사후 동작 차이를 그대로 남겼다 — 계약을 공유했으면 **뷰 복귀 정책도 공유**해야 한다.

### F4 (CONCERN) — `_loadConversationAttachmentList` 에 in-flight 가드가 없다 → 삭제한 행이 목록에 다시 나타날 수 있다

`_loadConversationAttachmentList` 는 generation token / AbortController 가 없다. 응답이 오면
무조건 `listEl` 을 덮어쓴다(`app.js:10064-10083`). 그런데 이 함수의 호출자는 이제 셋이다:
패널 열기(`app.js:10655`), pill 삭제, **목록 삭제(신규)**.

도달 경로: 행 A 의 × 클릭 → confirm OK → `DELETE` 네트워크 대기(이 구간 동안 **다른 행의 ×는
계속 enabled** — disabled 는 클릭된 버튼 하나뿐) → 행 B 의 × 클릭 → confirm OK →
재로드 2건이 경합 → **A 삭제 직후에 발사된 응답이 나중에 도착하면 B 가 목록에 남아 있는 스냅샷이
최종 렌더**가 된다. 사용자는 지운 파일이 그대로 있는 화면을 본다(F1 과 합쳐지면 "삭제가 안 먹는다"는
인상이 굳는다).

행 단위 disabled 는 **연타(같은 버튼 두 번)** 는 막지만 **동시 삭제(다른 버튼)** 는 막지 못한다.
목록 전체를 잠그거나(가장 단순) 요청 세대 토큰으로 stale 응답을 폐기해야 한다.

### F5 (MINOR) — `finally { delBtn.disabled = false; }` 는 성공 경로에서 **이미 detach 된 노드**를 만진다

성공 경로 타이밍: `_deleteConversationAttachment` 는 재로드를 `await` 하지 않고 던진다
(`app.js:9674`, `.catch(() => {})`). 그 호출은 첫 `await` 전까지 **동기 실행**되므로
`listEl.innerHTML = "불러오는 중..."` 이 먼저 적용되어 `delBtn` 이 DOM 에서 떨어진다.
그 다음에야 `_deleteConversationAttachment` 가 반환되고 `finally` 가 돈다.

예외는 나지 않는다(detached 노드의 `disabled` 대입은 무해). 문제는 **오해의 소지**다:
이 `finally` 는 성공 경로에서 아무 것도 보장하지 않으며, 실제 연타 방어는 (i) 모달 `confirm` 의
블로킹과 (ii) DOM 교체가 하고 있다. 취소·실패 경로에서만 유효하다.
`state.activeConversationId` 가 비어 재로드가 건너뛰어질 때
(`app.js:9673` 의 `if`)만 재활성화가 진짜로 의미를 갖는데, 그 조합은 현재 도달하기 어렵다.
의도를 코드에 남기려면 주석 한 줄이라도 필요하다.

### F6 (CONCERN) — 지시문 #5 답: 안내 문구는 **아직도 pill 뷰에서 안 보인다**

`#attachSidePanelNote`("AI 는 이 대화에 올린 파일 전체를 참고합니다. 필요 없는 파일은 × 로
삭제하세요.", `index.html:376-378`)의 표시/숨김을 제어하는 코드는 **`_loadConversationAttachmentList`
단 한 곳**이다(`app.js:10070`, `10080`). `_renderAttachmentPills` 는 이 노트를 **전혀 건드리지 않는다.**

재현 경로 (새 대화 첫 첨부 — 가장 흔한 시작 동선):

1. 새 대화에서 "+" → 첨부파일 목록 → `_loadConversationAttachmentList` 실행, 첨부 0건
   → `attach-list-empty` 렌더, **노트는 `hidden` 인 채 유지**
2. 파일 첨부 → `_renderAttachmentPills()` 가 같은 컨테이너에 pill 을 그린다
   → **노트는 여전히 hidden**

결과: 첨부를 처음 올린 사용자는 pill 과 × 는 보지만 "AI 가 이 대화 파일 전체를 참고한다"는
**참조 범위 고지 자체를 못 본다.** 이번 변경은 "안내가 가리키는 컨트롤이 화면에 없다"를 고쳤지만,
그 반쪽인 "컨트롤은 있는데 안내가 없다"는 그대로 남았다. 선행 cycle 의 design CONCERN(참조 범위
고지)이 pill 경로에서 미해결이라는 뜻이며, 이번 TASK 의 목적("안내 문구와 화면의 불일치 해소")
기준으로 **미완**이다.

### F7 (MINOR) — 시각·접근성 디테일

- **키보드 사용자에게는 danger 어포던스가 전혀 없다.** 위험 색은 `:hover` 에만 걸려 있고
  (`styles.css:3301`) `:focus-visible` 규칙이 없다. Tab 으로 이동하면 ⬇ 와 × 가 같은 크기·같은
  muted 색으로 나란히 있고, 브라우저 기본 아웃라인 외에 "이건 파괴적"이라는 신호가 0 이다.
  이 스타일의 설계 근거가 "hover 에서만 danger 노출(오클릭 유인 최소화)" 이므로,
  `:hover, :focus-visible` 로 확장하는 것이 그 근거와 일관된다.
- `color: var(--text-muted);` 에 **폴백이 없다**(`styles.css:3293`). 바로 위 형제 규칙은
  `var(--text-muted, #9ca3af)`, `var(--primary, #2563eb)` 로 전부 폴백을 둔다
  (`styles.css:3269`, `3277`). 변수가 없는 컨텍스트에서는 `color` 가 상속값(=본문색)으로 계산되어
  **× 가 의도보다 진하게** 렌더된다 — "기본은 muted" 라는 설계 의도가 조용히 뒤집힌다.
- `<button class="attach-list-item-del">` 에 `type="button"` 이 없다(이웃 ⬇ 도 없으므로 국소적으로는
  일관, 다만 pill 의 remove 버튼은 `type="button"` 을 명시한다 — `app.js:9598`). 현재 form 밖이라
  무해하나 코드베이스 내 규약이 갈린다.
- `data-id="${a.id}"` 는 핸들러가 closure `a.id` 를 쓰므로 사용되지 않는 죽은 속성이다(⬇ 와 동일 패턴).

## 2. Risks (위험)

| # | 위험 | 발생 조건 | 사용자 체감 |
|---|---|---|---|
| R1 | 삭제한 첨부가 pill 로 부활 + 개수 배지 불일치 (F1) | 목록 삭제 후 `_renderAttachmentPills()` 유발 동작(추가 업로드 등). **삭제→재첨부는 이 기능의 주 동선** | "삭제가 반영되지 않는다" — 선행 cycle 이 고친 바로 그 불신의 재발 |
| R2 | 그룹 대화에서 타 멤버 파일이 소유자 표시·복구 수단 없이 삭제됨 (F2) | 그룹 대화 + 아무 멤버 + 상시 노출되는 목록 뷰 | 남의 자료가 조용히 사라지고 AI 답변 품질이 전원에게 저하. 복구 route 부재 = 영구 |
| R3 | 권한 거부 시 무의미한 오류 문구(404 미매핑) / 403 시 토스트 2겹 (F2) | 권한 없는 계정의 × 클릭 | 왜 실패했는지 알 수 없음 → 반복 클릭 |

| R6 | 참조 범위 고지가 pill 뷰에서 미노출 (F6) | 새 대화 첫 첨부 | 노출 범위를 모른 채 파일 업로드 |

오클릭 위험(지시문 #2) 판정: ⬇ 와 × 가 같은 flex 행에 `gap: 8px`, 각각 `padding: 4px 6px`
(`styles.css:3243-3302`)로 인접한다. 실제 히트영역은 대략 20×22px 급이고 240px 최소폭 패널에서
행 우측 끝에 몰려 있다. **포인터 사용자에게는** hover 시 색 분화(파랑 vs 빨강)가 있어 판별 가능하며,
`confirm` 이 파일명을 포함하므로 1차 방어는 성립한다. 다만 (i) 키보드 경로에는 그 색 분화가 없고
(F7), (ii) **undo 가 구조적으로 부재**(restore route 없음, F2)하므로 confirm 이 유일 방어인 것은
과도하다. 최소한 confirm 문구에 "되돌릴 수 없습니다"를 명시하거나, 토스트에 실행취소를 붙일 수
있도록 restore 엔드포인트를 별도 항목으로 올려야 한다.

## 3. Recommendations (권고)

**BLOCK 해소 (머지 전 필수)**

1. **F1** — 목록 caller 가 반환값을 소비하도록 고친다. `_deleteConversationAttachment` 성공 시
   공통으로 bucket 정리까지 수행(뷰 무관)하거나, 목록 핸들러에서
   `if (await _deleteConversationAttachment(...)) { /* bucket splice + 배지 갱신 */ }`.
   최소 요건: 삭제 후 (a) `#composerAttachCountBadge` 즉시 정합, (b) 이후 어떤
   `_renderAttachmentPills()` 호출에서도 삭제된 항목이 pill 로 나타나지 않을 것.
2. **F2** —
   - 목록 응답에 `account_id`(또는 `uploader_label`)와 **`can_delete`** 를 추가하고
     (`_serialize_attachment_for_api`), 프론트는 `can_delete === false` 면 × 를 렌더하지 않는다.
     "눌러서 실패로 배우는" 어포던스를 없앤다.
   - 행에 **업로더 표시**를 넣는다(그룹 대화 한정이라도). 남의 파일임을 알 수 없는 상태에서
     삭제 버튼만 있는 현 구성은 위험.
   - `app.js:9669` 의 "업로더 본인만 삭제할 수 있다" 주석을 **사실대로 정정**한다
     (실제: `upload.any` 또는 `upload.own` + 대화 소유자/멤버).
   - 실패 문구를 실제 상태코드에 맞춘다: `e.status === 403 || e.status === 404` 를
     권한 문구로 매핑하되, `apiFetch` 가 이미 403 토스트를 띄우므로 **중복 토스트 회피**
     (403 은 apiFetch 에 맡기고 404 만 로컬 처리).
   - 타 멤버 첨부 삭제 허용이 의도인지 **제품 결정 필요**(Human Approval). 의도라면 confirm 문구에
     "다른 멤버가 올린 파일입니다 / 이 대화 전원에게 영향을 줍니다"를 명시.
3. **F6** — 노트 표시를 `_renderAttachmentPills` 에서도 관리한다(항목 유무 기준으로 두 경로가
   동일 규칙을 쓰도록 `_syncAttachPanelNote(hasItems)` 같은 단일 헬퍼로 추출).

**CONCERN (같은 cycle 내 처리 권장)**

4. **F3** — 뷰 복귀 정책을 계약에 포함한다. 목록 재로드는 "목록 뷰가 현재 표시 중일 때만" 수행하거나
   (예: 컨테이너에 `dataset.view = "pills" | "list"` 를 두고 분기), pill 경로에서는 재로드 대신
   bucket 기반 재렌더 + 배지 갱신만 한다. 마지막 항목 삭제로 패널을 숨길 때는 in-flight 재로드를

   `outline: 2px solid var(--danger, #dc2626)` 를 추가. `var(--text-muted, #9ca3af)` 로 폴백 보강.
   `type="button"` 명시.

**MINOR**

7. **F5** — 성공 경로에서 `delBtn` 이 detach 된다는 사실과 `finally` 의 실제 역할(취소·실패 경로 한정)을

8. **F8** — `tests/verify_attach_list_delete.mjs` 신설: (a) 목록 행이 `.attach-list-item-del` 을

## 4. Verdict rationale (판정 근거)

**BLOCK.** 방향과 문제의식은 옳다 — 안내가 가리키는 컨트롤이 상시 뷰에 없다는 진단은 정확했고,
삭제 경로를 공통 함수로 추출한 것도 맞는 구조다. 다만 두 가지가 머지를 막는다.

1. **자기 계약 위반(F1).** TASK.md 가 명시한 "caller 가 로컬 상태를 조건부로 갱신" 을 새 caller 가
   지키지 않아, 이 변경이 고치려던 바로 그 패널에서 **삭제한 파일이 되살아나 보이고 개수 배지가
   틀어진다.** "삭제→재첨부"라는 이 기능의 주 동선에서 확정적으로 재현되고, 선행 cycle 의 ux BLOCK
   ("×가 서버에 반영되지 않는다")과 사용자 체감이 사실상 동일하다. 라이브 검증
   (`[x] 라이브 재검증 (PB-0008)`)이 이걸 놓쳤다는 점 자체가 검증 시나리오가 단일 삭제에
   머물렀음을 시사한다 — 삭제 후 **추가 업로드**까지 이어가면 즉시 드러난다.

2. **파괴적·비가역·타인 대상 조작을 근거 없이 노출(F2).** 목록 API 응답에 권한 판단 근거
   (`account_id` / `can_delete`)가 **없음을 확인**했고, 백엔드는 업로더를 검사하지 않아 그룹 멤버
   누구나 타인 파일을 지울 수 있으며, restore 엔드포인트는 **존재하지 않는다.** 여기에 실패 문구는
   실제 상태코드(404)를 매핑하지 못해 무의미한 메시지를 낸다. 이 조합 — 소유자 표시 없음 + undo 없음
   + 오류 설명 없음 — 위에 삭제 버튼을 상시 뷰에 올리는 것은 UX 로 승인할 수 없다.
   허용 범위가 의도적 설계인지는 제품 결정이므로 **Human Approval Needed: yes**.

추가로 이번 TASK 의 선언 목표("안내 문구와 화면의 불일치 해소")는 **절반만 달성**됐다 — F6 대로
pill 뷰에서는 안내 자체가 여전히 뜨지 않으므로, 두 뷰 중 한쪽의 불일치가 그대로 남아 있다.

F1·F2·F6 이 해소되면 나머지(F3~F5, F7~F8)는 CONCERN 수준으로, 같은 cycle 내 후속 처리로 충분하다.
