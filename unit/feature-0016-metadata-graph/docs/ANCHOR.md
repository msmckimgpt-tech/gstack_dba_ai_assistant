# ANCHOR: feature-0016-metadata-graph 메타데이터 지식그래프

## §1. 외부 관점 요약

"이미 mermaid 다이어그램(feature-0013)도 있고 관계형 메타데이터 테이블도 있는데, 왜 또
Apache AGE 그래프 DB 를 도입하지?" → 라이브 데이터 검토 결과 **노드는 8,122 테이블·91 스키마로
풍부하나 관계 엣지는 0행**이고, AI 가 8K 테이블을 컨텍스트에 담을 수 없어 NL→SQL 정확도가
제약된다. 게임 운영 특성상 컨텐츠·기능 **용어 기반 질의가 잦아** 용어→테이블→관계를 따라가는
그래프 네비게이션이 자연스럽다. 관계형은 SSOT 로 두고 AGE 는 **재생성 가능한 투영**이라,
화면(UI)과 AI 가 같은 그래프를 공유해 "보이는 것 = AI 가 쓰는 것" 정합을 보장하는 것이 핵심.

## §2. 대안 분기

- **Alt-A: AGE 미도입(projection-only, RFC 의 A1).** 페르소나: 인프라 보수성을 최우선하는 운영팀.
  관계형 + `WITH RECURSIVE` k-hop 으로 UI·AI 정합 달성. 안 고른 이유: 사용자가 게임 용어 기반
  다중 hop 질의 빈도와 컨텍스트 초과 해소 효과를 근거로 A3(즉시 도입)를 명시 결정(2026-06-30).
- **Alt-B: 별도 그래프 DB(Neo4j) 도입.** 페르소나: 그래프-우선 대규모 팀. 안 고른 이유: 별도
  시스템 운영·ETL·이중 정합 부담. AGE 는 PG 안에서 pgvector·관계형과 한 트랜잭션 JOIN 가능해
  단일 엔진 유지가 가능.
- **Alt-C: AI 컨텍스트만 그래프화(UI 그래프 없음).** 페르소나: 백엔드 정확도만 보는 팀. 안 고른
  이유: 사용자 요청이 "UI 도 그래프 형태 + 검색"을 명시.

## §3. 가정된 사용 시나리오

마상소프트 게임 운영 담당자가 "확률형 아이템 지급 로그가 어느 테이블에 있고 결제와 어떻게
연결되나?"를 AI 에게 묻는다. AI 는 8K 테이블 전체를 보지 않고, 그래프에서 "확률/아이템/지급"
용어 노드 → 관련 Table 노드 → REFERENCES 엣지를 k-hop 으로 따라가 결제 테이블까지의 join
경로를 찾아 정확한 SQL 을 만든다. 동시에 운영 담당자는 관리콘솔 그래프 뷰에서 같은 서브그래프를
눈으로 확인하고, 노드를 클릭해 테이블 설명·컬럼·관계를 한 카드에서 본다.
