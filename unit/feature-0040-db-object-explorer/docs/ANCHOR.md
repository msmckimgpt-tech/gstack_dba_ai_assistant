# ANCHOR: feature-0040-db-object-explorer 역할 기반 DB 객체 탐색

## §1. 외부 관점 요약

"왜 트리거·이벤트·Agent 작업을 **역할**이라는 추상 축으로 묶었나? 그냥 벤더 객체 이름
그대로 `list_triggers`, `list_events`, `list_jobs` 도구를 만들면 더 직관적이지 않나?"
→ 대응 DBMS 를 늘리는 순간 그 방식은 도구 수가 벤더×객체로 곱해지고, 같은 일을 하는
객체가 이름만 달라 모델이 "이 DB 엔 이벤트가 없네"(실제로는 Agent 작업으로 존재) 라고
판단한다. 역할 축은 도구 2개를 고정하고 방언 매핑만 늘린다.

"왜 조회 결과가 0건인데 '없다' 고 안 하나? 방어적으로 과한 것 아닌가?"
→ 이 저장소가 반복 관측한 결함 클래스가 정확히 그것이다
(`FR-false-absence-zero-row-catalog-scope`: SQL Server 카탈로그가 DB 스코프라 2-part
조회가 구조적으로 0행 → 모델이 "프로시저가 없다" 단정). 역할 축은 그 함정을 **역할
단위로** 재생산할 수 있어(MySQL 에 시노님 개념 자체가 없음), 상태 구분을 타입 레벨로
올렸다.

"루틴은 왜 새 테이블로 안 옮겼나 — 반쪽 아닌가?"
→ `routine_objects`(ADR-016)는 라이브에서 검증된 서브시스템이고, 이관은 회귀 위험만
크고 얻는 것이 없다. taxonomy 는 6역할을 온전히 선언하되 저장만 두 곳으로 나눈다
(`DELEGATED` 상태가 그 경계를 사용자·모델에게 정확히 전달한다).

## §2. 대안 분기

**대안 A — 벤더 객체별 전용 도구 (`list_triggers`/`list_events`/`list_agent_jobs` …)**
- 페르소나: "지금 두 DBMS 만 쓰는데 추상화는 과설계 아닌가" 라고 보는 실용주의 개발자.
- 채택 안 함: 사용자가 축1 에서 **"궁극적으로 모든 DB 시스템에 대응"** 을 명시했다.
  벤더축은 DBMS 수에 선형으로 도구가 늘고, 모델의 도구 선택 정확도가 떨어진다.

**대안 B — 기존 `search_tables` 에 object_type 필터만 추가**
- 페르소나: 표면적을 최소로 유지하려는 리뷰어.
- 채택 안 함: 테이블과 역할 객체는 반환 스키마가 다르다(트리거는 시점·이벤트·대상 테이블,
  작업은 주기·상태·단계). 한 도구에 합치면 컬럼 계약이 역할마다 갈려 위치 파싱이 무너지고,
  `describe_table` 의 기존 계약도 오염된다.

**대안 C — routine 을 포함해 전 역할을 `db_objects` 로 통합 이관**
- 페르소나: "SSOT 가 둘로 갈리는 건 나쁜 냄새" 라고 보는 아키텍트.
- 채택 안 함(ADR-DBOBJ-0001): 이관 이득은 개념적 정결함뿐이고, 대가는 라이브 그래프
  투영·능동 분석·크로스-DB 참조 파싱을 관통하는 회귀 위험이다. 경계는 taxonomy 의
  `OWNED_ELSEWHERE` + `DELEGATED` 로 **명시**해 두 벌 관리의 함정을 막았다.

## §3. 가정된 사용 시나리오

운영자가 그래프 뷰에서 `t_order` 테이블을 클릭한다. 상세 패널에 이 테이블을 읽고 쓰는
프로시저(보라)와 함께, **이 테이블에 걸린 트리거**(구리, 파선 소유 관계)가 나타난다.
트리거를 클릭하면 시점(AFTER)·이벤트(INSERT)·활성 여부가 보이고, 그 트리거가 `t_log` 에
쓰기(실선)를 한다는 것이 선으로 이어진다. 운영자는 "주문 테이블에 왜 로그가 쌓이지" 를
코드를 뒤지지 않고 화면에서 답한다.

또는 사용자가 대화에서 "이 DB 에 자동으로 도는 게 뭐가 있나" 를 묻는다. assistant 는
`search_db_objects` 를 역할 없이 1회 호출해 뷰·트리거·예약 작업을 한 번에 받고,
MySQL 이면 "별칭·시퀀스는 이 DBMS 에 없는 객체 종류" 라고 정확히 구분해 답한다.
