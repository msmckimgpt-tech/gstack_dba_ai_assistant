개발 배경 · 왜 이 5주를 이렇게 썼나

"기능은 있는데 믿고 맡기기 어렵다" — 그 간극을 메우는 기간

지금까지상황

  • 질문·답변, 그룹 대화, 데이터 지도, 무중단 배포까지 기능은 갖춰졌습니다.
  • 실제 업무에 쓰이기 시작했고, 쓰는 사람이 늘수록 문제가 드러났습니다.

문제무엇이 걸렸나

  • 답을 기다리다 그냥 멈춘다 — 화면은 '진행 중'인데 실은 이미 실패해 있었습니다.
  • 배포할 때마다 서비스가 잠깐 멈춘다 — "느낌"이 아니라 실제 전면 장애였습니다.
  • 올린 파일을 AI가 놓친다 — "전부 고쳤다"면서 일부만 고치기도 했습니다.
  • 대화가 쌓이면 못 찾는다 — 정리할 수단이 없었습니다.

질문그래서 무엇을 해야 하나

  • 새 기능을 더 얹을 것인가, 쓰는 데 걸리는 것부터 없앨 것인가.
  • 불편을 그때그때 막을 것인가, 다시 안 생기게 구조로 막을 것인가.

답이번 기간 목표

  • 실사용에서 나온 불편을 원인까지 파고들어 봉인한다.
  • 업무에 꼭 필요한 세 가지 쓰임새를 넓힌다 — 파일·대화 정리·밖의 AI 연결.
  • 고칠 대상은 추측이 아니라 측정으로 고른다.
  • 이번 기간을 관통한 원칙 — "고쳤다"고 말하기 전에 정말 고쳐졌는지 실제 환경에서 확인하고, 확인하지 못한 것은 확인하지 못했다고 적었습니다.

1. 대화를 정리하고 찾는다 신규·완료

쌓인 대화를 폴더로 묶고, 폴더마다 AI에게 줄 지침을 걸어 둡니다

1배경·문제
  • 대화가 쌓일수록 목록이 한 줄로만 길어져 찾기 어려웠습니다.
  • 비슷한 업무를 할 때마다 같은 배경 설명을 매번 다시 써야 했습니다.
  • 이름 바꾸기·삭제는 브라우저 기본 팝업이라 어색했습니다.
2화면 흐름
왼쪽 대화 목록›폴더 만들기›끌어다 넣기›폴더 지침 설정›그 폴더의 대화는 지침 적용
폴더·하위 폴더로 묶기 지난 날짜는 월·연으로 접기 오른쪽 클릭으로 바로 메뉴 한/영 오타 검색·첨부 이름 검색
3변경 전 → 후
실제 화면 대신 개념 도식
4왜 이 방향
  • 폴더를 철저히 개인 것으로 정의 — 관리자라도 남의 폴더를 볼 수 없습니다.
  • 대화 생성이 가능한 모든 역할에 폴더를 열되, 부여는 한 번만 — 매번 다시 주면 관리자가 회수한 권한이 되살아나기 때문입니다.
  • 브라우저 기본 팝업을 전면 제거하고 화면 안에서 처리(되돌리기 6초 포함).
5기대 효과 완료·배포 후 확인
  • 반복 업무의 배경 설명 재작성이 사라집니다.
  • 공개 도중 관리자끼리 서로 폴더가 보이던 결함을 사용자 신고로 발견해 즉시 봉인했습니다.
2. 파일을 다룬다 신규·이번 기간 최대

"파일을 올린다"에서 "고쳐진 파일의 이력을 추적하고 견준다"로

1배경·문제
  • 이어지는 질문에서 앞서 올린 파일에 접근하지 못했습니다.
  • AI가 고쳐 준 파일을 다시 올리면 이력이 갈라져 원본을 잃었습니다.
  • "전부 갱신했다"면서 실제로는 일부만 고친 경우가 있었습니다.
  • 무엇이 바뀌었는지 눈으로 견줄 화면이 없었습니다.
2화면 흐름
파일 첨부(여러 개)›AI가 수정본 생성›파일명 클릭 → 원문›두 버전 나란히 비교›지우기 · 되살리기 · 한 번에 내려받기
줄 안의 바뀐 구간까지 표시 어느 기준으로 견줄지 선택 AI 수정본은 별도 갈래로 마크다운은 서식 그대로
3변경 전 → 후
실제 화면 대신 개념 도식
4왜 이 방향
  • 어떤 파일을 참조할지 정하는 주체를 화면(브라우저)에서 서버로 옮겼습니다 — 화면 쪽만 고치면 새 진입 경로가 생길 때마다 재발하기 때문입니다.
  • 모든 파일 내용을 통째로 넣으면 분량 한계에 다시 걸리므로, 목록은 전량 · 본문은 필요할 때만 읽는 방식을 택했습니다.
  • AI 수정본을 사용자 원본의 다음 버전으로 섞지 않고 갈래를 분리 — "내가 올린 최신"을 잃지 않게.
5기대 효과 완료·배포 후 확인
  • 스크립트·문서 검토 업무에서 "무엇이 어떻게 바뀌었나"를 화면에서 바로 확인합니다.
  • "전부 고쳤다"는 잘못된 보고가 구조적으로 차단됩니다.
  • 실제 재발이 줄었는지는 다음 주기에 측정합니다(아직 수치 없음).
3. 기다리는 시간을 관리한다 완료

지금 무엇을 하는 중인지 보이고, 오래 걸리면 계속할지 물어봅니다

1배경·문제
  • 요청 직후 말풍선이 '시작 중…'에 박제되고, 다른 대화에 갔다 와야 살아났습니다.
  • 어떤 요청은 응답도 오류 안내도 없이 계속 '진행 중'이었습니다.
  • 한도에 걸리면 그때까지 한 추론이 통째로 버려졌습니다.
2화면 흐름
질문 전송›실행 단계 패널›단계별 시작 시각·소요›한도 80% → "계속 추론?"›즉시 답변 · 중단 가능

한도 안내는 화면을 막지 않고 입력창 옆 배너로 나오며, 승인은 그 요청 한 번에만 적용됩니다.

3변경 전 → 후
실제 화면 대신 개념 도식
4왜 이 방향
  • '진행 중' 무한 대기의 원인은 끝나는 길은 12갈래인데 그 사실을 화면에 알리는 길은 3갈래였던 비대칭이었습니다 — 알림 경로를 맞췄습니다.
  • "재연결 중"에서 진전이 없던 것은 한 번의 시도에 준 시간이 정상 응답 시간보다 짧았기 때문 — 전송 방식을 바꿔 기준을 '완료까지'에서 '무응답 간격'으로 옮겼습니다.
  • 중요한 시행착오: 연장 기능 초판이 개별 호출 상한까지 풀어 '중단'과 '즉시 답변'이 듣지 않게 만들었습니다 — 연장은 전체 예산만 풀도록 정정했습니다.
5기대 효과 완료·배포 후 확인
  • 기다리는 동안 무슨 일이 벌어지는지 보이고, 오래 걸려도 하던 일이 버려지지 않습니다.
  • 모집단 전체에서 실제로 줄었는지는 다음 주기에 측정합니다.
4. 답변을 믿을 수 있게 한다 이어받음·확장

지적이 사라질 때까지 스스로 고치고, 확인 못 한 것은 '미확인'이라 말합니다

1배경·문제
  • 자체 점검이 한 번만 돌고, 지적이 남아도 그대로 답변이 나갔습니다.
  • 조회 결과가 안 나오면 "그런 건 없다"고 단정하는 경우가 있었습니다.
  • 조회가 막히면 왜 막혔는지·어떻게 바꿔야 하는지 알려 주지 않았습니다.
2화면 흐름
답변 초안›분리된 검토자가 지적›고쳐서 다시 점검›지적 없음까지 반복›전달 (남으면 하단 고지)

기다리기 어려우면 '즉시 답변'으로 그 시점 답변을 받을 수 있고, 관리 콘솔에서 몇 회 돌았고 무엇이 남았는지 확인합니다.

3변경 전 → 후
실제 화면 대신 개념 도식
4왜 이 방향
  • 속도보다 품질을 택한 결정 — 자체 점검이 답변 시간의 33%(평균 46.4초)를 쓴다는 것을 측정으로 확인했고, 설정 한 줄로 없앨 수 있었지만 없애지 않기로 했습니다.
  • 근거는 7일 실측에서 89건 중 21건(24%)이 실제로 답변을 고치게 만들었다는 것 — 24%의 품질을 시간과 바꾸지 않았습니다.
  • 대신 '즉시 답변'이라는 개인 선택지를 뒀습니다. 시스템이 일괄로 품질을 낮추는 대신 개인이 고르게.
5기대 효과 효과 측정은 다음 주기
  • 확인 못 한 것을 '미확인'으로 표시하고, 막힌 조회는 대안까지 안내합니다.
  • 정직하게 말씀드리면 — 검토가 실제로 결함을 잘 잡는지, 잘못된 답이 줄었는지는 아직 측정 전입니다.
5. 함께 쓴다 (그룹·공유) 이어받음

화면에는 보이는데 AI만 못 읽던 동료의 파일, 이제 함께 봅니다

1배경·문제
  • 그룹 대화에서 동료가 올린 파일이 화면에는 보이는데 AI만 읽지 못했습니다.
  • 초대받은 멤버에게 '나가기'가 보이지 않았습니다.
  • 공유 링크에서 질문한 사람이 전원 '사용자'로만 표시됐습니다.
2화면 흐름
그룹 대화 초대›첫 사용 안내 툴팁›동료가 파일 첨부›AI가 출처 라벨과 함께 참조›공유 · 나가기

공유 화면도 함께 정비 — 버튼을 하단 바로 모으고, 조회수를 위로, 링크를 열면 가장 최근 메시지부터 보입니다.

3변경 전 → 후
실제 화면 대신 개념 도식
4왜 이 방향
  • 종전 제한은 내려받아 다시 올리면 우회할 수 있어, 악의는 막지 못하고 정직한 사용자만 막았습니다.
  • 라이브에서 파일이 오간 그룹 대화 6곳 모두에서 이 불편이 관측됐습니다.
  • 읽기를 넓힌 것이지 쓰기를 넓힌 것이 아닙니다 — 새 권한·새 저장 구조 추가 없음.
5기대 효과 완료·배포 후 확인
  • 팀 단위 검토에서 파일을 각자 다시 올릴 필요가 없습니다.
  • 공유 화면 진입·참여·나가기 경로가 모두 정상화됐습니다.
6. 운영을 들여다보고 통제한다 신규·완료

사용 기록을 한 화면으로, 그리고 역할별로 쓸 수 있는 AI 모델을 제한합니다

1배경·문제
  • AI 사용 기록이 여러 화면에 흩어져 있어 한눈에 못 봤습니다.
  • 표를 정렬하거나 쪽수로 나눌 수 없어 기록이 쌓일수록 쓰기 어려웠습니다.
  • 누가 어떤 등급의 AI 모델을 쓸지 통제할 수단이 없었습니다(비용·권한 모두).
2화면 흐름
관리 콘솔›AI 사용량›요약 카드 클릭 → 차트 전환›사용 기록 정렬·쪽수›역할별 모델 제한
같은 화면 구성을 개인 프로필에도 캐시 사용분까지 계측·표시 역할별 모델 접근 제한 '무응답 대기 상한'으로 용어 정정
3변경 전 → 후
실제 화면 대신 개념 도식
4왜 이 방향
  • 모델 제한은 "기본은 모두 허용, 필요하면 해제" 방식 — 도입 시점에 아무도 못 쓰게 되는 일이 없도록.
  • 권한 부여는 항목이 처음 생길 때 한 번만 합니다. 매번 다시 주면 관리자가 일부러 해제한 것을 재시작이 되살려 통제가 무력화되기 때문입니다.
  • 관리 콘솔에 넣은 화면 구성을 개인 프로필에도 그대로 적용해 배우는 비용을 줄였습니다.
5기대 효과 완료·배포 후 확인
  • 비용이 어디서 얼마나 발생하는지 한 화면에서 추적됩니다.
  • 고성능 모델 사용을 역할 단위로 통제할 수 있습니다.
  • 주의 — 관리자가 자신을 잠글 수 있는 경로가 있어 복구 절차 정비가 후속 과제입니다.
7. 데이터 구조를 지도로 읽는다 이어받음·확장

연결선을 "읽을 수 있게" 다시 그리고, AI 설명을 실제 데이터와 대조합니다

1배경·문제
  • 연결선이 직선 다발이라 어느 방향으로 데이터가 흐르는지 못 읽었습니다.
  • 축소하면 글자가 깨지고 선이 화면을 덮었습니다.
  • 상세 목록이 "…외 N건"으로 잘려 실제로 정보가 누락됐습니다.
  • AI가 쓴 설명이 맞는지 아무도 확인하지 않았습니다.
2화면 흐름
관리 콘솔 › 지도›묶음(카테고리) 선택›표 펼치기›상세 패널 전량 표시›AI 설명 + 대조 판정 배지

읽기·쓰기 관계를 서로 다른 곡선으로 나누고, 겹칠수록 진해지게 해 중요도가 밀도로 드러나게 했습니다.

3변경 전 → 후
실제 화면 대신 개념 도식
4왜 이 방향
  • 느린 이유를 추측하지 않고 측정으로 세 곳에 귀속한 뒤 동시에 고쳤습니다.
  • AI 설명 검증의 핵심 원칙은 "판정에 실패한 것은 '검증됨'이 아니다" — 오류·시간초과는 기록을 남기지 않습니다. 잘못 찍힌 확인 도장은 아래층 오류를 위로 전파시키기 때문입니다.
  • 분석 대상을 중요도 순으로 자동 선정 — 종전에는 완료율 11.9%였고 그마저 "우연히 눌린 것"이라 중요도와 무관했습니다.
5기대 효과 일부 효과는 관측 대기
  • 구조를 모르는 담당자도 관계를 눈으로 따라갈 수 있습니다.
  • 정직하게 말씀드리면 — 묶음이 실제로 덜 잘게 쪼개졌는지는 다음 재계산 후에야 확인됩니다. 대규모 화면의 부드러움도 측정 수단 한계로 미확인입니다.
8. 밖의 AI가 우리 데이터를 쓴다 신규·새 제품면

외부 AI 도구가 자기 비용으로 우리 데이터를 안전하게 조회합니다

1배경·문제
  • 담당자들이 이미 각자 다른 AI 도구를 쓰고 있는데, 그 도구가 우리 데이터를 볼 방법이 없었습니다.
  • 우리가 대신 추론해 주면 비용이 전부 우리 계정에 쌓이고, 계정 한도가 차면 전체가 멈춥니다.
  • 실제로 계정 한도 소진 사건이 있었습니다.
2화면 흐름
외부 AI 도구›주소만 등록›우리 화면에서 로그인·동의›도구 9종 + 조회 실행›답변은 우리 콘솔에 보존

설치할 것이 없습니다 — 주소를 등록하면 표준 절차로 인증이 성립하고, 로그아웃하면 연결도 함께 끊깁니다.

3변경 전 → 후
실제 화면 대신 개념 도식
4왜 이 방향
  • 대안 4가지를 검토했고, 우리가 외부 자격증명을 보관하는 방식은 배제했습니다.
  • 위협의 방향이 뒤집힌 표면입니다 — 종전엔 "우리 AI가 남의 데이터를 읽는다"였다면 여기선 "우리가 통제하지 않는 AI에게 데이터를 내보낸다". 그래서 통제를 지침이 아니라 연결 규격 자체에 넣었습니다.
  • 사용량 기록이 실패하면 결과를 돌려주지 않습니다(기록 없는 사용 금지).
5기대 효과 1건 검증 잔여
  • 담당자가 쓰던 AI 도구를 그대로 쓰면서 우리 데이터를 조회합니다.
  • LLM 비용이 사용자 쪽으로 분산되어 우리 계정 한도 리스크가 줄어듭니다.
  • 남은 검증 — 사람이 브라우저에서 한 번 로그인·동의해야 하는 구간의 전 과정 확인 1건(설계상 자동화 불가).
9. 끊기지 않게 한다 완료·헤드라인

"배포할 때마다 서비스가 멈춘다" — 느낌이 아니라 실제였고, 없앴습니다

1배경·문제
  • 사용자 신고를 계측해 보니 배포 1회마다 12~17초 전면 오류, 하루 6회 발생.
  • 그런데 배포 절차는 매번 "성공"으로 보고하고 있었습니다.
  • 배포 중 진행 중이던 답변이 통째로 폐기되기도 했습니다.
  • 업데이트 후에도 예전 화면이 계속 보이는 문제가 오래 있었습니다.
2처리 순서
새 버전 준비›임시 인스턴스 투입›진행 중 작업 0 확인›한 대씩 교대›바깥에서 복귀 확인 후 다음

종전 게이트는 앱이 떴는지까지만 확인했습니다. 바깥(접속 관문)이 그 인스턴스를 다시 쓰는지는 아무도 보지 않았습니다.

3변경 전 → 후 실측
실제 화면 대신 개념 도식 · 수치는 배포 창 접속 로그 실측
4왜 이 방향
  • 첫 안은 격리 시간을 30초에서 3초로 낮추는 것이었으나, 자체 검토가 "그러면 문제 있는 서버가 3초마다 다시 투입된다"고 지적해 값은 되돌리고 게이트가 복귀를 확인하는 쪽으로 바꿨습니다.
  • 다음 문제는 "사용자가 쓸수록 배포가 안 되는" 구조였습니다 — 유입이 7~10분 간격이라 조용한 창이 안 생겨 시급한 변경이 도달하지 못했습니다. 그래서 기다리는 방식에서 교대하는 방식으로 전환.
  • 작업 종료 유예도 측정으로 정했습니다 — 실제 작업의 66%가 종전 유예(60초)를 초과하고 있었습니다.
5기대 효과 검증됨
  • 업무 시간에도 배포할 수 있습니다 — 보안 수정처럼 급한 변경이 밤을 기다리지 않습니다.
  • 배포·장애 중에도 하던 작업이 보존되고, 업데이트가 화면에 즉시 반영됩니다.
  • 정직하게 말씀드리면 — "정말 바쁠 때 기다렸다가 통과하는" 장면은 아직 관측되지 않았습니다.
범위와 여건 · 정직하게 구분

어디까지 했고, 무엇이 여전히 결정을 기다리고 있는가

직전 보고에서 '결정 대기'로 말씀드린 세 가지 — 이번 기간에도 변동 없음
항목직전 보고 시점지금
구글 드라이브 연동기능 토대만 구축 · 서비스 미통합변동 없음 — 사내 계정 접근 허용 여부 결정 대기
DB 복제본 부하분산환경 제약으로 미구성변동 없음 — 환경 확보 대기
운영 DB 접근 범위접근 범위 결정 대기변동 없음 — 연결 대상 데이터가 제한적인 상태 유지

이번 기간에 한 것사내 확대 도입 준비

  • 접속할 때 뜨던 "안전하지 않은 연결" 경고를 해소하는 자동 설정 페이지를 만들었습니다 — 담당 PC를 하나하나 손볼 필요가 없습니다.
  • 정식 주소(도메인) 발급을 위해 사내 인프라·웹 담당에 요청할 내용을 비기술 담당자도 읽을 수 있는 형태로 정리했습니다.

기다리는 것확대 도입 자체

  • 정식 주소 발급은 사내 인프라·웹 담당의 처리가 필요합니다.
  • 발급되면 접속 경로를 전환하고 대상 확대 안내로 넘어갑니다.
  • 측정에 대해 미리 밝혀둘 것 — '13초 → 0초'는 서버 접속 기록 기준, '−25~35초'는 서버 처리 경로 기준입니다.
  • 브라우저에서 체감하는 속도와 대규모 화면의 부드러움은 측정 수단의 한계로 아직 수치가 없습니다.
기대 효과 · 확인된 것과 아직인 것

확인된 성과와, 아직 수치로 말할 수 없는 것

확인된 성과

  • 배포 중 접속 중단이 사라졌습니다 — 13초 → 0초, 배포 창 요청 172건 전부 정상.
  • 답변 대기가 25~35초 짧아졌습니다 — 평균 141초를 구간별로 쪼개 측정한 뒤 정리작업을 응답 경로 밖으로 뺐습니다.
  • 사용자에게 138건의 변화가 안내와 함께 전달됐습니다.
  • 업무 시간에도 배포 가능해져 시급한 수정이 밤을 기다리지 않습니다.
  • 외부 AI 연결로 비용 구조가 분산됐습니다 — 우리 계정 한도가 그 경로를 멈추지 않습니다.

아직 수치로 말할 수 없는 것

  • 답변 품질이 실제로 얼마나 좋아졌는지 — 자체 점검이 결함을 잘 잡는지, 잘못된 답이 줄었는지는 다음 주기 측정 과제입니다.
  • 불편이 실제로 줄었는지 — 배포 전 기준선은 확보해 뒀고, 같은 지표로 다시 재는 일이 남았습니다.
  • 지도 묶음이 실제로 정돈됐는지 — 다음 재계산 후 확인됩니다.
  • 업무 시간이 얼마나 절약됐는지 — 사용자 쪽 정량 지표가 아직 없습니다.
  • 이번 기간에 자리 잡은 태도 — "고쳤다"고 보고하기 전에 실제로 고쳐졌는지 서비스에서 직접 확인했습니다.
  • 그 과정에서 완료로 표기됐지만 실제로는 구현되지 않은 항목, 운영자가 조여도 아무 일이 없던 설정, 늘 0으로 보고하던 점검을 스스로 찾아내 고쳤습니다.
  • 이 세 건은 모두 정상으로 보이던 것들이었습니다 — 그래서 확인 습관이 성과입니다.

  • 의사결정을 요청드립니다 — 아래 세 가지는 개발로 풀 수 있는 과제가 아니라 결정과 여건이 필요한 사안입니다.
  • ① 구글 드라이브 — 사내 계정으로 드라이브 문서를 답변 근거로 쓰도록 허용할지.
  • ② 운영 DB 접근 범위 — 어디까지의 데이터에 연결할지.
  • ③ 복제본 환경 — 부하 분산용 복제본을 확보할지.
마무리

정리하면 — 쓰이면서 드러난 문제를 구조로 막고, 쓰임새를 넓힌 5주

  • 가장 큰 성과는 배포할 때마다 있던 접속 끊김을 없앤 것입니다 — 이제 업무 시간에도 배포합니다.
  • 쓰임새는 세 갈래로 넓어졌습니다 — 파일의 이력을 추적·비교하고, 대화를 폴더로 정리하고, 밖의 AI가 자기 비용으로 우리 데이터를 조회합니다.
  • 고칠 대상은 측정으로 골랐습니다 — "느낌"으로 보고된 문제가 실제 장애였음을 계측으로 확정했고, 반대로 측정 결과가 전제를 뒤집어 착수를 취소한 항목도 있습니다.
  • 속도보다 품질을 택한 결정을 기록으로 남겼습니다 — 답변 시간의 33%를 없앨 수 있었지만, 그 검토가 24%의 답변을 실제로 고치고 있었기에 유지하고 개인이 고를 탈출구를 뒀습니다.
