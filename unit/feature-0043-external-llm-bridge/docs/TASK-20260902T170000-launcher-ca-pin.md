# TASK-20260902T170000 — 갱신은 있었다. 받지 못했을 뿐이다

## 1. 요청 (사용자, 2026-09-02)

> 「'업데이트 필요' 에 따라 자동으로 연결이 진행되었지만, 러너 파일이 그대로라는 오류
>  메세지가 나타났습니다. 자동 연결 시, 러너 파일도 스스로 갱신될 수 있도록 구성해주세요.」

## 2. 먼저 — 이미 있는 것부터 센다

두 cycle 이 이미 이 자리를 지났다.

| cycle | 무엇을 넣었나 |
|---|---|
| `TASK-20260902T100000` | 런처가 기동 때마다 배포본 러너를 받아 갈아 끼운다 |
| `TASK-20260902T140000` | 러너가 유휴일 때 **스스로** 받아 재exec (`agent/selfupdate.py`) |

그러니 「러너가 스스로 갱신되게 하라」는 요청에 대해 만들 것이 남아 있지 않아 보였다.
그런데 사용자 화면은 여전히 「다시 실행했지만 러너 파일이 그대로입니다」다. **기능이
없는 것이 아니라 동작하지 않는 것**이고, 그 둘은 코드를 읽는 것만으로는 구별되지 않는다.

## 3. 실측 — 신뢰 앵커가 축 하나에서만 풀려 있었다

`bridge_setup.ps1` 이 굽는 `launch.ps1` 의 갱신 블록:

```powershell
Invoke-WebRequest -Uri '$Base/static/agent/bridge_agent.py' -OutFile $new `
  -UseBasicParsing -TimeoutSec 30 -ErrorAction Stop
...
} catch { }          # ← 실패가 여기서 사라진다
```

`Invoke-WebRequest` 는 `rootCA.crt` 를 **보지 않는다**. OS 신뢰 저장소로 검증한다.
그리고 이 설치기는 CA 를 그 저장소에 넣지 않는다 — **같은 파일이 그렇게 적어 두었다**:

| `bridge_setup.ps1` 실측 인용 | 줄 |
|---|---|
| 「Windows 는 CA 를 시스템 저장소에 넣지 않고도 요청별로 신뢰시키기 어려워, curl.exe 가 있으면 `--cacert` 로」 | 363 |
| 「⚠ **Invoke-WebRequest 를 폴백으로 두지 않는다.** IWR 은 `$CaPath` 를 보지 않고 **OS 신뢰 저장소**로 검증한다」 | 454 |

설치 다운로드는 그 규율을 지켰다(`Get-RemoteFile` = curl `--cacert` → 파이썬 `cafile`).
**그 스크립트가 굽는 런처만 정확히 금지된 것을 썼다.** 한 파일 안에서 갈렸다.

축을 늘어놓으면 예외가 하나다:

| 축 | 받는 수단 | pin |
|---|---|---|
| `launch.sh` (POSIX) | `curl --cacert` | ✔ |
| `agent/selfupdate.py` (러너 자기 갱신) | `ssl.create_default_context(cafile=ca)` | ✔ |
| **`launch.ps1` (Windows)** | **`Invoke-WebRequest`** | **✘** |

그리고 사용자는 Windows 다. 그래서 결과는 «갱신 코드는 배포됐는데 그 사용자에게서는
100% 실패» 이고, 실패는 `catch { }` 안에서 **아무 흔적 없이** 사라졌다. 창은 숨겨져
있어(`-WindowStyle Hidden`) 증거가 남을 곳도 없었다.

⚠ 반대 방향도 결함이다: 사내 CA 가 OS 저장소에 **있는** 머신에서는 IWR 이 우리가 pin 한
CA 와 **무관하게** 통과한다(실측 2026-08-31, 위 454행 주석의 근거). 다음 순간 **실행될**
파일을 받는 자리다 — 조용한 미갱신과 조용한 pin 우회가 같은 한 줄에서 나온다.

## 4. 고친 것

1. **`launch.ps1` 은 파이썬으로 받는다.** 러너가 바로 아래에서 `--ca` 로 쓰는 것과 **같은
   신뢰 평가기**다 — 폴백이 아니라 신뢰 경로를 하나로 두기 위한 선택이다(설치 본체가
   같은 이유로 같은 선택을 했다). 크기 바닥 20000B·`ast.parse` 는 `selfupdate.py` 와 같은 값.
2. **`launch.sh` 에 파이썬 두 번째 손.** 종전에는 `command -v curl` 이 실패하면 갱신을
   통째로 건너뛰었다 — Windows 가 IWR 로 겪은 「조용한 미갱신」의 약한 판이다.
3. **실패를 조용히 삼키지 않는다.** Windows 는 `launch.log` 에, POSIX 는 stderr 에 사유를
   남긴다. 이 침묵이 결함을 여러 cycle 동안 살려 뒀다.
4. **heredoc 백틱 이스케이프.** `launch.sh` 를 굽는 unquoted heredoc 안에서 백틱이 **명령
   치환**되어, 생성된 파일의 주석에서 `--cacert` 가 통째로 지워져 있었다(실측). 종전부터
   있던 결함이고, 이 cycle 이 그 블록을 다시 쓰므로 함께 고친다.

## 5. 정직하게 — 이 수정이 만들지 않는 것

**이미 설치된 낡은 런처는 원격으로 고칠 수 없다.** 런처는 사용자 컴퓨터의 파일이고 서버가
그것을 바꿀 통로가 없다. 그래서 이 수정도 **1회 재설치**를 요구한다 — 지금 화면이 이미
요구하는 것과 같은 한 번이므로 마찰이 더해지지는 않는다.

달라지는 것은 **그 한 번 뒤**다. 종전에는 재설치를 해도 Windows 에서는 갱신이 계속 실패해
같은 자리로 돌아왔다(사용자가 겪은 반복). 이제 재설치 한 번이면 러너 자기 갱신(`T140000`)에
도달하고, 그 뒤로는 배포가 몇 번을 나든 러너가 스스로 따라간다.

이월: **런처 스크립트 자체의 자동 갱신**. 러너는 자기 자신만 갱신한다. `launch.*` 는 설치
시점 값(파이썬 경로·`$Base`·조사된 인자)이 구워지므로 서버 정적 파일로 덮어쓸 수 없고,
템플릿 + 파라미터 재조립이 필요하다. 이번 범위 밖이다.

## 6. 적대 패널이 뒤집은 것 (2026-09-02, security · qa)

여기까지 쓰고 두 패널을 돌렸다. **둘 다 실행으로 재현한 결함을 냈고, 이 cycle 의 헤드라인
주장(「pin 이 강제된다」)이 두 경로에서 거짓임을 실증했다.**

이 cycle 이 **새로 넣은** 것 3건 — `cat > "$_dl"` 이 `set -e` 아래라 **런처가 죽는** 경로 ·
heredoc 주석 백틱이 CR/BEL 로 굽히는 **제어문자 주입** · `try { } catch { }` 방어 제거(형제
스위트가 적발). 원래 있던 것 5건 — **리다이렉트로 평문 다운그레이드**(pin 무력화) · `http://`
base 무검증 · curl 손(기본 경로) 크기 바닥 부재(31B 통과) · `$LASTEXITCODE` stale(직전 값이
반드시 0=성공) · status 미확인. **전부 수정**했다.

그리고 내가 쓴 「뮤테이션 7종 전건 KILL」이 **성립하지 않았다** — 같은 스위트에 17종을 돌리자
**15종 생존**했고, 그중 하나는 `Invoke-WebRequest` 를 기본 별칭 `iwr` 로 바꾼 것, 즉 **원래
결함 그 자체**였다. 내가 고른 7종이 전부 죽은 것은 **내가 방어를 넣은 자리만 골랐기** 때문이다.
