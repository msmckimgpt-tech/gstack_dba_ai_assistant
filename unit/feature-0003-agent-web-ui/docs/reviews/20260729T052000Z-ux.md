## 1. Findings (발견)

### F1 (BLOCK) — "첨부 제거"(×) 버튼이 이번 변경으로 **거짓 어포던스**가 된다

체크박스는 제거됐지만 **선택/제거 개념은 pill 의 `×` 버튼 형태로 그대로 살아 있다.**

- `src/static/app.js:9469-9478` — 모든 첨부 pill 에 remove 버튼이 붙는다.
  `removeBtn.setAttribute("aria-label", "첨부 제거")` (app.js:9471)
- `src/static/app.js:9499-9507` `_removeAttachmentPill()` — **클라이언트 bucket 에서 splice 만 한다.**
  서버 호출이 전혀 없다.
  ```js
  function _removeAttachmentPill(attachmentId) {
    // UX-COMPACT: x 버튼 → 목록에서 즉시 제거 (기존 toggle 동작 대체)
    const key = _composerAttachmentKey(state.activeConversationId);
    const bucket = state.composerAttachments.byConv[key];
    if (!bucket) return;
    const idx = bucket.items.findIndex((it) => String(it.id) === String(attachmentId));
    if (idx >= 0) bucket.items.splice(idx, 1);
    _renderAttachmentPills();
  }
  ```
- 서버는 이제 `src/routers/conversations.py:3104-3111` 에서
  `_resolve_conversation_attachment_scope(...)` 로 스코프를 **DB 에서 재해소**한다
  (`src/routers/_conv_store.py:3061-3067`):
  `UploadStatus IN ('uploaded','ingested') AND SupersededAt IS NULL AND DeletedAt IS NULL AND DeletePending = 0`.
  `×` 는 이 조건 중 **무엇도 바꾸지 않는다.**

즉 **변경 전**: `×` → bucket 에서 제거 → `attachment_ids` 에서 빠짐 → 그 턴 동안 assistant 가 그 파일을 못 봄
(정직한 동작). **변경 후**: `×` → 서버가 DB 에서 다시 끌어옴 → assistant 가 그대로 본다. 게다가 신설된
`read_attachment` 도구로 **본문까지 자율 조회**할 수 있다. 사용자가 "제거했다"고 믿는 파일이 답변에
인용될 수 있다.

이것이 단순한 표시 오류가 아닌 이유:

1. **되돌릴 수단이 UI 에 전혀 없다.** `DELETE /api/attachments/{attachment_id}`
   (`src/routers/attachments.py:223`, soft-delete `DeleteReason='user'`) 는 존재하지만
   **app.js 어디에서도 호출하지 않는다** (app.js 의 `/api/attachments` 호출은
   `4737`/`9837` download, `9958` versions 뿐). 그래서 사용자는 잘못 올린 첨부를
   assistant 시야에서 빼낼 방법이 이제 **0개**다.
2. **거의 모든 첨부가 즉시 업로드된다.** `app.js:9564-9577` — lazy-create 경로조차 파일 선택 즉시
   대화 생성 + 업로드(`status:"uploading"` → 서버 id). `status:"staged"` 는
   `lazyConvCreating` race 한정. 따라서 "× 를 눌러도 서버엔 남아 있다"가 예외가 아니라 **기본값**이다.
3. **같은 `×` 가 두 가지를 뜻한다.** staged 항목(미업로드)에 대해서는 여전히 진짜 제거,
   업로드된 항목에 대해서는 표시만 제거 — 라벨은 동일한 "첨부 제거". 사용자 모델이 갈라진다.
4. **그룹 대화 증폭.** 그룹은 발신자 본인 첨부만 스코프(CSO F1 유지)지만, 그 첨부에서 나온 **답변 본문은
   전 멤버에게 보인다**. 잘못 올린 파일을 `×` 로 뺐다고 믿은 사용자가 그룹에서 질문하면 내용이
   답변으로 새어나갈 수 있다. 이전에는 `×` 가 그 턴을 막아줬다.

부가로, `selected` 플래그 자체는 이제 **완전히 vacuous** 하다 — app.js 전역에서 `selected` 를 `false` 로
바꾸는 코드가 단 한 줄도 없다(`9377`, `9569`, `9577`, `9618`, `9650`, `9676`, `9780`, `9821` 전부
`selected: true` 로만 push). 그러므로 `_composerAttachmentSnapshot` 의
`.filter((it) => it.selected && ...)` (app.js:9351) 는 항상 참인 조건이고, 실질 필터는 `×` 의 splice 다.
"selected 개념이 남아 있는가"의 답은 **필드로는 죽었고 버튼으로는 살아 있다**이며, 살아 있는 쪽이 문제다.

### F2 (CONCERN) — 스코프 의미를 알려주던 **유일한 문구가 사라졌고, 대체가 없다**

제거된 hint("현재 선택뿐 아니라 이 대화에 올린 전체 첨부를 컨텍스트로 사용합니다",
`index.html` 구 366행)를 대신할 안내가 `index.html:363-364` 에는 **주석만** 남았다.

패널 본문에는 **두 개의 렌더러가 같은 컨테이너(`#attachSidePanelList`)를 번갈아 덮어쓴다**:

- `_renderAttachmentPills()` (app.js:9394-9497) — 섹션 라벨
  `"세션 파일 (이전 첨부 — LLM 컨텍스트 유지)"` (app.js:9493) 가 있어 **부분적으로** 스코프를 알린다.
- `_loadConversationAttachmentList()` (app.js:9894-9975) — **스코프 안내가 0개**. 아이콘/크기/상태/
  버전 토글/다운로드만 렌더한다.

그런데 사용자가 "첨부파일 목록" 메뉴로 패널을 **명시적으로 열 때 실행되는 것은 후자**다
(app.js:10469 `if (cid) _loadConversationAttachmentList(cid);`). 즉 사용자가 첨부 스코프를 확인하려고
의도적으로 여는 화면이 **스코프에 대해 아무 말도 하지 않는 화면**이다. 제거된 체크박스 행은
`<aside>` 직속 sibling 이라 두 렌더러 모두에 살아남는 유일한 요소였는데, 그 자리가 비었다.

"기본 동작이니 안내 불필요"라는 반론은 F1 이 성립하는 한 성립하지 않는다 — 제거 버튼이 옆에 있는데
"제거해도 계속 본다"는 사실이 어디에도 없으면, 그것은 침묵이 아니라 **오도**다.

## 2. Risks (위험)

- **R1 (높음, F1)** 신뢰 파손 + 동의(consent) 파손. "제거"를 눌렀는데 AI 가 읽고 인용한다.
  그룹 대화에서는 답변이 전 멤버에게 노출되므로 파장이 발신자 밖으로 나간다.
  현재 UI 에는 회복 수단(soft-delete 호출)이 없다.
- **R2 (중간, F1)** 혼란 루프. `×` 로 지운 pill 은 전송 후
  `_syncConversationAttachmentsToBucket()` (app.js:11013) 으로 "세션 파일" 섹션에 **되살아난다**.
  사용자는 "지웠는데 계속 돌아온다"를 반복 경험하고, 이제 그것이 실제 동작과도 일치한다 —
  통제 불능감이 확정된다.
- **R3 (중간, F2)** 명시적으로 연 첨부 패널이 스코프를 설명하지 않아, 사용자가 "이 목록 = 내가 고른 것"
  이라는 옛 모델을 유지한다. 이전 턴 파일을 근거로 한 답변이 "왜 저걸 봤지?" 로 읽힌다.
- **R4 (낮음)** `?v=dev` 정적 캐시버스터(`index.html:14`, `index.html:635`)가 서빙·배포 어디서도
  치환되지 않는다(app.py/routers/bin grep 0건). JS 변경이 하드리프레시 전까지 브라우저에 도달하지 않을 수
  있다. 조합 파손은 없음(F5 확인)이나 배포 후 검증 시 캐시 무효화 확인 필요.
- **R5 (낮음, 비회귀)** `conversations.py:3121-3126` 의 "동기 ingest 대기는 이번 턴 첨부로 한정" 주석은
  실제와 다르다 — `_sync_ingest_ids = client_attachment_ids + new_attachment_ids_clean` 이고
  `client_attachment_ids` 는 bucket 의 session-source 항목까지 포함한다. 다만 변경 전
  `attachment_ids_clean` 과 동일 집합이라 **지연 회귀는 아니다**(과거 failed csv/xlsx 재시도 25s join 은
  이전과 동일). 문구만 부정확.

## 4. Verdict rationale (판정 근거)

체크박스 제거 자체는 정당하다 — `attachment_scope_all` 은 백엔드가 읽은 적 없는 no-op 이었고,
CSS·상태·전송 필드 정리는 잔재 0건으로 깔끔하며(F5), 레이아웃 회귀도 없다(F3).

그러나 이번 변경의 UX 판단은 "체크박스를 지웠는가"가 아니라 **"선택이라는 사용자 모델을 남김없이
지웠는가"** 로 내려야 한다. 지우다 만 부분이 하필 **가장 강한 어포던스**다: 모든 pill 에 달린
`aria-label="첨부 제거"` 버튼(app.js:9471)이 서버 스코프를 전혀 바꾸지 못한 채
(`_removeAttachmentPill` 은 순수 클라이언트 splice, app.js:9499-9507),
`_resolve_conversation_attachment_scope` 의 DB 재해소(`_conv_store.py:3061-3067`)로 즉시 무효화된다.
동시에 그 버튼을 대체할 실삭제 경로는 **API 는 있는데 UI 가 부르지 않는다**
(`attachments.py:223` vs app.js 호출 0건). 결과적으로 사용자는
"AI 에게 이 파일을 보이지 않게 하는" 수단을 이번 변경으로 **완전히 잃었고, 잃었다는 사실을 알 방법도
없다**(F2: 명시적으로 여는 패널에 스코프 안내 0건).

"제거했다고 믿게 하면서 실제로는 읽는다"는 것은 성능·정합 결함이 아니라 **동의 표면의 결함**이며,
그룹 대화에서는 답변을 통해 발신자 밖으로 파급된다. 수정 방향(실삭제 연결 / 라벨 정직화 / 버튼 제거)은
제품 결정이 필요하므로 자동 수정으로 닫을 수 없다.

→ **BLOCK**, Human Approval Needed: **yes**.
F2 만 남았다면 CONCERN 이었을 것이나, F1 이 사용자를 능동적으로 오도하므로 승격한다.
