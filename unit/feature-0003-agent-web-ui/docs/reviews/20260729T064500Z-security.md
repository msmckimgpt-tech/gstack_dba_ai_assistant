> 적대적(refute-first) 보안 리뷰. `/security-review` 스킬이 요구하는 sub-task fan-out 은 본 세션의
> 상위 우선순위 도구 제약("Do not call the AgentTool unless the user requested it")과 충돌하므로,
> AGENTS.md §18.8.2 "상위 우선순위 지시 carve-out" 에 따라 **제약 없는 채널(직접 코드 리뷰 +
> 기계적 점검)** 으로 수행했다. 미검증 도메인은 §5 에 명시한다.

### 1. Blocking issues

- **Finding A (medium-high, 흡수됨) — 계정 경계를 넘는 대화 본문 캐시 잔류.**
  Evidence: 본 cycle 이 신설한 `_branchViewCache` 는 `/api/history` payload(= 대화 **본문** 전량)를
  담는 **모듈 전역 Map** 인데, 최초 구현은 대화 전환/전송 후 등 "내용 변경 시점" 에서만 무효화하고
  **세션 경계에서는 비우지 않았다**. 이 앱의 `handleLogout`(static/app.js)은 **페이지를 새로
  고치지 않으며**, 바로 그 이유로 `state.messages`·`state.conversations`·모델 선택을 손으로 비운다
  (기존 주석: "로그아웃은 페이지를 새로 고치지 않으므로 … 공용 단말 계정 간 누출"). 즉 세션 경계는
  이 코드베이스가 이미 인정한 보안 경계다.
  Reason: 공용 단말에서 A 로그아웃 → B 로그인(페이지 리로드 없음) 후, B 가 같은
  `(conversation_id, versionId)` 로 버전 페이징하면 `_fetchHistoryPayload` 가 **A 기준으로 서버
  필터링된 payload** 를 캐시 적중으로 반환한다. 특히 공유창 window(`[from, to]`)가 계정마다 다른
  그룹 대화에서, **좁은 window 를 가진 B 가 넓은 window 의 본문을 보게 되는 누출** —
  `_resolve_display_window` / `_branch_resolve_readonly_leaf` 의 fail-closed 가시성 게이트가
  클라이언트 캐시로 우회된다. 같은 축의 변형: `conversation.read.any` 보유 관리자가 열람하던 대화를
  로그아웃 후 소유자가 열람하는 경우.
  Location: `unit/feature-0003-agent-web-ui/src/static/app.js` — `_branchViewCache` 정의부 및
  `handleLogout`.
  Action: 세션 경계 2곳에서 캐시를 비운다 — ① `handleLogout` 에서 `_branchViewCacheClear()` +
  지연 사이드바 타이머 취소(로그아웃 후 잔류 요청 방지), ② `initializeWorkspace` 진입 시
  `_branchViewCacheClear()`(세션 만료 후 리로드 없이 재로그인하는 `handleLogin → initializeWorkspace`
  경로는 logout 을 거치지 않음 — 2중 방어). → **수정 완료**.

### 2. Cross-domain concerns

- **`scope` 파라미터의 신뢰 경계 (반증됨)** — `_search_rate_limit_check(..., scope=)` 는 버킷 키에
  들어가므로 사용자 제어 시 버킷 분할 회피가 가능하다. 호출부 7곳 전수 확인 결과 **전부 모듈 상수
  (`app.RATE_SCOPE_*`)** 이고 요청 본문·쿼리에서 유입되는 경로가 없다. 신규 호출부가 기본값에 기대
  조용히 버킷을 병합하지 않도록 docstring 에 금지를 명시했다. 취약점 아님.
- **`Retry-After` 헤더 주입 (반증됨)** — `_json_rate_limited` 의 헤더 값은 `str(int)` 이고 1~60 으로
  clamp + 예외 시 1 폴백이라 CRLF 등 주입 문자가 들어갈 수 없다. 본문 문구도 서버 리터럴만 사용.
- **SQL 주입 (반증됨)** — `_branch_leaf_of` 에 추가한 `c.conversation_id = %s` 는 파라미터 바인딩이고,
  f-string 으로 들어가는 `table` 은 기존 allowlist(`("messages", "core_messages")`) 가 그대로 유효.
  결과 동등성은 브랜치 대화 12건 × 두 store 전 메시지 **442 조합 전수 대조로 불일치 0** 확인.
- **인가 경로 축소 (반증됨)** — 페이징에서 `refreshWorkspace` 를 걷어내며 `renderAccessNotice()` /
  `applyProductHydration()` 재호출이 빠졌다. 두 함수는 **표시 계층**이고 접근 판정은 전적으로 서버
  (`_account_can_access_conversation` / `_conversation_owned_by_account`)가 하며, 버전 페이징은
  접근 권한을 바꾸는 동작이 아니다. 권한 우회 아님.
- **`active_leaf` 영속 지연 (설계에서 배제)** — 요청 수를 더 줄이려면 `branch/switch` 를 디바운스할
  수 있으나, agent-core `modules/memory.py` 가 이 값으로 새 메시지의 부모 체인과 LLM recall 범위를
  정하므로 지연 중 발화하면 메시지가 화면과 다른 가지에 붙는다. 8ms 절약과 데이터 정합성을 맞바꾸지
  않는다 — 영속은 매 전환마다 즉시 확정(ADR alternatives (d) 기각 사유).

### 3. Non-blocking observations

- 캐시 TTL 30s 는 그룹 대화 읽기전용 페이징에서 최대 30초의 stale 열람 창을 남긴다. 권한이 아니라
  신선도 축이며, 활성 대화 본문은 기존 `_liveSyncTick`(5s 폴러)이 계속 갱신한다.
- 버킷 키 공간이 `계정수 × scope수` 로 늘어난다. `_RATE_LIMIT_BUCKETS_MAX_KEYS=4096` 초과 시
  **만료 버킷만** sweep 하고 활성 버킷은 보존하도록 구현했고 테스트 S5 가 이를 고정한다.

### 4. 제외 카테고리

DoS·자원 고갈·rate-limit 자체는 본 리뷰 채널의 명시 제외 범주다. 다만 본 cycle 의 상한 상향
(페이징 5 → 60)은 §12.3 Major 로 별도 분류해 실측 근거(페이징 p50 8.0ms vs LLM run p50 12,344ms)와
함께 ADR 에 남겼고, LLM·외부 비용을 태우는 경로의 상한은 무변경이다.
