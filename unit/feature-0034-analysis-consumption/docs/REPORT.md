# Report

## 진행 요약 (2026-07-30)

ITEM-09(분석 산출물의 대화 소비) 구현 완료. codex 적대 리뷰 P1 3건·P2 1건 반영, 출하 중.

## 왜 순서를 바꿨나

ROADMAP 은 ITEM-08(L3 lazy) → ITEM-09(소비) 순이었는데 뒤집었다. L2 요약이 이미 쌓이기
시작했는데 답변 경로가 읽지 않아 **여전히 콘솔 열람에만 갇혀 있었고**, L3 는 L2 위에 층을 하나
더 쌓는 일이라 소비 경로 없이 만들면 또 하나의 미사용 자산이 된다. 만든 것을 쓰는 경로를 먼저
이었다.

## 무엇을 했나

`_build_knowledge_context`(답변 grounding 조립의 choke-point)에 `TABLE GROUP SUMMARIES` 섹션을
추가했다. 질문이 언급한 테이블 → 그 테이블의 클러스터 라벨 → `cluster_summaries` 조회 →
근거 수와 함께 주입.

**가장 신경 쓴 것은 정직성**이다. 라이브 요약의 85%가 상세분석 근거 0(이름·구조 추정)이므로,
근거를 숨기고 요약만 주면 LLM 이 추정을 실측 결론으로 오독하고 그 오독이 사용자 답변에 실린다.
그래서 각 요약 앞에 `(멤버 48개 중 40개 상세분석 근거)` 또는 `(상세분석 근거 없음 — 이름·구조
기반 추정)`을 붙이고, 프롬프트에도 "근거 없음은 사실로 단정하지 말고 필요하면 실제 스키마·
데이터로 검증하라"를 명시했다.

## 리뷰에서 드러난 것

codex P1 3건이 전부 실질적이었다:

- **schema 격리 누수** — `cluster_summaries` 식별자는 `(scope, schema, …)` 인데 조회가
  `scope + label` 만 봤다. 같은 datasource 의 다른 스키마가 같은 라벨을 가지면 엉뚱한 요약이
  주입된다. 2단계 조회로 재구성하며 `effective_schema` 유도까지 정확히 맞췄다.
- **`SET LOCAL statement_timeout` 무효** — RO 연결은 autocommit 이라 트랜잭션이 없다. 상한이
  걸린다고 믿고 있었지만 실제로는 안 걸렸다.
- **ILIKE 와일드카드** — 테이블명의 `_` 가 "임의의 1문자"로 해석돼 질문에 없는 테이블이 매칭될
  수 있었다(자체 점검에서도 같은 결론).

그리고 `cursor()` 를 try 밖에 둔 결함은 **테스트가 먼저 잡았다**. feature-0031 에서 `connect()`
를 try 안으로 옮기며 배운 것과 정확히 같은 계열을 세 번째 반복한 것이다.

## 남긴 한계 (정직하게)

- 매칭은 질문이 **테이블명을 문자열로 언급**할 때만 작동한다. "결제 관련 구조 알려줘" 같은
  도메인 어휘 질문은 걸리지 않는다. 의미 검색으로 넓히려면 임베딩 왕복이 붙으므로 별도 판단이
  필요하다(이 프로젝트는 임베딩 cold-reload 로 ~50s 회귀를 겪은 이력이 있다).
- 주입되는 요약 대부분이 추정이다(근거 0이 85%). 커버리지를 올리는 ITEM-11(결정적 플래너)이
  이 층의 품질에 직결된다.
