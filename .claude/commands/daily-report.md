# Skill: daily-report (일일 작업 보고서 생성기)

당신은 **"daily-report" 생성기** 입니다.
역할: 지정한 날짜에 이 프로젝트(`repo` git 저장소)에서 진행한 작업을, **보고서에 그대로 붙여넣을 수 있는** 시간대별 한 줄 목록으로 정리한다.

## 불변 제약

- **근거는 git 로그뿐**. 대화 내역이 컨텍스트에 없어도, 추측하지 말고 해당일 커밋(시각 포함)에서만 사실을 재구성한다. 커밋이 없는 항목은 만들지 않는다.
- **read-only**. 코드/문서를 수정하지 않는다. (`Write`/`Edit` 사용 금지 — 이 스킬은 조회·요약 전용.)
- **한 줄 = 하나의 논리적 작업**. TASK-XXXX 번호가 있으면 그 단위로 묶고, 없으면 커밋 주제 단위로 한 줄.
- **작업(산출물) 중심 — 내부 진행 절차는 제외**. 보고서 줄은 **"무엇을 만들었/고쳤는지"(사용자·제품에 남는 결과)** 만 담는다. 검증·확인·증적 기록·캐시 갱신·머지·재작업 같은 **그 작업을 완성하기 위한 내부 진행 절차는 줄에 쓰지 않는다**. 한 TASK 의 여러 커밋(구현 + 검증 + 증적 + 자잘한 후속 수정)은 **최종 산출물 한 줄**로 접고, 절차 단계는 열거하지 않는다. 제외 대상의 구체 목록·판정은 §4.1 참조.
- **제품 기능 개발 vs 별첨 분리**. 시간대별(10–13 / 13–16 / 16–19) 섹션에는 **제품(사용자·운영자가 쓰는 애플리케이션)의 기능 개발·개선·버그 수정만** 넣는다. 개발·운영 보조 도구·스킬·파이프라인, 프로젝트 템플릿 업그레이드·빌드/배포 인프라, 제품 코드 변경 없는 문서·릴리즈노트·발표자료 같은 **기능 개발 외 산출물은 보고서 최하단 `별첨 (기능 개발 외)` 섹션에 시간대 구분 없이 모은다**. 분류 기준·부류는 §4.2 참조.
- **커밋 해시·브랜치 id 미노출**. 각 줄 끝에 커밋 해시(`d54b664` 등)나 브랜치 id 를 붙이지 않는다. 사람이 읽는 보고서 줄에는 작업 요약만 남긴다. (해시는 그룹핑 판단에만 내부적으로 쓰고 출력하지 않는다.)
- **내부 용어 일반화**. 보고서 줄(요약 서술)에는 프로젝트 내부 식별자·약어(`PB-0008`, `ADR-0030`, `feature-0003` / `#0003`, `ask-worker` / `insight-worker`, `cycle-init` 등)를 그대로 노출하지 않고, **일반 독자가 이해할 수 있는 용어로 풀어 쓴다** ("무엇을 했는지" 행위로 표현). 단 줄 머리의 `TASK-XXXX` 번호는 사내 추적 키로 **유지**한다 (이 항목의 유일한 예외). 치환 대상·방식은 §4.1 참조.
- **시각 기준 분리**. 커밋 author/commit 시각을 **세 시간대**(10:00–13:00 / 13:00–16:00 / 16:00–19:00) 로 나눈다. 한 TASK 가 두 시간대에 걸치면 각 시간대에 나눠 표기하고, 무엇이 각 시간대에 들어갔는지 명시한다.
- **보고일 경계 = 19:00**. 보고서가 다루는 하루는 **전날 19:00 ~ 당일 19:00** 이다. 즉 (a) **전날 19:00 이후** 작업은 당일 보고서의 **10:00 ~ 13:00 구간 안에 '전날(19:00 이후)' 하위 섹션으로 묶어 포함**하고, (b) **당일 19:00 이후** 작업은 당일 보고서에서 빼서 **익일** 보고서로 이월한다(당일 보고서에는 이월 건수만 각주로 남긴다). **전날분 표시는 섹션 구분으로만 하며, 개별 TASK 줄에 `(이전날)` 같은 마커를 붙이지 않는다.**

## 절차

### 1. 날짜 결정
- 인자가 있으면 그 날짜(`YYYY-MM-DD`)를 대상으로 한다.
- 인자가 없으면 **오늘** 을 대상으로 한다. 오늘 날짜는 `date +%F` 로 구한다.

### 2. 대상 저장소 식별
- 작업 디렉터리 기준 git 저장소는 `repo/` 이다. 먼저 그 경로의 git 로그를 사용한다.
  ```bash
  REPO=/root/download/docker/mysql_ai_delegated_dev/repo
  ```
- `git -C "$REPO" rev-parse --is-inside-work-tree` 로 확인. 경로가 다르면 현재 작업 디렉터리에서 `git rev-parse --show-toplevel` 로 보정한다.

### 3. 해당일 커밋 수집 (날짜·시각 포함, 시간순)
보고일 경계가 19:00 이므로 **전날 19:00 ~ 당일 24:00** 까지 한 번에 수집한다 (전날
야간분을 10–13 의 '전날(19:00 이후)' 하위 섹션으로 편입하고, 당일 19:00 이후분의 이월 건수를 각주로
밝히기 위해 당일 야간분도 함께 본다). 어느 날 커밋인지 판별해야 하므로 `--date`
포맷에 `%m-%d` 접두를 넣는다.
```bash
DAY=<대상날짜>            # 예 2026-06-09
PREV=$(date -d "$DAY -1 day" +%F)
NEXT=$(date -d "$DAY +1 day" +%F)
git -C "$REPO" log --all \
  --since="$PREV 19:00" --until="$NEXT 00:00" \
  --pretty="%cd %h %s" --date=format:'%m-%d %H:%M' \
  --reverse
```
- merge 커밋과 feature 커밋이 함께 잡힌다. 같은 TASK의 중복(예: feature 커밋 + merge PR)은 **하나의 논리적 작업으로 합친다**.
- `%m-%d` 접두로 **전날(PREV) / 당일(DAY)** 을 구분한다. 시각 표기·헤더에는 `HH:MM` 만 쓰고 `%m-%d` 접두는 분류 판단용 내부 참고로만 사용한다.
- 출력의 `%h` 해시는 **그룹핑·시각 판단용 내부 참고일 뿐** 이며, 최종 보고서 줄에는 노출하지 않는다 (위 불변 제약 참조).
- 커밋이 0건이면 "해당일 `repo` 커밋 없음" 을 그대로 보고하고, 다른 working dir의 저장소(예: 템플릿 `repo`)도 확인이 필요한지 사용자에게 한 줄로 안내한다.

### 4. TASK 단위 그룹핑
- 커밋 메시지의 `TASK-XXXX` 토큰으로 묶는다.
- 같은 TASK 번호의 여러 커밋(구현 + tz 수정 + 마감 등)은 **한 줄로 요약**하되 핵심 변경을 담는다.
- TASK 번호가 없는 작업(템플릿 업그레이드, 일반 UX 커밋 등)은 주제명으로 한 줄.

#### 4.1 요약 서술 — 작업(산출물) 중심 추출 + 내부 용어 일반화 (필수)
각 TASK 줄의 **요약 서술**(`**TASK-XXXX** — <요약>` 의 `<요약>` 부분)은 커밋 메시지를 그대로 옮기지 말고, 두 단계를 거친다: **(A) 산출물만 남기고 내부 진행 절차를 덜어낸 뒤 → (B) 남은 내용을 일반 독자가 읽을 수 있는 용어로 풀어 쓴다.** 줄 머리의 `TASK-XXXX` 번호만 추적 키로 유지한다(불변 제약 참조).

##### (A) 제외 — 줄에 쓰지 않는 내부 진행 절차 (필수)
보고서 줄은 **"무엇을 만들었/고쳤는지"** 만 담는다. 다음은 작업을 완성하기 위한 **진행 절차**일 뿐 산출물이 아니므로 **줄에서 제거**하고, "+ ~" 형태로도 덧붙이지 않는다 (한 TASK 의 여러 커밋을 최종 산출물 한 줄로 접을 때 함께 흡수).
- **검증/확인 절차** — `PB-0008`, `PB-0008 시각검증`, `Windows-browser 검증`, `render-injection`, `라이브 실측`, `시각검증 PASS`, `브라우저 화면 검증` 류 **전부 제거**. (예전 규칙은 이를 "브라우저 화면 검증 통과"로 풀어 붙였으나, 이제는 **쓰지 않는다** — 검증을 통과한 것은 기본 전제이지 그날의 작업이 아니다.)
- **증적·문서 기록** — `evidence 기록`, `evidence 스크린샷`, `마감`, docs-only 후속 커밋 → 제거(앞선 산출물 줄에 흡수).
- **반복·정비 작업** — `캐시버스터 / cache-buster bump`, `styles.css ?v= bump`, `rebase`, `재번호`, `tz 수정`, `lint`, `Merge pull request` → 제거.
- **같은 TASK 내 자체 후속 수정** — 구현 중 스스로 발견해 같은 TASK 에서 고친 버그(예: "접힘 무력화 수정", "audit action 미등록 500 수정")는 **별도 절로 열거하지 말고** 최종 산출물 서술에 녹인다 (그 기능이 의도대로 동작하도록 마무리한 것이므로 결과 문장 하나로 충분).
- **판정 기준**: "이 문구가 빠지면 *무슨 일을 했는지* 가 사라지는가?" → 사라지면 산출물(남긴다). 사라지지 않고 *어떻게/얼마나 꼼꼼히 했는지* 만 빠지면 진행 절차(제거).
  - 예: `작업 화면 좌측 대화목록 첫 진입 시 최근 일자 그룹만 펼침 (TASK-...) PB-0008 evidence 기록` → `**TASK-...** — 작업 화면 대화 목록을 처음 열 때 최근 날짜 그룹만 펼치도록 변경` (검증·증적 제거).
  - 예: 릴리즈 노트 구현 + "접힘 무력화 수정" + 캐시버스터 + evidence → `**TASK-...** — 작업 화면과 관리 콘솔에 릴리즈 노트 추가` (후속 수정·캐시·증적 모두 흡수).

##### (B) 일반화 — 남긴 산출물 서술의 내부 식별자·약어 치환
(A) 를 거쳐 남은 산출물 서술에서, 프로젝트 내부에서만 통하는 식별자·약어를 일반 용어로 바꾼다.
- **의사결정/문서 코드** — `ADR-0030`, `ADR-0020` 등 결정 기록 번호는 빼고 결정 내용만: (예: `SSRF 사설망 경계 env 토글 (TASK-0228, ADR-0030)` → "내부망 접근 차단을 설정으로 켜고 끄게 함").
- **기능/유닛 코드** — `feature-0003`, `#0003`, `(#0003)` 같은 feature id 접미는 제거한다 (TASK 번호로 이미 추적됨).
- **내부 컴포넌트·잡 명** — `ask-worker`, `insight-worker`, `rag_objects`, `_get_llm_client`, `cycle-init` 등 코드/잡 식별자는 역할로 풀어 쓴다: (예: `insight-worker 분석 완료율 UI` → "데이터 분석 진행률 화면").
- **PR/이슈 번호** — `(#157)`, `Merge pull request #161` 류는 노출하지 않는다 (이미 미노출 규칙).
- **약어·영문 식별자 일반** — 위 표에 없더라도 대문자 약어·코드명·snake_case/kebab 식별자가 그대로 보이면 일반 용어로 바꾼다. **판단 기준: 그 프로젝트를 모르는 사람이 읽어도 무슨 작업인지 통하는가.**
- 단, 외부에도 통용되는 표준 용어(`SSE`, `MSSQL`, `MySQL`, `SSRF`, `LLM`, `UI` 등)는 그대로 두어도 된다 — 일반화 대상은 **프로젝트 내부에서만 통하는** 식별자다.

#### 4.2 산출물 분류 — 제품 기능 개발 vs 별첨(기능 개발 외) (필수)
§4.1 로 다듬은 각 산출물 줄을 다음 두 갈래로 나눈다. **시간대별 섹션(§5)에는 "제품 기능 개발" 만 들어가고, "기능 개발 외" 는 전부 보고서 최하단 별첨으로 뺀다.**

- **제품 기능 개발 → §5 시간대별 섹션.** 사용자·운영자가 실제 쓰는 **애플리케이션(제품)의 기능·화면·데이터 처리·권한·버그 수정** 처럼 **제품에 남는 변경**. (예: 그래프 뷰, 대화 화면, 관리 콘솔 기능, 접근 권한, 데이터 분석·관계 처리.)
- **기능 개발 외 → 보고서 최하단 `별첨 (기능 개발 외)` 섹션.** 제품 기능이 아닌 다음 부류:
  - 개발·운영 **보조 도구·스킬·파이프라인** 신설/정비 (예: 개발 진척 보고 발표자료 생성기, `/_dqa` 계열 persona, `/daily-report` 등 스킬 자체 변경).
  - **프로젝트 템플릿 업그레이드**, 빌드/배포 인프라·스크립트, CI 정비 (예: 템플릿 버전 적용, 배포 스크립트 마이그레이션 게이트 수정).
  - 제품 코드 변경 없이 **문서·릴리즈노트·발표자료** 만 작성/정합 (예: 문서 drift 정합, 릴리즈 노트 블록 추가, 발표자료 작성).
  - 저장소 정비성 작업.

- **판정 기준**: "이 변경이 **제품(앱)을 쓰는 사람에게 보이거나 영향을 주는가**?" → 그렇다면 기능 개발(시간대별), 아니면 별첨. 애매하면 **제품 사용자 영향 유무**로 가른다.
- 별첨 줄도 §4.1 (산출물 중심 추출 + 내부 용어 일반화) 를 동일하게 적용한다. `TASK-XXXX` 번호가 있으면 유지, 없으면 주제명 한 줄.
- 별첨은 **시간대·전날/당일 하위 구분 없이** 한 목록으로 나열한다 (타임라인에서 빠지는 항목이므로). 단 보고일 경계(19:00) 규칙(§ 불변 제약·§5)은 동일 적용 — 당일 19:00 이후 별첨분도 익일로 이월(각주).

### 5. 시간대별 분리 출력
- 먼저 §3 의 `%m-%d` 접두로 각 커밋을 **보고일 경계(19:00)** 기준으로 분류한다:
  - **전날(PREV) 19:00 이후** 커밋 → 당일 보고서의 **10:00 ~ 13:00 구간 안의 '전날(19:00 이후)' 하위 섹션으로 편입**한다 (개별 줄에 `(이전날)` 마커를 붙이지 않고, 섹션 구분으로만 표시).
  - **당일(DAY) 19:00 이후** 커밋 → 당일 보고서에서 **제외**하고, "당일 19:00 이후 N건은 익일 보고서로 이월" 을 마지막 각주로 밝힌다 (보고서 본문 줄로는 출력하지 않는다).
  - 그 외 당일 커밋은 **첫 커밋 시각** 으로 다음 세 시간대에 배정한다 (하한 포함, 상한 제외):
    1. **10:00 ~ 13:00**
    2. **13:00 ~ 16:00**
    3. **16:00 ~ 19:00**
  - 당일 **10:00 이전(00:00~10:00)** 커밋은 10–13 구간에 흡수하되 해당 시각을 한 줄 각주로 밝힌다 (예: "09:55 커밋 1건은 10–13 구간에 포함").
- **별첨 부류(§4.2)는 시간대 배정 대상이 아니다** — '기능 개발 외' 로 판정된 산출물은 첫 커밋 시각과 무관하게 세 시간대 어디에도 넣지 않고 최하단 `별첨 (기능 개발 외)` 섹션으로 모은다. 시간대 배정·전날 하위 섹션·10:00 이전 흡수 규칙은 **제품 기능 개발 줄에만** 적용한다.
- 한 TASK 의 커밋이 두 시간대를 걸치면 각 시간대 줄에 나눠 적고, 어느 변경이 어느 시간대에 들어갔는지 명시한다. 전날분과 당일분이 한 TASK 에 섞이면 10–13 안의 '전날(19:00 이후)' 하위 섹션에 둔다 (주된 작업 시각 기준 — 줄에 마커는 붙이지 않는다).
- 각 시간대 헤더에는 해당 구간에 실제로 커밋이 존재하는 **첫시각 ~ 마지막시각** 을 괄호로 적는다. 커밋이 없는 시간대는 헤더를 생략한다.
- 시간순 정렬 (전날 19:00 이후 분은 10–13 의 맨 앞 '전날(19:00 이후)' 하위 섹션에 둔다).

### 6. 출력 형식 (보고서용)
아래 형식을 **그대로** 출력한다. 마크다운 헤더 + bullet, 각 bullet 은 `**TASK-XXXX** — 한 줄 요약` (줄 끝에 해시/브랜치 id 없음, **줄에 `(이전날)` 류 마커도 없음**, **요약 서술은 §4.1 대로 산출물만 남기고 내부 진행 절차를 덜어낸 뒤 내부 약어를 일반 용어로 치환** — 검증·증적·캐시 갱신 같은 절차 문구를 "+ ~" 로 붙이지 않는다).

전날 19:00 이후 작업이 있으면 10–13 구간 안을 **`**전날(19:00 이후)**` / `**당일**` 두 하위 섹션(굵은 라벨 줄)으로만 구분**한다. 전날분이 없으면 하위 라벨 없이 TASK 를 바로 나열한다.

```
## <대상날짜> 진행 작업

### 10:00 ~ 13:00 (<첫시각> ~ <마지막시각>)

**전날(19:00 이후)**
- **TASK-XXXX** — <전날 19:00 이후 작업 요약>

**당일**
- **TASK-XXXX** — <당일 작업 요약>
- **<주제>** — <한 줄 요약>

### 13:00 ~ 16:00 (<첫시각> ~ <마지막시각>)
- **TASK-XXXX** — <한 줄 요약>

### 16:00 ~ 19:00 (<첫시각> ~ <마지막시각>)
- **TASK-XXXX** — <한 줄 요약>
...

---

### 별첨 (기능 개발 외)
- **TASK-XXXX** — <도구·스킬·템플릿 업그레이드·문서·발표자료·배포 인프라 등 기능 개발 외 산출물 요약>
- **<주제>** — <한 줄 요약>
```
- 전날분이 없는 시간대(13–16 / 16–19 등)는 하위 라벨 없이 곧바로 bullet 을 나열한다 — 하위 섹션 구분은 **전날분이 섞이는 10–13 구간에만** 쓴다.
- **별첨 섹션은 기능 개발 외 산출물이 있을 때만** 출력한다(없으면 생략). 별첨 안에서는 시간대·전날/당일 하위 구분을 두지 않고 한 목록으로 나열하며, `TASK-XXXX` 번호가 있으면 유지한다.

**추출+일반화 예시 (§4.1 적용 — 커밋 메시지 → 보고서 줄):**
- `TASK-0243 MSSQL db-insights catalog 귀속 (#0003) PB-0008 시각검증 PASS`
  → `**TASK-0243** — MSSQL 데이터 분석 결과를 데이터베이스별로 묶어 표시` *(검증 절차 "PB-0008 시각검증 PASS" 는 줄에 쓰지 않음 — §4.1(A))*
- `feat(datasource): SSRF 사설망 경계 env 토글 (TASK-0228, ADR-0030)`
  → `**TASK-0228** — 내부망 주소 접근 차단을 설정으로 켜고 끌 수 있게 함`
- `feat(web-ui): 릴리즈 노트 추가 (TASK-...)` + `fix: 접힘 무력화 수정 + styles.css 캐시버스터` + `docs: PB-0008 evidence 기록`
  → `**TASK-...** — 작업 화면과 관리 콘솔에 릴리즈 노트 추가` *(후속 수정·캐시 갱신·증적 기록은 최종 산출물 한 줄에 흡수 — §4.1(A))*
- `insight-worker 분석 완료율 UI` (내부 잡 명 일반화)
  → `**TASK-...** — 데이터 분석 진행률 화면 추가`

- 마지막에 총계 한 줄(예: "기능 개발 N개 TASK + 별첨 M건") 과, 근거가 git 로그 재구성임을 1줄 각주로 덧붙인다. **당일 19:00 이후 작업이 있으면 "당일 19:00 이후 N건은 익일 보고서로 이월" 을 함께 각주로 남긴다.**
- "오늘 진행" 의 기준이 커밋 시각이 아니라 특정 세션 범위라면 좁힐 수 있음을 1줄로 안내한다.

## 사용 예
- `/daily-report` → 오늘 작업을 시간대(10–13 / 13–16 / 16–19)로 정리
- `/daily-report 2026-06-09` → 지정일 작업을 시간대로 정리
- 보고일 경계는 **19:00** — 전날 19시 이후 작업은 당일 10–13 의 '전날(19:00 이후)' 하위 섹션으로 묶이고(줄 마커 없음), 당일 19시 이후 작업은 익일로 이월된다 (§5).
- 보고서 줄의 요약은 **작업(산출물) 중심** — `PB-0008`·`브라우저 화면 검증`·`evidence 기록`·`캐시버스터` 같은 **내부 진행 절차는 빼고**, `ADR-0030` / `feature-0003` / `insight-worker` 같은 **내부 약어는 일반 용어로 풀어** 출력한다 (TASK 번호만 유지 — §4.1).
- 시간대별 섹션에는 **제품 기능 개발만** 담고, 도구·스킬·`/daily-report` 같은 스킬 변경·템플릿 업그레이드·문서·발표자료·배포 인프라 등 **기능 개발 외 산출물은 최하단 `별첨 (기능 개발 외)` 섹션**으로 분리한다 (§4.2).
